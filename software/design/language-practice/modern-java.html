The Modern Java Subset: What to Retire, What to Write Instead

engineering
languages
java
Records, sealed types, and pattern matching replace much of the boilerplate vocabulary of Java 8. Twenty-five numbered substitutions, what to write instead, and the five places where the subset runs out.
Published

November 5, 2026

Java now contains two languages. One is the Java most codebases still look like: mutable beans, null returns, checked exceptions that do not compose, synchronized blocks, and class hierarchies used for code reuse. The other arrived between Java 16 and Java 25. It expresses everything the first one expresses, and it leaves less for a reader to reconstruct.

This page is the substitution table. It names the construct to retire, the construct that supersedes it, and the reason the replacement is better. It also names where the replacement stops, because a guideline that claims full coverage leaves the reader to find the gaps in production.

If you read nothing else. Three substitutions carry most of the value:

  • Records and sealed types first. They replace the bean, the Visitor, and every instanceof cast, and they are local and cheap to adopt.
  • A result type where a failure crosses a boundary. Keep exceptions for bugs, for fatal JVM errors, and for frameworks that accept nothing else.
  • Virtual threads and scoped values for blocking work and request context, once the data shapes are settled.

Some rows name a mechanism code such as T10 or C5. Those codes come from a 99-entry inventory that prices what a language forces on the code, and each one links to its entry in the criteria catalogue.

Target: Java 25. It is the current long-term-support release, and every claim below was checked against the JDK 25 specification, the JDK 25 API documentation, and the Java Enhancement Proposals as of November 2026. Java 26 and Java 27 add no newly finalized language construct; both spend their releases on the runtime, and the Java 27 page records why. Two constructs useful to this subset are still previews in Java 27 — features the compiler accepts only behind the --enable-preview flag, and which may still change — so they are marked below rather than recommended [1], [2].

Three constructs do most of the work in this list: records, sealed types, and pattern matching. Records supply the data, sealed types close the set of cases, and a pattern switch makes the compiler check that every case is handled. None of the three does it alone.

A sealed interface declares in its permits clause which types may implement it, and no other type can [6]. Since Java 14 a switch can also be an expression that yields a value, and an arrow arm does not fall through [16]. Since Java 21 a case label can destructure a record: the pattern names the type and binds each component in header order [7]. Together those three turn a closed set of cases into a type whose dispatch the compiler checks:

// one file, held in an implicit class (Java 25)
sealed interface Shape permits Circle, Square, Rectangle {}

record Circle(double radius) implements Shape {}
record Square(double side) implements Shape {}
record Rectangle(double width, double height) implements Shape {}

static double area(Shape shape) {
    return switch (shape) {
        case Circle(double r) -> Math.PI * r * r;
        case Square(double s) -> s * s;
        case Rectangle(double w, double h) -> w * h;
    };
}

Every case is listed, so the compiler proves the switch exhaustive: it checks that no case is missing [8]. Add Triangle to the permits clause and each exhaustive switch expression stops compiling until it handles the new case. A switch that keeps a default branch absorbs the new case silently.

Two limits matter. A record is shallowly immutable: it holds its components final, but an array component still shares the array, so record Span(int[] values) shares its buffer and the compact constructor must copy it ([17], §8.10). And a sealed type is closed by design, which makes it wrong for extension points. Plugins, service providers, and framework hooks stay open interfaces.

The three code-point methods differ in what they return [18]. codePointAt(i) returns the code point at index i, codePoints() returns a stream of them, and offsetByCodePoints(i, n) advances n characters from index i and returns the new index.

map transforms a success and passes an error through. flatMap chains a step that can itself fail. fold takes one handler per branch and returns a single value.

The shape is small, and the same two constructs carry it: records for the cases, a sealed interface for the closed set [4], [6]:

sealed interface Result<T, E> permits Ok, Err {}

record Ok<T, E>(T value) implements Result<T, E> {}

record Err<T, E>(E error) implements Result<T, E> {}

sealed interface LookupError permits NotFound, Unavailable {}
record NotFound(UserId id) implements LookupError {}
record Unavailable(String reason) implements LookupError {}

and the call site reads as a mapping, not as control flow (var infers the component’s type, and the type arguments may be omitted):

Result<User, LookupError> found = users.find(id);

String label = switch (found) {
    case Ok<User, LookupError>(var user) -> user.displayName();
    case Err<User, LookupError>(var error) -> switch (error) {
        case NotFound ignored -> "unknown user";
        case Unavailable down -> "unavailable: " + down.reason();
    };
};

This substitution costs more to adopt than the others, and its cost lands outside the method that returns the value. A result type in a public signature propagates: every caller must adopt it, and every layer must agree on its shape. That agreement is a coupling of its own, the same coupling the missing result type imposed, because every layer already had to know the same implicit failure vocabulary. Adopt it at the domain core and convert at the edge. Keep exceptions for bugs, for fatal JVM errors, and for framework boundaries that accept only exceptions.

Java has no error-propagation operator (Rust’s ?), so a chain of five flatMap calls reads worse than the imperative early return it replaced. Two or three steps compose well. Beyond that, write the early return.

Ship the block-scoped ExecutorService for fan-out. StructuredTaskScope is a preview API that groups subtasks so that none outlives its block; it is the seventh preview in Java 27 [2], and a preview needs --enable-preview, so the class files do not load on a stock runtime. The ExecutorService block is the supported version of the same idea, and it is blunter: it waits for every task and reports no single subtask’s failure.

6 One module, both shapes

The tables give one substitution at a time. A module applies several at once, and that is where the costs and the wins both live. Here is a booking service in the shape this page retires:

final class BookingService {
    private final Map<String, Seat> seats = new HashMap<>();

    Booking confirm(String seatId) throws IOException {
        Seat seat = seats.get(seatId);
        if (seat == null) {
            return null;                    // absence, reported as a value
        }
        if (seat.taken()) {
            throw new IllegalStateException("seat is taken");   // failure, reported as a throw
        }
        seat.setTaken(true);                // the caller now holds a mutable alias
        return new Booking(seatId, new Date());
    }
}

Three different outcomes leave the method by three different routes: a null, a throw, and a value. The caller must know all three, and nothing in the signature says so.

The same module in the shape this page recommends:

record Seat(String id, boolean taken) {}
record Booking(String seatId, Instant at) {}

sealed interface Confirmation permits Confirmed, Rejected {}
record Confirmed(Booking booking) implements Confirmation {}
record Rejected(String reason) implements Confirmation {}

final class BookingService {
    private final Map<String, Seat> seats = new LinkedHashMap<>();

    Confirmation confirm(String seatId) {
        return switch (seats.get(seatId)) {
            case null -> new Rejected("unknown seat");
            case Seat s when s.taken() -> new Rejected("seat is taken");
            case Seat s -> new Confirmed(new Booking(s.id(), Instant.now()));
        };
    }
}

One return type carries every outcome, the compiler checks that no case is missing, adding Cancelled to permits stops every exhaustive switch until it is handled, and the ordered map makes the seat listing stable between runs. What the module gives up is visible in the same few lines: Seat no longer mutates, so the caller cannot mark a seat taken and must route through the service.

7 Where the subset runs out

Five needs fall outside the subset. Each one needs a named exception to the rule, not a silent one.

  1. Hot loops and large buffers. The data-shape table turns every tuple into a record. In a per-element loop that is an allocation and an indirection per element, so primitive arrays and local mutation stay.
  2. Designed extension points. sealed is closed by definition, so plugins and service providers keep open interfaces.
  3. Framework-mandated beans. A JPA entity — a class that the persistence provider maps to a table [23] — needs a non-final class that the provider can instantiate empty and populate afterwards. A record is final and sets all its state in the canonical constructor. Put an adapter at the edge and keep the domain in records. Jackson, the JSON library, reads records natively from 2.12 [24], without the no-argument constructor and setters that an ordinary class needs.
  4. Foreign and legacy APIs. JDBC and servlet containers return null and throw checked exceptions the domain cannot compose — SQLException, ServletException. Convert at the boundary; do not pretend the boundary is clean.
  5. Bugs and fatal errors. Throw NullPointerException, OutOfMemoryError, and failed assertions: they are bugs, not domain failures.

The numbers are stable. A row added later takes the next number, and the anchor #item-N keeps working for every row already cited.

9 Making it stick

Prose does not enforce itself. The workable enforcement is a compiler plugin that fails the build.

Error Prone runs as a javac plugin [25], so the flags are the same whatever builds the project. It needs -XDcompilePolicy=simple, the Error Prone and NullAway jars on the processor path, and one -Xplugin argument that carries both the plugin name and its settings. A check is set with -Xep:<Check>:<Severity> and configured with -XepOpt:<Key>=<Value>. On JDK 16 and later it also needs the --add-exports flags that its installation guide lists, because it reads compiler internals.

The javac parameters [26]:

-XDcompilePolicy=simple
-processorpath error_prone_core.jar:nullaway.jar:your-checks.jar
'-Xplugin:ErrorProne -Xep:NullAway:ERROR -XepOpt:NullAway:AnnotatedPackages=com.example -Xep:BanThrow:ERROR -Xep:BanUnorderedCollection:ERROR -Xep:BanMutableStatic:ERROR'
-Werror

Maven, in maven-compiler-plugin. The same flags go into compilerArgs, and the same jars into annotationProcessorPaths:

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <compilerArgs>
      <arg>-XDcompilePolicy=simple</arg>
      <arg>-Xplugin:ErrorProne -Xep:NullAway:ERROR -XepOpt:NullAway:AnnotatedPackages=com.example -Xep:BanThrow:ERROR</arg>
      <arg>-Werror</arg>
    </compilerArgs>
    <annotationProcessorPaths>
      <path>
        <groupId>com.google.errorprone</groupId>
        <artifactId>error_prone_core</artifactId>
        <version>${error-prone.version}</version>
      </path>
      <path>
        <groupId>com.uber.nullaway</groupId>
        <artifactId>nullaway</artifactId>
        <version>${nullaway.version}</version>
      </path>
      <!-- your own checks join here -->
    </annotationProcessorPaths>
  </configuration>
</plugin>

with the two versions pinned in <properties>.

Gradle, with the net.ltgt.errorprone plugin, which writes the plugin argument for you:

plugins {
  id 'net.ltgt.errorprone' version '4.1.0'
}

dependencies {
  errorprone "com.google.errorprone:error_prone_core:${errorProneVersion}"
  errorprone "com.uber.nullaway:nullaway:${nullawayVersion}"
}

tasks.withType(JavaCompile).configureEach {
  options.errorprone {
    error('NullAway')
    error('BanThrow')
    error('BanUnorderedCollection')
    error('BanMutableStatic')
    option('NullAway:AnnotatedPackages', 'com.example')
  }
  options.compilerArgs += ['-Werror']
}

Three tools, one set of checks. The build tool supplies only the classpath and the argument quoting.

NullAway is a published check that reports a possible null dereference [27], and it reads JSpecify annotations [28]. The three Ban* checks are yours to write: each is a small BugChecker, a class that inspects the compiler’s syntax tree and reports a match.

This catches null returns, mutable statics, unordered collections, and a throw outside a whitelist. It does not catch aliasing (two references to the same mutable object), and it cannot see Kotlin, generated members, or reflective writes. NullAway also treats unannotated third-party code as unknown, so library nulls pass through. The plugin is a check that only gets stricter over time; it is not a proof.

10 Migrating in order, and what it costs

The substitutions are not equally cheap, and the cheap ones unlock the expensive ones.

  1. Records first. They are local, mechanical, and they turn a bean into a value. They also make the other steps smaller, because every later substitution operates on fewer mutable fields.
  2. Sealed types and patterns next. One closed hierarchy per domain concept, each case a record. This is where switch becomes exhaustive, and where the Visitor disappears.
  3. Then errors. A result type touches every signature in the chain, so it is the first substitution that crosses module boundaries. Do it after records, when the cases are already records and the failure set is already a closed hierarchy.
  4. Then concurrency. Virtual threads and scoped values change how work is scheduled, not how data is shaped. Doing them last keeps one moving part at a time.
  5. Framework boundaries last, or never. Adapters at the JPA and JSON edge are the most boring code in the system, and they are the least urgent.

Three items are local: Optional.get(), Date to java.time, and a raw type to a generic. Most are module-wide. Two are codebase-wide, because they change every signature in a chain: the result type, and ScopedValue for context that crosses layers. Budget accordingly.

The subset also carries four costs the tables do not show:

  • A larger language. Records, sealed types, patterns, virtual threads, and modules add more syntax than Java 8 had. The subset narrows what you write; it does not narrow what you must read in other people’s code.
  • Two shapes for errors. During migration the codebase carries both exceptions and results. That is worse than either one alone, which is why migration should move one module at a time.
  • Allocation. Optional and Result allocate. The JIT compiler often removes that allocation when the value never escapes the method (escape analysis), and sometimes it does not.
  • Boundary adapters. Every framework that speaks beans or exceptions needs a translation layer, and that layer is code someone maintains.

A subset is a discipline, not a language change. It lowers what your code pays, not what Java costs, because the old construct remains available to the next team. Only a change to the language itself — a construct the compiler gives every project by default — changes what Java costs.
