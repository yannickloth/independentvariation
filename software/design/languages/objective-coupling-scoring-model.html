1 The Scoring Model

Companion to: The Great Language Smackdown · the Scoreboard · the Criteria

The main article ranks 101 languages by language-imposed coupling and by engineering readiness. This companion publishes the mechanism inventories, the arithmetic, and the tests that decide presence, so any reader can reproduce any number from first principles. The rules and the arithmetic are fixed; the weights and the band thresholds are authored judgments. The per-language data itself is on the Scoreboard.

What each mechanism means, what it forces to agree, and why it costs what it costs is explained in the Criteria.

The coupling analysis this model operationalizes — coupling as access to a shared resource, and the derivation of a modularisation directive from coupling — is developed in the published coupling papers [1], [2].

Analysis date: October 2026. All languages are assessed against the version shown.

1.1 What the model measures, and what it does not

The model prices harms, not features. A mechanism in the inventory is a cost somebody pays while the program is maintained, so a score moves in one direction only: points are removed when a harm is present.

The comparison this model replaces is the industry’s default one — adoption counts, adoption-rate trends, and feature checklists. Those yardsticks answer two questions: how many teams want the language, and what the language offers them. The model answers a third: which named agreements the language forces on the code written in it, and which readiness gaps it leaves in the artifact.

A feature earns nothing here. Where a language construct removes a harm, a language page records an enabling note, and the effect is the absence of a mechanism: the harm is not there, so no points are removed. That absence is the whole reward. A feature never offsets a harm that is present, and a present harm is never offset by a feature.

Coupling is the harm this inventory is built around. On the model’s definition a shared resource is the route a change travels, so every consumer of it pays when the producer moves. Whether coupling costs more than a readiness gap in a given system is not something the model measures. The inventory splits the cost by the place the language puts it. Core coupling (46 mechanisms, 350 points) prices what the language’s own constructs force into the program. Ecosystem coupling (34 mechanisms, 256 points) prices what the platform, the tooling, and the release packaging force at the boundary around the program. A high Core score means the language’s own constructs force few of the named agreements. A low Ecosystem score means the platform and the toolchain around it leave more of their own costs present. The two axes are separate lenses, and neither one prices writing time or shipping time.

The Core axis aims at accidental coupling. The coupling analysis states the floor: the shared-resource edges the system needs. Above the floor sit the accidental edges — agreements no requirement asked for. When a language forces them through its own constructs, the default code of any program written in it pays them, which is why the model prices them at the language level and not at the project level. A team that keeps a discipline can hold a mechanism at bay in practice; the model charges it, because the discipline is not in the language.

Adoption, popularity, and feature counts are not inputs to the model and never enter a score. Where this site names the TIOBE top 50, it names it as the coverage list of languages assessed, not as a ranking.

1.2 How a score is computed

The model is a fixed inventory scored by severity share:

  1. A fixed mechanism inventory. Each mechanism has a fixed weight, except the one recorded mechanism, which carries the fact and no weight.
  2. For each language, every mechanism is marked present or absent (a factual determination).
  3. Within each dimension of one axis the present weights are summed, and the axis is scored by the share of its own inventory those weights represent: score = 100 × (1 − present weight ÷ inventory weight). The inventory weight is the sum of every weight the inventory names on that axis, so the denominator is the inventory itself, not a chosen ceiling.
  4. Score = 100 × (1 − present weight ÷ inventory weight), computed per axis.

The share is the instrument. Coupling is cumulative: a maintainer pays every forced coupling, so the costs add. The denominator is the inventory itself — 350 points on Core, 256 on Ecosystem, 171 on Readiness — so the scale carries no free constant: 100 means a language forces none of the named couplings, and 0 means it forces every one of them. Nothing is capped and nothing is curved. A cap would hide every mechanism above it: Java 1.4 and Java 17 would both pay a full Type ceiling, and the generics and the module boundary that Java 17 adds would vanish from the score. Here they do not: Java 1.4 scores 64.6 on Core and Java 17 scores 68.0. A curve would price the tenth mechanism of a dimension below the first, which the inventory does not claim. The share is monotone instead: each removed mechanism moves the score by 100 × w ÷ inventory weight, and two languages that force the same severity share the same score exactly. The three inventories differ, so a mechanism of one tier is worth a different number of points on each axis: a Minor costs 1.1 on Core, 1.6 on Ecosystem, and 2.3 on Readiness, a Moderate 2.3, 3.1, and 4.7, and a High 4.3, 5.9, and 8.8. The step is the tier weight over the axis inventory, so an axis with fewer mechanisms moves in larger steps.

1.2.1 Score bands

Because the model is a fixed inventory scored by severity share, the bands are thresholds over the score. The raw cutoffs below are stated for Core, whose inventory is 326 points; the score thresholds are the same on every axis. The band policy is stated here: the score thresholds are fixed, and the raw cutoffs beside them are derived numbers, recomputed at every inventory change and never frozen. Adding a mechanism to an inventory lifts every score on that axis by a fraction, so a language can rise a band on inventory growth alone; the model states the growth in the denominator sentences above rather than re-anchoring the thresholds to hold a roster still. The bands are a presentation grouping over a continuous share, and a roster is a consequence of the data, not a target.

  • 90+: under 10 points of cost — on Core, under 33 raw weight, usually in one dimension.
  • 75–89: 10 to 25 points — on Core, 33 to 82 raw weight, across a few dimensions.
  • 60–74: 25 to 40 points — on Core, 82 to 130 raw weight.
  • 45–59: 40 to 55 points — on Core, 130 to 179 raw weight.
  • Below 45: over 55 points — on Core, over 179 raw weight. The language’s design trades separation of concerns for other goals (simplicity, flexibility, ubiquity, or direct hardware access).

All three axes use the same bands: 90+, 75–89, 60–74, 45–59, and below 45. The thresholds are a presentation choice, not a measurement; they group the field at round numbers. A readiness band is not comparable to a coupling band, because the two axes price different kinds of cost; the profile is never scored at all.

1.2.2 Dimension sub-scores

The comparison matrices show each dimension’s cost in score points: 0 means the language forces no mechanism in that dimension, and a negative number is the dimension’s share of the axis cost. The raw weight sum follows in parentheses, so the mechanism inventory stays checkable. A language’s Core score is 100 minus the sum of its six costs, its Ecosystem score the same over its eight, and its Readiness score the same over its six. Each cell is rounded for display and the axis total is computed from the integer raw sums, so a column can differ from its total by a few tenths.

Three scores, reported separately, and an unscored profile. The comparison reports Core coupling, Ecosystem coupling, and Engineering readiness as three separate numbers over the same severity share. They are reported separately and never summed: a language can be weakly coupled and hard to ship, or strongly coupled and easy to operate. Several mechanisms share one underlying fact across axes — a missing package registry affects both Ec1 and the supply-chain mechanisms — so the three scores are correlated in practice even though they are scored apart. Alongside them, the per-language profile records three axes the score deliberately does not price — energy and cost, AI and agent readiness, and safety certification — as evidence-backed notes, not numbers.

1.3.4 What counts as present

Presence is a factual determination about the language a programmer can write, not about a team’s house style or a third-party tool. Four coupling determinations need a stated rule:

  • A check behind a project switch. Some mechanisms depend on a compiler switch that the project file sets. The mark uses the configuration the language’s own project initialiser writes for the version shown, because that is what a new project gets without a decision. tsc --init writes "strict": true, and strict sets strictNullChecks, so TypeScript is not charged T10. dotnet new writes <Nullable>enable</Nullable>, so C# is not charged T10. Visual Basic’s compiler default is Option Strict Off and the SDK template sets no OptionStrict, so the narrowing conversion is charged T2. Where the initialiser writes no switch, the compiler default governs. A check that only a separate tool supplies is never counted — the mypy case under T1.
  • M2 — the collector’s schedule. Present when the run time reclaims memory on its own schedule rather than at the last reference, so the program cannot name when the heap shrinks. Deterministic reclamation is not charged: Swift’s ARC and Delphi’s strings and interfaces release at the last reference, and Delphi on Windows frees objects explicitly. Objective-C is charged, because an autorelease pool defers a release past the last reference and a Core Foundation handle is released by hand. The collector must be the one that reclaims the language’s own objects: a language that compiles to another scored language inherits that language’s collector (TypeScript inherits JavaScript’s), while a language whose artifact is consumed by a host rather than executed as its own objects is not charged here (a Rocq term is checked by the kernel, and a Scratch project runs inside the Scratch VM).
  • R2 — the collector’s pause. Present when the page records the collector’s pause as a cost the program must absorb — a ⚠️ or ❌ bullet on the pause itself, on a stop-the-world cycle, or on the program’s lack of control over the pause. Absent when the page names no collector cost at all, and absent when the page records the opposite (bounded collector steps, per-process collection, a collector mode stated as a strength). The mark is thus the page’s own assessment of its collector, which is what keeps the charge set checkable: where the page states the pause as a cost, the mechanism is charged.
  • Data rows for stored state — the two directions. A data-format row names the state the toolchain writes that outlives the program. Reading: present when the vendor publishes that the current release opens data written by an older one. Writing: present when the vendor publishes that data written now cannot be read by other releases. Ec9 charges a row whose evidence is a break — the reading promise published as broken, the writing direction published as unreadable, or a break the probe harness has reproduced with pinned releases and a committed result — and a format whose stored state carries a published version rule and a documented reading path is not charged. A row nothing decides is recorded on the page and prices nothing; a row the probe has tested without finding a break states the test and still prices nothing, because tested is not promised.

A mitigation is not an absence. Some languages offer an opt-in construct that avoids a mechanism: @CompileStatic in Groovy, try-with-resources in Java, reified in Kotlin, a lint rule, or a flag the initialiser does not set. The mechanism stays charged. The default code still pays it, and avoiding it needs knowledge that the language does not force. That is deliberate: the model measures what the language imposes, not what a disciplined team can achieve with the same language. If a mitigation lowered the score, two teams on one language would score differently, and the language would have no score. The mitigation is recorded on the page as a strength or a trade-off, never as a discount. The line between a mitigation and an absence is the project-switch rule above: what a new project gets without a decision is the language’s; what the developer must know to turn on is a discipline.

1.3.5 What imposes a mechanism

Every mechanism carries one tag: Imposed by: language, runtime, or context. A language mechanism is decided by the compiler, so a remedy is a change to the code. A runtime mechanism is decided by the executor — the memory manager, the compiler that runs later, the thread scheduler, or a default the platform chooses — so a remedy is a change to the deployment, to a flag, or to the version. A context mechanism is decided by the surroundings, so a remedy is outside both: a different vendor, toolchain, market, or standard. The tag is meta-information. It never enters a score, and it makes one thing visible: a release can change a runtime fact and no language fact, and the page will say so.

1.3.6 The mechanism that is recorded, not priced

V5, silent default drift, is in the inventory and carries no weight. A default that the source does not name changes between releases; nothing in the build reports it, so a deployment discovers the change when the behaviour of the running program moves. That is a real coupling — the agreement exists, and the code never wrote it down — but its direction is not fixed. The same change can help one workload and hurt another: G1 as the default everywhere helps a one-CPU container and moves the latency profile of a service that was measured under Serial, and a new default key encoding can be better interoperability and a break for an older peer. A price has to point one way, or the sum stops being arithmetic. So the model records the event, states its direction in the observation beside the mark, and prices nothing. The same rule keeps execution quality — footprint, throughput, energy — out of the score entirely. A delivery row, or a data row for stored state, marked recorded, not priced follows the same rule as V5: a crossing release boundary that no current document decides is recorded, and it removes no points.

All three axes are scored the same way. Readiness is a scored axis exactly like Core and Ecosystem: every mechanism carries a weight, a present mechanism removes that weight, the dimension subtotals sum to the axis cost, and the axis score is 100 minus that cost over the axis inventory. Presence is a factual determination on every axis, decided by a stated test rather than by a severity judgment. The readiness tests are stated with each mechanism in the Criteria — “build not reproducible” is present when the language’s own build tool does not default to byte-reproducible output, and “no signed provenance” is present when the registry ships no default attestation — so a reader can check a mark and regenerate the score, exactly as on the other two axes.

1.4 How the tables are ranked

Every score on this site is reported on its own axis. The ranking score is the one place where two axes meet, and coupling leads it. The rule is declared here:

Term Role Why
Core coupling Primary The coupling the language’s own constructs force into the code.
Engineering readiness Modifier, at most 15% of the coupling score A toolchain, registry, and observability stack can be fixed by process; coupling written into the code cannot.
Ranking score core × (0.85 + 0.15 × readiness / 100) Readiness lifts the coupling score by at most 15% of that score, so a full 0-to-100 readiness swing is worth 15 points at a core of 100 — about 3.3 High mechanisms on the Core scale — and proportionally less below that. Rows that tie share a rank; the table lists them by Core coupling, then readiness, then the name.

Ecosystem coupling does not enter the ranking. It is a dependency context, not a quality: a near-monoculture ecosystem lowers risk through consistency, so its band can disagree with its number (JavaScript scores 80.1 there and 54.0 on Core). It stays a lens, and the table sorts by it, but it does not decide the order.

Coupling is primary; readiness is a modifier. Once the code is written, the code is what remains, and a maintainer faces it for most of a system’s life. A language that forces accidental coupling into every line has damaged that artifact permanently. Readiness surrounds the code rather than entering it, and it is remediable by process: a toolchain, a registry, and an observability stack can be fixed, while coupling in the code cannot. So readiness does not weigh against coupling as a peer. Readiness earns its lift the way every axis earns ground: as the absence of present harms. A language lifts the ranking by having fewer readiness mechanisms present, never by having a feature. The remedy for a readiness gap is a process change; the measurement is the language’s own default toolchain, not a team’s discipline.

1.5 How to reproduce a score

To reproduce any score: read the language’s present mechanisms for one axis, sum their weights, and divide by the axis inventory weight — 350 on Core, 256 on Ecosystem, 171 on Readiness. The score is 100 × (1 − present weight ÷ inventory weight), rounded to one decimal. Repeat for each axis. The three axes are scored apart: no score is ever added to another, though several mechanisms share one underlying fact and the axes are correlated in practice.

Worked example — Java 26 (Core 72.6): present Core = T7, T10, T12, T14, C2, C5, C6, M2, M3, M4, Er2, Er4, K3, C8, T15.

Construction C2(−4) + C5(−4) + C6(−8) + C8(−8) = −24 −24 −6.9
Memory M2(−8) + M3(−4) + M4(−8) = −20 −20 −5.7
Error Er2(−8) + Er4(−4) = −12 −12 −3.4
