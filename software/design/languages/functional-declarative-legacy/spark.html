SPARK (Pro 25)

This assessment applies the coupling account — coupling as access to a shared resource, and the coupling floor [1], [2] — and the knowledge-embodiment theorem [3]; the language is assessed against its official reference [4].

1 Assessment

This page assesses SPARK in five parts: core coupling — what the language’s own constructs force; ecosystem coupling — what the surrounding platform, tooling, and community cost; engineering readiness — whether the artifact can be reproduced, verified, observed, worked in quickly, connected to other languages, and governed openly; the profile — the unscored facts a score cannot express; and the scoring detail — the mechanism marks and the arithmetic behind every score. A ✅ bullet marks a construct that helps. A ⚠️ or ❌ bullet marks a cost; the scoring model does not price every cost named here.

Core coupling 73/100 · Ecosystem coupling 69/100 · Engineering readiness 42/100

1.1 Core coupling

1.1.1 Type

  • ✅ The static type system is Ada’s: Every object, parameter, and function result has a declared type, and the compiler checks every assignment and call
  • ✅ Subtypes carry range constraints: subtype narrows a base type with a range or a predicate, and in the proved subset a violation is a proof obligation rather than a run-time check
  • ✅ Enumeration and discriminated record types express alternatives: An enumeration gives a finite value set, and a variant record’s discriminant states which branch is active
  • ✅ Generics are checked at each instantiation: An Ada generic is analysed where it is instantiated, so a reusable abstraction is verified at its use site
  • ✅ Type_Invariant states a property of a private type: The invariant is an obligation on every value of the type
  • ⚠️ Access types are admitted only under an ownership policy: SPARK allows a pointer when its owner is declared, so indirection is available but constrained

1.1.2 Construction

  • ✅ Contracts are part of the subprogram declaration: Pre, Post, and Contract_Cases state the obligation beside the parameters, so a caller reads it with the signature
  • ✅ Flow contracts state what a subprogram reads and writes: Global, Depends, and Refined_Global make the data flow a declared artefact
  • ✅ Abstract states confine a package’s state: Abstract_State declares the state as an abstraction, Refined_State binds it to concrete variables, and Initializes states what a package sets up
  • ✅ Separation is proved rather than advised: The ownership policy, the flow aspects, and the contracts are analysed by GNATprove, so a declared separation is verified and not merely recommended
  • ⚠️ The declarations carry more than the code needs: A proof requires a contract for every subprogram on the path, so construction carries an annotation burden
  • ⚠️ A unit can opt out with SPARK_Mode => Off: An analysed region and an unchecked region can sit in the same program

1.1.3 Memory

  • ✅ An ownership policy governs any access type: SPARK’s data-ownership regime gives a pointer a stated owner, so a dangling or duplicated reference is a proof failure rather than a run-time defect
  • ✅ No manual deallocation in the subset: Unchecked_Deallocation is outside SPARK, so a program never frees memory by hand
  • ✅ No garbage collector: SPARK compiles to native code and runs without a collector
  • ✅ Bounded containers remove the heap: Ada.Containers.Bounded_Vectors and its siblings hold their storage in the object
  • ✅ A local object’s lifetime is its scope: A stack variable’s extent is fixed by the block that declares it
  • ⚠️ An owned access type still allocates at run time: The allocation is allowed and proved, but the allocator’s behaviour remains a run-time fact

1.1.4 Error

  • ✅ A failure is a proof obligation: GNATprove reports an unproved check, so a fault is found in the toolchain rather than in a test run
  • ✅ A raise is stated in the contract: Exceptional_Cases names the exceptions a subprogram may propagate, so the failure set is declared
  • ✅ Run-time checks are proved impossible rather than disabled: Once GNATprove proves that an index, a range, or a division cannot fail, the check costs nothing
  • ✅ Assert becomes a proof obligation: pragma Assert states a property that the analysis must establish or report
  • ✅ Assume records an unproved fact explicitly: An assumption is written in the source and appears in the analysis report
  • ⚠️ The proof is no stronger than its assumptions: An Assume, an unproved check, or a SPARK_Mode => Off unit leaves a gap in the guarantee

1.1.5 Concurrency

  • ✅ Ada tasking is available and analysable: A task and a protected object are language constructs, and SPARK analyses the data flow of the supported subset
  • ✅ A protected object is the synchronisation boundary: A protected operation enforces mutual exclusion and a barrier, so the lock is not written by hand
  • ✅ The Ravenscar profile gives a static task set: No task is created dynamically, and the ceiling-locking protocol prevents priority inversion
  • ✅ Shared state must be declared: A variable shared between tasks appears in a Global or Depends aspect, so the sharing is visible
  • ⚠️ The analysed subset of tasking is smaller than Ada’s: An entry family, a dynamic rendezvous, or an unrestricted task is outside the analysed subset

1.1.6 Platform

  • ❌ SPARK is a subset of Ada and a program is an Ada program: GNAT compiles the code, and the language has no existence apart from the Ada platform (P1)
  • ❌ A foreign call leaves the proved region: An interface to C or another language is declared outside SPARK, so it cannot be analysed with the rest
  • ✅ GNAT is a mature and portable Ada compiler: The same source compiles for x86-64, ARM, and the embedded targets used in avionics
  • ✅ The qualified toolchain targets the certificated platforms: GNAT Pro supports VxWorks, LynxOS-178, and bare metal with a qualification for DO-178C
  • ⚠️ Full support is a commercial subscription: GNATprove is available in the community toolchain, and SPARK Pro adds support, libraries, and qualification
  • ⚠️ The build is a GNAT project: gprbuild and a project file describe the build, so the project couples to the Ada toolchain

1.1.7 Trade-offs (not coupling)

  • The proved subset is smaller than Ada: A feature outside SPARK is left out or isolated behind a SPARK_Mode => Off boundary
  • The restriction on pointers is a deliberate exchange: Aliasing is removed in return for an ownership regime and an array or a bounded container in place of a linked structure
  • The annotation burden is the price of the proof: A contract, an invariant, and a flow aspect are written for each unit on the path
  • The target domain is high-assurance by design: Aviation, space, and medical devices are the intended context, and the domain mark records that scope
  • Verification effort is a project decision: Zero-defect software is achievable given sufficient effort, which is a budget choice
  • The proof checks the contract, not the requirement: A verified program can implement the wrong specification, which no toolchain detects

1.2 Ecosystem coupling

1.2.1 Performance

  • ✅ The compiled output is an Ada program’s native binary: SPARK compiles to the same native code, so the verification adds no run-time cost
  • ✅ A proved check need not execute: A check that GNATprove established can be suppressed at that point, so the verified code does not pay for the guard
  • ✅ No collector and no interpreter: The run-time has neither a garbage collector nor a JIT, so the timing is the Ada run-time’s
  • ✅ The Ravenscar profile bounds the run-time behaviour: The task set, the priorities, and the locking are static, which makes the timing analysable
  • ⚠️ The run-time is the Ada run-time: Tasking, the secondary stack, and exception propagation cost what GNAT’s run-time costs
  • ⚠️ The proof is a build-time cost: GNATprove can take far longer than the compilation, which delays the build but not the program

1.2.2 Ecosystem

  • ❌ The SPARK ecosystem is a subset of Ada’s: A library must itself be in the SPARK subset to be analysed with the program (Ec3)
  • ✅ Ada’s tooling serves the project: Alire supplies packages and gprbuild builds the project
  • ✅ GNATprove and SPARK Pro are purpose-built and mature: The analyser and the commercial support layer are actively developed
  • ✅ The industrial community sustains the toolchain: The requirements of the certificated industries drive the analyser and the library work
  • ✅ A verified library base exists: SPARK’s own libraries and verified components ship with the toolchain
  • ⚠️ A library that uses pointers must be isolated: An Ada library outside the subset is reached through an unproved boundary

1.2.3 Evolution

  • ✅ SPARK tracks a published Ada standard: The subset is defined against Ada 2012 and Ada 2022, so a language change follows the standard revision
  • ✅ Successive SPARK releases widened the subset: The ownership policy, the functional contracts, and the proof of type invariants were added over several releases
  • ✅ Ada’s compatibility record is strong: An older Ada program generally compiles under a later revision
  • ⚠️ A new feature arrives with a toolchain release: The analyser states the subset it supports, so adoption follows the release
  • ⚠️ A proof depends on the toolchain version: A check proved under one GNATprove release can need a new annotation under another

1.2.4 Domain

  • ❌ The language exists for high-assurance systems: Aviation, space, and medical devices, where DO-178C, EN 50128, or IEC 62304 applies, are the intended domains (D1)
  • ❌ Outside those domains it is rarely chosen: A general application gains little from the proof and pays the toolchain cost (D1)
  • ✅ The fit in the intended domain is excellent: The tools, the libraries, and the certification evidence all target it
  • ✅ DO-333 credits the proof against the certification objectives: The formal-methods supplement to DO-178C lets the analysis substitute for some test objectives
  • ✅ The shipping uses are real: Airbus, Thales, and Lockheed Martin build critical software on it
  • ⚠️ The labour pool is small: An engineer with both Ada and formal-methods experience is hard to find

1.2.5 Learning

  • ❌ Two skills must be learned, not one: SPARK requires Ada fluency and formal-methods practice, so contracts, invariants, and the proof tool must all be mastered (L1)
  • ❌ A proof failure must be read as a counterexample: GNATprove reports an unproved check with a path, and turning the report into a fix takes experience
  • ✅ The analysis report is actionable: The tool names the check, the path, and the assumption that blocks the proof
  • ✅ The learning material is complete: AdaCore’s tutorial and the SPARK course material cover the language and the proof method
  • ⚠️ The learning curve is very steep: A first proved subprogram is quick to write, and a first proved package with an abstract state is not

1.2.6 Syntax

  • ✅ The syntax is Ada’s: A package, a subprogram, and a loop read as they do in Ada, and a contract appears as an aspect or a pragma
  • ✅ The block structure is explicit: A begin/end pair closes a block, and the end repeats the name it closes
  • ✅ Contracts sit beside the parameters: Pre =>, Post =>, and Global => are part of the subprogram declaration
  • ✅ Quantified expressions are first-class: (for all I in A'Range => A (I) > 0) states a property in the source
  • ⚠️ An aspect clause can be long: A Depends aspect over much state is a long expression that needs careful reading

1.2.7 Testing

  • ✅ The proof covers the property the contract states: An obligation is discharged for every value it quantifies, not for a sample
  • ✅ The test suite no longer has to trigger every check: A bounds or range check proved impossible needs no test to reach it
  • ✅ gnattest generates a unit-test harness: It reads a package specification and emits AUnit test stubs
  • ✅ AUnit covers the behaviour a contract does not state: The proof and the test suite answer different questions
  • ⚠️ A property that no contract states is not proved: The analysis reaches exactly the contracts and invariants that are written

1.2.8 Security

  • ✅ The classic memory-safety faults are proved absent: A buffer overflow, a use-after-free, and a null dereference are removed by the subset and the proof, so the vulnerability class does not exist in the analysed code
  • ✅ Input validity is stated and checked: A range constraint or a Pre aspect states what the caller must guarantee, and the proof covers the rest
  • ✅ Unchecked_Conversion and pointer arithmetic are outside the subset: The unsafe operations are not available to analysed code
  • ⚠️ The guarantee stops at the SPARK_Mode => Off boundary: An imported C function, a device driver, or an unchecked allocation is not proved
  • ⚠️ The trusted base includes the prover and the compiler: A defect in GNATprove or in the code generator is outside the proof

1.3 Engineering readiness

1.3.1 Reproducibility

  • ❌ Builds are not byte-reproducible by default.
  • ❌ Dependencies resolve without a lock by default.

1.3.2 Supply chain

  • ⚠️ Published packages carry no signed provenance by default.
  • ⚠️ The package registry is a flat name space.

1.3.3 Observability

  • ⚠️ No stable tracing and metrics standard.
  • ⚠️ The standard library has no structured logging.

1.3.4 Feedback

  • ✅ No charged mechanism in this dimension.

1.3.5 Interop

  • ⚠️ No maintained portable target.

1.3.6 Governance

  • ⚠️ One vendor decides the language’s direction.
  • ⚠️ The specification is not public.

1.4 Profile

Unscored, and kept separate from every score on purpose. The profile records what a mechanism price cannot express: what a running program costs, how well a coding model and an agent work in the language, and whether a safety-critical path exists.

1.4.1 Energy and cost

What this axis asks: what does a running program cost in energy and time?

  • ✅ Compiles to native code: the fastest class in the language energy and time benchmarks [5], [6]. A causal re-analysis attributes the difference to execution time [7].

1.4.2 AI and agent readiness

What this axis asks: how well does a coding model and an agent work in this language?

  • ❌ Sparse training data: models write it unreliably [8].

1.4.3 Safety certification

What this axis asks: is there a certified or standards-qualified path to a safety-critical system?

  • ✅ A standards-qualified toolchain or an established safety standard covers this language.

Verdict: SPARK’s design yields low core coupling for the work it is built for, and its platform cost is the price of a narrow domain. The static type system is Ada’s, the contracts and flow aspects make every global dependency explicit, an ownership policy removes coupling through shared references, and the toolchain proves the run-time checks that other languages leave to a test suite. The only scored core loss is P1: the language is a subset of Ada and does not exist apart from that platform. Main strengths: GNATprove, a toolchain qualified for DO-178C, DO-333 credit for the proof, and industrial use at Airbus, Thales, and Lockheed Martin; main weaknesses: an ecosystem that is a subset of Ada’s, a domain lock-in to high-assurance systems, and one of the steepest learning curves here.
