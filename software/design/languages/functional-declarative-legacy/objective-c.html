Objective-C (2.0)

This assessment follows the coupling analysis of the Independent Variation Principle [1]; the language is assessed against its official reference [2].

1 Assessment

This page assesses Objective-C in three parts: core coupling — what the language’s own constructs force; ecosystem coupling — what the surrounding platform, tooling, and community cost; and the scoring detail — the mechanism marks and the arithmetic behind both scores.

Core coupling 42/100 · Ecosystem coupling 65/100

1.1 Core coupling

1.1.1 Type

  • ❌ Dispatch is resolved at run time (T3): a message send such as [obj doThing] compiles to objc_msgSend, and the selector is looked up as the message is delivered, so an object can receive a message its declared interface does not list and the fault appears as unrecognized selector sent to instance.
  • ❌ There is no namespace (T6): every class and protocol shares one global name table, so code relies on prefixes such as NS, UI, and CG to keep names apart.
  • ❌ id erases the static type (T7): the generic object pointer carries no compile-time type, so a value held in id is checked only by -isKindOfClass: or -respondsToSelector: at run time.
  • ✅ Protocols separate specification from implementation: a @protocol declares a method set that any class can adopt with <NSCopying>, so conformance does not require inheritance and one class can adopt several protocols.
  • ✅ Categories extend a class without its source: @interface NSString (MyExtras) adds methods to an existing class, so a consumer extends behaviour without subclassing and without access to the original.
  • ⚠️ Static type information is optional and partly erased: declared parameter and return types (NSString *, instancetype) are checked at compile time, but lightweight generics such as NSArray<NSString *> * and the nullability annotations nonnull and nullable are erased at run time.

1.1.2 Construction

  • ❌ There is no immutability by default (C2): NSString, NSArray, and NSDictionary each have a mutable counterpart, and a property declared strong without copy shares a mutable object with its setter; @property (copy) is the opt-in that protects it.
  • ✅ alloc and init separate allocation from initialisation: [[NSObject alloc] init] and a designated initialiser such as -initWithFrame: let one class route every construction path through one setup method.
  • ✅ @property synthesises the accessors: @property (nonatomic, copy) NSString *name; generates the getter, the setter, and the instance variable, so a consumer binds to the property name rather than to the ivar layout.
  • ✅ Blocks carry behaviour as a value: a ^-literal closure captures its environment and is passed as an argument, as in -[NSArray enumerateObjectsUsingBlock:], so a callback needs no delegate class.
  • ✅ Class clusters hide the concrete class: NSNumber and NSString return a private subclass from a factory method such as +numberWithInt:, so construction does not couple a caller to one implementation class.
  • ⚠️ +new and -init are conventions, not enforced rules: the runtime does not require an object to be initialised, so an uninitialised instance is possible and the class author must insist on the designated initialiser.

1.1.3 Memory

  • ✅ ARC removes manual retain and release: the compiler inserts objc_retain, objc_release, and the autorelease-pool calls at the right points, so the common case needs no memory-management call.
  • ✅ strong and weak state the ownership intent: @property (weak) id delegate; and __weak make the reference weak, and a weak reference zeroes itself when its referent is deallocated.
  • ⚠️ An autorelease pool defers the release: an autoreleased object lives until its enclosing @autoreleasepool drains, so a loop that builds many objects adds its own pool.
  • ❌ There is no RAII (M3): ARC is not block-scoped, so a resource that is not an object, such as a FILE *, a malloc block, or a Core Foundation handle, is released by an explicit call or a @try and @finally block.
  • ❌ There is no ownership model (M4): no static lifetime or aliasing rule bounds an object, so a strong reference cycle leaks until it is broken with weak.
  • ❌ Reclamation timing is not a language rule (M2): the language never states when an object is freed; the tracing collector that once shipped with the Apple runtime was deprecated and then removed, and ARC’s reference counting is a compiler convention rather than a language guarantee.

1.1.4 Error

  • ❌ Exceptions are unchecked (Er2): @throw, @try, @catch, and @finally carry an NSException that no signature declares, so a caller cannot see the failure set, and the convention reserves exceptions for programmer errors.
  • ✅ NSError ** reports a recoverable failure: a method such as -[NSString writeToFile:atomically:encoding:error:] writes the failure into an out-parameter, so a caller recovers without an exception.
  • ✅ @try, @catch, and @finally are structured: a @catch clause names the exception class, and @finally runs on both the normal and the exceptional path.
  • ⚠️ Two error conventions coexist: NSException marks a programming error and NSError marks a domain failure, so a caller must know which convention a given API follows.
  • ⚠️ A message to nil fails silently: [nil doThing] returns nil or 0 and raises nothing, so a missed wiring point produces no error.
  • ⚠️ NSAssert and NSParameterAssert are run-time checks: they abort in a debug build and are compiled out under NS_BLOCK_ASSERTIONS, so they do not enforce a contract in a release build.

1.1.5 Concurrency

  • ❌ Synchronisation is manual with no race detection (K3): @synchronized, NSLock, NSRecursiveLock, and dispatch_semaphore leave the reasoning to the programmer, and the compiler reports no data race.
  • ✅ Grand Central Dispatch separates work from threads: dispatch_async(dispatch_get_global_queue(0, 0), ^{ ... }) submits a block to a queue, so the code names a queue rather than a thread.
  • ✅ A completion block returns on a named queue: an asynchronous API takes a block and a queue, so a caller need not share mutable state with the worker.
  • ✅ NSOperationQueue declares dependencies: -[NSOperation addDependency:] orders operations in the queue, so sequencing is stated rather than hand-scheduled.
  • ✅ @synchronized gives a per-object mutex: @synchronized(self) { ... } serialises a critical section on one object without a separate lock object.
  • ⚠️ @property (atomic) does not make a compound operation atomic: the default attribute serialises each accessor call, so a check-then-set sequence over the same property can still interleave with another thread.

1.1.6 Platform

  • ❌ One vendor owns the mainstream platform (P2): the complete language, its reference compiler (Clang), and its flagship frameworks (Cocoa and Cocoa Touch) are Apple’s.
  • ✅ GNUstep provides a second implementation: the GNUstep runtime, Foundation, and AppKit reimplementations let much Objective-C code build off Apple’s platform.
  • ✅ The language is a strict superset of C: a .m file mixes C functions and structs with message sends, so any C library is callable directly.
  • ✅ Modules replace recursive header inclusion: @import Foundation; imports a clang module, so a build does not depend on #import order.
  • ⚠️ The frameworks differ by platform: AppKit on macOS and UIKit on iOS share Foundation but not the user-interface layer, so UI code does not move between them.

1.1.7 Trade-offs (not coupling)

  • Message-passing syntax is a familiarity cost: [receiver selector:argument] differs from dot-syntax object languages, and the adjustment is a learning property rather than a forced dependency.
  • Long method names are a deliberate style: -[NSString stringByReplacingOccurrencesOfString:withString:] is verbose but self-describing, which is a readability choice.
  • Manual retain and release remains available: a project can leave ARC off and manage lifetimes itself, so the older memory model is a choice rather than a requirement.
  • NSException for programmer errors is a policy: treating an exception as a bug signal and NSError as a recovery signal is a convention the language permits but does not require.
  • Prefixes mitigate the flat namespace: a class prefix is a convention that reduces collisions; it is a workaround for the missing namespace, not an additional coupling.
  • A mixed Objective-C and Swift target is a migration decision: both languages share the runtime and call each other, so how far to migrate is a project choice.

1.2 Ecosystem coupling

1.2.1 Performance

  • ✅ The language compiles to native code: Clang lowers Objective-C to machine code through LLVM, so a message send is a real call and a program needs no warm-up.
  • ✅ The runtime is thin and written in C: libobjc supplies the selector table, the class metadata, and the reference-counting helpers with little work beyond the message send.
  • ⚠️ objc_msgSend costs more than a static call: every message send performs a selector lookup that is cached after the first use, so a tight loop of message sends is slower than the equivalent direct call.
  • ⚠️ Dynamic dispatch limits inlining and devirtualisation: because the receiver’s class is known only at run time, the compiler cannot always inline a method body.
  • ⚠️ Key-value observing and method swizzling add indirection: both change how a method runs after the fact, and the cost appears wherever they are installed.

1.2.2 Ecosystem

  • ❌ The primary ecosystem is proprietary (Ec4): the reference documentation, the frameworks, and the IDE (Xcode) come from one vendor under its licence terms.
  • ✅ The toolchain is mature inside that ecosystem: Xcode supplies one editor, compiler, debugger (lldb), Interface Builder, and the Instruments profiler in one install.
  • ✅ CocoaPods, Carthage, and Swift Package Manager resolve dependencies: several long-established package managers exist for Objective-C libraries.
  • ✅ GNUstep supplies a free Foundation: a portable implementation covers NSString, NSArray, and the rest of the Foundation API off Apple’s platform.
  • ⚠️ Current material is written for Swift first: the platform APIs and sample code are presented for Swift, so an Objective-C reader works from older or generated headers.

1.2.3 Evolution

  • ❌ The language is frozen (V2): Objective-C 2.0 (2006) is effectively the last language revision, and platform-facing work has moved to Swift.
  • ✅ The compiler keeps supplying new features: ARC, blocks, object literals such as @[] and @{}, lightweight generics, and nullability annotations arrived as Clang features rather than as language revisions.
  • ✅ A mixed Objective-C and Swift target is supported: both languages link against the same runtime and can call each other, so a project can migrate one file at a time.
  • ✅ Old source still compiles: OpenStep-era Foundation API and the 1990s NeXT runtime conventions are still supported by the current toolchain.
  • ⚠️ Documentation for new APIs follows the vendor’s current language: a header is the reliable reference for the Objective-C form of a new API.

1.2.4 Domain

  • ❌ The domain and the vendor are one decision (D1): the language is built for Apple’s platforms, so adopting it means shipping on macOS, iOS, iPadOS, watchOS, and tvOS.
  • ✅ Excellent fit for the Apple application model: the Cocoa delegate, target-action, and notification patterns and the main run loop are expressed directly in the language.
  • ✅ Foundation runs off Apple’s platform: portable Foundation code from GNUstep works on Linux and other systems for command-line and server work.
  • ⚠️ Cross-platform work needs a second toolkit: GNUstep supplies Foundation but has no equivalent of a modern Apple user-interface layer.
  • ⚠️ Server and command-line use is marginal: the language is used for it, but the design centre is the application platform.

1.2.5 Learning

  • ❌ Message passing is a barrier for a newcomer (L1): [receiver selector:argument], the colon-bearing selector notation, and the @-keyword set differ from dot-syntax object languages.
  • ❌ The C substrate must be learned as well: pointers, struct, C strings, manual C memory, and @encode sit underneath the object model, so the language is C plus message passing.
  • ⚠️ The runtime is a second topic: objc_msgSend, metaclasses, key-value coding and observing, and ARC semantics are separate from the source syntax.
  • ⚠️ Documentation quality follows the vendor: Apple’s guides and headers are thorough on the platform, and off-platform material is thinner.
  • ✅ The object model is conceptually small: once the message send is understood, most of the rest follows from it, including classes, selectors, and protocols.

1.2.6 Syntax

  • ✅ A message send names every argument: [view addSubview:subview positioned:NSWindowBelow relativeTo:nil] labels each argument at the call site, so the call reads as a sentence.
  • ✅ Object literals are compact: @42, @[@"a", @"b"], and @{@"k": @1} build an NSNumber, an NSArray, and an NSDictionary in one form.
  • ✅ @property shortens an accessor pair: one declaration replaces a hand-written getter, setter, and instance variable.
  • ⚠️ The selector includes its colons: addSubview:positioned:relativeTo: is one name, so a missing or an extra colon changes the selector.
  • ⚠️ Dot syntax and brackets both reach an accessor: obj.prop and [obj prop] are interchangeable, so a reader must accept two spellings for the same call.
  • ⚠️ The preprocessor is part of the surface: #import, #define, and macro-based API patterns are load-bearing in existing code.

1.2.7 Testing

  • ✅ XCTest ships with the platform toolchain: XCTestCase, the XCTAssert family, and performance tests are part of the developer tools.
  • ✅ Instruments profiles a real run: the Time Profiler, Allocations, and Leaks instruments show where time and memory go, so a test can measure a change.
  • ✅ The debugger understands messages: lldb can break on a selector, inspect the arguments of a message send, and evaluate an expression in the running process.
  • ⚠️ The framework is tied to the toolchain: XCTest and the simulator come from one vendor, so an off-platform run needs GNUstep and a different harness.
  • ⚠️ A wrong selector passes the build: with dynamic dispatch a missing method or a wrong type is a run-time failure, so the tested paths matter more than the compiled ones.

1.2.8 Security

  • ✅ ARC removes a class of memory faults: the compiler owns retain and release, so a use-after-free from a missing release is rare in ARC code.
  • ✅ A weak reference does not dangle: weak and __weak zero the reference when its referent is deallocated, so a stale link becomes nil.
  • ✅ A message to nil is safe: [nil doThing] returns nil or 0 instead of trapping, which removes a class of null-dereference crash.
  • ⚠️ id permits type confusion: a value typed id accepts any object, and a wrong cast is caught only where the code checks the class.
  • ⚠️ C is still underneath: malloc, pointer arithmetic, and a file compiled with -fno-objc-arc bypass every object-model guarantee.
  • ⚠️ Method swizzling changes behaviour after the build: method_exchangeImplementations replaces an implementation at run time, which is powerful and easy to misuse.

Verdict: Objective-C’s design yields moderate language-imposed coupling, and its weakest core dimensions are the ones the language was built around. Dynamic dispatch, the flat global namespace, and the id pointer defer type and dispatch checks to run time (T3, T6, T7). Against that, protocols give multiple inheritance of specification without implementation, categories extend a class without its source, blocks carry a callback as a value, and ARC removes manual retain and release while weak makes a stale reference zero itself. Its main weaknesses lie underneath and around the object model: there is no ownership rule and no block-scoped release, exceptions are unchecked, and the entire platform is one vendor’s, so the domain, the evolution, and the ecosystem are all locked to the same decision.
