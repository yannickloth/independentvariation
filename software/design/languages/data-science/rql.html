RQL (RavenDB 7.2)

This assessment applies the coupling account — coupling as access to a shared resource, and the coupling floor [1], [2] — and the knowledge-embodiment theorem [3]; the language is assessed against its official reference [4], [5].

Snapshot RQL (RavenDB 7.2) — released February 2026 · lifecycle current

Family RQL — shelf: Data and Science

The language’s primary object is a dataset or a numeric array, not a program loop. A shelf groups; it does not classify — the tags below carry every use, paradigm, and platform of this snapshot.

Trajectory RavenDB 1.0 (November 2010 — first stable release; queries ride the LINQ provider over document indexes) · RavenDB 3.5 (October 2016 — the last line whose raw queries predate RQL) · RavenDB 4.0 (February 2018 — RQL introduced as the raw query language the server executes) · RavenDB 6.2 LTS (September 2024 — the LTS line whose Corax search engine the 7.2 RQL clauses target) · 7.2 (February 2026 — assessed release: when() conditional filtering, nulls first/last sorting, and JSON schema validation ship with RQL 7.2)

1 Assessment

This page assesses RQL (RavenDB 7.2) in five parts: core coupling — what the language’s own constructs force; ecosystem coupling — what the surrounding platform, tooling, and community cost; engineering readiness — whether the artifact can be reproduced, verified, observed, worked in quickly, connected to other languages, and governed openly; the profile — the unscored facts a score cannot express; and the scoring detail — the mechanism marks and the arithmetic behind every score. A ✅ bullet marks a construct that helps. A ⚠️ or ❌ bullet marks a cost; the scoring model does not price every cost named here.

Core coupling 65.4/100 · Ecosystem coupling 47.3/100 · Engineering readiness 59.1/100

1.1 Core coupling

1.1.1 Type

  • ✅ The query states the result: from ... where ... select declares the projection to produce, and the reference lays the clause order over the server’s pipeline
  • ❌ The server checks values at execution: RQL carries no static check against the document shape — a document missing the filtered field ‘may return unexpected results’ in the docs’ own words, and a nulls first clause against a Lucene index answers InvalidQueryException at runtime (T1)
  • ❌ Dynamic fields drive the dispatch: a query on an unindexed field creates an auto-index from the documents found, in and all in behave per array flattening, and a field’s type follows the JSON document, not a schema (T3)
  • ❌ No sum types: a field holds a string, number, array, or nested object from the document, and an alternative is modeled by collection naming and exists() guards, not by a type (T4)
  • ❌ No parameterized query: the declare block defines one JavaScript function per query, values arrive as $param markers, and reusable logic is copied query to query (T5)
  • ❌ One flat name space: collections, indexes, and declared functions are named strings inside a database, and nothing in RQL imports definitions across databases (T6)
  • ❌ Null and absent share the filter: where on a missing field matches by index semantics, the 7.2 nulls first/last clauses exist to pin where missing-field documents land (Corax only), and exists() is the documented anchor for the distinction (T10)
  • ❌ No module boundary: declare is query-local, static-index definitions live in the server’s own map-reduce languages, and RQL text imports nothing (T11)
  • ❌ Statements state no effect: update runs a JavaScript patch over every matched document, load pulls related documents into the projection, and no signature records the write (T12)
  • ❌ JavaScript is the language’s second surface: declare functions and update patches execute server-side, and values cross between JSON documents and script objects with no typed boundary check (T14)

1.1.2 Construction

  • ✅ The pipeline mirrors the syntax: from, where, include, order by, limit, and select are the server’s pipeline stages in the order the reference states them
  • ❌ Documents mutate in place: update patches stored documents with a script, counters increment, time series append, and patching is the language’s own write surface (C2)
  • ❌ No constructor validates a patched document: a patch script can produce any JSON shape, the server ships JSON Schema validation as a feature beside the language (7.2), and the patched document’s shape is checked by the deployment, not by the query (C4)
  • ⚠️ Conditional patches race writers: an update script runs server-side over a query’s results, and RavenDB’s per-document change vectors resolve what the language does not scope

1.1.3 Memory

  • ✅ Allocation is the server’s: Voron pages, index files, and query results live in the RavenDB process, and the query text allocates nothing
  • ⚠️ A query is served by an index the server builds: a dynamic query on an unindexed field creates and maintains an auto-index, and the 7.2.5 notes fix non-ASCII index terms truncated after a 2048-character value lands in the same field — storage-engine facts the language hides

1.1.4 Error

  • ❌ No structured path in the language: a type-mismatched comparison is logged by the engine and the document drops from the result, a clause the index engine rejects raises InvalidQueryException as a server error, and the query text carries no path around either (Er1)
  • ❌ Non-matching filters are the error: a document without the filtered field falls out of where results, NOT cannot start a clause so the docs prescribe an exists() anchor, and the anchors behave differently on scoring (exists() adds a constant score, where true adds none, 7.2.6) (Er3)
  • ❌ No composable result type: documents, projections, included relateds, counters, time series, and explanations share one flat response envelope, and success and absence are read from the collection’s emptiness (Er4)
  • ✅ The response can carry its own diagnostics: include exposes query timings and explanations, published in the keyword list, so a caller reads a defined report about the query beside the data

1.1.5 Concurrency

  • ✅ Concurrency is the server’s: indexing, ETL, subscriptions, cluster transactions, and replication run as server tasks, and the language names no threads, tasks, or channels
  • ⚠️ A patch-all races writers: an update over a dynamic query’s results runs per document, and per-document change vectors and cluster transactions resolve conflicts outside the language

1.1.6 Platform

  • ❌ One product speaks RQL: the language is RavenDB’s query surface — its index engines, its Studio, its client APIs — and nothing in the language runs against another database (P1)
  • ❌ A poor fit outside document data: the unit is the JSON document, every query runs through an index the reference states as universal, and relational and analytic workloads move to the server’s ETL side (P4)
  • ✅ A typed front end shares the surface: LINQ and the high-level session methods translate to RQL before sending, per the reference, so application code plans queries through the same pipeline statically

1.1.7 Trade-offs (not coupling)

  • Every query pays for an index: the index-first pipeline publishes fast, sorted reads and auto-index convenience, and the price is write-time index maintenance every document write pays, queried or not
  • Two engines, one language, not one language: the reference states 7.2’s nulls clauses as Corax-only and answers InvalidQueryException on Lucene indexes, so the same text carries two legalities inside one product line
  • Embedded JavaScript buys projection power and server trust: declare functions format results and update scripts rewrite documents inside the query, and the language’s security surface becomes script execution bounded by admin access
  • The upgrade is a ratchet: the 7.2.5 revisions schema update publishes no downgrade path, so a deployment that adopts the newest RQL surface cannot roll its data back to the version it came from

1.2 Ecosystem coupling

1.2.1 Performance

  • ✅ The index serves the query: every RQL query runs on an auto or static index, the 7.2.6 notes ship bitmap evaluation for large Corax result sets, and the projection stage reads stored fields, not documents
  • ⚠️ Auto-indexes pay at write time: a dynamic query on an unindexed field creates an auto-index the server then maintains, a cost the docs attribute to the server’s decision, not the query’s

1.2.2 Ecosystem

  • ❌ Tooling fragments across the stack: Studio and RavenCLI ship with the server, the monitoring integrations (SNMP, Telegraf, Grafana) are per-vendor plugins, and the client tooling is per-language SDK (Ec2)
  • ❌ A niche market: RavenDB expertise concentrates in .NET-lineage application shops, and the hiring pool is a fraction of SQL’s (Ec3)
  • ❌ Source-available under the vendor’s license: the server source is published on GitHub under RavenDB’s source-available terms with usage caps, so a deployment reads the vendor’s license before its code (Ec4)
  • ❌ A .NET monoculture: the client APIs, Studio, the LINQ provider, and the deployment tooling center on .NET, and the 7.2 notes ride .NET 10 updates with a multiarch server image (Ec6)
  • ❌ Two engines kept alive under one language: the 7.2 nulls clauses are published as Corax-only, InvalidQueryException on a Lucene index, and the docs maintain a client-migration guide for the API surface the language rides on (Ec7)
  • ✅ The reference layer is open: docs.ravendb.net publishes every version 1.0 through 7.2, the Query view ships in every license, and the community channel is a click from every page

1.2.3 Evolution

  • ❌ The vendor renames, reparses, and ratchets: RQL gains keywords per release (when() conditional filtering, nulls first/last, vector.search()), the client migration guide publishes breaking changes per major, and the 7.2.5 What’s New page states the revisions storage schema update as a one-way door — after upgrading, downgrading to an earlier version is not possible (V1)
  • ✅ A yearly line with LTS points: 5.4, 6.2, and 7.2 are LTS releases with published support end dates, patches ship quarterly (7.2.7 in late 2026), and the What’s New pages state each release’s surface
  • ✅ The language moves on the product’s clock: RQL gains surface in quarterly patches, not committee drafts, so a feature arrives in release notes before it settles in the reference

1.2.4 Domain

  • ❌ Adopting RQL means adopting RavenDB’s index model: every query is served by an index, collections and fields are named strings inside a database, and counters, time series, spatial fields, and vectors are extensions the language reaches through its own keywords (D1)
  • ❌ The index-first pipeline forces the architecture: the reference states that all queries in RavenDB use an index as universal, an auto-index appears when a query needs one, and static indexes are map-reduce code in the server’s language — the application’s shape follows from what the query language can bind to (D3)
  • ✅ RQL queries stored document data: from names the source, where filters the index, and select projects the matching documents

1.2.5 Learning

  • ❌ Index semantics under SQL-shaped syntax: a SQL reader meets auto-indexes, all in answering empty where in answers full, NOT needing an anchor, and where true scoring documents differently from exists() — the reference devotes sections to these traps (L1)
  • ❌ Three syntaxes, one server: RQL text, the LINQ provider, and the DocumentQuery methods all land on RQL, JavaScript rides inside declare and update, and Lucene full-text syntax embeds inside where via lucene() (L2)
  • ✅ One reference page covers the language: the 7.2 RQL page lists every clause with worked examples, the pipeline order, and the keyword-method table

1.2.6 Syntax

  • ❌ The surface is uneven: = and == are interchangeable, NOT cannot start a clause, limit 5, 10 and limit 10 offset 5 and offset 5 coexist for the same paging, the nulls clauses are Corax-only, and declare function embeds JavaScript in a SQL-shaped text (S2)
  • ❌ Punctuation carries meaning: Lines[].ProductName for flattened arrays, all_docs? for the all-collection source, $param1 for parameters, quoted “Collection/Name” strings, // and /* */ comments — a misread token usually parses and changes the result (S3)
  • ✅ The common query is one line: from “Employees” where FirstName = “Laura” select FirstName states the projection in three clauses, and keywords are case-insensitive

1.2.7 Testing

  • ❌ No standard query-test harness in the language: the documented test story is a client-side base class over an embedded server for application code, the Query view is manual, and RQL text names no regression harness (G1)
  • ✅ The language can report its own execution: include carries query timings and explanations in the published keyword list, and Studio’s Query view runs RQL against the live database with code assistance
  • ❌ Type and field faults land on the data: a comparison against a field typed as the other type is logged and the document skipped, and the docs’ where true / exists() caveat — unexpected results when documents lack the field — is a data-shape fact found at execution (G3)
  • ❌ Only the wall clock: today() and now() compare against the current server date per the reference, when() evaluates its condition against query parameters at evaluation time, and elapsed-time tests read the server (G4)

1.2.8 Security

  • ❌ Values coerce at evaluation: order by … as long casts at the sort stage, between requires matching border types, string-and-number comparisons ride on index collation, and the 7.2.5 notes fix control-character equality and hashing as a storage consistency bug, rejecting control characters in document ids for new databases (Q2)
  • ❌ String-built queries are the injection surface: RQL is request text the RawQuery path sends as written, so concatenated user input can add clauses to a where expression, and the documented mitigation is binding values through $param markers out of band (Q3)
  • ⚠️ Stored script is the server’s trust decision: declare functions and patch scripts execute on the server, so write access to the language grants script execution, bounded per database by admin-level access

1.3 Engineering readiness

1.3.1 Reproducibility

  • ✅ A query is a request text: the same RQL on the same server version and dataset reproduces the same documents, and there is no build artifact (Y1)
  • ✅ Drivers pin by NuGet version: the client packages ship per release with the server’s version (the 7.2 notes track .NET 10.0.9), and an application pins them as ordinary dependencies (Y14)
  • ⚠️ The deployment lives server-side: results reproduce on a cluster’s topology, index state, and version — the 7.2.5 storage-schema note makes even the version a one-way fact

1.3.2 Supply chain

  • ❌ Published libraries carry no signed provenance by default: the client SDKs ship on NuGet named to their publishers, and a consumer trusts the package installed (Y3)
  • ✅ NuGet namespaces every package, so there is no flat namespace to hijack (Y4)
  • ❌ No maintained advisory feed names the product: security fixes land in release notes and vendor communication, and no CVE-mapped public advisory database tracks RQL-era releases the way Apache and CNCF projects publish theirs (Y16)

1.3.3 Observability

  • ❌ No stable tracing standard is part of the language: OpenTelemetry export is a server monitoring feature (the 7.2.5 notes add service-name configuration), SNMP and Grafana integrations are server-side, and the query text carries no trace hook (Y5)
  • ❌ No structured logging in the language: the server routes logs through NLog, keeps an audit log, and added a Studio admin logs view in 7.2.6, and the language defines no logging construct (Y6)
  • ✅ The server ships its own post-mortem: the debug package for a (sharded) database named in the 7.2.5 notes, the audit log, and the cluster dashboard give an operator the artifacts around a failure (Y15)

1.3.4 Feedback

  • ✅ Studio is submit-and-run: the Query view runs RQL against the open database with code assistance, and RavenCLI answers with no build step (Y7)
  • ✅ A maintained analyzer ships with the product: RQL code assistance in Studio’s Query view is published as part of the server, so syntax and completion land in the vendor editor before the server sees the text
  • ❌ No source-level debugger: diagnosis goes through include-explanations, query timings, the server’s logs, and Studio’s views (Y13)

1.3.5 Interop

  • ✅ JavaScript is the published extension point: declare function defines server-side functions callable from a projection, update runs patch scripts over matched documents, and values cross as JSON — the function mechanism is in the language, if untyped
  • ❌ No portable target: a query runs on a RavenDB server, and nothing in the language runs without one (Y10)
  • ✅ HTTP, ETL, and wire protocols move data across systems: queries answer over HTTP, ETL sinks publish Parquet, SQL, Kafka, and queue paths, and the PostgreSQL-protocol integration answers BI tools

1.3.6 Governance

  • ❌ Governance is the vendor: RQL gains keywords when Hibernating Rhinos ships them — the What’s New pages are release notes, not a standards process — the LTS schedule and license terms are the vendor’s, and no external body owns the language (Y11)
  • ✅ The reference is published: the clause list, keyword-method table, and per-feature guides are on the public docs site, and the server’s source is readable on GitHub (Y12)
  • ❌ No conformance mechanism exists: RQL has one implementation, so conformance is the vendor’s own test suite, and no published suite with implementation reports decides a third-party claim (Y17)
  • ✅ The parser is readable in the source: the server repository is public and source-available, and RQL parses in published code the ecosystem can inspect (Y19)

1.4 Profile

Unscored, and kept separate from every score on purpose. The profile records what a mechanism price cannot express: what a running program costs, how well a coding model and an agent work in the language, and whether a safety-critical path exists.

1.4.1 Energy and cost

What this axis asks: what does a running program cost in energy and time?

  • ⚠️ Runs on a RavenDB server: energy is the engine’s, and the reader’s levers are the index choice — auto versus static, Corax versus Lucene — that the language’s from clause makes visible.

1.4.2 AI and agent readiness

What this axis asks: how well does a coding model and an agent work in this language?

  • ⚠️ A SQL-shaped language models write fluently, and 7.2 ships an AI Assistant in Studio that generates RQL — the index-first semantics and the all in, NOT, and exists() traps are exactly where generated queries need review.

1.4.3 Safety certification

What this axis asks: is there a certified or standards-qualified path to a safety-critical system?

  • ⚠️ No certified path; RavenDB ships ACID writes, optimistic concurrency, and cluster transactions, and its safety record is the vendor’s, stated in release notes.

Verdict: RQL is a SQL-shaped surface over a document store that refuses to answer a query without an index: from, where, order by, and select read the index the server builds, an auto-index appears when a dynamic query needs one, and JavaScript rides inside the language for projection and patching. Its costs are RavenDB’s own: values coerce at evaluation, a where over a missing field drops documents silently, two index engines publish two legality rules for the same 7.2 clauses, and governance, licensing, and the roadmap are one vendor’s. Main strengths: a one-page reference with worked examples and a published trap list, query diagnostics inside the language itself (timings, explanations), Studio code assistance the vendor maintains, and LINQ as a static front end that shares the pipeline. Main weaknesses: single-vendor governance with no conformance mechanism, no portable target at all, a source-available license with usage caps, a .NET-centered ecosystem, and a published one-way storage schema on the newest line.
