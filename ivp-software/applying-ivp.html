How to Apply IVP

Applying the Independent Variation Principle is an iterative design activity, not a mechanical algorithm. It follows a six-step cycle; you revisit earlier steps as understanding deepens. The depth of analysis should be proportionate to the system’s expected lifetime and how often it changes.

This page first lays out the six steps, then works through them on a complete example, following the principle as stated in the published paper on the Independent Variation Principle (Loth 2026).

1 The six-step process

  1. Identify the elements. Choose the grain of artifact the analysis operates on — functions, classes, methods, data structures, modules. Every element is something that can change in response to a change driver.
  2. Identify the change drivers. Read the external conditions whose activation forces the system to change. This is discovery, not invention. Apply the “who asks for this change?” and “independent clock” tests: a change driver is a source of variation that can change without forcing the others to change.
  3. Map drivers to elements. Assign each element the set of change drivers that force it to change — build the assignment Γ\Gamma. Record whether each element is pure (one driver) or composite (several).
  4. Assess the current modularization. Compare the existing module structure to the Γ-equivalence partition. Name the violations: which modules are impure (IVP-3), which are incomplete (IVP-4).
  5. Refactor toward compliance. Move elements so the structure converges to the partition. Merge modules that scatter one driver’s elements; split modules that mix different drivers.
  6. Verify and iterate. Re-check the assignment and the partition as understanding deepens and as the domain changes.

2 A worked example: a notification system

To make the process concrete, consider a notification system of the kind found in any SaaS application. It is small enough to fit one page yet rich enough to exhibit both a Unit Purity and a Unit Completeness violation.

2.1 The starting point

The system sends notifications to users when events occur — account creation, order placed, payment failed, subscription expiring. It supports three delivery channels (email, SMS, push) and enforces business rules such as user preferences and rate limits.

A developer has implemented all of this in a single class, NotificationService, containing these nine methods:

Element Responsibility
e1e_1: resolveTemplate Selects the message template for a given event type
e2e_2: renderContent Populates the template with event-specific data and policy-driven personalization
e3e_3: deliverEmail Sends the notification via SMTP
e4e_4: deliverSMS Sends the notification via SMS gateway API
e5e_5: deliverPush Sends the notification via push notification service
e6e_6: checkPreferences Evaluates which channels the user has enabled
e7e_7: enforceRateLimit Throttles notifications per channel (max NN per hour per user)
e8e_8: logDelivery Records each delivery attempt for audit compliance and channel metrics
e9e_9: formatForChannel Adapts the rendered message to each channel’s constraints (e.g. SMS length, push truncation)

All nine elements live in one module: Mnotify={e1,…,e9}M_\text{notify} = \{e_1, \dots, e_9\}. As in a real system, the elements differ in how many change drivers force them to change: some are pure (assigned to one driver), others are composite (assigned to several).

2.2 Step 1: System description

The element inventory is the table above; at this granularity, each method is an element. The system’s purpose FF: deliver event-triggered notifications to users through their preferred channels, subject to business rules.

2.3 Step 2: Change driver identification

Apply the “who asks for this change?” and “independent clock” tests.

  • Message content changes when the marketing team redesigns templates, when the UX team changes wording, or when a new event type is added. None of these affect delivery or channel preferences.
  • Delivery infrastructure changes when operations switches SMTP providers, when the SMS gateway publishes a new API version, or when a new channel (e.g. WhatsApp) is added. These do not affect message content or business rules.
  • Business policy changes when the product team modifies rate limits, when legal requires changes to audit logging, or when new preference options are introduced. These are independent of formatting and delivery.

Analysis reveals three change drivers:

C={γcontent,γchannel,γpolicy} C = \{\gamma_\text{content},\ \gamma_\text{channel},\ \gamma_\text{policy}\}

The “independent clock” test confirms their independence: a template redesign (γcontent\gamma_\text{content}) can happen without changing the SMS gateway (γchannel\gamma_\text{channel}) or the rate-limiting rules (γpolicy\gamma_\text{policy}), and vice versa.

2.4 Step 3: The Γ assignment

Element Γ(e)\Gamma(e) Type
e1e_1: resolveTemplate {γcontent}\{\gamma_\text{content}\} pure
e2e_2: renderContent {γcontent,γpolicy}\{\gamma_\text{content}, \gamma_\text{policy}\} composite
e3e_3: deliverEmail {γchannel}\{\gamma_\text{channel}\} pure
e4e_4: deliverSMS {γchannel}\{\gamma_\text{channel}\} pure
e5e_5: deliverPush {γchannel}\{\gamma_\text{channel}\} pure
e6e_6: checkPreferences {γpolicy}\{\gamma_\text{policy}\} pure
e7e_7: enforceRateLimit {γpolicy,γchannel}\{\gamma_\text{policy}, \gamma_\text{channel}\} composite
e8e_8: logDelivery {γpolicy,γchannel}\{\gamma_\text{policy}, \gamma_\text{channel}\} composite
e9e_9: formatForChannel {γcontent,γchannel}\{\gamma_\text{content}, \gamma_\text{channel}\} composite

Five elements are pure (|Γ(e)|=1|\Gamma(e)| = 1); four are composite (|Γ(e)|=2|\Gamma(e)| = 2). Each composite element is irreducibly so — both of its drivers genuinely force it to change:

  • e2e_2 renderContent changes when the message content changes and when policy-driven personalization (language, consent) changes.
  • e7e_7 enforceRateLimit changes when the policy sets a new limit and when a channel’s capacity changes.
  • e8e_8 logDelivery changes when audit policy changes and when the channel’s reporting format changes.
  • e9e_9 formatForChannel changes when content changes and when a channel’s constraints change.

None of these can be split into sub-elements with strictly smaller driver sets, so each is an irreducible composite — the realistic norm, not a special case.

2.5 Step 4: Compliance assessment

Evaluate the monolithic modularization {Mnotify}\{M_\text{notify}\}:

  • Element Admissibility (IVP-1). Every element has a non-empty Γ(e)\Gamma(e). ✓
  • Change-Driver Assignment (IVP-2). Every element is pure or irreducibly composite. ✓ (the four composite elements are all irreducible.)
  • Unit Purity (IVP-3). Γ(Mnotify)\Gamma(M_\text{notify}) contains γcontent,γchannel,γpolicy\gamma_\text{content}, \gamma_\text{channel}, \gamma_\text{policy} and elements with six distinct driver-assignment sets coexist in one module. Violated.
  • Unit Completeness (IVP-4). With only one module, all elements responding to each driver are trivially together. ✓ (trivially)

The diagnosis: MnotifyM_\text{notify} is a mixed module. Any activation of a change driver touches the whole module, even though only a subset of its elements actually varies. This is the god-module pattern.

2.6 A naive first attempt

A common first instinct is to decompose by technical layer: one module for content handling, one for transport, one for business logic, one for logging.

ModuleSet1={Mcontent,Mtransport,Mlogic,Mlogging} \text{ModuleSet}_1 = \{M_\text{content},\ M_\text{transport},\ M_\text{logic},\ M_\text{logging}\}

Module Elements Γ(M)\Gamma(M)
McontentM_\text{content} {e1,e2}\{e_1, e_2\} {γcontent,γpolicy}\{\gamma_\text{content}, \gamma_\text{policy}\}
MtransportM_\text{transport} {e3,e4,e5,e9}\{e_3, e_4, e_5, e_9\} {γchannel,γcontent}\{\gamma_\text{channel}, \gamma_\text{content}\}
MlogicM_\text{logic} {e6,e7}\{e_6, e_7\} {γpolicy,γchannel}\{\gamma_\text{policy}, \gamma_\text{channel}\}
MloggingM_\text{logging} {e8}\{e_8\} {γpolicy,γchannel}\{\gamma_\text{policy}, \gamma_\text{channel}\}

By technical category, the modules look clean — each holds the elements that “feel like” they belong to that layer. But the driver assignments tell a different story:

  • Unit Purity (IVP-3). Three of the four modules are mixed — they group elements that answer to different drivers. McontentM_\text{content} mixes content and policy (because e2e_2 is composite), MtransportM_\text{transport} mixes channel and content (because e9e_9 is composite), and MlogicM_\text{logic} mixes policy and channel (because e7e_7 is composite). Violated.
  • Unit Completeness (IVP-4). Elements answering to γpolicy\gamma_\text{policy} are scattered across McontentM_\text{content}, MlogicM_\text{logic}, and MloggingM_\text{logging}; elements answering to γchannel\gamma_\text{channel} across MtransportM_\text{transport}, MlogicM_\text{logic}, and MloggingM_\text{logging}. Violated.

The technical-layer decomposition fails on both directives. A change in business policy touches three modules; a change in a channel’s infrastructure touches three modules. This is shotgun surgery spread wide, plus hidden coupling: the composite elements land in whichever layer their technical category suggests, silently wiring together drivers that should be separated.

Why this mistake is common. Decomposing by technical layer (presentation, logic, data) is a deeply ingrained habit. Technical layers sometimes conform to change drivers, but not always — and the more composite elements a system has, the more the two diverge. The test is not “what kind of thing is this element?” but “what causes this element to change?” A composite element belongs with the elements it shares drivers with, not with the layer its name suggests.

2.7 Step 5: The IVP-compliant decomposition

The fix is to group elements by their exact driver-assignment set. Each distinct set forms one equivalence class — one module. The nine elements fall into six classes:

ModuleSet2={M1,M2,M3,M4,M5,M6} \text{ModuleSet}_2 = \{M_1,\ M_2,\ M_3,\ M_4,\ M_5,\ M_6\}

Module Elements Γ(M)\Gamma(M)
M1M_1 {e1}\{e_1\} {γcontent}\{\gamma_\text{content}\}
M2M_2 {e3,e4,e5}\{e_3, e_4, e_5\} {γchannel}\{\gamma_\text{channel}\}
M3M_3 {e6}\{e_6\} {γpolicy}\{\gamma_\text{policy}\}
M4M_4 {e2}\{e_2\} {γcontent,γpolicy}\{\gamma_\text{content}, \gamma_\text{policy}\}
M5M_5 {e9}\{e_9\} {γcontent,γchannel}\{\gamma_\text{content}, \gamma_\text{channel}\}
M6M_6 {e7,e8}\{e_7, e_8\} {γpolicy,γchannel}\{\gamma_\text{policy}, \gamma_\text{channel}\}
  • Element Admissibility (IVP-1). Every element has non-empty Γ(e)\Gamma(e). ✓
  • Change-Driver Assignment (IVP-2). Every element is pure or irreducibly composite. ✓
  • Unit Purity (IVP-3). Each module groups elements with the same driver assignment. ✓
  • Unit Completeness (IVP-4). Every element of a given assignment set is in the same module. ✓

IVP-compliant. Each distinct driver-assignment set is one module. The pure modules (M1,M2,M3M_1, M_2, M_3) each hold a single driver’s elements. The composite modules (M4,M5,M6M_4, M_5, M_6) each hold one assignment set; because their elements are irreducibly multi-driver, these modules are necessarily impure — they must answer to two drivers because the domain forces it.

The driver space is shown as a symmetric Venn diagram below. The driver sets overlap at 120°, and their partial overlaps generate seven regions, each a distinct change-driver-assignment set — a possible partition class. The single-driver regions hold the pure modules; the composite elements occupy the overlap regions.

2.8 Step 6: Reflecting on the result

The three modularizations differ in how far a change propagates. The measure that matters is not how many modules are touched, but how many elements must be inspected or modified when a change driver activates — and how many of those were touched unnecessarily.

When a driver activates, the elements that must change are fixed by the domain: γcontent\gamma_\text{content} forces e1,e2,e9e_1, e_2, e_9; γchannel\gamma_\text{channel} forces e3,e4,e5,e7,e8,e9e_3, e_4, e_5, e_7, e_8, e_9; γpolicy\gamma_\text{policy} forces e2,e6,e7,e8e_2, e_6, e_7, e_8. The designs differ in how many elements they actually touch beyond that unavoidable set:

Driver activation Elements that must change Monolithic touches IVP-compliant touches
γcontent\gamma_\text{content} {e1,e2,e9}\{e_1, e_2, e_9\} (3) 9 3
γchannel\gamma_\text{channel} {e3,e4,e5,e7,e8,e9}\{e_3, e_4, e_5, e_7, e_8, e_9\} (6) 9 6
γpolicy\gamma_\text{policy} {e2,e6,e7,e8}\{e_2, e_6, e_7, e_8\} (4) 9 4

The monolithic design places all nine elements in one module, so every driver activation touches all nine elements, even though only a fraction of them actually vary — up to six unnecessary touches per change. The IVP-compliant design touches exactly the elements that must change and nothing else — zero unnecessary touches, because every module holds only the elements of its driver. This is what IVP’s partition theorem guarantees: the IVP-compliant modularization minimizes change propagation — the scope that must be read and modified when a change driver activates.

The composite elements make the per-driver footprint larger than in a pure system — γchannel\gamma_\text{channel} alone forces six elements across three modules — but this is the domain’s cost, not a defect: each of those elements genuinely must change when the channel changes. IVP cannot reduce the required set; it only ensures that nothing outside it is touched.

2.9 What about dependencies between modules?

The modules in ModuleSet2\text{ModuleSet}_2 will have structural dependencies between them: the orchestration that calls resolveTemplate, then checkPreferences, then deliverEmail introduces inter-module coupling.

IVP does not eliminate dependencies — it organizes them. Dependencies between modules conforming to different change drivers are expected and manageable. Dependencies within a mixed module are the hidden ones that cause maintenance surprises. The composite modules sit between the pure ones by necessity: e9e_9 bridges content and channel, e2e_2 bridges content and policy, e7e_7 and e8e_8 bridge policy and channel. Each is an explicit bridge the domain requires — better a few named bridges than a hidden tangle inside a monolithic module.
