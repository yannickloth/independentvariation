Architecture Patterns as Knowledge-Gap Indicators

A list of short posts that read each pattern as a completeness check on domain knowledge.

Each architecture pattern names a boundary the domain must already have drawn. The five styles get their full assessments under Verdicts: Hexagonal, Onion, Clean, Layered, Vertical slice.

Pick a post on the left. It opens on the right.

Case study: Command Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

The faithfulness test asks for an answer on record, not an answer in someone’s head. A pattern is a knowledge check only when a missing answer stops the design.

Ask what the fact is and where it is written. Then ask where the term is defined, and whether all its users share that definition. If either answer is missing, the design waits until the artifact exists.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF: Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations. [1]

The domain knowledge gap it signals

The fact that an action is a first-class thing — not just a method call — is domain knowledge. If your domain model already crystallizes that “an operation must be recorded, queued, undone, or scheduled — the action itself is a domain entity with identity and lifecycle,” then Command is just embodying that knowledge.

ImportantWhen it’s applicable (cohesion-increasing)

The domain treats actions as entities: they can be stored, replayed, reversed, and audited. An order-fulfillment system where “ShipOrder,” “CancelOrder,” and “RefundOrder” are domain commands — with undo semantics, execution timestamps, and audit trails — is the domain speaking. Command closes the gap: it prevents the action logic from being a method buried on some service class, which would make the action invisible to the domain model. Instead, each command is a domain object with its own data, validation, and undo path.

WarningWhen it’s inapplicable (cohesion-reducing)

The “commands” are not domain commands — they’re method-call wrappers. Wrapping every service-method invocation in a Command object because the framework expects it doesn’t reify a domain concept; it wraps function calls in infrastructure ceremony. Command here adds object-allocation and indirection costs to what should be a direct call, signaling entity-richness where the domain has none. Event-sourcing architectures are a valid exception — commands as persisted entities with identity serve a persistence/routing infrastructure that IS the architecture.

TipThe faithfulness test

Does the domain expert talk about this operation as a thing that exists — “the shipment,” “the refund,” “the approval request”?

  • If yes → applicable: Command is the code catching up to the knowledge.
  • If no → inapplicable: it is function-call packaging.
  • If you can’t answer → stop. The artifact to produce is the operation register: each operation the business names, with what records it, who may request it, and what undoes it. Until it is on file, a method call is wearing an entity’s name.

Case study: Dependency Injection

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Dependency injection is how a service declares what it needs and receives it from outside, without knowing where the dependency comes from or how it is built. Dependency injection is not the composition root. One is a technique, the other a place.

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: A form of Inversion of Control in which a component is given its dependencies rather than creating them itself. [2]

The domain knowledge gap it signals

With dependency injection, a service declares: I need these dependencies — but I do not need to know where to get them, or how to build them; give them to me. A faithful declaration carries domain knowledge: an order service needs persistence and messaging. Even which database, which queue, and how they are built is a domain decision: someone chose them. The interface states the need; the composition root supplies the answer. The gap it signals is whether the need is real and whether the supply can vary.

ImportantWhen the domain mandates it (cohesion-increasing)

The need is real and the supply can vary. The order service always needs persistence; which database serves it can change. The interface declares the need once; the composition root supplies the answer.

WarningWhen the domain doesn’t (cohesion-reducing)

The need is invented, or the need is real but the supply cannot vary. Either way the injection point asserts a boundary the domain never decided: the external seam is unwritten.

TipThe faithfulness test

Is the need real, and can the supply vary?

  • If the need is real and the supply can vary → applicable. Dependency injection is the code catching up to the knowledge.
  • If the need is invented → inapplicable; nothing to abstract. If the supply cannot vary → inapplicable; no variation justifies it.
  • If you can’t answer → stop. The artifact to produce is the supply record: for each collaborator, the need it serves and the list of suppliers that may satisfy it, with the owner who chooses. Until it is on file, the binding is invented by the container.

=== DI is not the composition root === DI is a technique: how a service declares its dependencies and receives them from outside. The composition root is a place: where the application assembles its object graph, at the entry point. Only applications should have one — composition belongs to the application. A DI container belongs only there. DI does not specify where the object graph is assembled; the composition root answers that. Two failures hide when the names are conflated:

  • Scattered wiring: composition at each use site, with no root. A deployment change touches many files.
  • A frozen choice: a root that bakes a per-operation choice in at startup.

Case study: Composition Root

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

A composition root is the single place where the object graph is assembled, at the entry point. It looks like a purely technical construct, but what it assembles — and where it sits — follows from a modularization rule derived from domain knowledge.

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Seemann: A single, logical location in an application where modules are composed together. [3]

The domain knowledge gap it signals

The assembly looks purely technical, but it is still a domain decision: the same modularization rule decides where the composition root goes, what each service receives, what belongs inside each service, and whether each dependency is fixed for the object’s lifetime. The root decides those choices once, for the whole graph. The rule is derived from domain knowledge: it follows from which choices the domain owns and which it leaves open. The service’s content is fixed by the rule, not by the wiring that supplies it. The gap is the rule: if you cannot say which choices the domain owns, you cannot say where the composition root goes or what the services contain.

ImportantWhen the domain mandates it (cohesion-increasing)

The modularization rule is clear, so the composition root sits where it belongs, and each service receives what the rule assigns. A change to one choice touches one place.

WarningWhen the domain doesn’t (cohesion-reducing)

The rule is unstated. A choice the domain owns is supplied at the composition root, so the domain can no longer vary it — every such change now edits the composition root. Or the composition root sits in a library or framework, so it carries choices that belong to its caller.

TipThe faithfulness test

Where is the rule written that places the composition root and assigns what each service receives?

  • If the placement rule and the wiring table are on file → applicable. Composition Root is the code catching up to the knowledge.
  • If neither exists → inapplicable. The composition root is placed by guesswork.
  • If you can’t answer → stop. The artifacts to produce are the root’s placement rule and the table of injections it performs. Until both are on file, the wiring states nothing the design decided.

Case study: Hexagonal Architecture (Ports & Adapters)

“Keep the domain at the centre. Let the outside change around it.” Hexagonal architecture (Ports & Adapters) draws its boundary between the core domain and every integration mechanism. IVP asks the prior question: is that boundary real, or is it a packaging habit?

Reaching for a pattern? Ask “does the domain’s change structure mandate this boundary?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the style adds nothing the domain hadn’t already decided.

The domain knowledge gap it signals

Every architecture style is a claim about the axis along which change happens. Hexagonal guesses the axis: core domain versus integration mechanism. It says the business rules can change without touching how the system is reached (HTTP, CLI, message queue) or what it stores (SQL, files, third-party services). A port is the core’s own interface; an adapter is the mechanism that fits it. The knowledge behind the style is a change-driver claim: the core’s change drivers are disjoint from the adapters’.

ImportantWhen the domain mandates it (cohesion-increasing)

The core’s change-driver sets are disjoint from the adapters’. A domain rule changes for its own reason — a business rule, a regulation. The transport or storage changes for a different reason — a framework upgrade, a vendor swap. Two independent change drivers, two modules, one boundary. The port names the core’s need once; the adapter absorbs the mechanism. The style names a partition the domain already fixed.

WarningWhen the domain doesn’t (cohesion-reducing)

The boundary asserts an independence the change drivers do not have. When a business-rule change forces an adapter change — the rule leaks into the query or the payload — the two sides share a change driver, and change propagates through the port. A port invented to wrap a mechanism the domain never treated as separate is ceremony, not a boundary.

TipThe faithfulness test

Do the core’s change drivers differ from the adapters’ — would a change to one leave the other untouched?

  • If yes → applicable. Hexagonal is the code catching up to the knowledge; the boundary is the domain’s own.
  • If no → inapplicable. The port asserts an independence that is not there; the cut is packaging.
  • If you can’t answer → stop. The artifact to produce is the change-driver record: for each change the system must absorb, the requirement that forces it and the side that owns it. Until that record is on file, the boundary is packaging and the drivers are unassigned.

⚠️ The claim is relative, not absolute. The core is independent of the mechanism — not of everything. A business-rule change still changes the core. The style promises independence from integration, never changelessness. Sibling styles guess other axes: layering guesses technical roles (#171), vertical slices guess features (#172), Clean (#173) and Onion (#174) guess concentric rings. Do not choose the style. Find the change-driver assignment; a style is valid only if that structure mandates it — the style is whichever cut matches.

Case study: Layered Architecture (Horizontal Slices)

Layers cut the system horizontally: presentation, application, domain, persistence — each layer talks to the next. IVP asks the prior question: do the domain’s changes actually follow those technical roles?

Reaching for a pattern? Ask “does the domain’s change structure mandate this boundary?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the style adds nothing the domain hadn’t already decided.

The domain knowledge gap it signals

Layering guesses the axis: technical role. It claims that changes arrive already classified as presentation, application, domain, or persistence work, and that each concern belongs in its own horizontal band. The knowledge behind the style is a change-driver claim: the domain’s change drivers equal those technical roles.

ImportantWhen the domain mandates it (cohesion-increasing)

A change driver is confined to one layer. A layout or formatting change stays in the presentation layer. A wire-format or storage change stays in the persistence layer. No change driver crosses a layer boundary, so each layer groups exactly one change-driver assignment, and a change touches one band.

WarningWhen the domain doesn’t (cohesion-reducing)

A change driver crosses layers. “Add a discount rule” edits the controller, the service, and the repository. One change driver now lives in three modules, and change propagates across two boundaries — the cut scattered a single change driver. Layering is a horizontal cut by construction, so it is right only when the domain’s change drivers happen to equal presentation, domain, and persistence. That coincidence is rare when the real change drivers are features or business rules.

TipThe faithfulness test

For the changes you expect, does each change land inside one layer?

  • If yes → applicable. The layers coincide with the change-driver assignment.
  • If no → inapplicable. The layers group different change-driver assignments; the cut is technical, not structural.
  • If you can’t answer → stop. The artifact to produce is the change-driver record: for each change the system must absorb, the requirement that forces it and the side that owns it. Until that record is on file, the boundary is packaging and the drivers are unassigned.

Sibling styles guess other axes: vertical slices guess features (#172), hexagonal guesses core-versus-mechanism (#170), Clean (#173) and Onion (#174) guess concentric rings. Do not choose the style. Find the change-driver assignment; a style is valid only if that structure mandates it — the style is whichever cut matches.

Case study: Vertical Slice Architecture

A vertical slice cuts end to end for one feature: request, rule, storage, response, all in one place. IVP asks the prior question: does each feature carry its own change driver, or does one rule run across them all?

Reaching for a pattern? Ask “does the domain’s change structure mandate this boundary?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the style adds nothing the domain hadn’t already decided.

The domain knowledge gap it signals

Vertical slicing guesses the axis: features or use cases. It claims each operation has its own reasons to change, so one slice per operation keeps each reason in one module, end to end. The knowledge behind the style is a change-driver claim: each feature’s elements share one change-driver set, different from the other features’.

ImportantWhen the domain mandates it (cohesion-increasing)

Each feature changes for its own change driver. “Place order” and “issue refund” change for different business reasons. A slice per operation keeps each change driver inside one module, from the entry point to storage, and a change to one feature touches one slice.

WarningWhen the domain doesn’t (cohesion-reducing)

A change driver spans features. A cross-cutting rule — currency handling, tax, audit, authorisation — changes every slice at once. That shared change driver is scattered across N slices; each slice now holds its feature change driver plus the shared rule’s change driver, and one edit to the rule touches every slice. The slice boundary cut a change driver in half.

TipThe faithfulness test

Does a change land inside one slice, or does one rule reach across many?

  • If it lands in one → applicable. The slice is the change driver’s home.
  • If it reaches across → inapplicable. A shared change driver was split; the slices assert an independence that is not there.
  • If you can’t answer → stop. The artifact to produce is the change-driver record: for each change the system must absorb, the requirement that forces it and the side that owns it. Until that record is on file, the boundary is packaging and the drivers are unassigned.

Layers and slices are dual guesses — one cuts by technique, the other by feature. A domain can carry both a feature change driver and a shared rule change driver, so neither pure cut need be right. Sibling styles: layered (#171), hexagonal (#170), Clean (#173), Onion (#174).

Case study: Clean Architecture

Clean Architecture rings the system: Entities, Use Cases, Interface Adapters, Frameworks & Drivers — and the Dependency Rule says source dependencies point inward only. IVP asks the prior question: does the domain actually govern in that direction?

Reaching for a pattern? Ask “does the domain’s change structure mandate this boundary?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the style adds nothing the domain hadn’t already decided.

The domain knowledge gap it signals

Clean guesses an axis of decisional dependency: an outer choice exists to satisfy an inner rule. The knowledge behind the style is which rules the business owns as policy — the rule that governs — and which are mechanism chosen to serve it. The Dependency Rule is the code’s expression of that direction. Clean adds a stratification the hexagonal style leaves flat: it splits the outer side into use cases, adapters, and frameworks, and orders them.

ImportantWhen the domain mandates it (cohesion-increasing)

The decisional ordering is real. The use case is written against the entity’s rules; the adapter is chosen to serve the use case; the framework is chosen to serve the adapter. Every dependency points inward, and each ring’s change-driver set is disjoint from the others. When a dependency is reversed — an interface owned by the inner ring and implemented by the outer — only placement changes; the change-driver set is unchanged.

WarningWhen the domain doesn’t (cohesion-reducing)

The ordering is asserted, not real. The inner ring changes because an outer ring changed — a framework upgrade forces an entity change — so the decisional dependency points the wrong way. Or the “use case” ring is a pass-through that changes with the framework, and the ring boundary groups elements with different change-driver assignments.

TipThe faithfulness test

For each dependency, which side’s requirement was the other chosen to satisfy?

  • If every answer points to the centre → applicable. The ordering is the domain’s own.
  • If an outer choice is independently governed → inapplicable. The ring asserts a direction the domain does not have.
  • If you can’t answer → stop. The artifact to produce is the change-driver record: for each change the system must absorb, the requirement that forces it and the side that owns it. Until that record is on file, the boundary is packaging and the drivers are unassigned.

⚠️ Entities are the innermost ring, not an unchanging one. Clean claims independence from mechanism, not from everything; a business-rule change still reaches the centre. Sibling styles: hexagonal (#170), layered (#171), vertical slice (#172), Onion (#174).

Case study: Onion Architecture

Onion Architecture puts the domain model at the very centre: the model, then domain services, then application services, then infrastructure at the rim. Every dependency points inward. IVP asks the prior question: do those rings follow the domain’s real seams?

Reaching for a pattern? Ask “does the domain’s change structure mandate this boundary?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the style adds nothing the domain hadn’t already decided.

The domain knowledge gap it signals

Onion guesses an axis with the domain model as kernel and services as rings. Unlike Clean Architecture, Onion separates two service layers — domain services and application services — and centres the model, not the use cases. The knowledge behind the style is a change-driver claim: the model depends on nothing; orchestration is itself an outer concern; infrastructure is the rim. Dependency inversion carries the direction at every boundary.

ImportantWhen the domain mandates it (cohesion-increasing)

The model’s change-driver set is disjoint from the service and infrastructure change drivers. Domain rules change the model. Workflow and orchestration change the application-service ring. Mechanism changes infrastructure. Each ring groups one change-driver assignment, and every dependency points inward.

WarningWhen the domain doesn’t (cohesion-reducing)

A business rule is expressible only through a service — an invariant that needs coordination — so the model depends on the service ring, and the two share a change driver. Or an “application service” accumulates business rules and collapses into the model ring, grouping different change-driver assignments in one ring. In both cases a ring boundary cuts a change driver.

TipThe faithfulness test

Can every business rule be placed in exactly one ring — model, domain service, application service — without leaking across?

  • If yes → applicable. The rings are the domain’s own.
  • If a rule needs two rings → inapplicable. The boundary cut a change driver.
  • If you can’t answer → stop. The artifact to produce is the change-driver record: for each change the system must absorb, the requirement that forces it and the side that owns it. Until that record is on file, the boundary is packaging and the drivers are unassigned.

Onion and Clean are cousins: both order policy inward. Onion’s distinctive kernel is the domain model with two service rings; Clean’s inner ring is enterprise policy with use cases next. Sibling styles: hexagonal (#170), layered (#171), vertical slice (#172), Clean (#173).
