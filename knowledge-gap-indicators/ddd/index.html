Domain-Driven Design as Knowledge-Gap Indicators

A list of short posts that read each pattern as a completeness check on domain knowledge.

Almost every design pattern/principle can be used as a completeness-check on domain knowledge. For DDD’s tactical patterns, the justification is explicitly domain-driven — which makes the gap check sharper: is the pattern the knowledge itself, or ceremony wearing its clothes?

Pick a post on the left. It opens on the right.

Case study: Value Object

Evans: “An object that describes some characteristic or attribute but carries no concept of identity.” [1]

A Value Object is a small immutable type that code compares by field values, not by identity.

The domain knowledge gap it signals

The fact that this thing is defined by its attributes and has no identity is domain knowledge. If your domain model crystallises that “a €10 note is any €10 note,” “an address is whatever its fields say,” or “two measurements of 5 kg are the same measurement,” then equality-by-value is a domain rule, not a convenience. A Value Object is that rule made executable: immutable, interchangeable, replaceable wholesale.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain treats the concept as a measure, a quantity, a description — something with no “which one is it?” question. A Value Object closes the gap: it prevents the concept from being tracked by identity, which would let two domain-equal instances be distinguished by accident. Immutability is the domain’s own “a value doesn’t change; you get a new one” rule, and validation in the constructor is the domain’s own “a value cannot exist in an invalid state” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

The concept has real identity the domain tracks over time — this customer, this order, this account — even when every attribute changes. Forcing it into a Value Object erases the “which one is it?” question the domain asks constantly. Conversely, wrapping every string and number in a Value Object because immutability is fashionable is still a decision, but it signals “the domain distinguishes these” when the domain never named a distinction. That is the gap — the distinction is unwritten, not “merely technical.”

TipThe faithfulness test

Would a domain expert ask “which one is it?” about this thing — or only “what is it?” If equality of attributes settles the matter, it’s a value.

  • If yes (identity matters) → inapplicable. Model an Entity; identity is the domain’s own question.
  • If no (attributes settle it) → applicable. The Value Object is the code catching up to the knowledge.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Entity

Evans: “An object that is not fundamentally defined by its attributes, but rather by a thread of continuity and identity.” [1]

An Entity is a type whose instances code tracks by an identity separate from their fields.

The domain knowledge gap it signals

The fact that this thing remains itself while everything about it changes is domain knowledge. If your domain model crystallises that “the customer who moves house and changes her name is still the same customer,” then identity over time is a domain rule, not a database convenience. An Entity is that rule made executable: identity that persists through state changes, and a lifecycle the domain tracks.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain distinguishes this instance from that one by identity, not by attributes, and tracks each through birth, change, and closure. An Entity closes the gap: it prevents the thing from being copied or compared by fields, which would let the domain lose track of which customer is which. Equality by identity is the domain’s own “same customer even after moving” rule; the lifecycle methods are the domain’s own “what may happen to it, and when” rules.

WarningWhen the domain doesn’t (cohesion-reducing)

The “entity” has no identity the domain cares about — it is a measure, a description, a quantity, where attribute equality settles every question. Assigning it an ID invents a “which one is it?” question the domain never asks, and forces the code to maintain identity maps for things that are interchangeable. The ID signals “the domain tracks this through time” when the domain only reads its value.

TipThe faithfulness test

Does the domain track this thing through time as “the same thing” — same customer, same order, same account — even as its attributes change?

  • If yes → applicable. The Entity is the code catching up to the knowledge; identity is the domain’s own thread.
  • If no → inapplicable. Model a Value Object; inventing identity fabricates a domain question.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Aggregate

Evans: “A cluster of associated objects that we treat as a unit for the purpose of data changes.” [1]

An Aggregate is a group of objects that code loads, changes, and saves as one unit through a single root.

The domain knowledge gap it signals

The fact that these things change together, and that this rule must hold at every moment, is domain knowledge. If your domain model crystallises that “an order’s total can never disagree with its lines,” or “a reservation may not exceed the room’s capacity,” then the invariant is a business rule and the boundary around it is the domain’s own consistency claim. An Aggregate is that claim made executable: one root, one transaction, invariants enforced inside.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain names a rule that must always hold, and every path that could break it is known. An Aggregate closes the gap: it funnels all change through the root, so the invariant cannot be bypassed. The boundary is the domain’s own “these change together, or not at all” rule; references by identity to other aggregates are the domain’s own “these stay independent” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

There is no knowledge-free half of this split. Grouping a screen’s data into one Aggregate is still a decision: someone chose that boundary. But the boundary asserts one transaction and one invariant. It fits only when the domain names the rule that must always hold inside it. If the domain allows eventual, separate change, it never named that rule, and the Aggregate’s lock asserts a consistency nobody decided. That is the gap — the invariant is unwritten, not a save-a-join trick.

TipThe faithfulness test

Can a domain expert name the invariant — the rule that must always hold inside this boundary, the way a banker names “the balance always equals the sum of entries”?

  • If yes → applicable. The Aggregate is the code catching up to the knowledge; the boundary is the domain’s own consistency claim.
  • If no → inapplicable. Draw the boundary around the actual invariant — or discover there isn’t one.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Repository

Evans: “A mechanism for encapsulating storage, retrieval, and search behavior which emulates a collection of objects.” [1]

A Repository is an interface that gives code collection-like access to stored domain objects.

The domain knowledge gap it signals

The fact that the domain speaks of a collection of these things is domain knowledge. If your domain model crystallises that “all active orders are here; we add orders; we find open ones,” then the collection metaphor is the domain’s own vocabulary. A Repository is that vocabulary made executable: an in-memory-collection facade (add, find, remove) over persistence, named in domain terms.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain genuinely reasons about a set of things — “all overdue invoices,” “the customer by number” — and the queries map to expert phrases. A Repository closes the gap: it gives the domain its collection language while hiding storage, and it confines query logic to interfaces the experts can read. It prevents persistence calls from scattering through domain code, which would couple business rules to SQL.

WarningWhen the domain doesn’t (cohesion-reducing)

There is no knowledge-free half of this split. A method that mirrors one screen, one report, or one ORM call is still a decision, but a Repository asserts that the domain speaks of collections. It fits only when an expert phrase matches the query. If no phrase matches, the Repository supplies vocabulary the domain never adopted — the collection is unwritten, not “merely technical.” Repositories over Value Objects or read-only projections add a facade with no collection semantics behind it.

TipThe faithfulness test

Can each repository method be read aloud to a domain expert as something they say — “find open orders,” “get customer by number” — rather than as a data-access operation?

  • If yes → applicable. The Repository is the code catching up to the knowledge; the collection is the domain’s own concept.
  • If no → inapplicable. It’s a DAO; name it honestly or reshape the queries around domain phrases.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Domain Service

Evans: “An operation offered as an interface that stands alone in the model, without encapsulating state, as entities and value objects do.” [1]

A Domain Service is a stateless operation that holds a domain rule belonging to no single entity.

The domain knowledge gap it signals

The fact that this operation belongs to the domain yet has no natural home on a single entity is domain knowledge. If your domain model crystallises that “transferring money involves two accounts and a rule neither owns alone,” then the Domain Service is that fact made executable: a stateless operation named in domain language, placed where the domain says it lives.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain performs an action that spans several entities or needs domain knowledge no single entity should hold. A Domain Service closes the gap: it prevents the operation from being squeezed onto one entity (wrong owner) or diluted into an application helper (no domain home). Its name is the domain’s own verb — “transfer,” “allocate,” “renegotiate” — and its logic is the business rule, not orchestration.

WarningWhen the domain doesn’t (cohesion-reducing)

The “domain service” is where logic went because no one could decide who owned it — an entity skirted of its own behaviour. Then the service is an anemic-model accelerant: entities hold data, the service holds all rules, and the domain’s own subjects stop carrying their own knowledge. Likewise, a service that only fetches, orchestrates, or calls infrastructure is an application service wearing the wrong name.

TipThe faithfulness test

Can you name the operation in the experts’ words, and is it genuinely homeless — belonging to no single entity — rather than parked there for convenience?

  • If yes → applicable. The Domain Service is the code catching up to the knowledge; the verb is the domain’s own.
  • If no → inapplicable. Move the behaviour to the entity that owns it, or rename the service to what it really is.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Domain Event

Fowler: “A Domain Event is a full-fledged part of the domain model, a representation of something that happened in the domain.” [2]

A Domain Event is a message that records something meaningful that happened in the domain.

The domain knowledge gap it signals

The fact that the business talks about this occurrence — that it has a name, a time, and consequences — is domain knowledge. If your domain model crystallises that “when an order is placed, fulfilment and invoicing both react,” then “OrderPlaced” is a domain fact, not a messaging artefact. A Domain Event is that fact made executable: something that happened, named in the experts’ words, with the past tense the experts use.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain recognises the occurrence as a milestone: experts refer to it, reports count it, other parts of the business respond to it. A Domain Event closes the gap: it prevents the occurrence from being a side effect buried in a method, and it lets reacting parts subscribe without the placer knowing them. The event name is the domain’s own vocabulary; the timestamp is the domain’s own “when it happened.”

WarningWhen the domain doesn’t (cohesion-reducing)

There is no knowledge-free half of this split. A table change such as “OrderSaved,” “FieldChanged,” or “RowUpdated” is still a decision, and publishing it asserts a named occurrence. It fits only when the experts name the moment and its consequences. If the experts do not, the Domain Event asserts a milestone nobody decided and forces consumers to reconstruct meaning the producer should have named. That is the gap — the occurrence is unwritten, not “merely technical.”

TipThe faithfulness test

Would a domain expert use this occurrence in a sentence — “the order was placed, so we…” — with the same name and the same consequences?

  • If yes → applicable. The Domain Event is the code catching up to the knowledge; the milestone is the domain’s own fact.
  • If no → inapplicable. It’s a change notification; name the integration honestly instead of borrowing domain dress.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Factory

Evans: “Shift the responsibility for creating instances of complex objects and aggregates to a separate object, which may itself have no responsibility in the domain model.” [1]

A Factory is a construct that wraps the code that creates an object.

The domain knowledge gap it signals

The fact that creating this thing involves rules — what must be true for it to exist at all — is domain knowledge. If your domain model crystallises that “an order cannot exist without a customer and at least one line,” or “a policy is created through quotation, not directly,” then the creation rules are domain invariants. A Factory is that fact made executable: the domain’s own birth rules, stated once, at the birthplace.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain has creation rules the experts could state — required companions, initial state, eligibility. A Factory closes the gap: it prevents half-born objects from existing, which would push invariant checks into every method that touches the thing afterwards. Creation through the factory is the domain’s own “it may only come into existence this way” rule; a complex constructor argument list is often the factory’s knowledge looking for a name.

WarningWhen the domain doesn’t (cohesion-reducing)

There is no knowledge-free half of this split. Creating an object is still a decision, and a Factory asserts that creation follows a rule. It fits only when the experts can state the conditions under which the thing may come into existence. If the domain attaches no conditions to creation, the Factory claims governance nobody decided. That is the gap — the creation rule is unwritten, not “merely technical.”

TipThe faithfulness test

Can a domain expert state the conditions under which this thing may come into existence — and would violating them be a domain error, not a null-pointer?

  • If yes → applicable. The Factory is the code catching up to the knowledge; the birth rules are the domain’s own.
  • If no → inapplicable. Construct directly; the ceremony invents governance the domain never claimed.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Specification

Evans: “A predicate that determines if an object does or does not satisfy some criteria.” [1]

A Specification is a rule object that code can check and combine with other rules.

The domain knowledge gap it signals

The fact that this predicate is a named business rule — one the experts evaluate, discuss, and sometimes change — is domain knowledge. If your domain model crystallises that “eligibility for the discount” is a thing the business defines, audits, and redefines, then the rule is a domain concept in its own right. A Specification is that fact made executable: a first-class, nameable, combinable rule object.

ImportantWhen the domain mandates it (cohesion-increasing)

The experts name the rule, apply it in several places, or change its terms without changing the surrounding process. A Specification closes the gap: it prevents the rule from being re-implemented in a validation here, a where-clause there, and a report query somewhere else — three copies drifting apart. The specification’s name is the domain’s own phrase (“OverdueForRenewal”), and combining specifications mirrors how the experts combine the rules.

WarningWhen the domain doesn’t (cohesion-reducing)

There is no knowledge-free half of this split. A predicate such as “id != null” or “createdAfter(threshold)” is still a decision, and a Specification asserts that the rule is named policy. It fits only when the experts have a phrase for the rule and own it. If the experts never pronounced it, the Specification claims a policy nobody decided. That is the gap — the rule is unwritten, not “merely plumbing.”

TipThe faithfulness test

Do the experts have a phrase for this rule, and would they recognise their policy when they read the specification’s name?

  • If yes → applicable. The Specification is the code catching up to the knowledge; the rule is the domain’s own.
  • If no → inapplicable. Keep it as a plain predicate; the wrapper fabricates policy.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Bounded Context

Evans: “A description of a boundary (typically a subsystem, or the work of a particular team) within which a particular model is defined and applicable.” [1]

A Bounded Context is a boundary inside which one model and one set of terms apply.

The domain knowledge gap it signals

The fact that the same word means different things to different parts of the business is domain knowledge. If your organisation crystallises that “a ‘product’ to sales is a SKU with margin; to logistics it is a box with weight; to support it is a warranty scope,” then one shared model is a falsehood, and the boundary between the meanings is the domain’s own division. A Bounded Context is that division made executable: inside this boundary, each term has exactly one meaning.

ImportantWhen the domain mandates it (cohesion-increasing)

The business genuinely divides — distinct vocabularies, distinct rules, distinct teams — and the split is discoverable in how experts talk past each other. A Bounded Context closes the gap: it prevents a single “unified” model from being stretched across conflicting meanings, which forces every term into nullable, optional, “sometimes it means” contortions. The context border is the domain’s own “here, this word means this” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

The “contexts” are team territories or microservice quotas, drawn where the vocabulary is actually shared. Splitting one coherent model into several contexts adds translation layers between meanings that never diverged, and every context boundary the domain doesn’t recognise becomes a mapping tax. The boundary signals “the words differ here” when only the org chart does.

TipThe faithfulness test

Do the experts themselves divide — does “order” or “customer” actually mean different things across these groups, with different rules attached?

  • If yes → applicable. The Bounded Context is the code catching up to the knowledge; the border is the domain’s own.
  • If no → inapplicable. Keep one model; the extra contexts invent translation the vocabulary doesn’t need.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Ubiquitous Language

Evans: “A language structured around the domain model and used by all team members within a bounded context to connect all the activities of the team with the software.” [1]

A Ubiquitous Language is the shared vocabulary that both domain experts and code use.

The domain knowledge gap it signals

The fact that a term has an agreed meaning between experts and code is itself the completeness-check. Ubiquitous Language is not a structure but a claim: “the words in the code are the words the business uses, with the meanings the business gives them.” Wherever the claim breaks — a “record” that the business calls a “booking,” a “status” no expert recognises — you have found the gap directly.

ImportantWhen the domain mandates it (cohesion-increasing)

The terms are settled: experts use them in conversation, the code uses the same words, and a glossary would have one line per term. The language then closes the gap continuously: renaming a class is renegotiating meaning with the business, and a new expert can read the domain model as their own vocabulary. Each named term carries its rules with it.

WarningWhen it exposes the gap (cohesion-reducing)

There is no clean “doesn’t fit” here; the failure mode is pretence. Code that borrows domain words without domain meaning — an “Account” that is really a database row, a “Policy” that is a config entry — manufactures false recognition: experts nod at words that do not behave as they say. That is worse than honest technical naming, because it hides the missing knowledge behind familiar dress.

TipThe faithfulness test

Could a domain expert read the class and method names aloud in a meeting — and would every statement made with them be true in their terms?

  • If yes → the language is real; it is the completeness-check running all the time.
  • If no → you’ve found a knowledge gap by name: the term’s real meaning is not settled, or the code’s meaning is not the business’s.
  • If you can’t answer → unclear. You haven’t found the naming wrong; you’ve found knowledge that isn’t settled yet.

Case study: Anti-Corruption Layer

Evans: “Create an isolating layer to provide clients with functionality in terms of their own domain model.” [1]

An Anti-Corruption Layer is a translation boundary between your model and a foreign one.

The domain knowledge gap it signals

The fact that the foreign system’s model is not our model — and must not become it — is domain knowledge. If your domain crystallises that “the legacy system’s ‘customer’ is a billing record, not our customer,” then the translation between the two models is a domain decision. An Anti-Corruption Layer is that decision made executable: one place where foreign concepts are converted into ours, and ours never leak out raw.

ImportantWhen the domain mandates it (cohesion-increasing)

The external model genuinely conflicts with yours — different identities, different meanings, a different way of slicing the world — and you cannot change the source. An ACL closes the gap: it prevents legacy concepts from leaking into the new model, where each foreign quirk would become a permanent local rule. The layer is the domain’s own “we translate at the border; inside, our words only” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

The “ACL” wraps a model you actually share — a well-designed API whose vocabulary matches yours — adding a translation layer that converts identical concepts into slightly renamed copies. Then the layer hides agreement, doubles maintenance, and signals “their model is foreign” when it is simply upstream. When the real problem is that your model was never built, an ACL around the foreign model doesn’t protect your model; it replaces it.

TipThe faithfulness test

Do the two models genuinely disagree — same word, different meaning, different identity — or do they differ only in naming and technology?

  • If yes → applicable. The ACL is the code catching up to the knowledge; the border is the domain’s own.
  • If no → inapplicable. Use the shared model directly or a thin adapter; a full ACL manufactures foreignness.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Anemic Domain Model (anti-pattern)

Fowler: “The fundamental horror of this anti-pattern is that it is so contrary to the basic idea of object-oriented design — to combine data and process together.” [3]

An Anemic Domain Model is a model of data classes that hold no behavior of their own.

The domain knowledge gap it signals

A model of data classes with no behaviour claims, implicitly, that the domain has facts but no rules — that orders merely have totals but nothing enforces validity. That claim is almost never true. The anemic model is therefore a standing question: where did the rules go? The answer is usually “into services no expert named,” and that displacement is the knowledge gap made visible.

ImportantWhen the domain justifies it (rare, but real)

Some boundaries are genuinely data-only because the knowledge genuinely lives elsewhere: DTOs crossing a process boundary, persisted projections in CQRS read sides, integration messages. There the domain itself says “this is an envelope, not a model” — and dressing these up with fake behaviour would be the misplaced structure, not the anemia.

WarningWhen it’s a knowledge gap

The “entities” are the domain model — experts speak of orders, policies, claims — yet every rule about them lives in XxxManager or XxxHelper services. Each such service is an unnamed domain concept: the experts’ verbs exist, but no one found their owner. The anemia signals “the rules had no discoverable home,” which means the model-building stopped before the knowledge was placed. Adding getters does not fix it; finding who owns each verb does.

TipThe faithfulness test

For each behaviour sitting in a service: would an expert name the thing that performs it — “the order validates itself at submission”? Or is the performer genuinely a process, not an object?

  • If a thing performs it → the behaviour has a home; move it there.
  • If it’s genuinely a process → keep the service, but name it in the domain’s words.
  • If you can’t answer → unclear. You haven’t found a style problem; you’ve found knowledge with no assigned owner.

Case study: Module (tactical packaging)

Evans: “Choose modules that tell the story of the system and contain a cohesive set of concepts.” [1]

A Module is a named package that groups related domain concepts.

The domain knowledge gap it signals

The fact that these concepts belong together in the experts’ minds is domain knowledge. If your domain model crystallises that “leasing, maintenance, and resale are different parts of the fleet business — each with its own vocabulary,” then the module divisions are the domain’s own chapters. A Module is that division made executable: a named, cohesive packaging of a piece of the domain, whose name an expert would recognise.

ImportantWhen the domain mandates it (cohesion-increasing)

The module corresponds to a piece of the business that experts name — “Underwriting,” “Fulfilment,” “Billing” — with a vocabulary used only inside it. A Module closes the gap: it prevents concepts from different vocabulary areas being interleaved until nothing can be discussed in one place, and it makes the domain’s own sections visible in the code layout. High cohesion inside, low coupling across — because the business itself works that way.

WarningWhen the domain doesn’t (cohesion-reducing)

There is no knowledge-free half of this split. Grouping code into models/, services/, utils/, or helpers/ is still a decision, but a Module asserts that the grouping matches the experts’ own sections. It fits only when the domain names those sections. If the domain’s groupings were never consulted, every business concept is smeared across the drawers and no module can be shown to an expert. That is the gap — the domain’s own structure is unwritten, not “merely technical.”

TipThe faithfulness test

Could you read the module names to a domain expert and hear “yes, those are the parts of our business” — and would each module’s terms be used by exactly that part?

  • If yes → applicable. The Module is the code catching up to the knowledge; the packaging is the domain’s own.
  • If no → inapplicable. Repackage around the domain’s own sections; the drawers hide the knowledge’s structure.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Policy / Process (tactical)

A Policy is a rule object that expresses “when this happens, do that.”

The domain knowledge gap it signals

The fact that the business responds to occurrences with prescribed actions — “when a claim is filed, assign an adjuster within two days” — is domain knowledge. A Policy is that fact made executable: a rule in the experts’ own if-then shape, attached to the occurrence it responds to. It is the domain’s own “when X, then Y” made first-class instead of buried in a sequence of ifs.

ImportantWhen the domain mandates it (cohesion-increasing)

The experts state the rule as a standing instruction, and it may change without the surrounding process changing. A Policy closes the gap: it prevents the response from being smeared through whatever code happens to trigger the occurrence, and it gives the rule one name, one home, one audit trail. The trigger is the domain’s own event; the response is the domain’s own obligation.

WarningWhen the domain doesn’t (cohesion-reducing)

There is no knowledge-free half of this split. A reaction such as “retry three times” or “log a metric” is still a decision, and a Policy asserts that the business prescribed it. It fits only when an expert would state the rule and expect to be consulted before it changed. If the library set it and no expert decided, the Policy claims authority nobody granted. That is the gap — the rule is unwritten, not “merely technical.” The structure also obscures real policies: when everything is a policy, nothing is.

TipThe faithfulness test

Would an expert state this rule in a meeting — “when this happens, we do that” — and would they expect to be consulted before it changed?

  • If yes → applicable. The Policy is the code catching up to the knowledge; the if-then is the domain’s own.
  • If no → inapplicable. Keep it as a plain default; dressing it as policy invents authority nobody granted.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Immutable Value Objects

Evans: “Value objects should be immutable: rather than modifying one, you create a new one in its place.” [1]

A value object is an immutable type identified by its values; you replace it instead of changing it.

The overlap, and the one thing this post adds

#85 established the construct: a value object makes executable the domain rule “a €10 note is any €10 note.” Immutability is the other half of that same claim, and #85 named it only in passing. The OOP angle is narrower: immutability is a language-level commitment that the domain replaces this fact rather than revises it. An address correction is a new address, not a mutated one. If the business speaks that way, immutability is the code catching up. Where it goes wrong is on both sides. Immutability adopted without a domain warrant — chosen for thread safety, cacheability, or safe sharing on things the domain revises — forces contortions: builders and copy-methods emulating updates the domain actually performs. The choice is still a decision, but the domain never named a replacement rule, and that is the gap — not that immutability is “merely technical.” The inverse is a mutable value-shaped object, whose shared aliasing silently couples changes the domain never coupled.

TipThe narrower test this post adds

For a value-shaped class: when this fact “changes” in the business language, does the old one stop being true, or does the same thing acquire a new state?

  • If the old one stops being true (the domain replaces it) → immutable. The Value Object is the code catching up to the knowledge.
  • If the same thing acquires a new state (the domain revises it) → not a value object at all. The identity question is #85/#86, not the language mechanism.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete domain knowledge.
