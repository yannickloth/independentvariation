Enterprise Integration Patterns as Knowledge-Gap Indicators

A list of short posts that read each pattern as a completeness check on domain knowledge.

Most design patterns and principles can be used as a completeness-check on domain knowledge.

Pick a post on the left. It opens on the right.

Case study: Content-Based Router Pattern

EIP Intent: “How do we handle a situation where the implementation of a single logical function (e.g., inventory check) is spread across multiple physical systems?” [1]

The domain knowledge gap it signals

The fact that messages carry content that determines their destination is domain knowledge. If your domain model crystallizes that “an order from region R goes to warehouse W, a payment above threshold T goes to fraud-check,” then Content-Based Router embodies that knowledge. The routing table is the domain’s own dispatch logic; each destination is a domain actor that receives specific kinds of work.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that which component receives a message depends on the message’s content — and the classification rule is a domain rule, not a technical convenience. When a claims-processing domain says “auto claims under $5,000 go to fast-track; auto claims over $5,000 go to full review; all property claims go to property adjustment,” the router encodes domain knowledge that would otherwise be buried in each receiving component’s guard clause. Without the router, every receiver must independently re-implement content-based filtering, scattering the routing rule across the system and creating accidental coupling — each receiver must know about every message type it could receive.

WarningWhen it’s inapplicable (cohesion-reducing)

The “routing” is not a domain rule — it’s a technical partition masquerading as a content decision. “Based on the message XML namespace, route to parser version 1 or version 2.” Or “route to the service instance with the lowest current load.” The domain doesn’t recognize XML namespaces, parser versions, or load distribution as input variables — it sees “process this order.” Content-Based Router here becomes a technology-level dispatcher that hides the real domain concern (what happens to the order?) behind a mechanical classification the domain expert would never produce. When the routing criteria are implementation details, every domain change that affects content may invisibly re-route without the domain expert knowing.

TipThe faithfulness test

Can a domain expert produce the routing table from their own knowledge, without asking an engineer what’s “technically easier”?

  • If yes → applicable. Content-Based Router is the code catching up.
  • If no → inapplicable. It’s a technical switchyard disguised as domain routing.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Publish-Subscribe Channel Pattern

EIP Intent: “How can the sender broadcast an event to all interested receivers?” [1]

The domain knowledge gap it signals

The fact that multiple parties independently care about the same occurrence is domain knowledge. If your domain model already crystallizes that “when an order is fulfilled, the warehouse needs to restock, the customer needs a notification, the loyalty program needs to update points, and the finance system needs to recognize revenue,” then Publish-Subscribe is just embodying that knowledge. The topic is the domain event; the subscribers are domain actors who, by the rules of the domain, must react when that event occurs.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that one occurrence triggers multiple independent responses — and the publisher has no domain reason to know about the subscribers. A publisher should not know who consumes its events; the event itself is the coupling point, and the downstream reactions are separate domain responsibilities. Publish-Subscribe closes the gap: it prevents the publisher from growing a list of explicit callbacks for each new consumer, which would couple the publisher to downstream concerns it has no domain interest in. Each subscriber declares its interest in the event independently; the publisher emits once and the domain network reacts.

WarningWhen it’s inapplicable (cohesion-reducing)

The “subscribers” are not domain-independent — they are implementation partitions of a single domain concern. Splitting a single logical operation into multiple subscribers bound by a publish-subscribe channel creates an invisible coupling: the subscribers depend on each other’s execution to complete the operation, but neither the channel nor the subscribers encode this dependency. The domain says “one procedure does X, then Y, then Z” — but Publish-Subscribe scatters X, Y, Z into independent endpoints whose ordering is implicit. A domain expert would say “no, X and Y and Z are the same thing.”

TipThe faithfulness test

Can you name the event and every subscriber using only domain vocabulary, with no implementation words?

  • If yes → applicable. Publish-Subscribe is the code catching up to the knowledge.
  • If no → inapplicable. You’re broadcasting for technical convenience, not because the domain broadcasts.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Dead Letter Channel Pattern

EIP Intent: “What will the messaging system do with a message it cannot deliver?” [1]

The domain knowledge gap it signals

The fact that some messages cannot be delivered and that the domain has rules for what happens then is domain knowledge. If your domain model already crystallizes that “an insurance claim missing a policy number is undeliverable and goes to manual triage; a payment with a mismatched currency code goes to the reconciliation desk; and anything else unrouteable gets queued for the operations team,” then Dead Letter Channel is just embodying that knowledge. The dead-letter queue is the domain’s own undeliverable-work queue; the dead-letter consumer is the domain’s own exception-handling actor.

ImportantWhen it’s applicable (cohesion-increasing)

The domain recognizes that messages can legitimately fail to reach a destination, and the domain itself distinguishes categories of failure with different remediation paths. Dead Letter Channel closes the gap: it prevents each sender from embedding fallback logic for the failure it caused, which would scatter undeliverable-work handling across every component and create accidental coupling — each sender would need to know about manual triage, reconciliation desks, and operations queues. The dead-letter queue consolidates exception routing into one place, reflecting the domain’s own classification of failure modes.

WarningWhen it’s inapplicable (cohesion-reducing)

The dead-letter channel is a catch-all for anything the developer didn’t handle — “put failed messages here and we’ll figure it out later.” The domain has no classification of failure modes, no notion of undeliverable work as a distinct domain state, and no remediation process. The dead-letter queue becomes silent data loss: messages accumulate in a queue no one monitors, and the domain event they represented is simply dropped. A domain expert would say “what do you mean the order disappeared — did it ship or not?”

TipThe faithfulness test

Does the domain have a named process, role, or procedure for handling work that cannot reach its destination?

  • If yes → applicable. Dead Letter Channel is the code catching up to the knowledge.
  • If no → inapplicable. It’s a black hole with a tidy name.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Message Filter Pattern

EIP Intent: “How can a component avoid receiving uninteresting messages?” [1]

The domain knowledge gap it signals

The fact that a component should only receive a subset of the messages flowing through the system is domain knowledge. If your domain model crystallizes that “the premium-customer system cares only about orders from customers at loyalty tier 3 or above; the standard-order pipeline should never see test-mode orders,” then Message Filter embodies that knowledge. The filter predicate is the domain’s own membership condition.

ImportantWhen it’s applicable (cohesion-increasing)

The domain assigns different message subsets to different domain actors — and the subset condition is a domain rule, not a performance optimization. Message Filter closes the gap: prevents each receiver from re-implementing the filter in a guard clause at the entry point, which would couple the receiver to message types it should have no knowledge of. A receiver that filters out orders below $1,000 at its own entry point must still know that such orders exist — spreading knowledge of the full message universe into every receiver. The filter externalizes the membership rule so each receiver sees only its domain-relevant messages.

WarningWhen it’s inapplicable (cohesion-reducing)

The filter is adopted without a constraint that selects which messages to drop — “drop messages when queue depth exceeds 500” or “route every other message when CPU is > 80%.” Queue depth and CPU load tell you that you need to shed load — not which messages to shed. The filter predicate (drop oldest? drop lowest-priority? drop at random?) is undetermined by the constraint. When selection is arbitrary, the filter couples message survival to infrastructure state without a defensible rule.

TipThe faithfulness test

Can you state the filter predicate as a domain rule — a sentence that starts with “The system is only interested in messages where…” and mentions no implementation concepts?

  • If yes → applicable. Message Filter is the code catching up — a constraint external to the code (membership condition, regulatory boundary, domain scope rule) selects which messages pass.
  • If no → inapplicable. You’re dropping messages without a constraint that identifies which ones.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Recipient List Pattern

EIP Intent: “How do we route a message to a list of dynamically specified recipients?” [1]

The domain knowledge gap it signals

The fact that a message has a domain-determined list of recipients — where the list itself is a domain artifact, not a configuration file — is domain knowledge. If your domain model already crystallizes that “a customs declaration must go to the importing country’s customs authority, the exporting country’s customs authority, the carrier, and the importer of record; a trade confirmation goes to both counterparties’ settlement desks,” then Recipient List is just embodying that knowledge. The list of recipients is the domain’s own distribution rule.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that a single message be delivered to a specific, domain-determined set of recipients — and those recipients are each domain actors, not technical mirroring targets. Recipient List closes the gap: it isolates the distribution logic so the sender doesn’t embed a hardcoded list of downstream systems, which would couple the sender to the topology of the integration landscape. Without it, adding a new regulatory recipient means modifying the sender’s code — making the sender change with the regulatory environment even though its domain logic (produce the trade confirmation) hasn’t changed.

WarningWhen it’s inapplicable (cohesion-reducing)

The recipient list is an availability tactic — send to primary and backup instances, or fan-out to multiple replicas. The domain doesn’t recognize “instance 1” and “instance 2” as distinct recipients; it recognizes one recipient (the order-processing system) — the fact that it runs on two machines is an implementation detail. Recipient List here masks infrastructure redundancy as domain distribution, creating coupling between the sender and deployment topology. A domain expert would say “just send it to order-processing — how many machines that runs on is not my concern.”

TipThe faithfulness test

Would a domain expert, given only knowledge of the business process, produce the same list of recipients without knowing how the system is deployed?

  • If yes → applicable. Recipient List is the code catching up to the knowledge.
  • If no → inapplicable. It’s deployment topology leaking into domain logic.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Splitter Pattern

EIP Intent: “How can we process a message if it contains multiple elements, each of which may have to be processed in a different way?” [1]

The domain knowledge gap it signals

The fact that a composite message is domain-recognized as containing independently processable parts, and that the decomposition rule is a domain rule, is domain knowledge. If your domain model already crystallizes that “an insurance claim package contains a claim form, a police report, medical records, and repair estimates — each processed by a different team,” then Splitter is just embodying that knowledge. The decomposition rule is the domain’s own partitioning; each sub-message is a domain-recognized unit of work.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that a composite message be decomposed into independent parts that travel different paths — and the decomposition corresponds to a domain-recognized partition. Splitter closes the gap: it prevents each downstream processor from re-extracting its own piece, which would couple each processor to the composite message format and scatter extraction logic across the system. Without it, the medical-records processor must know how to locate its section within the full claim package — structure knowledge that belongs in one place (the splitter), not in every downstream handler.

WarningWhen it’s inapplicable (cohesion-reducing)

The composite message is a technical envelope — a batch of messages bundled for transport efficiency — and the domain sees the individual messages as the real units of work that were always separate. Splitter here just unwraps a transport artifact. Worse: if the original messages were produced independently at different times, splitting them doesn’t re-establish their original arrival order or context, and a later aggregator may produce results that arrived in a different sequence than they were produced.

TipThe faithfulness test

Does the domain recognize the composite as a single thing that contains multiple independently meaningful things — like an “order” containing “line items” — rather than as a bunch of messages in a box?

  • If yes → applicable. Splitter is the code catching up to the knowledge.
  • If no → inapplicable. It’s unwrapping a transport artifact and calling it domain decomposition.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Aggregator Pattern

EIP Intent: “How do we combine the results of individual, but related messages so that they can be processed as a whole?” [1]

The domain knowledge gap it signals

The fact that multiple independent messages together form a domain-recognized whole — and that the domain specifies when the whole is complete — is domain knowledge. If your domain model already crystallizes that “a trade is complete only when we have both the execution report from the exchange and the allocation from the trader; a purchase order is fully processed when all its line items have been fulfilled from their respective warehouses,” then Aggregator is just embodying that knowledge. The completion condition is the domain’s own completeness rule; the aggregated result is the domain’s own composite state.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that a result is the composition of multiple independent sub-results — and the domain itself defines when “enough sub-results have arrived” (by count, by timeout, by content, by domain predicate). Aggregator closes the gap: it prevents each downstream consumer from tracking partial state and re-implementing the completion check, which would scatter the aggregation logic across every consumer. Without it, the trade-settlement system must know when both the execution report and the allocation have arrived — knowledge that belongs at the aggregation point, not at every settlement subsystem.

WarningWhen it’s inapplicable (cohesion-reducing)

The “aggregation” is a technical re-assembly of parts that were split for transport — the splitter split by count, the aggregator reassembles by count, with no domain knowledge involved. The completion condition is “got all three pieces” rather than a domain predicate like “we have both the execution report and the allocation.” Aggregator here becomes a stateless reassembly mechanism that adds latency and a stateful waiting point for no domain reason.

TipThe faithfulness test

Does the domain define the completeness condition — and would a domain expert state it in domain terms (“we need both the execution report and the allocation”) rather than as a count (“all three parts arrived”)?

  • If yes → applicable. Aggregator is the code catching up to the knowledge.
  • If no → inapplicable. It’s re-gluing what was unnecessarily split.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Scatter-Gather Pattern

EIP Intent: “How do you maintain the overall message flow when a message needs to be sent to multiple recipients, each of which may send a reply?” [1]

The domain knowledge gap it signals

The fact that a single request requires answers from multiple domain sources, and that the best answer is a domain-defined composition of those answers, is domain knowledge. If your domain model already crystallizes that “to price a shipment, you need quotes from carrier A, carrier B, and carrier C, then you select the lowest; to approve a loan, you need a credit-score check, an income-verification check, and a fraud check — all must pass,” then Scatter-Gather is just embodying that knowledge. The recipients are the domain’s own information sources; the aggregation rule (lowest, all-pass, majority) is the domain’s own decision procedure.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates a fan-out to multiple domain actors whose results must be combined by a domain rule — and the rule itself (not just the data) is domain knowledge. Scatter-Gather closes the gap: it prevents the requester from invoking each source sequentially, collecting results, and combining them inline — which would couple the requester to the list of sources, their invocation patterns, and the combination rule. Without it, adding a fourth carrier means modifying the pricing module’s internal loop.

WarningWhen it’s inapplicable (cohesion-reducing)

The “scatter” is a technical fan-out for performance — send the same query to all three replicas and take the fastest response. The domain doesn’t recognize replica voting; it recognizes one source (the product catalog), and the fact that it has copies is irrelevant. Scatter-Gather here masks a latency-hedge as a domain composition, introducing a gather step whose “aggregation rule” is “first one back” — a rule with no domain meaning. A domain expert would say “you’re asking the same question to three copies of the same book and taking whichever page turns first.”

TipThe faithfulness test

Would a domain expert, asked “how do you decide the answer?” produce the same aggregation rule that the Scatter-Gather uses — without mentioning system architecture?

  • If yes → applicable. Scatter-Gather is the code catching up to the knowledge.
  • If no → inapplicable. It’s a race condition dressed as a decision procedure.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Routing Slip Pattern

EIP Intent: “How do we route a message consecutively through a series of processing steps when the sequence of steps is not known at design-time and may vary for each message?” [1]

The domain knowledge gap it signals

The fact that a message must visit a sequence of processors, and that the sequence itself is a domain process that changes based on domain rules, is domain knowledge. If your domain model already crystallizes that “a purchase order above $10,000 goes: budget check → compliance review → director approval → procurement; a purchase order below $10,000 goes: compliance review → procurement — and for international orders, add export-control review after compliance,” then Routing Slip is just embodying that knowledge. The slip is the domain’s own process definition; each step is a domain actor in a domain sequence.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates a variable multi-step process whose steps are domain operations — and the step sequence depends on domain conditions (order value, jurisdiction, product category). Routing Slip closes the gap: it prevents the process logic from being embedded in a central process manager that must know every step for every variation, which would couple all process variants together. Without it, the process manager becomes a god object that grows with every regulatory change.

WarningWhen it’s inapplicable (cohesion-reducing)

The routing slip encodes a technical pipeline, not a domain process: “validate the message, transform the format, enrich with reference data, persist, notify.” The domain doesn’t recognize these as distinct business steps — it sees “process the order.” Routing Slip here wraps a technical ETL pipeline in the vocabulary of a business process, adding domain-coded step names (compliance, approval) to steps that are really validation, transformation, and persistence.

TipThe faithfulness test

Can a domain expert, given a specific scenario (e.g., “an international order above $10,000”), list the steps in the correct sequence without consulting anyone technical?

  • If yes → applicable. Routing Slip is the code catching up to the knowledge.
  • If no → inapplicable. The “process” is a technical pipeline with domain window-dressing.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Process Manager Pattern

EIP Intent: “How do we route a message through multiple processing steps when the required steps may not be known at design-time and may not be sequential?” [1]

The domain knowledge gap it signals

The fact that a long-running multi-step process has a domain-defined state machine — where states, transitions, and compensating actions are all domain concepts — is domain knowledge. If your domain model crystallizes that “a trade lifecycle is: initiated → allocated → affirmed → confirmed → settled; an insurance claim lifecycle is: filed → assessed → approved/rejected → paid; and each state transition has domain preconditions and domain rollback procedures,” then Process Manager embodies that knowledge. The state machine is the domain’s own lifecycle; each transition is a domain event; compensating actions are the domain’s own reversal procedures.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates a long-running process whose intermediate states are domain-recognized states — and the domain itself specifies what can happen from each state and what undoes a failed transition. Process Manager closes the gap: prevents the process logic from being scattered across the message handlers that implement each step, where each handler must independently decide whether the step is valid given the current state and what to do if it fails.

WarningWhen it’s inapplicable (cohesion-reducing)

The “process” is a saga — a technical transaction-coordination mechanism that chains service calls with compensating actions to simulate distributed atomicity. The domain doesn’t recognize compensating actions like “refund the payment” as a business process; it recognizes “the payment was refunded” as an independent event. Process Manager here becomes a distributed-transaction coordinator that hides failure-handling code behind state-machine syntax. A domain expert would say “the payment shouldn’t have been taken in the first place if the rest of the process couldn’t complete — fix the order of operations.”

TipThe faithfulness test

Does the domain have a name for each intermediate state, and can a domain expert draw the state machine from memory — states, transitions, and what goes wrong at each transition — using only business vocabulary?

  • If yes → applicable. Process Manager is the code catching up.
  • If no → inapplicable. It’s a distributed-transaction coordinator wearing a state-machine costume.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Message Broker Pattern

EIP Intent: “How can you decouple the destination of a message from the sender and maintain central control over the flow of messages?” [1]

The domain knowledge gap it signals

The fact that the systems in a domain are decoupled — that system A should not know about system B, that the topology is a domain property not a deployment detail — is domain knowledge. If your domain model crystallizes that “the order-entry system produces orders; the warehouse system consumes orders; the revenue-recognition system consumes fulfilled orders — and none of them should know about each other because they’re separate bounded contexts with different ownership and release cadences,” then Message Broker embodies that knowledge. The broker is the domain’s decentralized hub; the channels are the domain’s communication paths.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that components communicate without direct knowledge of each other — because they evolve independently, are owned by different teams, or sit in different bounded contexts. Message Broker closes the gap: prevents each producer from maintaining a registry of consumers and each consumer from knowing the producer’s endpoint, which would couple the entire ecosystem together. Without it, changing the warehouse system’s endpoint means modifying the order-entry system — coupling two systems that the domain says should be independent.

WarningWhen it’s inapplicable (cohesion-reducing)

The systems are in the same bounded context and the “decoupling” is architectural dogma — “we always put a broker between things” — when no external constraint mandates it. A broker between services sharing the same team, repository, domain model, and release cadence turns a function call into a message round-trip with serialization and new failure modes. The knowledge gap is adopting a decoupling structure without a constraint that demands decoupling.

TipThe faithfulness test

Does the domain recognize the two sides of the broker as genuinely separate things — different bounded contexts, different owners, different evolution cadences — or are they one logical system that you split across two services?

  • If yes → applicable. Message Broker is the code catching up.
  • If no → inapplicable. It’s adding a network boundary where the domain already had a module boundary.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Content Enricher Pattern

EIP Intent: “How do we communicate with another system if the message originator does not have all the required data items available?” [1]

The domain knowledge gap it signals

The fact that a message arrives with incomplete information and that the missing information has a domain-designated source is domain knowledge. If your domain model already crystallizes that “an order message carries a customer ID, but the warehouse needs the shipping address — which is owned by the customer profile service,” then Content Enricher is just embodying that knowledge. The missing field is domain information that belongs to a different domain authority; the enricher is the domain’s own information-completion step.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that certain information belongs to a specific domain authority — and the downstream consumer legitimately needs that information but shouldn’t own the authority to produce it. Content Enricher closes the gap: it prevents the consumer from calling the authority directly, which would couple the consumer to the authority’s interface and create a runtime dependency that the domain didn’t intend. Without it, the warehouse system must know how to call the customer profile service — coupling the warehouse to customer-profile concerns, when its domain job is “ship to this address,” not “look up addresses.”

WarningWhen it’s inapplicable (cohesion-reducing)

The “missing” information is not missing from a domain perspective — the downstream consumer doesn’t need it, but the developer thinks it’s “nice to have” or is preemptively enriching for a future use case. Or the information belongs to the producer and should have been in the original message — the producer was lazy and Content Enricher is doing the producer’s job post hoc. A domain expert would say “if orders always ship to the customer’s default address, why doesn’t the order-entry system put the address on the order to begin with?”

TipThe faithfulness test

Does the missing piece of information belong to a different domain authority than the producer — and does the consumer legitimately need it to do its job?

  • If yes → applicable. Content Enricher is the code catching up to the knowledge.
  • If no → inapplicable. It’s either gold-plating or compensating for a producer that skimped on its domain responsibility.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Content Filter Pattern

EIP Intent: “How do you simplify dealing with a large message, when you are interested only in a few data items?” [1]

The domain knowledge gap it signals

The fact that a downstream component should receive only a subset of the fields in a message — and that the subset is defined by the component’s domain responsibility, not by technical parsimony — is domain knowledge.
