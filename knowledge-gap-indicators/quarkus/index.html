Quarkus Build-Time Decisions

Build-time versus runtime decisions in Quarkus.

The framework decides at build time what the code left open. Each post names what was baked in, and which fact set it.

If you can, the image is knowledge embodied — the build catching up to what the deployment decided.

Case study: Build-time augmentation

The key was changed in production, the service restarted, and the new value took effect nowhere.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: Quarkus moves what a framework used to do at boot — bean discovery, bytecode transformation, config resolution — into a build step called augmentation. The shipped artifact is already resolved, so startup is tens of milliseconds and the footprint stays small. The trade is exact: a key fixed at build time cannot change after the build — the binary ignores any value the deployment sends. quarkus.http.root-path, the datasource kind, ORM schema generation — read at build time, fixed in the binary.

The Quarkus knowledge gap it signals

The team must know which config is a fact about the deployed environment and which about the build. One artifact runs everywhere, so any value that differs between environments belongs to the run, not the build: port, credentials, URLs. A key miscategorized the other way loses its dynamism silently — the binary keeps the baked value and logs a warning nobody reads.

The gap question: which keys are build-time, and would we have decided the same knowing they can never change without a rebuild?

ImportantWhen the domain mandates it

A scale-to-zero service behind a queue: the platform bills cold start on every wake-up, and measured startup decides if the design holds.

WarningWhen it’s a guess dressed as engineering

A build-time key edited in the production config map, deployed, restarted. The service comes up green. The value is ignored, so the change did nothing — and the team learns this days later, debugging what the change was meant to fix. The quieter reverse trap: making everything runtime-overridable for “flexibility,” returning the boot cost to every replica for dynamism nobody used.

TipThe faithfulness test

Which config keys are build-time — listed — and who knows they cannot change without a rebuild?

  • If yes → augmentation carries the workload’s facts. Check the list is in the readme, not just the config reference.
  • If no → the artifact holds decisions nobody tracked. Diff the build-time keys against what ops believes is runtime.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. Measure startup, then count deploys that changed a build-time key.

Case study: Dev Services

Dev Services started a database for you. It is the image your Quarkus platform version pins, not the one production runs.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: When no datasource URL is configured in dev or test mode, Quarkus starts the container itself — Postgres, Kafka, Redis, Keycloak — and wires the connection. A new developer clones and runs, with no setup. The image is pinned by the Quarkus platform version you build with, not by your production manifest. The trade: parity nobody had to configure, against an environment nobody configured.

The Quarkus knowledge gap it signals

The container is a stand-in for a versioned external service, and it may differ where dev and production were never compared: image version, extensions, collation, timezone, TLS, roles, and data already present. Each difference is a fact about production the developer never met. Tests pass against the substitute and say nothing about the original.

The gap question: which versions does dev actually run, and how were they verified against production?

ImportantWhen the domain mandates it

A team whose production images are pinned and whose CI job compares each Dev Services image tag to the deployed tag. Parity is then a checked fact, and the zero-config start costs nothing but the check.

WarningWhen it’s a guess dressed as engineering

Dev Services pulls the platform default — a newer Postgres than production runs — and the schema, the JSON functions, and the query planner all behave differently. Everything works locally. The migration passes in CI. Production rejects the syntax, or accepts it and returns a different order. The opposite failure is quieter: tests that pass only because something was listening on the port, never asserting they reached the intended store.

TipThe faithfulness test

Which versions does dev actually run — pinned — and are they verified against production, how?

  • If yes → the stand-in is constrained by the same facts. Check the comparison runs on every build, not once at setup.
  • If no → dev parity is a coincidence that holds until a version differs. Pin the images, then align them to production.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. List every container dev starts and the tag it resolves to.

Case study: Native image builds

The native build took 14 minutes, and the hot service it produced lost a quarter of its peak.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: GraalVM compiles the application ahead of time under a closed-world assumption: reachable code is fixed at build time, reflection needs explicit registration. The trade: minutes of CI per build, harder debugging, and slower peak throughput on long-running CPU-bound work, against startup in the tens of milliseconds and resident memory a fraction of the JVM’s.

The Quarkus knowledge gap it signals

Native pays back only where startup or footprint is billed. The team must know which of its services is charged for cold start, which is memory-constrained in density, and which runs hot and long enough to prefer the JIT. Those are three different services, and the build profile is a claim about all of them.

The gap question: which services pay their native build cost back in startup and footprint, measured?

ImportantWhen the domain mandates it

The services that scale to zero, where the platform bills the wake-up and the measured cold start and RSS decide whether the trade pays back. The native profile applies there and where footprint is billed. Everything else stays in JVM mode, deliberately.

WarningWhen it’s a guess dressed as engineering

Native for every service, because “Quarkus is fast.” CI accumulates hours per day, reflection failures surface late in the cycle, and the profile attached to the pipeline stops being readable. A throughput regression on the CPU-bound service ships with the build; an operator finds it months later, not a benchmark. The build cost was real; the payoff was never measured, only assumed.

TipThe faithfulness test

Which services pay their native build cost back — measured?

  • If yes → the profile is a fact about each service. Check the numbers are recorded per service, not per organization.
  • If no → the build is a habit. Measure cold start and RSS in both modes on the services that scale to zero.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. Time the native build, then measure what it bought.

Case study: JVM-mode footprint tuning

Quarkus means small, so someone set a 256 MB limit. The first traffic spike killed the container.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: In JVM mode Quarkus starts fast, but the heap is still the JVM’s: sized from the container limit, a quarter by default, with GC headroom, metaspace, thread stacks, and native buffers living outside it. The trade: defaults calibrated for a modest workload — small heap, quick start, a default collector — against the headroom a real peak load needs, where allocation spikes push the process past its limit.

The Quarkus knowledge gap it signals

Resident memory is heap plus what sits outside it; the peak is the number. The team must know its live set at peak, its allocation rate at peak, and the RSS that follows from both, per replica. Density is computed from RSS; a limit set from a heap estimate or from an idle reading is a guess about a number nobody took.

The gap question: what is the measured RSS at peak load, and is the container limit above it with stated headroom?

ImportantWhen the domain mandates it

A platform that bills density, not idle: RSS measured per replica at peak, the limit set above it with headroom named in the manifest, and density computed from that RSS rather than from the heap. The small footprint is then a fact the platform can plan against.

WarningWhen it’s a guess dressed as engineering

“Quarkus is small” carried into JVM mode with the default heap: a 256 MB limit, a 64 MB heap, and thread stacks and direct buffers outside it. It works in dev, works in the load test at half rate, and dies on the first real spike: RSS crosses the limit while the collector spends the spike collecting. The kill looks like an infrastructure fault, not a sizing decision. Idle RSS measured once, then multiplied into a density plan, sets the same limit.

TipThe faithfulness test

What is the measured RSS at peak load — and is the container limit above it with stated headroom?

  • If yes → the footprint is a measured fact. Check the reading is at peak, not at idle.
  • If no → the limit guards nothing. Measure RSS under the peak profile before setting it.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. Measure RSS at peak, then compare it to the limit.

Case study: The reactive REST layer

One JDBC call in a Uni-returning endpoint, and every other request on that event loop waits behind it.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: quarkus-rest dispatches by return type: a plain return goes to a worker thread, a Uni or Multi return stays on the event loop. A reactive method that blocks holds the loop, and every request assigned to that thread waits for it. @Blocking forces a worker, @NonBlocking forces the loop. The trade: event-loop dispatch — no thread per request, high concurrency on few threads — against blocking endpoints whose stall is paid by requests that never blocked.

The Quarkus knowledge gap it signals

The return type is a claim about the endpoint’s behavior: a reactive return promises no blocking, and dispatch trusts it. The team must know which reactive endpoints still block — JDBC, file I/O, a synchronous client, heavy CPU work — because the type promises and the body decides.

The gap question: which endpoints block — listed — and is that marking deliberate or trusted by default?

ImportantWhen the domain mandates it

Reactive dispatch for the I/O-bound endpoints, returning Uni and Multi so the thread is released while waiting. Plain returns, or @Blocking, on the CPU-heavy and JDBC-backed ones, chosen per endpoint and written down. The dispatch model then matches what each endpoint does.

WarningWhen it’s a guess dressed as engineering

A blocking JDBC call in a Uni-returning endpoint. It passes in dev, passes under a light load test, then degrades nonlinearly: one stall per event-loop thread stalls every request queued behind it, and latency rises without CPU rising. The diagnosis is hard because nothing is saturated. The opposite trap is tidier — @Blocking on everything, which queues every call on a small fixed worker pool and gives up the reason the reactive layer was chosen.

TipThe faithfulness test

Which endpoints block — listed — and is that marking deliberate or trusted by default?

  • If yes → dispatch matches behavior. Check the list is reviewed when an endpoint gains a database call.
  • If no → the default is doing the deciding. Walk the resource methods and mark the blocking ones.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. List every endpoint, then its I/O.

Case study: Config profiles and build-time keys

A manifest sets the database kind to Postgres for production, the pipeline applies it, and the application keeps talking to the H2 database the build chose — no error, no restart, no diff anyone reads.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: Quarkus sorts every configuration key into a phase: runtime keys are read at startup, build-time keys once on the build machine, then written into the artifact. Profiles (%dev, %test, %prod) select values in either phase. A %prod value for a fixed build-time key is baked, and no environment variable moves it; some build-time keys still keep their value overridable at run time.

The Quarkus knowledge gap it signals

A phase is a claim about the workload. The database kind, its JDBC driver, and the extension set are shipped decisions; the URL, the credential reference, and the pool ceiling belong to the deployment. Getting the split wrong is not a framework bug — it is a missing statement about which facts belong to the artifact. The gap question: for each key, is it build-time or runtime, and does anyone on the team know?

ImportantWhen the domain mandates it

Runtime keys change per deploy and arrive from the environment: a pool size the operator tunes, a region flag set per cluster. Build-time keys stay identical everywhere and are documented in the artifact. The split then matches how the platform actually differs, and the build records what it decided.

WarningWhen it’s a guess dressed as engineering

An environment-specific value placed in runtime configuration for a build-time key. It looks right in the manifest, it sits beside keys that do work, and it is ignored: the jar starts, serves traffic, and uses whatever the build baked in. The failure reads as “staging works, production is slow” with identical configuration files.

TipThe faithfulness test

For each key: build-time or runtime — known — and how is that verified at deploy time?

  • If yes → the configuration follows the workload. Check that verification runs where the deploy happens, not in a wiki page.
  • If no → the key is a wish. Look up its phase, then move it to where it is actually read.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. Dump the resolved configuration at startup and compare it against the keys the build fixed.

Case study: SmallRye health and metrics

The readiness probe calls the payment gateway. The gateway slows past the probe timeout, every replica leaves the load balancer at once, and the outage arrives before the dependency does.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: SmallRye Health exposes /q/health/live and /q/health/ready, each aggregating CDI checks run on every probe call; readiness decides Service membership, liveness decides a container restart. The trade is which remedy a red probe triggers, against checks that are green while useless or red while the application is healthy.

The Quarkus knowledge gap it signals

Readiness answers “should traffic reach this instance now” — a fact about dependencies cheap to check per call. Liveness answers “can this process still make progress” — a fact that must never depend on a peer, because the remedy is a restart. A team needs to know which dependencies are fatal, which degrade, and which a restart cannot repair. The gap question: what does readiness check, and which failure is it meant to catch?

ImportantWhen the domain mandates it

Readiness inspects its own pool and each datastore no request survives without, with a timeout shorter than the probe period. Liveness stays minimal: the event loop answers, nothing else. The platform’s remedy then matches the fault.

WarningWhen it’s a guess dressed as engineering

Readiness fanning out to every downstream: gateway, search, the broker. Each was added after an incident and looks responsible. Then one slow peer marks the whole fleet NotReady, traffic has nowhere to go, and fleet availability equals the weakest dependency’s. The companion trap: green checks on /q/health while the app returns 500s on the paths that matter.

TipThe faithfulness test

What does readiness actually check — and would a failed dependency flip it, tested how?

  • If yes → the probes state the fault tolerance. Check that a test breaks the dependency on purpose and watches endpoints drain.
  • If no → the probe measures nothing. Make it check the one dependency a request cannot survive.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. List the dependencies per request, then ask which failures a restart repairs.

Case study: Generated Kubernetes manifests

During an incident someone raises a memory limit to 2Gi on one cluster. The generated manifest still says 512Mi, so every pipeline run proposes to revert the fix — and nobody runs the pipeline.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: The Quarkus Kubernetes extension writes target/kubernetes/kubernetes.yml at build time from the same properties that configure the application: replicas, resource limits, probes. The manifest is an artifact with a version, not a hand-edited document. The trade is deployment knowledge living in the build against the risk of divergence from hand-edited production YAML.

The Quarkus knowledge gap it signals

A limit is a claim about the workload: a memory ceiling the heap fits under, a CPU request matching measured usage, a replica count derived from load. When those live in the build, one writer owns them: the build. A hotfix then costs a rebuild. A team needs to know which facts are environment-specific — an ingress host, a secret — and which belong to the artifact. The gap question: is the deployed manifest the generated one, or has the cluster become the source?

ImportantWhen the domain mandates it

Manifests generated from the same keys that set the application’s configuration, so heap maximum and container limit come from one number and cannot drift apart. The manifest is versioned with the code, and CI diffs it against the live cluster before applying.

WarningWhen it’s a guess dressed as engineering

An ops-edited limit that exists on one cluster only. The generated file and the running system disagree, neither is authoritative: the next apply reverts the fix, the next incident re-applies it. The companion trap: hand-maintained YAML drifting until it describes a service that no longer exists.

TipThe faithfulness test

Is the deployed manifest the generated one — diffed regularly — or did operational drift become the truth?

  • If yes → deployment knowledge lives where it is versioned. Check that the diff runs on a schedule, not when someone remembers.
  • If no → the cluster is the configuration, the build a suggestion. Adopt the live change back into the properties, or write down why it stays local.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. Fetch the live manifest, diff it against the generated one, and name who changed each line.

Case study: Panache (active record and repository)

A resource class calls Order.findAll() and reads order.customer.email. The query layer, the fetch strategy, and the entity boundary now sit in the web tier — and nothing failed to compile.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: Panache offers two shapes. PanacheEntity puts static find, list, and count on the entity and rewrites public field access at build time; PanacheRepository puts the same queries in a repository bean. Both are supported, and the documentation asks a project to pick one. The trade is terse entities and queries against a pattern decision: where a query lives, and who owns it.

The Quarkus knowledge gap it signals

A query states which facts the domain asks for — by identity, by state, by date range — and where it lives marks who may change it. On the entity, the query is part of the model; in a repository, it has an owner and a name. Panache is terse because it assumes that decision is made, and terseness amplifies whatever you assumed. The gap question: can you state which style this service chose, and why?

ImportantWhen the domain mandates it

Panache adopted deliberately per service, the style written down where a reviewer sees it, and every query landing where that style puts it: simple lookups on the entity or in the repository, field access inside the model, so the rewritten access has one owner.

WarningWhen it’s a guess dressed as engineering

findAll and field access drifting into controllers. Each hop is one line and reads well, and after a year the web tier builds predicates, the entity is an anemic data bag, and one query exists four times with three fetch strategies. The framework made every step easy, and easy is not decided.

TipThe faithfulness test

Where does a query live in this service — stated — and can a reviewer find it in one hop?

  • If yes → the pattern is a decision, not a drift. Check that new queries land in the same place and that field access stays inside the model.
  • If no → the web tier is the persistence layer. Move the queries behind one boundary and name the style where they land.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. List the queries the service runs, then map each to the file that owns it.

Case study: Hibernate Reactive

Four event-loop threads are offered 8,000 requests a second. One legacy validator makes a blocking JDBC call on every request, and at most four run at once — the loop count, not the request rate.

Accepting a Quarkus default? Ask “which decision did the framework make — at build time or at run time — and which fact did it bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: Hibernate Reactive pairs the ORM API with reactive SQL clients. Queries return Uni and Multi, and @Transactional scopes a transaction to the reactive context. The constraints are real: no lazy loading, a reactive driver per database, and no mixing with classic Hibernate ORM in one persistence unit. The trade is a non-blocking path end to end against driver support and transactional semantics that must be verified.

The Quarkus knowledge gap it signals

Non-blocking is a property of the whole path, not of an annotation. The facts to hold: every dependency speaks a reactive protocol natively, every transaction is short, every association is fetched where needed, and nothing in the dependency tree opens a JDBC connection. One blocking call returns the stall to the event loop, and the damage scales with concurrency, not request count. The gap question: which step in this path can block, and has anyone checked?

ImportantWhen the domain mandates it

An IO-bound service, reactive end to end, driver included, with a build that rejects a blocking driver. Quarkus flags a blocked event-loop thread in dev and test mode, so the property is observed, not asserted.

WarningWhen it’s a guess dressed as engineering

One blocking call inside the reactive chain. A JWT validator that reads a key from a database, a legacy cache client, a driver that advertises reactive support and hands back a JDBC connection. Each arrives as “just this once”, passes a smoke test, and stalls every request sharing that event loop.

TipThe faithfulness test

Is every step of the request path non-blocking — verified — and does the driver truly support it?

  • If yes → the choice is the workload’s. Check the warning log for blocked threads, and that no lazy association is traversed in the chain.
  • If no → the annotation is a costume. Find the blocking step, then wrap it off the event loop or remove it.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete workload knowledge. Trace every endpoint’s path once and list each library it touches.
