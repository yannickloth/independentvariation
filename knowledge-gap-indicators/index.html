Patterns & Constructs as Knowledge-Gap Indicators

A series of short posts that read each design pattern as a completeness check on domain knowledge.

Case study: Abstract Factory Pattern

GoF Intent: “Provide an interface for creating families of related or dependent objects without specifying their concrete classes.” [1]

The domain knowledge gap it signals

The set of concrete types that must vary together (the “product family”) is domain knowledge. If your domain model already crystallizes that “when you’re in context X, you use implementations A₁, B₁, C₁; in context Y, you use A₂, B₂, C₂” — and that these groupings are cohesive units in the domain (e.g., a regulatory regime, a hardware platform, a deployment tier) — then an Abstract Factory is just embodying that knowledge. The factory interface is the domain’s own abstraction; the concrete factories are its real partitions.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates product-family coherence but the language offers no native construct to express “these N types co-vary.” The Abstract Factory is a technical artifact that closes the gap — it prevents each client from individually selecting concrete types, which would scatter the family-binding knowledge across the system and create accidental coupling (every client must know which concrete A goes with which concrete B).

WarningWhen it’s inapplicable (cohesion-reducing)

The domain has no notion of product families. The concrete types vary independently. Forcing them into an Abstract Factory imposes a grouping the domain doesn’t recognize — it bundles change-drivers that are actually independent, creating a single point of modification for unrelated changes. That’s the cohesion-reducing move.

TipThe faithfulness test

Does the domain recognize the concrete-type groupings as a thing?

  • If yes → applicable. The Abstract Factory is the code catching up to the knowledge.
  • If no → inapplicable. It’s the code inventing knowledge the domain doesn’t have.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Strategy Pattern

GoF Intent: “Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.” [1]

The domain knowledge gap it signals

The existence of multiple algorithms for the same operation is domain knowledge. If your domain model already crystallizes that “this operation admits variants A, B, C, and there is a domain rule that selects among them,” then Strategy is just embodying that knowledge. The strategy interface is the domain’s own abstraction (the what); the concrete strategies are its real alternatives (the how).

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates algorithmic substitutability — it recognizes that the operation meaningfully differs across contexts, and a domain rule dictates which variant applies. The Strategy pattern closes the gap: it prevents each caller from embedding variant-selection logic inline, which would scatter the selection rule across the system and create accidental coupling (every caller must re-encode which variant to use under which conditions). The pattern collects each variant behind a shared interface; the selection rule lives wherever the strategy reference is assigned.

WarningWhen it’s inapplicable (cohesion-reducing)

The domain has no notion of multiple algorithms for this operation. The “variants” are a decomposition artifact, not a domain partition — the developer split one algorithm into pieces for readability or reuse and wrapped them in a strategy interface as organizational glue. This imposes a grouping the domain doesn’t recognize: it bundles what the domain treats as one thing into an interface-plus-implementations structure, adding ceremony that signals a richness of variation that isn’t there. If the variants also pull in different data dependencies, Strategy scatters data-acquisition logic across implementations that must each independently discover their inputs.

TipThe faithfulness test

Does the domain recognize multiple algorithms for this operation as a real thing?

  • If yes → applicable. Strategy is the code catching up to the knowledge.
  • If no → inapplicable. It’s the code inventing variation the domain doesn’t have.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Observer Pattern

GoF Intent: “Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.” [1]

The domain knowledge gap it signals

The fact that “a change in A constitutes a domain event that B, C, and D must know about” is domain knowledge. If your domain model already crystallizes that certain state transitions are meaningful events to other entities — that the event is a first-class domain concept — then Observer is just embodying that knowledge. The subject interface is the domain’s own event source; the observer interface is the domain’s own event consumer.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that certain state changes constitute events with multiple consumers, and the set of consumers is open-ended. Observer closes the gap — it prevents the event source from encoding the full list of consumers and their reaction logic inline, which would bundle every downstream concern into a single class and couple the event source to each consumer’s change-drivers.

WarningWhen it’s inapplicable (cohesion-reducing)

The “event” is not a domain event — nothing in the domain recognizes the state transition as meaningful in itself. B must recompute when A changes not because the domain treats A’s transition as an event, but because the developer chose to cache or denormalize. Observer used for technical consistency (UI model-view synchronization, the GoF’s canonical example) is valid engineering. The cohesion risk is when notification cascades for technical reasons (cache invalidation, denormalization-update chains) are presented as domain event propagation, inventing event semantics the domain model never had.

TipThe faithfulness test

Would the domain model this state transition as an event even if the system weren’t software?

  • If yes → applicable. Observer is the code catching up to the knowledge.
  • If no → inapplicable. It’s the code manufacturing events the domain doesn’t have.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Dispose Pattern

The domain knowledge gap it signals

The fact that a resource has a bounded lifetime — that acquiring it and releasing it are two ends of a single domain transaction — is domain knowledge. If your domain model already crystallizes that “this resource must be acquired before use and released after, and the interval between acquisition and release is a meaningful domain scope (a session, a connection, a lock window),” then Dispose is just embodying that knowledge. The disposal interface is the domain’s own “bounded lifetime” contract; the using block is the domain’s own scoping rule made mechanical.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that a resource has a deterministic end-of-life tied to a domain scope. Dispose closes the gap — it prevents each caller from manually pairing acquire and release calls, which would scatter the lifetime knowledge across the system. Every call site would need to know both the acquisition protocol and the release protocol, coupling unrelated code to resource lifecycle details it shouldn’t own.

WarningWhen it’s inapplicable (cohesion-reducing)

The “resource” is not a domain resource — it’s a memory-management artifact. The developer wraps a plain object in IDisposable because the GC won’t finalize it soon enough, not because the domain mandates a bounded lifetime. Dispose here addresses a runtime behavior, not domain knowledge. Infrastructure resources — file handles, database connections, network sockets — have bounded lifetimes by OS nature, and Dispose is correct for them even when the domain is silent. The inapplicable case: domain objects with no resource semantics beyond memory, where disposal introduces lifecycle coupling the domain never defined.

TipThe faithfulness test

Would the domain model this resource as having a defined end-of-life — or is the resource inherently finite by the nature of the computing environment?

  • If yes → applicable. Dispose catches up to domain knowledge.
  • If no → inapplicable. But the resource is infrastructure (files, sockets, connections) or the domain is resource-constrained (embedded/real-time), it remains valid — the bounded lifetime comes from the environment. If purely a GC workaround, the pattern adds lifecycle coupling the domain didn’t require.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Adapter Pattern

GoF Intent: “Convert the interface of a class into another interface clients expect. Adapter lets classes work together that couldn’t otherwise because of incompatible interfaces.” [1]

The domain knowledge gap it signals

The fact that two entities must talk to each other but speak incompatible languages is domain knowledge. If your domain model already crystallizes that “system A understands protocol α, system B understands protocol β, and there is a domain rule requiring A and B to interoperate,” then Adapter is just embodying that knowledge. The adapter is the domain’s own translation rule; the adapted interface is the domain’s own target vocabulary.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates interoperability across a boundary the domain itself recognizes — a third-party service, a legacy subsystem, an external standard, a different bounded context. The adapter closes the gap: it isolates the translation logic in one place rather than forcing every caller of B to speak B’s protocol directly. Without it, each caller would embed translation logic inline, coupling unrelated code to B’s vocabulary and scattering the adaptation rule across the system.

WarningWhen it’s inapplicable (cohesion-reducing)

The “incompatibility” is not a domain boundary — it’s a pair of self-owned interfaces that encode the same concepts differently. Wrapping one in an adapter to match the other adds a permanent translation layer between abstractions that should be unified. Sometimes this is transitional — two teams built different interfaces that need reconciliation. But when the adapter becomes permanent without a unification plan, it institutionalizes an interface mismatch the domain never imposed. The distinguishing test is whether both sides have independent change-driver authorities: an adapter between domain port and infrastructure adapter (Hexagonal/Ports-and-Adapters) embodies a domain-imposed boundary, not duplication disguised as adaptation.

TipThe faithfulness test

Does the domain recognize the two sides of the adapter as genuinely separate things that must interoperate?

  • If yes → applicable. The adapter is the code catching up to the knowledge.
  • If no → inapplicable. It’s indirection the domain didn’t impose — which may still be legitimate if the sides have distinct authorities (e.g., domain port vs. infrastructure), but warrants unification if the same team owns both.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Builder Pattern

GoF Intent: “Separate the construction of a complex object from its representation so that the same construction process can create different representations.” [1]

The domain knowledge gap it signals

The fact that constructing an object is a multi-step process whose steps are domain-significant — not just parameter-passing — is domain knowledge. If your domain model already crystallizes that “creating an X requires collecting parts A, B, C from different sources, in an order that matters, with validation between steps,” then Builder is just embodying that knowledge. The builder is the domain’s own construction protocol; each step is a domain operation.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that construction is a process, not a one-shot operation. The object cannot be created atomically because its parts come from different domain sources or require intermediate domain validation — and a partially-built object is a meaningful domain state (a draft, an incomplete form, a staged assembly). Builder closes the gap: it isolates the construction logic so the object doesn’t expose setters allowing mutation after construction, and so callers don’t each re-encode the construction sequence.

WarningWhen it’s inapplicable (cohesion-reducing)

The domain has no notion of incremental construction. All parts are available at once, and a partially-built object has no domain meaning. Builder is often reached for here to emulate named parameters — e.g., Pizza.builder().size(12).crust("thin").sauce("marinara") reads better than positional new Pizza(12, "thin", "marinara"…). But this ergonomics problem exposes a deeper gap: the constructor arguments are weakly typed. crust isn’t a String, it’s a Crust. Once the domain is properly typed — Pizza(Size, Crust, Sauce, Set<Topping>) — the constructor is self-documenting and Builder adds nothing. Builder here isn’t fixing a language limitation, it’s masking underspecified types.

TipThe faithfulness test

Does the domain treat “in the process of being built” as a real state?

  • If yes → applicable. Builder is the code catching up to the knowledge.
  • If no → inapplicable. Check first whether weak typing or some other issue is the real gap. When the domain is properly typed and construction is still painful, the language genuinely lacks expressive constructors — but this is rare and worth distinguishing from a type-design gap.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Command Pattern

GoF Intent: “Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations.” [1, p. 233]

The pattern decouples invoker from receiver — the invoker must NOT know which concrete receiver handles the request. This is structural: the invoker dispatches to a Command interface and stays receiver-agnostic. (Queuing, logging, and undo follow from the encapsulation.)

The knowledge gap it signals

Command needs the invoker to be receiver-agnostic. The question is not “would the domain break if the invoker knew?” — the pattern exists because the invoker must NOT know. The gap: does your architecture need receiver-agnostic dispatch?

ImportantWhen it’s needed

The invoker must dispatch to different receivers without knowing which at compile time: a menu dispatches to dialogs, a scheduler to job handlers, a transaction manager to rollback actions, an event bus to subscribers. The invoker cannot name the receiver — requests are queued, parameterized, or submitted by unknown clients. Command closes the gap: the interface abstracts over receivers the invoker was never meant to know.

WarningWhen it’s not needed

The invoker always calls the same concrete receiver. Wrapping every service-method invocation in a Command interface because “we might need undo later” adds indirection where the invoker already knows its target. The interface adds maintenance and dispatch overhead to a call that should be direct. Command here guesses at flexibility no requirement demands.

TipThe faithfulness test — a 3-step decision procedure
  1. Does the invoker need to dispatch without knowing the concrete receiver?
  2. Is there more than one receiver, or will the receiver be determined at runtime?
  3. Decide. If yes → applicable (Command provides the receiver-agnostic dispatch your architecture needs). If no → inapplicable (call directly). If you can’t answer → unclear — you haven’t found the pattern wrong, you’ve found incomplete domain knowledge.

CQS/CQRS “Command” is a different concept — a message that mutates state (contrast: Query) — and is not covered here.

Case study: Composite Pattern

GoF Intent: “Compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.” [1]

The GoF Composite pattern composes objects into tree structures to represent part-whole hierarchies. It lets clients treat individual objects and compositions of objects uniformly through a shared Component interface.

The domain knowledge gap it signals

The domain recognizes a part-whole hierarchy where the whole and its parts answer the same questions. A department and its sub-departments both have budgets. A file and a directory both have sizes. When you find yourself reaching for Composite, the gap is: does the domain actually treat wholes and parts uniformly, or are you imposing a tree structure on something the domain views as flat or differently?

ImportantWhen the pattern follows domain knowledge

The domain has genuine part-whole recursion where the same operations apply at every level. Making “a department contains sub-departments, and both compute a budget” explicit in the domain model is the work. Composite’s uniform interface then prevents callers from branching on “is this a single thing or a group?” before every operation — the hierarchy delegates recursively, and callers operate on the abstract type.

WarningWhen the pattern overreaches

The domain has no part-whole recursion. The hierarchy is a tree-shaped data structure for navigation convenience, not a domain fact. UI component trees are the GoF’s canonical Composite example and are valid — they address the domain of UI toolkit design, where the part-whole relationship IS the problem space. A file-system directory tree is domain recursion; an internal cache organized as a tree for lookup efficiency is not. When the hierarchy is artificial, leaf types implement operations that make no sense for them — a structural mismatch the domain did not create.

TipThe faithfulness test

Does the domain say “an X is either a single thing or a group of things, and both answer the same questions”?

  • If yes → applicable. The pattern codifies what the domain already dictates.
  • If no → inapplicable. The tree structure may still be valid — valid in infrastructure domains (UI toolkits, scene graphs, ASTs) where the part-whole relationship IS the problem space — but misplaced where the domain has no recursion.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Decorator Pattern

GoF Intent: “Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.” [1]

The domain knowledge gap it signals

A decorator adds behavior without changing the interface or what the object is. Domain intuition: a paper invoice through administration. One office stamps “PAID” — still an invoice, now endorsed. Another stamps “CONFIDENTIAL” — still an invoice, now classified. Each endorsement decorates without changing identity; for clients it is still the same object. The gap: what is intrinsic to the entity vs. an optional endorsement. An unpaid invoice is still an invoice — “paid” is an endorsement, not part of what makes it an invoice. Baking payment status into the invoice class reveals the gap.

ImportantWhen it’s applicable (cohesion-increasing)

A responsibility is optional — some objects need it, others don’t. Without Decorator, independent endorsements must be enumerated by subclass, conditional-branch, or enum state. For fully independent endorsements factoring into 2ⁿ combinations, that is an explosion the domain never created. Each decorator stays a single endorsement.

WarningWhen it’s inapplicable (cohesion-reducing)

The wrapping transforms the object’s semantics instead of endorsing it. Tax calculation that changes the invoice total is Pipes and Filters: sequential transformations producing a semantically different result, not a stamp. Decorator preserves contract meaning — the invoice is still an invoice after every endorsement. If wrapping changes what the thing is, you are not decorating.

Also inapplicable when the added behavior is independent of the causal domain — pure orthogonal wrapping (logging, caching, auth, retry): a business-agnostic interceptor, not a domain endorsement. The GoF’s examples (scrollbars, borders, buffered streams) are infrastructure. The pattern’s domain value emerges when the business operates through endorsements on stable documents: approvals, certifications, status stamps.

TipThe faithfulness test

Can each responsibility be attached or removed without changing what the object is?

A “PAID” stamp doesn’t make an invoice something else → applicable (Decorator). Tax wrapper changes the total → inapplicable (Pipes and Filters, not Decorator). If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: State Pattern

GoF Intent: “Allow an object to alter its behavior when its internal state changes. The object will appear to change its class.” [1]

The domain knowledge gap it signals

That an entity’s behavior depends on which state it’s in — and that the set of states and the transitions between them are domain rules — is domain knowledge. If your domain model already crystallizes a state machine — “an order starts as Pending, can transition to Confirmed or Cancelled, and in each state different operations are allowed” — then State is just embodying that knowledge: each state is a domain state; each transition is a domain rule.

ImportantWhen it’s applicable (cohesion-increasing)

The domain recognizes a state machine: a finite set of states, well-defined transitions, and behavior that varies per state. Each state is a real domain notion the domain expert can name, say what operations it permits, and say what can follow it. State preserves the domain’s own boundaries: one module per domain state, keeping each state’s rules with its state.

Lifecycle vs interchangeable choice is the discriminator. State is right only when switching behavior is the object moving through stages of a lifecycle — each stage follows from and leads to others. If the switches pick between interchangeable alternatives with no ordered progression, the domain describes a Strategy, not a State machine.

WarningWhen it’s inapplicable (cohesion-reducing)

The “states” are not domain states — they’re status flags with no behavioral variation. An entity carries several independent flags, each its own domain notion: active, verified, and premium are each judged on their own. Collecting these into one lifecycle and treating each combination as a state only works if the domain recognizes a lifecycle over those combinations — but it doesn’t. The domain expert sees three separate facts, not stages that follow one another.

TipThe faithfulness test

Can the domain expert draw the state-transition diagram from memory?

  • If yes → applicable. State is the code catching up to the knowledge.
  • If no → inapplicable. It’s boolean flags encoded as a state machine — the domain doesn’t define a lifecycle over these combinations.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

A second check: does the object appear to change its class when it changes state — does its whole behavior repertoire shift? Real states do. Flags merely flip a bit; the behavior was never different.

Case study: Template Method Pattern

GoF Intent: “Define the skeleton of an algorithm in an operation, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm’s structure.” [1]

The domain knowledge gap it signals

The fact that operations share an invariant skeleton with variant steps can be domain knowledge — but only when the skeleton itself is a domain rule. If your domain model already crystallizes that “the regulatory review process has the same framework (notify, review, approve) regardless of jurisdiction; only the steps within each phase differ,” then Template Method is just embodying that knowledge. The base class is the domain’s own procedural framework; the hook methods are the domain’s own variation points. In most applications, however, the “skeleton” is code similarity mistaken for domain structure — the domain expert sees one coherent algorithm, not a template with extension points.

ImportantWhen it’s applicable (cohesion-increasing)

The domain recognizes the skeleton as a domain-invariant process: a regulatory framework, a certification pipeline, a protocol with mandated phases. Template Method closes the gap: it prevents each implementation from re-encoding the invariant sequence, which would scatter the procedural knowledge across the system and risk divergence. The base class is the domain’s own “these steps always happen in this order” rule; the concrete subclasses fill in the domain’s own variation points.

WarningWhen it’s inapplicable (cohesion-reducing)

The skeleton is code similarity, not domain structure. “ReportGenerator has a generate() method that calls openFile(), writeData(), closeFile() — and CSV and PDF differ only in writeData().” The domain doesn’t recognize openFile/writeData/closeFile as a legitimate decomposition — it sees “generate a report.” Template Method here encodes a technical sequence (file open/write/close) as if it were a domain invariant, coupling all report types to a file-based implementation. When a report type arrives that doesn’t use files, the template breaks.

TipThe faithfulness test

Can you state the invariant skeleton as a domain rule without mentioning implementation details?

  • If yes → applicable. Template Method is the code catching up to the knowledge.
  • If no → inapplicable. It’s code similarity mistaken for domain invariance.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Facade Pattern

GoF Intent: “Provide a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.” [1]

The domain knowledge gap it signals

The fact that a subsystem presents a single entry point — that “to interact with this part of the system, you go through here” — is domain knowledge if the boundary is a domain boundary. If your domain model already crystallizes that “ordering involves inventory, payment, and shipping, but from the customer’s perspective it’s one operation,” then Facade is just embodying that knowledge. The facade is the domain’s own simplified interface; the subsystem behind it is the domain’s own internal complexity.

ImportantWhen it’s applicable (cohesion-increasing)

The domain recognizes a bounded context: a cluster of related operations that outsiders should consume through a single, simplified interface. Facade closes the gap: it prevents every external caller from knowing the internal structure of the subsystem and orchestrating calls to its components directly. Without it, each caller would couple to the subsystem’s internal topology, making every internal refactor a cross-system ripple. The facade is the domain’s own “this is the interface” contract.

WarningWhen it’s inapplicable (cohesion-reducing)

The “subsystem” is not a domain boundary — it’s a package the developer created for code organization. A facade over “DataAccessLayer” or “UtilPackage” isn’t expressing a domain simplification; it’s expressing an organizational boundary the domain model doesn’t define. The risk is that over time, every cross-cutting concern lands in the facade, coupling unrelated domain rules under a single class. The distinction matters: a Repository (facade over data access in DDD) IS domain-meaningful; a general-purpose “Utils” facade is not.

TipThe faithfulness test

Does the domain recognize this boundary as a meaningful simplification — “you deal with X, not with the machinery behind X”?

  • If yes → applicable. Facade is the code catching up to the knowledge.
  • If no → inapplicable. It’s an organizational boundary the domain doesn’t recognize — valid for technical subsystems (the GoF’s compiler example), but structurally different from a domain-simplification facade.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Singleton Pattern

GoF Intent: “Ensure a class only has one instance, and provide a global point of access to it.” [1]

The domain knowledge gap it signals

The fact that there is exactly one of something — and that “exactly one” is a domain rule, not a coincidence — is domain knowledge. If your domain model already crystallizes that “there is one and only one tax authority, one central bank, one system clock,” then Singleton is just embodying that knowledge. The singleton instance is the domain’s own uniqueness constraint; the global access point is the domain’s own “ask the one X.”

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates uniqueness: the concept itself implies singleness, and having two would be a domain error. Singleton closes the gap: it prevents the system from accidentally creating duplicate instances of something that the domain says cannot be duplicated. Without enforcement, every caller becomes a potential duplication point — the uniqueness knowledge is scattered across the system as a convention (“don’t create two”) rather than a constraint.

Case study: Anemic Domain Model (anti-pattern)

Fowler: “The fundamental horror of this anti-pattern is that it is so contrary to the basic idea of object-oriented design — to combine data and process together.” [17]

An Anemic Domain Model is a model of data classes that hold no behavior of their own.

The domain knowledge gap it signals

A model of data classes with no behaviour claims, implicitly, that the domain has facts but no rules — that orders merely have totals but nothing enforces validity. That claim is almost never true. The anemic model is therefore a standing question: where did the rules go? The answer is usually “into services no expert named,” and that displacement is the knowledge gap made visible.

ImportantWhen the domain justifies it (rare, but real)

Some boundaries are genuinely data-only because the knowledge genuinely lives elsewhere: DTOs crossing a process boundary, persisted projections in CQRS read sides, integration messages. There the domain itself says “this is an envelope, not a model” — and dressing these up with fake behaviour would be the misplaced structure, not the anemia.

WarningWhen it’s a knowledge gap

The “entities” are the domain model — experts speak of orders, policies, claims — yet every rule about them lives in XxxManager or XxxHelper services. Each such service is an unnamed domain concept: the experts’ verbs exist, but no one found their owner. The anemia signals “the rules had no discoverable home,” which means the model-building stopped before the knowledge was placed. Adding getters does not fix it; finding who owns each verb does.

TipThe faithfulness test

For each behaviour sitting in a service: would an expert name the thing that performs it — “the order validates itself at submission”? Or is the performer genuinely a process, not an object?

  • If a thing performs it → the behaviour has a home; move it there.
  • If it’s genuinely a process → keep the service, but name it in the domain’s words.
  • If you can’t answer → unclear. You haven’t found a style problem; you’ve found knowledge with no assigned owner.

Case study: Module (tactical packaging)

Evans: “Choose modules that tell the story of the system and contain a cohesive set of concepts.” [15]

A Module is a named package that groups related domain concepts.

The domain knowledge gap it signals

The fact that these concepts belong together in the experts’ minds is domain knowledge. If your domain model crystallises that “leasing, maintenance, and resale are different parts of the fleet business — each with its own vocabulary,” then the module divisions are the domain’s own chapters. A Module is that division made executable: a named, cohesive packaging of a piece of the domain, whose name an expert would recognise.

ImportantWhen the domain mandates it (cohesion-increasing)

The module corresponds to a piece of the business that experts name — “Underwriting,” “Fulfilment,” “Billing” — with a vocabulary used only inside it. A Module closes the gap: it prevents concepts from different vocabulary areas being interleaved until nothing can be discussed in one place, and it makes the domain’s own sections visible in the code layout. High cohesion inside, low coupling across — because the business itself works that way.

WarningWhen the domain doesn’t (cohesion-reducing)

There is no knowledge-free half of this split. Grouping code into models/, services/, utils/, or helpers/ is still a decision, but a Module asserts that the grouping matches the experts’ own sections. It fits only when the domain names those sections. If the domain’s groupings were never consulted, every business concept is smeared across the drawers and no module can be shown to an expert. That is the gap — the domain’s own structure is unwritten, not “merely technical.”

TipThe faithfulness test

Could you read the module names to a domain expert and hear “yes, those are the parts of our business” — and would each module’s terms be used by exactly that part?

  • If yes → applicable. The Module is the code catching up to the knowledge; the packaging is the domain’s own.
  • If no → inapplicable. Repackage around the domain’s own sections; the drawers hide the knowledge’s structure.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Policy / Process (tactical)

A Policy is a rule object that expresses “when this happens, do that.”

The domain knowledge gap it signals

The fact that the business responds to occurrences with prescribed actions — “when a claim is filed, assign an adjuster within two days” — is domain knowledge. A Policy is that fact made executable: a rule in the experts’ own if-then shape, attached to the occurrence it responds to. It is the domain’s own “when X, then Y” made first-class instead of buried in a sequence of ifs.

ImportantWhen the domain mandates it (cohesion-increasing)

The experts state the rule as a standing instruction, and it may change without the surrounding process changing. A Policy closes the gap: it prevents the response from being smeared through whatever code happens to trigger the occurrence, and it gives the rule one name, one home, one audit trail. The trigger is the domain’s own event; the response is the domain’s own obligation.

WarningWhen the domain doesn’t (cohesion-reducing)

There is no knowledge-free half of this split. A reaction such as “retry three times” or “log a metric” is still a decision, and a Policy asserts that the business prescribed it. It fits only when an expert would state the rule and expect to be consulted before it changed. If the library set it and no expert decided, the Policy claims authority nobody granted. That is the gap — the rule is unwritten, not “merely technical.” The structure also obscures real policies: when everything is a policy, nothing is.

TipThe faithfulness test

Would an expert state this rule in a meeting — “when this happens, we do that” — and would they expect to be consulted before it changed?

  • If yes → applicable. The Policy is the code catching up to the knowledge; the if-then is the domain’s own.
  • If no → inapplicable. Keep it as a plain default; dressing it as policy invents authority nobody granted.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Immutable Value Objects

Evans: “Value objects should be immutable: rather than modifying one, you create a new one in its place.” [15]

A value object is an immutable type identified by its values; you replace it instead of changing it.

The overlap, and the one thing this post adds

#85 established the construct: a value object makes executable the domain rule “a €10 note is any €10 note.” Immutability is the other half of that same claim, and #85 named it only in passing. The OOP angle is narrower: immutability is a language-level commitment that the domain replaces this fact rather than revises it. An address correction is a new address, not a mutated one. If the business speaks that way, immutability is the code catching up. Where it goes wrong is on both sides. Immutability adopted without a domain warrant — chosen for thread safety, cacheability, or safe sharing on things the domain revises — forces contortions: builders and copy-methods emulating updates the domain actually performs. The choice is still a decision, but the domain never named a replacement rule, and that is the gap — not that immutability is “merely technical.” The inverse is a mutable value-shaped object, whose shared aliasing silently couples changes the domain never coupled.

TipThe narrower test this post adds

For a value-shaped class: when this fact “changes” in the business language, does the old one stop being true, or does the same thing acquire a new state?

  • If the old one stops being true (the domain replaces it) → immutable. The Value Object is the code catching up to the knowledge.
  • If the same thing acquires a new state (the domain revises it) → not a value object at all. The identity question is #85/#86, not the language mechanism.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete domain knowledge.

Case study: Party

Fowler: Model people and organizations with a common supertype, Party. [18]

Party is the analysis pattern that lets a person and an organisation stand in for each other wherever a role applies.

The domain knowledge gap it signals

The fact that a person and an organisation can play the same role — both can be a customer, a supplier, an employee — is domain knowledge. If your domain crystallises that “whoever we invoice may be a person or a company, and downstream we don’t care which,” then Party is that fact made executable: a common abstraction above Person and Organisation, where the roles live.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain assigns the same roles and rules to people and organisations: both order, both pay, both are contacted. Party closes the gap: it prevents duplicating every role (“CustomerContact” vs “CorporateContact”) and every rule for each subtype, and it lets contracts, accounts, and addresses point at one concept. The abstraction is the domain’s own “who matters, not what kind of who” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here people and organisations look like separate kinds, with different lifecycles and different rules. But it is still a domain decision whether they share a role. Party fits only when the domain names a role that is true of both. If the domain has not named one, the abstraction asserts a sameness nobody decided, and every consumer branches on type to escape it. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Can a domain expert state a rule using only “the customer” / “the contact” — a phrase that is true whether it is a person or a company?

  • If yes → applicable. Party is the code catching up to the knowledge; the shared role is the domain’s own.
  • If no → inapplicable. Model Person and Organisation separately; the abstraction fabricates a role the domain doesn’t share.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Organization Hierarchy

Fowler: An organization hierarchy in which each organization has at most one parent. [18]

Organization Hierarchy is the analysis pattern that treats every unit as having exactly one superior.

The domain knowledge gap it signals

The fact that the organisation is a strict tree — every unit has exactly one superior, authority flows one way — is a domain claim, and often an unexamined one. Organization Hierarchy is that claim made executable: single-parent structure with transitive rules (“the whole branch reports up through here”).

ImportantWhen the domain mandates it (cohesion-increasing)

The domain genuinely is a tree: command chains, statutory consolidation, single ownership. The hierarchy closes the gap: transitive queries (“all subunits”), single-line accountability, and roll-up rules become simple and correct because the domain guarantees one parent. The strictness is the domain’s own “no shared bosses, no dotted lines” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the organisation looks like a tree, and a hierarchy looks purely structural. But it is still a domain decision: someone claimed authority is single-threaded. Organization Hierarchy fits only when the domain names exactly one superior per unit. If the real authority is many-threaded — matrix, shared services, dotted lines — the domain has not named a single parent, and the tree asserts a chain nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Can every unit in the business name exactly one superior — and would experts confirm there are no “it depends” reporting lines?

  • If yes → applicable. The hierarchy is the code catching up to the knowledge.
  • If no → inapplicable. Model a graph or multiple typed structures; the tree would encode an org that doesn’t exist.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Knowledge Level

Fowler: Separate the knowledge level (the rules) from the operational level it governs. [18]

Knowledge Level is the analysis pattern that separates the rules about kinds of things from the things themselves.

The domain knowledge gap it signals

The fact that the business distinguishes kinds of things from the things themselves — job positions vs. the people in them, account types vs. accounts, ward categories vs. wards — is domain knowledge. A Knowledge Level is that distinction made executable: one layer defines the types and their rules; the other holds the operational objects that must obey them.

ImportantWhen the domain mandates it (cohesion-increasing)

The experts maintain the rules about kinds separately from the instances: HR defines positions, finance defines account types, and changes to one never touch the other. The knowledge level closes the gap: it prevents type rules from being copy-pasted onto each instance, where a rule change means editing every record. The level is the domain’s own “the rules of the kind live with the kind” structure — a classic and legitimate use of meta-data.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the types never vary and never carry rules — it looks like one kind, with a config table only developers edit. But it is still a domain decision: someone claimed the business owns rules about kinds. Knowledge Level fits only when the experts maintain those rules and change them without touching the instances. If the table is only a developer lookup, the layer asserts business governance nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Do the experts maintain rules about kinds of things — and do they change those rules without touching the individual things?

  • If yes → applicable. The Knowledge Level is the code catching up to the knowledge; the meta-layer is the domain’s own.
  • If no → inapplicable. Keep types in the schema; the extra layer fabricates business governance.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

The log shows paths the model forbids, steps the model never mentions, and rework the picture hides. Does the log match the model — and if it does not, which one does the business intend to be true?

  • If they match → the model is knowledge.

  • If you can’t answer → you have found the gap without even needing a question.

Case study: State Machines for Business Entities

Harel: Statecharts model the permitted states and transitions of a system. [24]

The domain knowledge gap it signals

The fact that a thing may change only in ways the business allows is domain knowledge. “An order cannot go from shipped back to draft”; “a claim cannot be approved before it is assessed.” A state machine is that fact made executable: named states and permitted transitions, so the entity’s allowed changes are stated once and enforced everywhere.

ImportantWhen the model is faithful

The business names the states and the moves between them, and experts recognise a forbidden transition as a real error (“you can’t un-ship an order”). The state machine is the domain’s own rule about how things may change, and every code path that touches the entity obeys it.

WarningWhen the model misrepresents

A status field is written freely by whichever code path runs, and the “states” are whatever strings appear. Then the model claims transitions the business forbids — a refunded invoice that is later marked paid, an approved claim that was never assessed. The absence of a state machine is not neutral: it asserts that any change is possible, which is a claim the domain denies.

TipThe faithfulness test

Can an expert list the states and say which moves are forbidden — and would a forbidden move be a business error?

  • If yes → the state machine is the domain’s own transition rule.
  • If no → free-form status is faithful; a machine would invent states.
  • If you can’t answer → the gap is the lifecycle: nobody has said what this thing’s allowed changes are.

Case study: EPC — Event/Function Alternation

Scheer: An event-driven process chain alternates events and functions to describe a process. [25]

The domain knowledge gap it signals

EPC’s structural claim is that events and functions alternate: every action is triggered by a state, and produces one. That is a domain distinction — an event is a fact the business observes (“what happened”), a function is an act the business chose (“what we did”). These are different kinds, and EPC forces the difference where BPMN does not.

ImportantWhen the model is faithful

The business genuinely distinguishes the state that licenses an action from the action itself, and the alternating chain captures it: nothing is done without a condition that made it permissible. This is also why an EPC compiles almost as-is to event handlers — events are named states, functions are transitions, and the diagram hands you the transition table, not just a flowchart.

WarningWhen the model misrepresents

A fact is recorded as an act, or an act as a fact: “shipped” modelled as a step, “verify” modelled as an observation. The alternation then forces an event and a function apart where the domain saw a single step, and the model asserts a difference the business never made.

TipThe faithfulness test

Is this element something we observed or something we did — and does every action have a state that licensed it?

  • If the distinction holds → EPC’s alternation is the domain’s own grammar.
  • If not → the chain has lost the knowledge, or the domain never drew the distinction.

ImportantWhen the model is faithful

Encapsulation is a language mechanism — access control on fields and methods. Whether a boundary earns its keep is not a language question; it is a question about what callers depend on.

Case study: Encapsulation

Parnas: Modules should hide a design decision behind an interface so that the decision can change without affecting clients. [27]

The domain knowledge gap it signals

An encapsulation boundary splits a type into what callers may depend on and what they never see. The real claim is not “something is hidden here” but “this interface is exactly what callers need.” That claim has content only if the team knows the callers’ needs — which parts the domain assigns to this thing, and which are one way of fulfilling them. The gap shows when the split is drawn by habit: the interface carries choices no caller asked about, or withholds something needed. Where the domain fixes a concrete detail, that detail belongs in the interface; an abstraction above it asserts a concept nobody decided.

ImportantWhen the domain mandates it (cohesion-increasing)

The team can point at each exposed operation and name the need it serves: “converting a payment uses the current rate” is a domain-assigned responsibility, and how the rate is stored is one way of fulfilling it. Callers depend on the responsibility, not the fulfillment, so reworking the internals touches no one.

WarningWhen the domain doesn’t (cohesion-reducing)

Encapsulation as a default virtue. Private fields with public getters and setters: the representation becomes part of the commitment, so an internal choice and the callers’ needs are fused — reworking the internals means renegotiating with every caller. Interfaces wrapped around things no caller needs: commitments with nobody to commit to. Where the domain mandates the concrete detail, the abstraction asserts a concept nobody decided; the concept is unwritten, and callers couple to the invention. The mirror failure: withholding what callers need produces workarounds — reflection, duplicated internals, paths that bypass the boundary. The mechanism runs without the knowledge.

TipThe faithfulness test

For each thing this type exposes: which need does it serve? For each thing it withholds: why may no caller reach it?

  • If you can answer both → applicable. The boundary is the code catching up to the knowledge.
  • If the answer is “private by default” → inapplicable. The mechanism runs without the principle.
  • If you can’t answer → unclear. You found incomplete domain knowledge, not a wrong pattern.

An extends clause is a claim: “this IS-A that, permanently, in the domain.” Usually it is code reuse wearing a taxonomy hat.

Liskov and Wing: A subtype must be usable in place of its supertype without altering the correctness of the program. [28]

The domain knowledge gap it signals

Every extends freezes a classification into the code: the child is declared a kind of the parent, for all time. That claim has content only if the domain draws the distinction — if a domain expert would state the classification as a fact of the business, and if substitution holds under every change the domain can force. The gap shows when the hierarchy answers a question nobody asked the business: the taxonomy reflects how the code happens to be organised, not how the domain classifies. The square–rectangle trap is the textbook case; the everyday version is a parent class that exists only because two classes shared three methods.

ImportantWhen the domain mandates it (cohesion-increasing)

The classification is a domain fact with a forcing condition. Banking regulation distinguishes account types, and a savings account IS a bank account in the regulator’s own language — substitution is a legal truth, not a programming nicety. When the business itself reasons through the subtype (“any account may be frozen; savings accounts additionally accrue interest”), the hierarchy is the code catching up to the knowledge.

WarningWhen the domain doesn’t (cohesion-reducing)

Inheritance used to reuse implementation. Two classes share code, someone extracts a base class, and the child is coupled to every future change of the parent — while the code asserts a classification the domain has not stated; that knowledge is unwritten.   • If the honest answer is “we wanted to share the code” → inapplicable. Reuse wearing a taxonomy hat.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Composition over inheritance is the flip side of yesterday’s post (#136). The domain question is: “is this a stable classification, or a role the thing plays?”

Case study: Composition over Inheritance

Gamma et al.: Favour object composition over class inheritance. [1]

The domain knowledge gap it signals

Choosing inheritance freezes a relationship as permanent taxonomy; choosing composition says the relationship is a role — attached, detachable, reassignment-capable. An employee is a person who plays the employee role; a discount policy is attached to an order, not what an order is. The gap shows when the structural choice was made for reuse or convenience without asking which reading the domain supports — the choice still encodes a claim about the business, and that claim is unwritten until the domain states it. Only one reading is true.

ImportantWhen the domain mandates it (cohesion-increasing)

Composition wins when the domain itself reassigns roles: a contractor becomes an employee; a customer is also a supplier; a policy attaches to this order today and that one tomorrow. Roles vary independently of the carrier’s identity, and composition encodes exactly that independence — a change in the role’s rules arrives without touching the thing that plays it. Inheritance stays honest in the opposite case (#136): the domain holds the classification fixed, and a changed relationship would mean a different thing entirely.

WarningWhen the domain doesn’t (cohesion-reducing)

Composition adopted as a blanket slogan. The relationship is a stable domain classification, but the code models it as an attachable role “for flexibility” — flexibility against a change no domain mechanism can force. The price is real: indirection, identity workarounds (the composed parts re-deriving what “the same thing” means), and a structure that invites the domain-illegal move — swapping a component the business considers constitutive.

TipThe faithfulness test

For a given relationship: can the domain change it without changing the thing’s identity?

  • If yes — the business reassigns, swaps, stacks roles → composition. The domain treats it as played, not inherited.
  • If the domain would say “it would then be a different thing” → the classification is stable; inheritance may be the honest encoding.
  • If you can’t answer → unclear. The structure is a guess about permanence the business never confirmed.

DRY says every piece of knowledge must have a single representation. It presupposes you know which duplications are the same domain rule — and which are coincidental text similarity.

Case study: DRY (Don’t Repeat Yourself)

Hunt and Thomas: Every piece of knowledge must have a single, unambiguous representation within a system. [29]

The domain knowledge gap it signals

DRY is about knowledge, not text — but the only instrument the programmer has operates on text. Two fragments look alike, someone extracts the common code, and the extraction itself is a claim: “these are one rule, and a change to it must reach both.” That claim has content only if the domain agrees. The gap shows when the team merged by similarity without asking whether one domain decision stands behind both fragments — the merge couples two change drivers, and when one rule moves and the other must not, the shared abstraction breaks in production.

ImportantWhen the domain mandates it (cohesion-increasing)

Both fragments encode the same domain decision: the same VAT rule, the same rounding policy, the same eligibility criterion. The domain itself guarantees they change together — when the rule is revised, every place that applies it must move in lockstep, and a single representation is what makes that guarantee structural rather than hopeful. The deduplication is the code catching up to the knowledge.

WarningWhen the domain doesn’t (cohesion-reducing)

Merging by text similarity. Two price calculations that coincide today because the numbers happen to align; two validation blocks that share a shape but answer to different authorities. The duplication was the faithful structure — two rules, two drivers, two futures — and the merge planted a coupling no rule behind the fragments mandates; if each fragment answers to a different authority, each rule is unwritten and the merge hides both. Every later change now starts with an archaeology dig: which of the callers may follow this edit, and which must be peeled off first?

TipThe faithfulness test

For a candidate merge: if the domain rule behind fragment A changes, must fragment B change with it — always, by the domain’s own logic?

  • If yes → one knowledge, one representation. Merge.
  • If no → the duplication is faithful. Extracting couples two drivers.
  • If you can’t answer → unclear. The similarity is visible; whether it is one rule is exactly the knowledge you’re missing.

The Law of Demeter says a method may call its immediate collaborators only, never reach through them. “Who may know whom” is a coupling claim. An a.b().c() chain asserts a navigation path the domain may not mandate.

Case study: Law of Demeter

Lieberherr and Holland: A method should talk only to its immediate collaborators, not to their collaborators. [30]

The domain knowledge gap it signals

Every reach-through chain asserts that the caller’s business genuinely depends on the far object along this route — that the path is a stable domain relationship, not an accident of object layout. Sometimes it is: an order’s customer’s billing address is a path the business itself reasons about. Sometimes it is digging: the caller exploits an implementation trail, following a route that exists only in the object graph. The gap shows when nobody can say which of the two a given chain is — the coupling exists, its legitimacy unexamined.

ImportantWhen the domain mandates it (cohesion-increasing)

The law earns its keep where the chain is NOT a domain path. Rewriting a.b().c() into a direct ask keeps the caller coupled only to the object whose job the operation is — so when the intermediate structure changes for its own reasons, the caller doesn’t move. The caller now depends on what the domain mandates (the outcome) and not on what it doesn’t (the route). Note the asymmetry: the law is a heuristic about structure; its violations are the signal worth auditing, one chain at a time.

WarningWhen the domain doesn’t (cohesion-reducing)

Mechanically eliminating every chain. Where the chain is a domain relationship the business itself reasons about, the rewrite replaces a recognised route with a direct ask nobody decided; where it was an implementation route, wrapper methods tunnel the same dependency and only move the coupling out of sight. The caller’s real dependence on the far object is hidden, not removed.

TipThe faithfulness test

For a given chain: is this path a relationship the domain itself recognises, or a traversal of an object graph that exists only as implementation?

  • If the domain recognises it → the coupling is mandated; keep it visible and direct.
  • If not → the path exists only as an implementation route; the chain couples the caller to structure the domain never mandated.
  • If you can’t answer → unclear. The navigation compiled, but nobody checked it against the map.

Speculative extension points are guessed change drivers. YAGNI is the discipline of refusing structure for a driver you cannot name — and it is not a license to ignore drivers you can.

Case study: YAGNI

Fowler: Build only what the requirements demand now; do not add speculative generality. [31]

The domain knowledge gap it signals

Every “we’ll need this to be flexible” asserts that the domain can force a variation here — a forcing condition exists, and the structure stands ready for it. The gap is anticipating variation no domain mechanism can force: a plugin point for providers the market does not contain, a config switch for a rule the business holds fixed, an abstraction layer against a change nobody can cause. The reverse gap is costlier: “you aren’t gonna need it” said about a variation the business has already announced — the seam was domain knowledge, and YAGNI was invoked to unsee it.

ImportantWhen the domain mandates it (cohesion-increasing)

No forcing condition exists for the anticipated change, and the team can say so honestly — not “we didn’t ask,” but “we asked, and the domain holds this fixed.” Deleting the speculative structure removes a coupling to a phantom driver: the code now covers exactly the variations the domain can produce, and nothing pays rent for the rest. YAGNI here is knowledge applied, not effort avoided.

WarningWhen the domain doesn’t (cohesion-reducing)

Two failure modes, same root. YAGNI invoked against a variation the domain demonstrably forces — a regulator who can change the rule, a market that adds channels, a pricing policy with a history of revision — because “we’ll add it when we need it,” as if adding structure under deadline pressure were free. The refusal asserts that no forcing condition exists; the domain has one, so the seam’s absence is a structure nobody decided. And the mirror: building for a forcing condition nobody can name. Both share one gap: the future change was decided without consulting the domain that owns it.

TipThe faithfulness test

For a given piece of flexibility (or a refused one): name the forcing condition that would make you use it.

  • If you can name the domain mechanism → the structure is knowledge, whether you build it now or deliberately defer it.
  • If the answer is “someday, maybe” → the structure is a guess; YAGNI applies.
  • If you can’t answer either way → unclear. The decision to build or not build is currently a coin flip dressed as engineering judgment.

ImportantWhen the domain mandates it (cohesion-increasing)

The correspondence holds both ways. WarningWhen the domain doesn’t (cohesion-reducing)

Two classic traps, same root. Static mutable state — the cache, the counter, the registry — asserts “the whole universe of discourse shares one of these.” Sharing scope is a domain decision. If the domain has not named it, the assertion is a claim nobody decided — the mandate is unwritten, not absent — and the result is a hidden global that couples every caller to one change driver. And the static utility class: behavior that acts on instances, parked at the type level — the class asserts a type-level fact the domain never stated. Even static final deserves suspicion: TAX_RATE = 0.21 hardcodes a domain decision with a forcing condition — the value is fixed so far, the speculative seam’s mirror image (#140, #143).

TipThe faithfulness test

For a given static member: does the domain state this fact without referring to any particular instance — or did the code lose track of which thing owns it?

  • If the domain speaks instance-free → applicable. The keyword encodes the knowledge’s true level.
  • If the knowledge consults one thing’s state → inapplicable. Place the behavior with the thing.
  • If it’s shared mutable state nobody justified → unclear at best. The coupling is real; the mandate for it was never checked.

Patterns & Constructs as Knowledge-Gap Indicators

The faithfulness test is a 3-way verdict, not a binary: Applicable — if yes, the pattern encodes what the domain already dictates.

Inapplicable — if no, the pattern forces coupling the domain doesn’t have. Unclear — if you can’t answer, you’ve found incomplete domain knowledge. If you can’t answer, you haven’t found that the pattern is wrong — you’ve found that your domain knowledge is incomplete.

Case study: Command Pattern

GoF: Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations. [1]

The domain knowledge gap it signals

The fact that an action is a first-class thing — not just a method call — is domain knowledge. If your domain model already crystallizes that “an operation must be recorded, queued, undone, or scheduled — the action itself is a domain entity with identity and lifecycle,” then Command is just embodying that knowledge.

ImportantWhen it’s applicable (cohesion-increasing)

The domain treats actions as entities: they can be stored, replayed, reversed, and audited. An order-fulfillment system where “ShipOrder,” “CancelOrder,” and “RefundOrder” are domain commands — with undo semantics, execution timestamps, and audit trails — is the domain speaking. Command closes the gap: it prevents the action logic from being a method buried on some service class, which would make the action invisible to the domain model. Instead, each command is a domain object with its own data, validation, and undo path.

WarningWhen it’s inapplicable (cohesion-reducing)

The “commands” are not domain commands — they’re method-call wrappers. Wrapping every service-method invocation in a Command object because the framework expects it doesn’t reify a domain concept; it wraps function calls in infrastructure ceremony. Command here adds object-allocation and indirection costs to what should be a direct call, signaling entity-richness where the domain has none. Event-sourcing architectures are a valid exception — commands as persisted entities with identity serve a persistence/routing infrastructure that IS the architecture.

TipThe faithfulness test

Does the domain expert talk about this operation as a thing that exists — “the shipment,” “the refund,” “the approval request”?

  • If yes → applicable: Command is the code catching up to the knowledge. If no → inapplicable: it’s function-call packaging. If you can’t answer → unclear: you haven’t found the pattern wrong, you’ve found incomplete domain knowledge.

Case study: Dependency Injection

Fowler: A form of Inversion of Control in which a component is given its dependencies rather than creating them itself. [32]

The domain knowledge gap it signals

With dependency injection, a service declares: I need these dependencies — but I do not need to know where to get them, or how to build them; give them to me. A faithful declaration carries domain knowledge: an order service needs persistence and messaging. Even which database, which queue, and how they are built is a domain decision: someone chose them. The interface states the need; the composition root supplies the answer. The gap it signals is whether the need is real and whether the supply can vary.

ImportantWhen the domain mandates it (cohesion-increasing)

The need is real and the supply can vary. The order service always needs persistence; which database serves it can change. The interface declares the need once; the composition root supplies the answer.

WarningWhen the domain doesn’t (cohesion-reducing)

The need is invented, or the need is real but the supply cannot vary. Either way the injection point asserts a boundary the domain never decided: the external seam is unwritten.

TipThe faithfulness test

Is the need real, and can the supply vary?

  • If the need is real and the supply can vary → applicable. Dependency injection is the code catching up to the knowledge.
  • If the need is invented → inapplicable; nothing to abstract. If the supply cannot vary → inapplicable; no variation justifies it.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

DI is not the composition root

DI is a technique: how a service declares its dependencies and receives them from outside.

The composition root is a place: where the application assembles its object graph, at the entry point. Only applications should have one — composition belongs to the application. A DI container belongs only there.

DI does not specify where the object graph is assembled; the composition root answers that.

Two failures hide when the names are conflated: - Scattered wiring: composition at each use site, with no root. A deployment change touches many files. - A frozen choice: a root that bakes a per-operation choice in at startup.

A composition root is the single place where the object graph is assembled, at the entry point. It looks like a purely technical construct, but what it assembles — and where it sits — follows from a modularization rule derived from domain knowledge.

Case study: Composition Root

Seemann: A single, logical location in an application where modules are composed together. [33]

The domain knowledge gap it signals

The assembly looks purely technical, but it is still a domain decision: the same modularization rule decides where the composition root goes, what each service receives, what belongs inside each service, and whether each dependency is fixed for the object’s lifetime. The root decides those choices once, for the whole graph. The rule is derived from domain knowledge: it follows from which choices the domain owns and which it leaves open. The service’s content is fixed by the rule, not by the wiring that supplies it. The gap is the rule: if you cannot say which choices the domain owns, you cannot say where the composition root goes or what the services contain.

ImportantWhen the domain mandates it (cohesion-increasing)

The modularization rule is clear, so the composition root sits where it belongs, and each service receives what the rule assigns. A change to one choice touches one place.

WarningWhen the domain doesn’t (cohesion-reducing)

The rule is unstated. A choice the domain owns is supplied at the composition root, so the domain can no longer vary it — every such change now edits the composition root. Or the composition root sits in a library or framework, so it carries choices that belong to its caller.

TipThe faithfulness test

Can you state the rule that places the composition root and assigns what each service receives?

  • If yes → applicable. Composition Root is the code catching up to the knowledge.
  • If no → inapplicable. The composition root is placed by guesswork.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.
