JVM Tuning as Knowledge-Gap Indicators

A series of short posts that read each JVM flag and practice as a trade between two measured numbers.

Every flag or practice below moves two numbers: the one it aims at, and one it did not. Each post names the flag, states the trade, and asks which measured fact of this workload answers it.

Pick a post on the left. It opens on the right.

Changing a JVM flag or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every flag moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the flag is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Case study: Collector choice (G1, ZGC, Parallel)

Mechanism: G1 is the default: it hides most collection work behind concurrent threads while keeping a young generation. Generational ZGC, default since Java 23, pushes pauses towards sub-millisecond with a barrier cost and larger headroom. Parallel GC stops everything and spends the cores on throughput.

The JVM knowledge gap it signals

A collector answers a pause budget the SLA states and a throughput number the peak hour carries. G1’s mixed collections land in the low hundreds of milliseconds by default, so a path with no written budget inherits that number by accident. The gap question: what is the measured pause budget you must meet, and what did throughput cost under the chosen collector at peak?

ImportantWhen the domain mandates it

A payment path with a stated 50 ms p99.9 budget on a 6 GB live set: generational ZGC held stops under a millisecond, for a tenth of throughput against G1 in the same harness and a heap target raised from 8 GB to 12 GB. A nightly reconciliation nobody waits on stayed on Parallel, finished fastest, and counted its multi-second stops as nothing.

WarningWhen it’s a guess dressed as engineering

ZGC everywhere, because low pauses read as strictly better. On the batch box it buys pauses nobody observes and pays the barrier tax plus headroom the limit must now cover. The mirror image is quieter: G1 at default on a user-facing path, mixed collections to 200 ms against a budget nobody wrote down, the incident blamed on the network.

TipThe faithfulness test

What is the measured pause budget from the SLA — and what did throughput cost under the chosen collector, at peak?

  • If yes → it answers a number you hold. Watch the pause distribution, not the mean, and re-measure after any heap change.
  • If no → you have a default, not a decision. Write the budget down, then run one harness under two collectors.
  • If you can’t answer → unclear. You haven’t found the flag wrong — you’ve found incomplete workload knowledge. Measure pause distribution and work completed per collector at peak.

Case study: Heap sizing (-Xmx, MaxRAMPercentage)

Mechanism: The heap flag caps the heap; the container limit caps everything the process touches. Between them sit metaspace, the code cache, GC native structures, thread stacks, and direct buffers — none of them inside -Xmx. Sizing sets that gap deliberately, or loses it to a kill.

The JVM knowledge gap it signals

The live set at peak gives the heap floor; the distance from it to the limit gives headroom for bursts and the native reservation, which follows thread count, class loading, and direct buffer use. The gap question: what is the measured live set at peak, and how much of this container’s memory lives outside the heap?

ImportantWhen the domain mandates it

A service measuring 900 MB live after a full collection at peak, bursting to 1.6 GB between collections, 40 threads in a 4 GB container: heap at 2 GB, leaving 2 GB for metaspace, code cache, stacks, and direct buffers, MaxRAMPercentage tuned against the limit rather than a bare-metal value. The load test held at 82% of the limit, no kill.

WarningWhen it’s a guess dressed as engineering

-Xmx equal to the container limit, because the container is “the memory” and the heap is “the memory” — the arithmetic feels complete, and it passes in staging, where nothing else grows. In production the kill arrives before any collection can act. MaxRAMPercentage at 100 is the same choice in percent form. The opposite failure is quieter: native exhaustion with gigabytes of heap free, as metaspace, direct buffers, or threads grew into an unreserved gap.

TipThe faithfulness test

What is the measured live set at peak — and how much of this container’s memory lives outside the heap?

  • If yes → the heap is derived from a number. Check native growth at peak and watch the headroom.
  • If no → you have a budget, not a heap size. Take the live set, add a growth factor, then subtract the native reservation.
  • If you can’t answer → unclear. You haven’t found the flag wrong — you’ve found incomplete workload knowledge. Measure the live set after a forced full collection at peak, and read RSS against the limit.

Case study: Compact object headers

Mechanism: -XX:+UseCompactObjectHeaders, product-ready in Java 25, shrinks an object header from 16 bytes to 8. The saving lands on footprint, then on cache locality, then on collection frequency, which tracks the live set. The direct cost on a modern 64-bit JVM is negligible; the real work is measuring the migration, since some agents assume the old header layout, and vendor support still differs.

The JVM knowledge gap it signals

The win is proportional to the object count in the live set, not to the heap total. A heap dominated by large primitive arrays — sample buffers, matrix rows, byte payloads — carries few headers, so the saving rounds away. The gap question: what share of the live set is object-dominated, measured, and did the heap and the collection frequency actually move?

ImportantWhen the domain mandates it

A service holding 3.1 million live order objects with references: 2.4 GB before the flag, 2.05 GB after, in the same staging harness. Roughly 15% off the live set, young collections from 22 to 18 per minute, throughput unchanged, no tooling objection in a soak run.

WarningWhen it’s a guess dressed as engineering

Enabling it because the release notes call it free, on a service whose live set is a handful of large arrays. The flag works, the migration runs, the heap barely moves, and the team records a win it cannot reproduce under load. The cost is not the flag: it is the soak run, the agent audit, and the false confidence from quoting a benchmark built on small objects when yours holds arrays.

TipThe faithfulness test

What share of the live set is object-dominated, measured — and did the heap and the collection frequency actually move?

  • If yes → it answers an object-count fact you hold. Compare heap and collection rate before and after, at peak.
  • If no → the flag cannot help you, because there are too few headers to reclaim.
  • If you can’t answer → unclear. You haven’t found the flag wrong — you’ve found incomplete workload knowledge. Take a heap histogram by class and instance count, then compare the live set with the flag on and off.

Case study: MaxGCPauseMillis as an SLO knob

Mechanism: On G1 the value is a goal, not a guarantee: the collector shrinks the young generation and collects fewer regions per mixed cycle to approach it. A smaller target means more collections, more concurrent marking, and more CPU for shorter stops. It cannot collect less than the live young generation demands.

The JVM knowledge gap it signals

The number belongs to the SLA, and it must be defended against the measured distribution — the tail, not the mean. A target of 5 ms against a 100 ms budget buys nothing and costs CPU; the 200 ms default against a 50 ms budget fails silently while looking configured. The gap question: which SLA derived this target, and does the measured pause distribution meet it at what CPU cost?

ImportantWhen the domain mandates it

A request path with a stated 100 ms p99.9 budget and a measured pause tail of 190 ms at default, given a target of 50 ms for headroom: the pause p99.9 settled at 55 ms, young collections rose from 12 to 30 per minute, and process CPU moved from 55% to 68%. The budget was met with room, the CPU rise recorded beside the win.

WarningWhen it’s a guess dressed as engineering

Setting 5 ms on G1 to obtain ZGC behavior. The reasoning holds as far as it goes — pauses are latency, latency is the complaint, so lower the pause target — and it fails on the mechanism: G1 buys shorter stops with more of them and more marking in between, so CPU rises while the tail stays where the live young generation puts it.

TipThe faithfulness test

Which SLA derived this target — and does the measured pause distribution meet it, at what CPU cost?

  • If yes → the target encodes a number you hold. Re-read the distribution after every heap change.
  • If no → you have a wish, not a target. Derive the number from the budget, or drop the flag.
  • If you can’t answer → unclear. You haven’t found the flag wrong — you’ve found incomplete workload knowledge. Log pause durations at peak and plot the tail before and after.

Case study: String deduplication on G1

Mechanism: -XX:+UseStringDeduplication spends collection time hashing the backing arrays of surviving strings and pointing duplicates at one copy. It touches the character data behind each string, not the objects, and reaches only strings old enough to survive a collection. The trade is collector CPU against footprint, which moves only where duplicates exist.

The JVM knowledge gap it signals

The saving equals the duplicated character bytes, a property of what the workload stores: key-heavy caches, parsed documents repeating field names, payloads carrying the same codes. A heap of numeric arrays holds little character data, so the pass finds nothing. The gap question: what share of the live set is character data in duplicated strings, measured, and could a design fix hold the dedup instead?

ImportantWhen the domain mandates it

A parsed-document pipeline holding 200,000 records with repeated field names: character data at 1.1 GB of a 2.8 GB live set, roughly 38% duplicated. Dedup brought the live set to 2.0 GB, young collections fell with it, and collector CPU for the pass stayed under 3%.

WarningWhen it’s a guess dressed as engineering

Enabling it as a general memory optimization: it costs nothing to add and reads as strictly good. On a workload of numeric arrays it burns collector CPU scanning strings that are not there, and full collections grow longer — a small tax with no invoice. The subtler version uses it in place of a design fix: keys that should be interned, shared by construction, or replaced by enum constants stay duplicated, and the flag compresses the waste.

TipThe faithfulness test

What share of the live set is character data in duplicated strings, measured — and could a design fix hold the dedup instead?

  • If yes → the pass answers a duplication fact you hold. Keep its CPU share under watch: it is paid on every collection.
  • If no → the flag cannot pay for itself. Fix the duplication where it is created, then re-measure.
  • If you can’t answer → unclear. You haven’t found the flag wrong — you’ve found incomplete workload knowledge. Break the live set down by content type.

Case study: Virtual threads (waiting made cheap, and only waiting)

Mechanism: A virtual thread is a continuation the JVM mounts on carrier threads, one per CPU. Blocked on IO it unmounts and frees the carrier, so a parked request costs a heap object, not an OS thread. Final since Java 21; since Java 24 synchronized no longer pins the carrier it blocks on. The trade: waiting becomes cheap, computing does not, and the pool stops limiting concurrency.

The JVM knowledge gap it signals

You must know the waiting-to-computing ratio here, and where its threads stop being virtual — a native call holds its carrier until it returns. You must also know what replaces the pool as the gate. The gap question: is the measured waiting of this workload IO-blocking rather than CPU — and does anything still pin a carrier thread?

ImportantWhen the domain mandates it

An API gateway measured 92 percent of request time in downstream waits: 200 platform threads, 1,800 req/s, p99 240 ms, saturated at 210 concurrent. On virtual threads the same heap held 4,000 in-flight requests on 8 carriers — p99 90 ms, kilobytes of stack per parked request. A semaphore held 500 concurrent database calls, the number the pool could serve.

WarningWhen it’s a guess dressed as engineering

The seductive version: read “threads are cheap” and parallelize a CPU-bound job over 10,000 tasks. Nothing waits, nothing unmounts, every task holds a carrier to the end — throughput equals the carrier count. The pool then reappears as a virtual-thread “pool” capped at 500: it controls nothing, since creating one costs nothing and the semaphore was always the control.

TipThe faithfulness test

Is the measured waiting of this workload IO-blocking rather than CPU — and does anything still pin a carrier thread?

  • If yes → the win is the waiting, and the gate is a semaphore sized from the connection pool.
  • If no → you bought heap-resident stacks for a workload that computes, and you still need the pool.
  • If you can’t answer → unclear. You haven’t found the practice wrong — you’ve found incomplete workload knowledge. Sample thread states at peak, pinning event on.

Case study: Thread-pool sizing (a number that states a claim)

Mechanism: A platform thread pool carries one number, and that number asserts a task profile: on N cores, CPU-bound tasks want N threads, IO-bound tasks want N × (1 + waiting ÷ computing). The trade: the pool turns the claim into a ceiling and a queue — correct, the queue drains; wrong either way, the queue is where the damage shows.

The JVM knowledge gap it signals

The formula needs two measurements of your workload, CPU time per task and waiting time per task, taken at peak hour, not the average day. It also needs the consequence of a full queue. The gap question: what is the measured CPU-to-waiting ratio of these tasks — and who sized the pool from that number?

ImportantWhen the domain mandates it

An image service measured 12 ms of CPU and 60 ms waiting on object storage per task — a ratio of six — on 8 cores: 48 threads, a queue bounded at 200, a rejection handler returning 429. At 400 tasks/s it held p99 at 180 ms. The 32-thread pool before it ran the queue 40,000 deep at p99 9 s: same ceiling, latency in a queue no dump shows.

WarningWhen it’s a guess dressed as engineering

Two shapes, both respectable. A cached pool under IO load: threads are created until the load stops, so 3,000 threads at a megabyte of stack each, and a heap that dies before the queue fills. Or 4 × cores “for IO”, applied to tasks that block on a lock: the wait ratio is real, the conclusion is not, and the queue never drains.

TipThe faithfulness test

What is the measured CPU-to-waiting ratio of these tasks — and who sized the pool from that number?

  • If yes → the pool is a priced claim. Re-measure when the dependency changes, and read queue depth first.
  • If no → the number is a guess with a queue attached, which absorbs the error as latency.
  • If you can’t answer → unclear. You haven’t found the sizing wrong — you’ve found incomplete workload knowledge. Measure CPU time and wall time per task at peak, then divide.

Case study: Parallel streams (a shared pool you never sized)

Mechanism: parallel() splits a stream across the JVM-wide common ForkJoinPool — seven workers on an eight-core box — and joins the results. The trade: one line buys data parallelism, spent from an account every parallel stream shares, a pool whose size and failure behaviour nobody in your code chose.

The JVM knowledge gap it signals

The pool’s size is a default, its tenants are someone else’s code, and its work-stealing assumes tasks that finish on their own. You must know whether the operations are pure computation, whether the data amortizes the forking, and who else draws on the pool. The gap question: are the operations strictly CPU-bound and the data large enough to amortize forking — measured how, and who else shares this pool?

ImportantWhen the domain mandates it

A nightly report aggregates 10 million rows through a 12 µs arithmetic transform: 120 s serial, 18 s measured across seven workers, against a 17 s ideal. Nothing else in that JVM uses parallel streams then, and the transform allocates too little to make the collector a bottleneck.

WarningWhen it’s a guess dressed as engineering

The line reads fine. Then a downstream call goes inside the stream — 80 ms against a service that is usually fast — and it parks one of seven workers. Six concurrent requests saturate the common pool, and the unrelated report sharing it measured 4 s instead of 200 ms, its stack trace saying it waited. As common and cheaper: parallel() on a hundred elements, where splitting and joining outweigh the work.

TipThe faithfulness test

Are the operations strictly CPU-bound and the data large enough to amortize forking — measured how, and who else shares this pool?

  • If yes → the common pool is adequate, while nothing blocking enters the stream.
  • If no → you are spending a shared resource on work that does not repay it. Use a sequential stream, or a pool you own.
  • If you can’t answer → unclear. You haven’t found parallel streams wrong — you’ve found incomplete workload knowledge. Time the serial loop, then the parallel one, at your real element count.

Case study: ScopedValue (context with a visible lifetime)

Mechanism: A ScopedValue binds a value for the dynamic extent of a block — ScopedValue.where(TENANT, t).run(...) — readable inside, gone on return. Final in Java 25. The trade: you give up a mutable per-thread slot that survives until someone removes it, for cleanup that cannot be forgotten and inheritance from a task scope, still a preview in 25.

The JVM knowledge gap it signals

The question is not which API is newer; it is whether the context is immutable for the request’s life — mutate it downstream and the scoped version cannot express that. You must also know who owns the boundary: a value bound in the wrong scope is invisible where needed. The gap question: which context values are effectively immutable — and who guarantees the cleanup that ScopedValue makes structural?

ImportantWhen the domain mandates it

A service carries tenant, actor, and trace id four levels down into a data layer that reads them without an argument in any signature. On virtual threads at 4,000 concurrent requests it binds once at the edge and reads everywhere inside, with no remove() on nine exit paths. It measured no faster: the win is that handlers nobody wrote a cleanup for are correct.

WarningWhen it’s a guess dressed as engineering

ThreadLocal keeps working, which is the trap. A forgotten remove() lands on a reused platform thread, and the next task inherits the tenant — a defect that shows in logs, not in tests, which start fresh threads. Then the invisible-parameter variant: a method needing the user id takes no argument for it, so the dependency hides in every signature.

TipThe faithfulness test

Which context values are effectively immutable — and who guarantees the cleanup that ScopedValue makes structural?

  • If yes → bind them at the boundary of the work, and delete the remove() calls that guarded them.
  • If no → the context is mutable by design, and no scoping API fixes that; find the mutation.
  • If you can’t answer → unclear. You haven’t found ThreadLocal wrong — you’ve found incomplete workload knowledge. List every thread-local the path sets, and where each is cleared.

Case study: Container CPU detection (one number, many consumers)

Mechanism: The JVM reads the container’s CPU allowance at startup and publishes it through Runtime.availableProcessors(). GC threads, concurrent marking threads, the common ForkJoinPool, and the JIT compiler threads all size from that number. The trade: right-sizing when detection is right, correlated over-allocation when it is wrong.

The JVM knowledge gap it signals

You must know which number the runtime sees, which number the quota grants, and which of your settings came from it. Detection reads quotas and shares by rules that vary across cgroup versions: confirm it, do not trust it. The gap question: how many CPUs does the runtime actually see — and do the GC and ForkJoin thread counts agree with the quota rather than the host?

ImportantWhen the domain mandates it

A worker under a two-CPU quota reported availableProcessors 2: two parallel GC threads, common-pool parallelism 1, heap 1 GB, p99 collection pause 40 ms. Where detection returned 64 — shares set, no quota — the same worker ran 42 parallel GC threads inside two CPUs and spent 30 percent of its quota collecting. Setting ActiveProcessorCount=2 took that to 4 percent.

WarningWhen it’s a guess dressed as engineering

Latency rises, so heap is raised — the lever everyone trusts. Sixteen GC threads then share two CPUs, the collection has more heap to walk, and the pause grows, so the fix makes the symptom a memory problem for a quarter. The quieter variant: a ForkJoin pool of sixteen on the same two CPUs, matched to the host it was born on — sixteen workers for a quota that schedules two.

TipThe faithfulness test

How many CPUs does the runtime actually see — and do the GC and ForkJoin thread counts agree with the quota rather than the host?

  • If yes → the sizing chain is consistent, while quota and detection agree.
  • If no → every derived count is wrong at once. Set the count deliberately, then re-measure the collection share.
  • If you can’t answer → unclear. You haven’t found the flag wrong — you’ve found incomplete workload knowledge. Print the flag values at startup, then compare them with the quota.

Case study: AOT cache and ahead-of-time compilation

Mechanism: An AOT cache and ahead-of-time method compilation (Java 24–25, the Leyden work) move class loading, linking, and some code generation into the build: run the application once, record what it touched, ship what was learned. The trade is a training run and a cache artifact as build inputs, against code that never gets as hot as C2 would make it.

The JVM knowledge gap it signals

Two facts decide this, and teams rarely hold either: how long the process lives, as a distribution not a mean, and where the steady-state cost surfaces — p50 means every request pays it, p99 means only the saturated tail does. The gap question: what share of this process’s life is measured as startup-to-useful-work — and where does AOT’s steady-state cost land, p50 or only p99?

ImportantWhen the domain mandates it

Serverless handlers, command-line tools, short batch jobs: anywhere startup was measured at most of the process’s life. One team shipped a trained cache for a webhook handler and cut startup to first request from 1.4 s to 240 ms, because the linking that request needed had happened at build time.

WarningWhen it’s a guess dressed as engineering

The same cache shipped to a service that runs for weeks. Startup improves by a figure nobody disputes, and the regression surfaces as a fatter right tail on the busiest nodes, months later, blamed on the release after. The training run is the seductive part: a real measurement, taken once, against an artifact changed twice since — profiling a program that no longer exists.

TipThe faithfulness test

What share of this process’s life is measured as startup-to-useful-work — and where does AOT’s steady-state cost land: p50, or only p99?

  • If yes → the trade is cheap. Rebuild the training run in CI on every release.
  • If no → throughput was traded for noise. Measure sustained throughput with and without the cache.
  • If you can’t answer → unclear. Not a wrong practice — incomplete workload knowledge. Measure the lifetime distribution, then p50 and p99 at steady load.

Case study: JMH and the discipline of measurement

Mechanism: JMH runs warmup iterations, then measurement iterations, in forked JVMs, consumes every result through a black hole so the compiler cannot delete the work, and reports a confidence interval instead of a number. The trade is time and care — minutes per benchmark, code written for the harness rather than the product — against an answer that survives production.

The JVM knowledge gap it signals

Three facts about the measurement, not the code: whether steady state was reached before counting began, whether the timed work still existed after optimization, and whether variance between runs is smaller than the effect claimed. Without warmup you measure the interpreter’s first steps; with one fork you measure that fork’s luck. The gap question: was this “faster” claim measured with warmup, several forks, and dead-code control — or did it feel faster?

ImportantWhen the domain mandates it

Any decision that changes a hot path, or that will be argued in a design review. One team kept a serialization library only after measuring both: warmup discarded, five forks, a GC profiler attached, a 12% throughput gain whose confidence interval did not cross zero.

WarningWhen it’s a guess dressed as engineering

The plain main() with nanoTime around it, seductive because it looks honest: a real JVM, real input, real elapsed time. Three things vanish. Dead code — the result is never read, so the computation goes. Warmup — early iterations are interpreted, so two programs’ opening steps are compared. Fork isolation — one run in one JVM becomes the number in the ticket, carried into a migration nobody benchmarked.

TipThe faithfulness test

Was this “faster” claim measured with warmup, several forks, and dead-code control — or did it feel faster?

  • If yes → the number is an estimate with a range. Compare it to the effect size.
  • If no → it is not a measurement, it is an anecdote with units. Re-run it under a harness before it hardens into code.
  • If you can’t answer → unclear. Not a wrong practice — incomplete workload knowledge. Rewrite the benchmark in JMH with warmup, three forks, and a profiler.

#Java #JVM #JMH #Benchmarking #Performance #CausalKnowledge #SoftwareArchitecture

Case study: Java Flight Recorder, left on

Mechanism: JFR records runtime events — allocation, GC pauses, lock contention, code cache occupancy — into a bounded ring buffer, and it can stay enabled in production. The trade is a measured cost near one percent, plus storage discipline, against no evidence at the moment the anomaly arrives.

The JVM knowledge gap it signals

Whether the question you will ask at 3 a.m. is answerable from events the runtime already emits, and what always-on costs on this workload. One percent is a measurement, not a law: allocation-heavy services pay more. The gap question: can tonight’s anomaly be answered from recordings — and what does always-on cost, measured on this workload?

ImportantWhen the domain mandates it

A payments service kept a continuous recording at the default profile and measured 1.1% of CPU with no shift in p99. A nightly batch degraded three weeks later and the recording answered it from one file: allocation pressure in a single code path, a wrapper object built per row, inside the exact forty seconds everyone had argued about.

WarningWhen it’s a guess dressed as engineering

Two failures that look like opposites. “Enabled for emergencies only” sounds prudent, but the emergency is when no data exists, so the incident is argued from theory and the postmortem concludes “likely GC” without one allocation event. The other wears a lab coat: every event at maximum detail on the busiest nodes, until the observer effect is real and the team blames the release for the slowdown the configuration caused. Both are one gap: nobody measured observability’s cost on the workload carrying it.

TipThe faithfulness test

Can tonight’s anomaly be answered from recordings — and what does always-on cost, measured on this workload?

  • If yes → the evidence exists before the question does. Check retention and that files survive the node.
  • If no → the incident will be reconstructed from memory. Enable a bounded recording now.
  • If you can’t answer → unclear. Not a wrong practice — incomplete workload knowledge. Measure p99 and CPU with the recording on and off at peak.

Case study: The code cache and its eviction

Mechanism: The JVM reserves a bounded region for JIT-compiled code, sized by ReservedCodeCacheSize. When it fills, the runtime sweeps and frees compiled methods; if nothing can be freed, compilation stops and the affected methods run interpreted — an order of magnitude slower, no exception. The trade is memory reserved for compiled code against a silent ceiling.

The JVM knowledge gap it signals

Two facts: how fast this workload’s compiled-code footprint grows, and whether growth is bounded or continuous. A steady application plateaus; one that generates classes at runtime — proxies, lambda forms, script engines — climbs until it hits the ceiling. The gap question: what is the measured fill trend of the code cache — and when it fills, does an alert fire or does silence fall?

ImportantWhen the domain mandates it

A long-running application where the footprint was charted before the flag was touched: occupancy over a week, a slow rise at peak hours, a plateau under the default. The size was raised deliberately, fill curve in hand, kept as a dashboard so the next rise is a signal, not a surprise.

WarningWhen it’s a guess dressed as engineering

The value copied from a tuning guide, doubled to be safe. It removes the symptom and keeps the cause: if occupancy climbed because a library generates a class per request, a bigger ceiling buys weeks and arrives at the same cliff, further from the change that caused it. The quieter failure: hot methods fall back to the interpreter on a hot deployment, latency doubles, and the only symptom is a slow afternoon until someone reads occupancy. Nothing alerts — nobody decided a full cache was worth watching.

TipThe faithfulness test

What is the measured fill trend of the code cache — and when it fills, does an alert fire or does silence fall?

  • If yes → you know the slope and the ceiling. Watch the slope; a change in it is the finding.
  • If no → a latency cliff with no instrument. Chart occupancy, find what generates classes.
  • If you can’t answer → unclear. Not a wrong flag — incomplete workload knowledge. Sample occupancy across a week, including a redeploy.

Case study: Records and sealed hierarchies

Mechanism: A record states the type is a transparent carrier of its components: final fields, accessors, equals and hashCode from them. A sealed hierarchy states its implementations are a closed set, and an exhaustive switch turns a missing case into a compile error. The trade is two claims — value and closure — checked at compile time, against the flexibility classes grant.

The JVM knowledge gap it signals

Whether the domain makes those claims. A record is wrong when identity or mutation is part of the meaning; a sealed type when someone outside the module legitimately adds a case. Each is a statement about the domain, enforced by the compiler in every consumer. The gap question: is this set genuinely closed by the domain — and does the next variant break compilation everywhere, or break production somewhere?

ImportantWhen the domain mandates it

  • If yes → disable it and keep the visibility. Alarm on the replacement series.
  • If no → you are trading an instrument for disk hygiene. Find the consumers first.
  • If you can’t answer → unclear. You haven’t found the flag wrong — you’ve found incomplete workload knowledge. Check the effective flag on a live process, then trace who reads that file.
