GoF Design Patterns as Knowledge-Gap Indicators

A list of short posts that read each pattern as a completeness check on domain knowledge.

The GoF catalogue read as a completeness check: each pattern names a grouping the domain must already have decided — the product family, the algorithm family, the event, the part-whole recursion.

Pick a post on the left. It opens on the right.

Case study: Abstract Factory Pattern

Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Provide an interface for creating families of related or dependent objects without specifying their concrete classes.” [1]

The domain knowledge gap it signals

The set of concrete types that must vary together (the “product family”) is domain knowledge. If your domain model already crystallizes that “when you’re in context X, you use implementations A₁, B₁, C₁; in context Y, you use A₂, B₂, C₂” — and that these groupings are cohesive units in the domain (e.g., a regulatory regime, a hardware platform, a deployment tier) — then an Abstract Factory is just embodying that knowledge. The factory interface is the domain’s own abstraction; the concrete factories are its real partitions.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates product-family coherence but the language offers no native construct to express “these N types co-vary.” The Abstract Factory is a technical artifact that closes the gap — it prevents each client from individually selecting concrete types, which would scatter the family-binding knowledge across the system and create accidental coupling (every client must know which concrete A goes with which concrete B).

WarningWhen it’s inapplicable (cohesion-reducing)

The domain has no notion of product families. The concrete types vary independently. Forcing them into an Abstract Factory imposes a grouping the domain doesn’t recognize — it bundles change-drivers that are actually independent, creating a single point of modification for unrelated changes. That’s the cohesion-reducing move.

TipThe faithfulness test

What is the grouping, and where is it written?

  • If the grouping is on file, and each variant’s consumers name it the same way → applicable. The Abstract Factory is the code catching up to the knowledge.
  • If the grouping is on file, but two consumers assign a type to different variants → the meaning is not settled. Nobody has decided which reading binds in this system. A written definition records that decision; it does not make it.
  • If no text states the grouping, and the types vary on their own → inapplicable. It is the code inventing knowledge the domain does not have.
  • If you can’t answer → stop. The artifact to produce is the variant table with its owner named; the design does not ship until that table is on file.

Case study: Strategy Pattern

Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.” [1]

The domain knowledge gap it signals

The existence of multiple algorithms for the same operation is domain knowledge. If your domain model already crystallizes that “this operation admits variants A, B, C, and there is a domain rule that selects among them,” then Strategy is just embodying that knowledge. The strategy interface is the domain’s own abstraction (the what); the concrete strategies are its real alternatives (the how).

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates algorithmic substitutability — it recognizes that the operation meaningfully differs across contexts, and a domain rule dictates which variant applies. The Strategy pattern closes the gap: it prevents each caller from embedding variant-selection logic inline, which would scatter the selection rule across the system and create accidental coupling (every caller must re-encode which variant to use under which conditions). The pattern collects each variant behind a shared interface; the selection rule lives wherever the strategy reference is assigned.

WarningWhen it’s inapplicable (cohesion-reducing)

The domain has no notion of multiple algorithms for this operation. The “variants” are a decomposition artifact, not a domain partition — the developer split one algorithm into pieces for readability or reuse and wrapped them in a strategy interface as organizational glue. This imposes a grouping the domain doesn’t recognize: it bundles what the domain treats as one thing into an interface-plus-implementations structure, adding ceremony that signals a richness of variation that isn’t there. If the variants also pull in different data dependencies, Strategy scatters data-acquisition logic across implementations that must each independently discover their inputs.

TipThe faithfulness test

Does the domain recognize multiple algorithms for this operation as a real thing?

  • If yes → applicable. Strategy is the code catching up to the knowledge.
  • If no → inapplicable. It’s the code inventing variation the domain doesn’t have.
  • If you can’t answer → stop. The artifact to produce is the rule choosing between the algorithms, with its condition and its owner. Until it is on file, the code invents variation the domain does not have.

Case study: Observer Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.” [1]

The domain knowledge gap it signals

The fact that “a change in A constitutes a domain event that B, C, and D must know about” is domain knowledge. If your domain model already crystallizes that certain state transitions are meaningful events to other entities — that the event is a first-class domain concept — then Observer is just embodying that knowledge. The subject interface is the domain’s own event source; the observer interface is the domain’s own event consumer.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that certain state changes constitute events with multiple consumers, and the set of consumers is open-ended. Observer closes the gap — it prevents the event source from encoding the full list of consumers and their reaction logic inline, which would bundle every downstream concern into a single class and couple the event source to each consumer’s change-drivers.

WarningWhen it’s inapplicable (cohesion-reducing)

The “event” is not a domain event — nothing in the domain recognizes the state transition as meaningful in itself. B must recompute when A changes not because the domain treats A’s transition as an event, but because the developer chose to cache or denormalize. Observer used for technical consistency (UI model-view synchronization, the GoF’s canonical example) is valid engineering. The cohesion risk is when notification cascades for technical reasons (cache invalidation, denormalization-update chains) are presented as domain event propagation, inventing event semantics the domain model never had.

TipThe faithfulness test

Would the domain model this state transition as an event even if the system weren’t software?

  • If yes → applicable. Observer is the code catching up to the knowledge.
  • If no → inapplicable. It’s the code manufacturing events the domain doesn’t have.
  • If you can’t answer → stop. The artifact to produce is the event catalogue entry: the state transition, its name, and who must be told of it. Until it is on file, the code manufactures events the domain does not have.

Case study: Adapter Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Convert the interface of a class into another interface clients expect. Adapter lets classes work together that couldn’t otherwise because of incompatible interfaces.” [1]

The domain knowledge gap it signals

The fact that two entities must talk to each other but speak incompatible languages is domain knowledge. If your domain model already crystallizes that “system A understands protocol α, system B understands protocol β, and there is a domain rule requiring A and B to interoperate,” then Adapter is just embodying that knowledge. The adapter is the domain’s own translation rule; the adapted interface is the domain’s own target vocabulary.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates interoperability across a boundary the domain itself recognizes — a third-party service, a legacy subsystem, an external standard, a different bounded context. The adapter closes the gap: it isolates the translation logic in one place rather than forcing every caller of B to speak B’s protocol directly. Without it, each caller would embed translation logic inline, coupling unrelated code to B’s vocabulary and scattering the adaptation rule across the system.

WarningWhen it’s inapplicable (cohesion-reducing)

The “incompatibility” is not a domain boundary — it’s a pair of self-owned interfaces that encode the same concepts differently. Wrapping one in an adapter to match the other adds a permanent translation layer between abstractions that should be unified. Sometimes this is transitional — two teams built different interfaces that need reconciliation. But when the adapter becomes permanent without a unification plan, it institutionalizes an interface mismatch the domain never imposed. The distinguishing test is whether both sides have independent change-driver authorities: an adapter between domain port and infrastructure adapter (Hexagonal/Ports-and-Adapters) embodies a domain-imposed boundary, not duplication disguised as adaptation.

TipThe faithfulness test

Does the domain recognize the two sides of the adapter as genuinely separate things that must interoperate?

  • If yes → applicable. The adapter is the code catching up to the knowledge.
  • If no → inapplicable. It’s indirection the domain didn’t impose — which may still be legitimate if the sides have distinct authorities (e.g., domain port vs. infrastructure), but warrants unification if the same team owns both.
  • If you can’t answer → stop. The artifact to produce is the authority record: which side owns each model, and the contract that must be met across the seam. Until it is on file, the indirection serves an authority split nobody declared.

Case study: Builder Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Separate the construction of a complex object from its representation so that the same construction process can create different representations.” [1]

The domain knowledge gap it signals

The fact that constructing an object is a multi-step process whose steps are domain-significant — not just parameter-passing — is domain knowledge. If your domain model already crystallizes that “creating an X requires collecting parts A, B, C from different sources, in an order that matters, with validation between steps,” then Builder is just embodying that knowledge. The builder is the domain’s own construction protocol; each step is a domain operation.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that construction is a process, not a one-shot operation. The object cannot be created atomically because its parts come from different domain sources or require intermediate domain validation — and a partially-built object is a meaningful domain state (a draft, an incomplete form, a staged assembly). Builder closes the gap: it isolates the construction logic so the object doesn’t expose setters allowing mutation after construction, and so callers don’t each re-encode the construction sequence.

WarningWhen it’s inapplicable (cohesion-reducing)

The domain has no notion of incremental construction. All parts are available at once, and a partially-built object has no domain meaning. Builder is often reached for here to emulate named parameters — e.g., Pizza.builder().size(12).crust("thin").sauce("marinara") reads better than positional new Pizza(12, "thin", "marinara"…). But this ergonomics problem exposes a deeper gap: the constructor arguments are weakly typed. crust isn’t a String, it’s a Crust. Once the domain is properly typed — Pizza(Size, Crust, Sauce, Set<Topping>) — the constructor is self-documenting and Builder adds nothing. Builder here isn’t fixing a language limitation, it’s masking underspecified types.

TipThe faithfulness test

Does the domain treat “in the process of being built” as a real state?

  • If yes → applicable. Builder is the code catching up to the knowledge.
  • If no → inapplicable. Check first whether weak typing or some other issue is the real gap. When the domain is properly typed and construction is still painful, the language genuinely lacks expressive constructors — but this is rare and worth distinguishing from a type-design gap.
  • If you can’t answer → stop. The artifact to produce is the staged-construction rule: which fields must be set before the thing is valid, and in what order. Until it is on file, the builder enforces a staging the domain never named.

Case study: Command Pattern

🔥 A design pattern is a completeness-check on domain knowledge — not a verdict that patterns are useless, but a probe for whether the domain justifies one.

When you’re reaching for a pattern, ask “does the domain mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the domain prescribes the structure directly.

GoF Intent: “Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations.” [1, p. 233]

The pattern decouples invoker from receiver — the invoker must NOT know which concrete receiver handles the request. This is structural: the invoker dispatches to a Command interface and stays receiver-agnostic. (Queuing, logging, and undo follow from the encapsulation.)

The knowledge gap it signals

Command needs the invoker to be receiver-agnostic. The question is not “would the domain break if the invoker knew?” — the pattern exists because the invoker must NOT know. The gap: does your architecture need receiver-agnostic dispatch?

ImportantWhen it’s needed

The invoker must dispatch to different receivers without knowing which at compile time: a menu dispatches to dialogs, a scheduler to job handlers, a transaction manager to rollback actions, an event bus to subscribers. The invoker cannot name the receiver — requests are queued, parameterized, or submitted by unknown clients. Command closes the gap: the interface abstracts over receivers the invoker was never meant to know.

WarningWhen it’s not needed

The invoker always calls the same concrete receiver. Wrapping every service-method invocation in a Command interface because “we might need undo later” adds indirection where the invoker already knows its target. The interface adds maintenance and dispatch overhead to a call that should be direct. Command here guesses at flexibility no requirement demands.

TipThe faithfulness test
  1. What does the invoker need to dispatch without knowing, and where is that written?
  2. Is there more than one receiver, or will the receiver be determined at runtime — and does a written rule say which receiver serves which request?
  3. Decide. If both answers are on file → applicable (Command provides the receiver-agnostic dispatch your architecture needs). If no rule names a second receiver → inapplicable (call directly). If you can’t answer → stop: the dispatch rule is the artifact to produce, and until it exists the receiver choice is the code’s.

CQS/CQRS “Command” is a different concept — a message that mutates state (contrast: Query) — and is not covered here.

Case study: Composite Pattern

🔥 Almost every design pattern can be used as a completeness-check on domain knowledge.

When you reach for a pattern, ask: “does the domain knowledge prescribe the structure this pattern would add?” If you cannot answer, you found a knowledge gap — the domain model is incomplete. If you can answer, the domain knowledge prescribes the structure; the pattern codifies what the domain already dictates.

GoF Intent: “Compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.” [1]

The GoF Composite pattern composes objects into tree structures to represent part-whole hierarchies. It lets clients treat individual objects and compositions of objects uniformly through a shared Component interface.

The domain knowledge gap it signals

The domain recognizes a part-whole hierarchy where the whole and its parts answer the same questions. A department and its sub-departments both have budgets. A file and a directory both have sizes. When you find yourself reaching for Composite, the gap is: does the domain actually treat wholes and parts uniformly, or are you imposing a tree structure on something the domain views as flat or differently?

ImportantWhen the pattern follows domain knowledge

The domain has genuine part-whole recursion where the same operations apply at every level. Making “a department contains sub-departments, and both compute a budget” explicit in the domain model is the work. Composite’s uniform interface then prevents callers from branching on “is this a single thing or a group?” before every operation — the hierarchy delegates recursively, and callers operate on the abstract type.

WarningWhen the pattern overreaches

The domain has no part-whole recursion. The hierarchy is a tree-shaped data structure for navigation convenience, not a domain fact. UI component trees are the GoF’s canonical Composite example and are valid — they address the domain of UI toolkit design, where the part-whole relationship IS the problem space. A file-system directory tree is domain recursion; an internal cache organized as a tree for lookup efficiency is not. When the hierarchy is artificial, leaf types implement operations that make no sense for them — a structural mismatch the domain did not create.

TipThe faithfulness test

Does the domain say “an X is either a single thing or a group of things, and both answer the same questions”?

  • If yes → applicable. The pattern codifies what the domain already dictates.
  • If no → inapplicable. The tree structure may still be valid — valid in infrastructure domains (UI toolkits, scene graphs, ASTs) where the part-whole relationship IS the problem space — but misplaced where the domain has no recursion.
  • If you can’t answer → stop. The artifact to produce is the part-whole rule: what the whole answers, and which of its parts are answered the same way. Until it is on file, the tree is imposed on a domain with no recursion.

Case study: Decorator Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly.

GoF Intent: “Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.” [1]

The domain knowledge gap it signals

A decorator adds behavior without changing the interface or what the object is. Domain intuition: a paper invoice through administration. One office stamps “PAID” — still an invoice, now endorsed. Another stamps “CONFIDENTIAL” — still an invoice, now classified. Each endorsement decorates without changing identity; for clients it is still the same object. The gap: what is intrinsic to the entity vs. an optional endorsement. An unpaid invoice is still an invoice — “paid” is an endorsement, not part of what makes it an invoice. Baking payment status into the invoice class reveals the gap.

ImportantWhen it’s applicable (cohesion-increasing)

A responsibility is optional — some objects need it, others don’t. Without Decorator, independent endorsements must be enumerated by subclass, conditional-branch, or enum state. For fully independent endorsements factoring into 2ⁿ combinations, that is an explosion the domain never created. Each decorator stays a single endorsement.

WarningWhen it’s inapplicable (cohesion-reducing)

The wrapping transforms the object’s semantics instead of endorsing it. Tax calculation that changes the invoice total is Pipes and Filters: sequential transformations producing a semantically different result, not a stamp. Decorator preserves contract meaning — the invoice is still an invoice after every endorsement. If wrapping changes what the thing is, you are not decorating.

Also inapplicable when the added behavior is independent of the causal domain — pure orthogonal wrapping (logging, caching, auth, retry): a business-agnostic interceptor, not a domain endorsement. The GoF’s examples (scrollbars, borders, buffered streams) are infrastructure. The pattern’s domain value emerges when the business operates through endorsements on stable documents: approvals, certifications, status stamps.

TipThe faithfulness test

Can each responsibility be attached or removed without changing what the object is, and does a written rule list which responsibilities the thing carries?

A “PAID” stamp doesn’t make an invoice something else, and the invoice rule names the stamp → applicable (Decorator). Tax wrapper changes the total that the price rule fixes → inapplicable (Pipes and Filters, not Decorator). If no rule lists the responsibilities → stop: write the list, then re-run the test. Until it is on file, you have found incomplete knowledge, not a wrong pattern.

Case study: State Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Allow an object to alter its behavior when its internal state changes. The object will appear to change its class.” [1]

The domain knowledge gap it signals

That an entity’s behavior depends on which state it’s in — and that the set of states and the transitions between them are domain rules — is domain knowledge. If your domain model already crystallizes a state machine — “an order starts as Pending, can transition to Confirmed or Cancelled, and in each state different operations are allowed” — then State is just embodying that knowledge: each state is a domain state; each transition is a domain rule.

ImportantWhen it’s applicable (cohesion-increasing)

The domain recognizes a state machine: a finite set of states, well-defined transitions, and behavior that varies per state. The state table records those states and transitions, with its owner named. State preserves the domain’s own boundaries: one module per domain state, keeping each state’s rules with its state.

Lifecycle vs interchangeable choice is the discriminator. State is right only when switching behavior is the object moving through stages of a lifecycle — each stage follows from and leads to others. If the switches pick between interchangeable alternatives with no ordered progression, the domain describes a Strategy, not a State machine.

WarningWhen it’s inapplicable (cohesion-reducing)

The “states” are not domain states — they’re status flags with no behavioral variation. An entity carries several independent flags, each its own domain notion: active, verified, and premium are each judged on their own. Collecting these into one lifecycle and treating each combination as a state only works if the domain recognizes a lifecycle over those combinations — but it doesn’t. The domain expert sees three separate facts, not stages that follow one another.

TipThe faithfulness test

What is the state table, and where is it written?

  • If the table is on file, and every consumer names the states and their transitions the same way → applicable. State is the code catching up to the knowledge.
  • If the table is on file, but two consumers disagree on what a state permits → the meaning is not settled. Nobody has decided which reading binds in this system. A written definition records that decision; it does not make it.
  • If no text states a lifecycle, and the flags are judged one by one → inapplicable. It is boolean flags encoded as a state machine — the domain does not define a lifecycle over these combinations.
  • If you can’t answer → stop. The artifact to produce is the state table with its owner named; the design does not ship until that table is on file.

A second check: does the object appear to change its class when it changes state — does its whole behavior repertoire shift? Real states do. Flags merely flip a bit; the behavior was never different.

Case study: Template Method Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Define the skeleton of an algorithm in an operation, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm’s structure.” [1]

The domain knowledge gap it signals

The fact that operations share an invariant skeleton with variant steps can be domain knowledge — but only when the skeleton itself is a domain rule. If your domain model already crystallizes that “the regulatory review process has the same framework (notify, review, approve) regardless of jurisdiction; only the steps within each phase differ,” then Template Method is just embodying that knowledge. The base class is the domain’s own procedural framework; the hook methods are the domain’s own variation points. In most applications, however, the “skeleton” is code similarity mistaken for domain structure — the domain expert sees one coherent algorithm, not a template with extension points.

ImportantWhen it’s applicable (cohesion-increasing)

The domain recognizes the skeleton as a domain-invariant process: a regulatory framework, a certification pipeline, a protocol with mandated phases. Template Method closes the gap: it prevents each implementation from re-encoding the invariant sequence, which would scatter the procedural knowledge across the system and risk divergence. The base class is the domain’s own “these steps always happen in this order” rule; the concrete subclasses fill in the domain’s own variation points.

WarningWhen it’s inapplicable (cohesion-reducing)

The skeleton is code similarity, not domain structure. “ReportGenerator has a generate() method that calls openFile(), writeData(), closeFile() — and CSV and PDF differ only in writeData().” The domain doesn’t recognize openFile/writeData/closeFile as a legitimate decomposition — it sees “generate a report.” Template Method here encodes a technical sequence (file open/write/close) as if it were a domain invariant, coupling all report types to a file-based implementation. When a report type arrives that doesn’t use files, the template breaks.

TipThe faithfulness test

Can you state the invariant skeleton as a domain rule without mentioning implementation details?

  • If yes → applicable. Template Method is the code catching up to the knowledge.
  • If no → inapplicable. It’s code similarity mistaken for domain invariance.
  • If you can’t answer → stop. The artifact to produce is the skeleton rule, written without naming any implementation step. Until it is on file, code similarity is mistaken for domain invariance.

Case study: Facade Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Provide a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.” [1]

The domain knowledge gap it signals

The fact that a subsystem presents a single entry point — that “to interact with this part of the system, you go through here” — is domain knowledge if the boundary is a domain boundary. If your domain model already crystallizes that “ordering involves inventory, payment, and shipping, but from the customer’s perspective it’s one operation,” then Facade is just embodying that knowledge. The facade is the domain’s own simplified interface; the subsystem behind it is the domain’s own internal complexity.

ImportantWhen it’s applicable (cohesion-increasing)

The domain recognizes a bounded context: a cluster of related operations that outsiders should consume through a single, simplified interface. Case study: Visitor Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Represent an operation to be performed on the elements of an object structure. Visitor lets you define a new operation without changing the classes of the elements on which it operates.” [1]

The domain knowledge gap it signals

The fact that an operation must be defined over a fixed set of element types — and that new operations are added more often than new element types — is domain knowledge. If your domain model already crystallizes that “a tax rule must be applied to every kind of financial instrument (stock, bond, derivative), and new tax rules appear more frequently than new instrument types,” then Visitor is just embodying that knowledge. The element hierarchy is the domain’s own stable taxonomy; each visitor is a domain operation that must handle every case.

ImportantWhen it’s applicable (cohesion-increasing)

The domain has a stable type hierarchy and a family of operations that must be exhaustive over it. Visitor closes the gap: it prevents each operation from being scattered across the element classes as a method, which would couple the element hierarchy to every operation’s change-drivers. Adding a new operation means adding one visitor class, not modifying every element.

WarningWhen it’s inapplicable (cohesion-reducing)

The distinction depends on hierarchy stability, exactly the GoF’s design trade-off. AST visitors over syntax trees, the GoF’s canonical example, are valid: compiler construction IS a domain, and AST traversal IS a domain operation. The inapplicable case is when the hierarchy genuinely IS unstable — new element types arrive frequently, requiring modification of every visitor. The GoF explicitly warn against Visitor in this scenario. In languages with pattern matching over sum types (modern Java, Scala, Rust), Visitor’s double-dispatch machinery is largely redundant — but without it, Visitor remains the standard encoding. The faithfulness test separates genuinely stable taxonomies (financial instruments, document types) from those that change next sprint.

TipThe faithfulness test

Does the domain have a stable taxonomy of element types, and do operations over that taxonomy arrive more frequently than new element types?

  • If yes → applicable. Visitor is the code catching up to the knowledge.
  • If no → inapplicable. The hierarchy is unstable — or your language already has pattern matching over sum types, making Visitor’s double-dispatch unnecessary.
  • If you can’t answer → stop. The artifact to produce is the taxonomy and its change record: the element types, and which of the two directions has changed more often. Until it is on file, double dispatch is added to an unstable hierarchy.

Case study: Interpreter Pattern

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

When you’re reaching for a pattern, ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

GoF Intent: “Given a language, define a representation for its grammar along with an interpreter that uses the representation to interpret sentences in the language.” [1]

The domain knowledge gap it signals

The fact that the domain has its own language — a grammar, a syntax, and rules for evaluating sentences in that language — is domain knowledge. If your domain model already crystallizes that “a trading system has a domain-specific language for defining trading strategies; a rule engine evaluates expressions like ‘if risk > threshold and exposure > limit, then reject’,” then Interpreter is just embodying that knowledge. The grammar is the domain’s own syntax; each expression type is a domain concept.

ImportantWhen it’s applicable (cohesion-increasing)

The domain has a well-defined grammar that domain experts use to express rules, queries, or configurations — and the grammar is stable enough to justify encoding it as a class hierarchy. Interpreter closes the gap: it gives each grammar rule its own class, so a new expression type adds one class rather than modifying a monolithic parser. The parse tree is the domain’s own sentence structure; the interpret() method is the domain’s own evaluation rule.

WarningWhen it’s inapplicable (cohesion-reducing)

The “language” is not a domain language — it’s a configuration format, a query syntax, or a wire protocol the developer designed. The developer defines a grammar, creates a class per production, and builds an interpreter — but the domain expert would never write a sentence in this language; they’d fill out a form or click a button. Interpreter here adds a class hierarchy for every grammar rule, coupling the grammar to the implementation so that changing the syntax means changing the class structure. A parser generator or a simple recursive-descent parser would handle the same task without institutionalizing the grammar as a class hierarchy.

TipThe faithfulness test

Would the language’s vocabulary serve a recurring need where the grammar is stable enough to justify encoding as a class hierarchy — and would domain experts recognize the language’s expressions as things they reason about?

  • If yes → applicable. Interpreter is the code catching up to the knowledge.
  • If no → inapplicable. It’s a parser for a technical language — valid when the grammar is stable and the language serves a real need, but not a domain language the domain expert would recognize.
  • If you can’t answer → stop. The artifact to produce is the grammar: the expressions the business writes, and the rule that makes the set closed. Until it is on file, a parser is built for a language the business does not speak.
