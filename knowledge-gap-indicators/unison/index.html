Unison

Abilities and content-addressed definitions.

Effects are declared in types, and a definition’s hash is its identity. Each post asks which knowledge the type carries and which the hash replaces.

Pick a post on the left. It opens on the right.

Writing Unison? Ask “which knowledge does the signature carry, and which does the definition hash replace?” If you can’t answer, you’ve found a knowledge gap: the effect is undeclared or the dependency unpinned. If you can, the signature is knowledge embodied — the codebase recording what the domain decided.

Case study: Abilities (effects in the signature)

A function that logs, reads the clock, and can fail carries all three in {IO, Exception} — visible before the first line runs.

Writing a Unison definition? Ask “which fact does the hash and the signature carry — what this does, which version this is — and what can no longer be a guess?” If you can’t answer, you’ve found a knowledge gap. If you can, the definition is knowledge embodied — the codebase catching up to what the program means.

Mechanism: In Unison’s documented model an ability declares operations, and a function’s type records the abilities it requires: {} pure, {IO} writing. A call site must handle each one or propagate it, so effects travel inside the type. The trade: no effect hides behind the signature, at the cost of threading abilities through every caller in between.

The Unison knowledge gap it signals

The developer must know which effects the program performs — which reads, which writes, which failures — and who is responsible for each. An ability in a type is a claim about how the function touches the world; a handler is a claim about where that responsibility stops. A signature assembled by habit describes a program nobody verified.

The gap question: does the effect set name every way this function touches the world?

ImportantWhen the types encode reality

A report job that reads a file and writes a summary needs {IO}; a validator with no effects gets {}, and the compiler will not let it print. Every caller shows what it inherits, so the boundary where effects are discharged — one main, one test harness — is visible in the types.

WarningWhen it’s a guess dressed as engineering

The team arrives from a language where the type read Promise<User> and the database call inside was invisible. A review step grew to catch what the compiler did not: does this touch the database, can this throw. In Unison that step hunts effects the signature already lists, and what remains is a checklist that always passes. The trap is keeping the ceremony and calling it rigor.

TipThe faithfulness test

For each function: do its effects match its signature — and is that checked by the compiler or by hope?

  • If yes → the signature is the contract. Check that each ability is handled where the program wants the responsibility, not merely somewhere.
  • If no → the type does not describe the function. Narrow the ability set, or move the effect to its handler.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. List what it reads, writes, and can fail with, then compare it to the type.

Case study: Content-addressed definitions

Rename a function across a thousand files and its hash does not move; change one character inside it and every dependent’s hash does.

Writing a Unison definition? Ask “which fact does the hash and the signature carry — what this does, which version this is — and what can no longer be a guess?” If you can’t answer, you’ve found a knowledge gap. If you can, the definition is knowledge embodied — the codebase catching up to what the program means.

Mechanism: In Unison’s documented model a definition’s identity is a hash of its normalized form, including the hashes of everything it references; the name is a separate, editable annotation. Renaming changes nothing, and an edit changes its hash plus every definition above it. The trade: an identity that cannot drift, against a name that no longer tells you what you are calling until you follow it.

The Unison knowledge gap it signals

The developer must know which definitions the program depends on at the level of the individual definition, not the repository. “We use library X” becomes a set of hashes, and two identical-looking call sites may sit on different ones.

The gap question: for each shared definition, is the consumer’s copy the same definition, or a copy that drifted?

ImportantWhen the types encode reality

Two codebases referencing the same hash hold provably identical code — not “the same version”, the same term. A security review or an audit transfers with the hash: whoever verified that hash verified the code your build runs; a measurement does not — it describes one run.

WarningWhen it’s a guess dressed as engineering

A helper “shared” by two services, edited on separate days, now sits at two hashes with quietly different behavior — and in Unison the divergence is visible, because the hashes differ. The seductive trap runs the other way: believing a shared name means shared code. A name is a claim; the hash is the fact, and a diff between hashes is not a formality.

TipThe faithfulness test

For each shared function: which hash do the consumers reference — and is any divergence visible, or buried in git blame?

  • If yes → the hash is the identity. Compare the hashes across consumers that claim to share a definition; a mismatch is a fork, not a version.
  • If no → the name is carrying an identity it cannot. Record the hash where the dependency lives, and compare before assuming behavior.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Check whether “same function” is a claim about a name or about a hash.

Case study: The escape hatches that do not exist

A function that can fail returns Either Failure Success — no caller reaches the success path without matching the failure first.

Writing a Unison definition? Ask “which fact does the hash and the signature carry — what this does, which version this is — and what can no longer be a guess?” If you can’t answer, you’ve found a knowledge gap. If you can, the definition is knowledge embodied — the codebase catching up to what the program means.

Mechanism: In Unison’s documented model there is no null and no unchecked exception: absence is Optional a, failure is Either e a, and a partial operation such as list head returns an Optional rather than throwing. Matching is exhaustive, so a new case breaks every match with no wildcard branch. The trade: every case is handled where it arises or carried explicitly to a caller, against the verbosity of matching at each step.

The Unison knowledge gap it signals

The developer must know which failures the domain admits and what should happen at each, because the type is now the list of them. The construct forces the belief open: a crash and an unhandled None are both statements about what the program assumes.

The gap question: is every failure a caller can meet named in the return type?

ImportantWhen the types encode reality

A parser returns Either ParseError Ast, so the syntax error is a value the caller destructures and reports; adding a second error case fails compilation at every match that assumed one. Nothing reaches Right by accident, and no failure survives only as a log line.

WarningWhen it’s a guess dressed as engineering

The habit from other languages: a defensive check for the value that cannot be null, a catch-all handler around a call that cannot throw. Both compile. Then the optimism returns as a wildcard match branch that turns exhaustiveness back into a guess, or a helper that crashes on None, reinstating the exception the language removed. The compiler audits the match; it does not audit the wildcard you added to silence it.

TipThe faithfulness test

For each failure path: is it in the return type — where every caller sees it — or in an exception nobody declared?

  • If yes → failure is data. Check that each match names every case, and that no wildcard branch hides a case someone must handle.
  • If no → failure is an implementation detail, invisible at the boundary. Return it as a value, or declare it in the signature.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. List how each call can fail, then read the type back.

Case study: The codebase as a database

Nothing in the build says “4.2.x”. It says the hash of one definition, and that definition is the one that runs.

Writing a Unison definition? Ask “which fact does the hash and the signature carry — what this does, which version this is — and what can no longer be a guess?” If you can’t answer, you’ve found a knowledge gap. If you can, the definition is knowledge embodied — the codebase catching up to what the program means.

Mechanism: In Unison’s documented model the codebase is a database of definitions keyed by hash, and a dependency is a set of exact hashes rather than a package version. There is no range to resolve and no “compatible with 4.2.x” — either the definition your code calls is present, or it is not. The trade: the build’s contents are decidable in one lookup, against ranges that let a patch version flow in without a decision.

The Unison knowledge gap it signals

The developer must know which definition each dependency resolves to, and for each upgrade what actually changed. A range encodes a hope about compatibility; an exact hash encodes a fact somebody recorded. “Which version am I running” stops being archaeology and becomes a lookup — so the honest answer is available, and therefore expected.

The gap question: for each dependency, can you name the definition the build contains?

ImportantWhen the types encode reality

An upgrade is deliberate: a dependent moves to a new hash, its own hash changes, and every consumer of it sees a hash it must re-verify. Nothing arrives by accident through a resolved range, and two builds of one commit contain the same definitions by construction.

WarningWhen it’s a guess dressed as engineering

The range “4.2.x” that behaves two ways in two builds, and a lockfile cited as proof that the code is known. A lockfile records what a resolver chose; it does not name definitions, so two lockfiles can agree on a version string while the code underneath differs. Carry that habit over and “we pin it” becomes a sentence nobody can check.

TipThe faithfulness test

For each dependency: which exact definition does this build contain — answerable in one lookup — or is it a range and a hope?

  • If yes → the dependency is pinned to a definition. Check that the hash in the build is the hash anyone reviewed.
  • If no → compatibility is a belief, not a record. Replace the range with the hash you verified, and note what changed.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Read the dependency’s hash out of the codebase, then read its diff.

Case study: Publishing and consuming definitions

A consumer does not depend on “the library” — it depends on eleven definitions inside it, each one pinned by hash.

Writing a Unison definition? Ask “which fact does the hash and the signature carry — what this does, which version this is — and what can no longer be a guess?” If you can’t answer, you’ve found a knowledge gap. If you can, the definition is knowledge embodied — the codebase catching up to what the program means.

Mechanism: In Unison’s documented model publishing makes a codebase’s definitions available, and consuming brings a definition into your own codebase by its hash, where it can be browsed and diffed like local code. The trade: upgrades become explicit — take one function’s new version and leave the rest — against a project that tracks many hashes and keeps docs as a separate artifact.

The Unison knowledge gap it signals

The developer must know what the consumer actually uses, and what changed between two hashes of it. “We use the whole library” stops being true once the dependency is a set of definitions, and the set says which ones you took. A changelog is someone’s summary of a diff; the diff is available, so the summary is convenience, not evidence.

The gap question: can a consumer state, definition by definition, what it depends on?

ImportantWhen the types encode reality

A library’s consumers pin exact hashes, and an upgrade is a reviewed hash change per definition. A consumer using four of a hundred definitions says so, and a change to any definition the four do not reach never enters that consumer’s build — the pinned set is the dependency and the inventory of trust.

WarningWhen it’s a guess dressed as engineering

The hand-maintained changelog, drifted from the code: “Renamed X” when the break was a changed error type, no entry because nobody wrote one. In Unison “what changed” is answered by comparing hashes and reading the term diff, so the trap is trusting the prose, not the hash — and releasing under a label that promises more than the definitions deliver.

TipThe faithfulness test

Can a consumer state exactly which definitions it depends on — by hash — or does “what changed” live in a document someone forgot?

  • If yes → the dependency set is the contract. Check that each pinned hash was reviewed, and diff the old and new before releasing.
  • If no → a label carries the claim. Publish the hashes, and let consumers pin what they verified.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. List the definitions the build contains, then diff them against the ones you meant.
