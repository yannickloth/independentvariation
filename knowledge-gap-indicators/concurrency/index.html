Concurrency Constructs as Knowledge-Gap Indicators

A list of short posts that read each pattern as a completeness check on domain knowledge.

The concurrency constructs below encode facts about the workload: what may interleave, what must be ordered, how long a wait is acceptable, and how much may fail together.

Pick a post on the left. It opens on the right.

Case study: Actor Model

Hewitt et al.: The actor model represents concurrency as independent actors that communicate only by asynchronous messages. [1]

An actor is an isolated unit that owns its state and processes arriving messages one at a time.

The domain knowledge gap it signals

The fact that a domain entity owns its state and reacts to the work that arrives to it is domain knowledge. If your domain model crystallises that “this entity processes its work one unit at a time, in isolation, and the only way to influence it is to hand it a new unit of work,” then the Actor Model embodies that knowledge. The heart of an actor is the behaviour: the entity’s own rule for each unit of work. However the code is dressed, this entity owns its state and changes it only in response to what it received.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates that each entity is a self-contained unit that owns its state and changes it only in response to the work it is given. Actors close the gap: they stop outside code from reaching in and rewriting that state, which would scatter ownership across every caller. The queue of arriving work is the domain’s own “work is consumed as it arrives” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the domain treats the work as one immediate, ordered step with nothing to protect. The actor still looks technical, but it is a domain decision: someone chose to model this work as an isolated entity with a queue. It fits only when the domain names the state ownership and the queue as requirements. If not, the actor asserts a boundary nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Would a domain expert describe this entity as owning its state and responding to the work it is given — a thing that “handles what arrives, in isolation,” not a thing you reach into and change?

  • If yes → applicable. The Actor Model is the code catching up to the knowledge.
  • If no → inapplicable. The construct asserts an ownership boundary the domain never drew. Decide it, or use a plain call that does not invent one.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Semaphore / bounded resource

Dijkstra: A semaphore is an integer with atomic wait and signal operations used to coordinate access to a shared resource. [2]

A semaphore is a counter that limits how many tasks may use a shared resource at once.

The domain knowledge gap it signals

The fact that only a fixed number of these things may be in use at once is domain knowledge. If your domain model already crystallises that “there are exactly eight loading docks,” “we hold at most fifty concurrent licences,” or “the lot has two hundred spaces,” then the bound is a fact about the world. A semaphore is that fact made executable. The count is the domain’s own “how many can exist at once” rule; the acquire/release discipline is the domain’s own “hold one only while the world lends it” rule.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates a hard ceiling on concurrent use, and exceeding it is a domain error, not just a slowdown. A semaphore closes the gap: it stops the code from treating a limited resource as unlimited, which would let callers exceed a limit the world does not permit. The permit count is the domain’s own capacity; the wait is the domain’s own “queue until one frees” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the bound looks like a performance knob — a connection-pool size, a thread count, a rate limit. But even a capacity limit is a domain decision: someone chose the bound. A semaphore fits only when the domain names the resource as a bounded shared pool. If the number is an arbitrary, freely changeable knob, the domain has not named a bound, and the semaphore asserts a constraint nobody decided. That is the gap — the bound is unwritten.

TipThe faithfulness test

Would a domain expert name the limit — “eight docks, fifty licences, two hundred spaces” — as a fact of the business rather than a setting someone picked?

  • If yes → applicable. The Semaphore is the code catching up to the knowledge; the count is the domain’s own capacity.
  • If no → inapplicable. The count asserts a bound the domain never set. Name the bound, or use a plain limiter that does not claim one.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Read-Write Lock

Courtois et al.: A readers-writer lock permits concurrent readers or a single writer. [3]

The domain knowledge gap it signals

The fact that many parties may look at the same thing at once, but only one may change it, is domain knowledge. If your domain model crystallises that “a timetable may be read by every dispatcher while a single edit is in flight,” or “a catalogue may be browsed while one price is corrected,” then the read-write asymmetry is a fact about the world, not a performance guess. A read-write lock is that fact made executable: readers share, writers exclude.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain distinguishes observation from modification, and the two are asymmetrically compatible — many observers may coexist, but a change must be alone. A read-write lock closes the gap: it gives readers concurrent access while keeping the writer exclusive, which is the domain’s own “look freely, change carefully” rule. Using a plain mutual-exclusion lock instead would needlessly serialise observers the domain says may proceed together.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the “readers” and “writers” split may look purely technical. But it is still a domain decision: someone claimed these operations differ in kind. A read-write lock fits only when the domain names observation and modification as distinct activities. When everything is an update, the domain has not named that distinction, and the second lock state and writer-starvation risk assert a role nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the domain treat reading and changing this thing as genuinely different activities — many may look, one may alter — or is that distinction only about performance?

  • If yes → applicable. The Read-Write Lock is the code catching up to the knowledge; observers and changers are domain roles.
  • If no → inapplicable. The split asserts an observer role the domain never named. Name the distinction, or use a plain mutex that does not invent one.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Producer–Consumer

Dijkstra: A producer–consumer system decouples production from consumption through a bounded buffer. [2]

The domain knowledge gap it signals

Producer–Consumer is a pattern where one side adds work to a queue and the other takes it off. The fact that work arrives on one rhythm and is handled on another is domain knowledge. If your domain model crystallises that “orders arrive whenever customers click, but the kitchen cooks one ticket at a time,” then the queue is not an optimisation — it is the domain’s own buffer between two activities that run at different rates, with the bounded queue as the domain’s own “we can hold only so much waiting work” rule.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain contains two distinct activities — arrival and handling — that proceed at different rates, and the gap between them is real waiting work. Producer–Consumer closes the gap: it prevents the arrival side from being coupled directly to the handling side, which would force clicks to block on cooking and cooking to be paced by clicks. The queue decouples the rhythms the domain already treats as separate.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the domain sees one immediate, ordered step: the work arrives and is done in the same breath, with no waiting state. A queue still looks technical, but it is a domain decision: someone claimed arrival and handling are separate. Producer–Consumer fits only when the domain names a real waiting state. If not, the queue asserts a waiting room nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the domain have a real waiting state — work that has arrived but is not yet handled — or is arrival and handling one immediate act?

  • If yes → applicable. Producer–Consumer is the code catching up to the knowledge; the queue is the domain’s own waiting room.
  • If no → inapplicable. The queue asserts a waiting state the domain never named. Name it, or use a direct call that does not invent one.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Barrier (phase synchronization)

Goetz et al.: A barrier makes a set of threads wait until all have reached a common point. [4]

A barrier makes every participant wait until all have arrived, then releases them together.

The domain knowledge gap it signals

The fact that a stage cannot begin until all participants have finished the prior stage is domain knowledge. If your domain model crystallises that “the meeting cannot start until every attendee has arrived,” or “the tally is only valid once every ward has reported,” then the barrier is the domain’s own rendezvous rule made executable.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates a rendezvous: the next step is well-defined only when every participant has completed the current one, and a partial set is meaningless. A barrier closes the gap: it stops fast participants from racing ahead into a stage the domain says is not yet valid, which would let a premature actor act on an incomplete world. The barrier is the domain’s own “wait for all” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the “wait for everyone” looks like a technical staging device — a synchronisation point that exists because one task happens to depend on several results. But it is still a domain decision: someone claimed the participants form one collective. A barrier fits only when the domain names the group as a real unit and the moment as shared. If the domain has not named a collective, the all-must-arrive rule asserts one nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the domain treat the stage as meaningful only when all participants have completed the prior one — is the group itself a domain entity?

  • If yes → applicable. The Barrier is the code catching up to the knowledge; the rendezvous is the domain’s own rule.
  • If no → inapplicable. The rendezvous asserts a collective the domain never named. Name it, or use a future or gather that does not invent one.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Double-Checked Locking / lazy initialization

Goetz et al.: Double-checked locking tests a flag, then locks and tests again before creating an object, to avoid locking on the common path. [4]

Double-checked locking tests a flag first, then locks and tests again before it creates the object.

The domain knowledge gap it signals

The fact that this thing should not come into existence until it is first needed is domain knowledge. If your domain model crystallises that “a ledger is opened only when the first entry is posted,” or “the archive is materialised only when someone asks for it,” then laziness is the domain’s own “existence begins on demand” rule. Double-checked locking makes that rule executable safely. When the domain has not named when existence begins, that is unwritten knowledge.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates that the object’s lifecycle begins on first use: its creation has a real cost or meaning, and eager creation would assert existence before the domain says it exists. Double-checked locking closes the gap: it keeps creation lazy while avoiding the cost of serialising every access. The laziness is the domain’s own “not until needed” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the laziness looks purely technical — a startup-cost optimisation. But it is still a domain decision: someone chose when the object exists. Double-checked locking fits only when the domain names that moment as meaningful. If creation timing is a free choice the domain never named, the volatile flag and null-check assert a lifecycle rule nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the domain care when this thing begins to exist — does it recognise a real “not yet” state — or is creation timing purely a performance question?

  • If yes → applicable. Double-Checked Locking is the code catching up to the knowledge; laziness is the domain’s own lifecycle rule.
  • If no → inapplicable. The laziness asserts a lifecycle rule the domain never named. Name it, or create eagerly without the memory-model ceremony.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Immutable Snapshot / copy-on-write

Goetz et al.: An immutable snapshot exposes a consistent instance while writers replace it copy-on-write. [4]

The domain knowledge gap it signals

The fact that an observation must reflect a single consistent instant is domain knowledge. If your domain model crystallises that “a quote is the price at the moment it was issued,” “a bank statement is the balance as of the closing date,” or “a submitted tax return is frozen,” then a snapshot is the domain’s own “this reading is a point in time” rule made executable. Copy-on-write is one encoding: the reader sees a stable version while a writer prepares a new one.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain requires point-in-time consistency: what an observer sees must be one coherent state, not a mixture of before and after. An immutable snapshot closes the gap: it prevents a concurrent reader from observing a half-applied change, which would show the domain a state that never legally existed. The snapshot is the domain’s own “freeze this reading” rule; the writer’s new version is the domain’s own “changes take effect as a new whole” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the snapshot is taken to avoid locks or allocations, so it looks purely technical. But it is still a domain decision: someone claimed a reader must see one consistent moment. Copy-on-write fits only when the domain names the instant of observation as meaningful. If the domain has not named it, copying the whole structure adds allocation and garbage pressure for a rule nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the domain treat this reading as a fact fixed at a moment — a quote, a statement, a frozen submission — rather than a casual glance at whatever is current?

  • If yes → applicable. Immutable Snapshot is the code catching up to the knowledge; the frozen reading is the domain’s own fact.
  • If no → inapplicable. The snapshot asserts a frozen instant the domain never named. Name it, or read directly without inventing one.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Saga / compensating action

Garcia-Molina and Salem: A saga splits a long-lived transaction into steps, each with a compensating action to undo it. [5]

A saga runs local steps in sequence and, on failure, compensates each completed one.

The domain knowledge gap it signals

The fact that the domain knows how to reverse or offset each step is domain knowledge. If your domain model crystallises that “a booking can be cancelled,” “a shipment can be returned and restocked,” and “a charge can be refunded,” then a saga is the domain’s own set of reverse actions made executable. Each compensating step is a domain rule — the reverse of a domain act — not a technical rollback invented by the transaction machinery.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain comprises several long-running steps across boundaries that cannot be made atomic, and each step has a reversal the business already performs. A saga closes the gap: it prevents a distributed transaction from pretending that the whole process is atomic, which the domain does not permit. The compensations are the domain’s own “how we undo this” rules; the sequence is the domain’s own business process.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the “compensation” looks purely technical — a data cleanup to fix a failed write. But it is still a domain decision: someone claimed the steps are separately reversible. A saga fits only when the domain names a real reversal for each step. When the steps are atomic within one boundary, the domain has not named a reversal, and the undo path asserts one nobody decided. That is the finding: the knowledge is unwritten.

TipThe faithfulness test

Does the domain perform these reversals in the real world — a cancellation, a refund, a restock — or would the “compensation” be a cleanup only engineers understand?

  • If yes → applicable. The Saga is the code catching up to the knowledge; compensations are the domain’s own reverse acts.
  • If no → inapplicable. The saga asserts reverse steps the domain never named. Name them, or keep one transaction that does not invent undo.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Circuit Breaker

Nygard: A circuit breaker trips after repeated failures and short-circuits calls until the dependency recovers. [6]

The domain knowledge gap it signals

The fact that the domain names a dependency as unavailable is domain knowledge. If your domain model crystallises that “when the card processor is down, we take the order on account,” or “when the address service is unavailable, we route to manual review,” then the domain has named the failure state: this dependency is down. A circuit breaker is that state made executable — after repeated failure it trips open and stops the calls. The trip threshold is a chosen bound; the down state it acts on is the domain’s rule.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain names the condition under which a dependency is unavailable, and it accepts that calls must stop while the dependency is down. A circuit breaker closes the gap: it prevents the code from hammering a failing dependency, and it records the domain’s own down state. The open state is the domain’s own “stop calling” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the domain treats every call as independently worth attempting, with no named state in which the dependency is down. The breaker still looks technical, but it is a domain decision: someone claimed this dependency has a failure state. A circuit breaker fits only when the domain names that state. If the domain has not named it, the trip threshold and open state assert a failure boundary nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the domain name a state in which this dependency is unavailable — a real down state — or is every call independently worth attempting?

  • If yes → applicable. The Circuit Breaker is the code catching up to the knowledge; the open state is the domain’s own down state.
  • If no → inapplicable. The open state asserts a failure boundary the domain never named. Name it, or retry plainly without inventing one.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Scheduler / time-triggered job

A scheduler runs a job at a set time or on a recurring timetable.

The domain knowledge gap it signals

The fact that something happens at a particular time is domain knowledge. If your domain model crystallises that “the books close at end of business on the last working day,” “interest posts on the first of the month,” or “the report runs every Friday before the stand-up,” then the trigger is a domain rule and the cron expression is merely its encoding. The schedule is the domain’s own calendar made executable; the job is the domain’s own “this must happen then” rule.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain attaches meaning to the moment: a deadline, a settlement date, a statutory filing window. A scheduler closes the gap: it prevents the timing from being buried in an operator’s habit or a manual reminder, and it records the domain’s own calendar. The trigger time is the domain’s own fact; the recurring run is the domain’s own recurring obligation.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the “schedule” looks like an operational convenience — a nightly cache warm, a log rotation, a cleanup at 03:00. But it is still a domain decision: someone chose the time. A scheduler fits only when the domain names the moment as meaningful. If the time is a free choice the domain never named, the trigger asserts an obligation nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Would a domain expert say the business requires that this happens at that time — a deadline, a settlement, a statutory date — or is the time just when it is convenient to run?

  • If yes → applicable. The Scheduler is the code catching up to the knowledge; the trigger is the domain’s own calendar.
  • If no → inapplicable. The trigger asserts a business date the domain never named. Name it, or run an interval that does not invent one.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Thread Confinement / thread-local state

Goetz et al.: Thread confinement restricts an object to a single thread, removing the need for synchronization. [4]

The domain knowledge gap it signals

The fact that one worker handles one case from start to finish is domain knowledge. If your domain model crystallises that “the assigned caseworker owns the case until it closes,” or “one clerk processes one application throughout,” then confinement of the working state to that worker is the domain’s own “this caretaker owns this case” rule made executable. Thread-local state is one encoding: the state belongs to the worker, not to the shared code.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain assigns a case to a single owner for the duration of its handling, and no other party may touch the in-progress work. Thread confinement closes the gap: it prevents the in-progress state from being shared and mutated by unrelated workers, which would let a case be advanced by two clerks at once. The confined state is the domain’s own “one owner while in progress” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the confinement looks like an accident of the runtime — state stashed in a thread-local to avoid passing it explicitly. But it is still a domain decision: someone claimed a single worker owns this work. Thread confinement fits only when the domain names that owner. If ownership is whatever thread happened to pick the work up, the domain has not named an owner, and the thread-local asserts one nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the domain assign this work to a single owner for its whole duration — one clerk, one case — or is the “ownership” only whatever thread happened to pick the work up?

  • If yes → applicable. Thread confinement is the code catching up to the knowledge; the confined state is the domain’s own case ownership.
  • If no → inapplicable. The confinement asserts an owner the domain never named. Name it, or pass the state explicitly.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.
