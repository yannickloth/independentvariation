Case study: IO scheduler choice (none, mq-deadline, bfq, kyber)

An NVMe box hands a measurable share of its IOPS to a scheduler reordering what the drive reorders in silicon.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: Four schedulers front the device, each selling a different ordering service. none reorders nothing; mq-deadline bounds one request’s wait; bfq divides bandwidth by cgroup weight; kyber caps queue depth per operation type. Three of the four add per-IO CPU work — overhead where hardware already reorders; none buys no ordering and pays no CPU, and it runs no fairness layer.

The kernel knowledge gap it signals

The choice encodes two claims about your own system: how much contention the device sees, and how much ordering its hardware still lacks. Both belong to your device class and tenant count, not the kernel. The gap question: which blocking behavior does this class still lack, and is the CPU you pay buying what the drive already does?

ImportantWhen the domain mandates it

bfq where many tenants compete on spinning or slow storage: one backup job stopped starving the foreground path, its p99 read latency falling from seconds to tens of milliseconds. mq-deadline on a database box whose writes must not queue behind a read burst. none on NVMe once request merging above the scheduler is confirmed: more IOPS, less CPU per IO.

WarningWhen it’s a guess dressed as engineering

The copied tuning guide. bfq is the “low latency” scheduler in every post for spinning disks, so it lands on NVMe, where the drive reorders in hardware and the bookkeeping runs on every submitting core. The quieter trap: none on a SATA SSD with many concurrent fsync writers, because “none is fastest” — one queue, no fairness layer, one fsync-heavy writer takes the disk while the rest wait.

TipThe faithfulness test

Can you state the device class, the contention level, and the p99 target — and did you measure the scheduler’s effect on this box?

  • If yes → you hold the three facts it rests on. Re-measure when the device or tenant count changes.
  • If no → the scheduler is an inherited default, not a decision. Name the device and tenant count, then measure an alternative at production queue depth.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Run the workload under two schedulers and read p99, IOPS and CPU per IO together.

Case study: CPU frequency governor

One config line buys a front-end box back its p99 tail, and bills the choice in watts on every idle core.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: Three governors, three claims. performance pins the clock at the top P-state; schedutil derives a target from scheduler utilization; powersave on intel_pstate hands frequency to the hardware’s own control loop. The trade is a latency floor against energy and heat — a constant clock removes the ramp, a scaled clock charges ramp delay on wakeup and saves the watts between.

The kernel knowledge gap it signals

The governor encodes a claim about load shape: whether the CPU is busy enough that the top clock is nearly always right, and whether a wakeup arriving mid-ramp is visible to your SLA. Neither ships with the kernel. The gap question: which tail number did the ramp actually move, and what does the watt delta cost at your fleet size?

ImportantWhen the domain mandates it

A front-end box whose p99 spiked: a frequency trace put the spike at the ramp, the CPU dropping clock between requests before the next arrived. Pinning performance removed it. An idle-heavy fleet at 5% utilization went the other way: schedutil cut energy with no p99 change that fleet measured.

WarningWhen it’s a guess dressed as engineering

performance copied from a gaming guide onto a fleet idling 95% of the day. The gain is real for the benchmark behind it — single-thread latency — and the bill is every idle core holding its top P-state: power, heat, less turbo headroom for the cores at work. The reverse is subtler: schedutil on a trading or audio path where the ramp is the spike. Those boxes idle by design between events, so utilization reads low and each event can pay the delay the governor was meant to avoid.

TipThe faithfulness test

Who owns the SLA — and which currency did the choice spend, watts or wakeup delay, at fleet size?

  • If yes → you can defend the line in both currencies. Re-check when the idle fraction changes.
  • If no → the governor is a copied default. Measure the tail under both, then multiply the watt delta by fleet and month.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Trace frequency beside latency for an hour of real traffic.

Case study: Kernel preemption model

A kernel built for latency can cost a render fleet several percent of throughput, and no dashboard shows what it bought.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: Voluntary preemption runs kernel code to completion at safe points; full preemption allows it nearly anywhere; real-time adds threaded IRQs and priority inheritance. Since 5.12, PREEMPT_DYNAMIC picks among the built variants at boot, so the choice can be per boot, not per build. The trade is throughput against wakeup latency: fewer involuntary switches mean better cache behavior and a longer wait for the task an interrupt woke.

The kernel knowledge gap it signals

Both sides belong to your workload: how long the longest kernel path gets under your IO pattern, and how much runqueue delay your SLA tolerates. A distro default is a compromise across workloads it never saw. The gap question: which wakeup-latency number does your SLA name, and was it measured on the kernel build you run?

ImportantWhen the domain mandates it

A capture path dropping buffers: full preemption cut worst-case wakeup from 3 ms to 20 µs on the same hardware, and the dropouts stopped — the batch job on the same host lost 4% throughput and had the slack to absorb it. A render farm took the opposite line: voluntary preemption, no latency target, maximum throughput under a full runqueue.

WarningWhen it’s a guess dressed as engineering

The custom kernel built once “for performance” and never re-measured: full preemption everywhere, so the throughput cost is paid continuously against an unmeasured win. The commoner version is quieter: the distro default assumed adequate for a latency SLA it never heard of. Tests pass because tests are idle, and the first production burst can show a wakeup delay nobody has a number for.

TipThe faithfulness test

Which SLA measured the wakeup path — on which kernel build, and how often is that re-checked?

  • If yes → you know what preemption buys here and its cost. Re-check after a kernel upgrade, which changes both.
  • If no → the model is a distro artifact. Measure worst-case wakeup latency under real IO and CPU load, then decide.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Read the worst wakeup, not the mean.

Case study: CPU isolation and IRQ steering

Four cores reserved for a latency-critical thread that spends its life sleeping on a lock held on a housekeeping core.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: isolcpus stops the scheduler placing ordinary tasks on named CPUs; IRQ affinity policy keeps interrupts off them; a cpuset or taskset must then put the threads there. The trade is direct: quiet cores for the workload against fewer cores for everything else — housekeeping, softirq work, and the rest of what it runs.

The kernel knowledge gap it signals

Isolation answers a measured jitter question, so it needs a jitter number and a named noise source. You must know whether the spikes came from interrupt delivery, from migration, or from cache contention with a neighbour — each needs a different fix; all three are served by moving work off the core, by a different lever: the IRQ mask, isolcpus, or pinning the thread away. The gap question: which jitter number did isolation improve, measured before and after, and what do the reserved cores cost the rest of the box?

ImportantWhen the domain mandates it

A tail-sensitive service whose p99.9 spikes lined up with NIC interrupt and softirq activity: moving the queue interrupts off four cores, pinning the workers there, and leaving housekeeping on the remainder removed the spikes, with both numbers recorded. The half usually skipped: the remaining cores must still cover the ordinary work.

WarningWhen it’s a guess dressed as engineering

The cargo cult: cores isolated, threads never scheduled onto them, because the pool’s affinity was never set or the workers sleep on a lock held elsewhere. So the quiet cores idle while the real path stays as noisy as before, on a box with fewer cores for the work. Its fleet cousin reserves those cores on every instance for one benchmark that ran once.

TipThe faithfulness test

Which jitter number improved, measured before and after — and what do the reserved cores cost the rest of the box?

  • If yes → you have a measured win and a named noise source. Re-check when the interrupt layout or core count changes.
  • If no → the cores are reserved on faith. Trace the spikes first, then isolate only what the trace implicates.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Compare the tail with and without isolation, not the mean.

Case study: cgroup limits as contract

A memory limit set at current usage plus ten percent, and the OOM killer arrives on the first busy afternoon.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: memory.max and cpu.max are ceilings the workload may not exceed; io.weight is a share, not one. On breach the kernel throttles per period, or reclaims then kills; under contention a low io.weight deprioritises the cgroup’s IO. The trade is a guarantee for the neighbours against a throttle or a kill for the limited workload itself.

The kernel knowledge gap it signals

A limit claims a peak, so it needs that peak measured — not one inferred from a quiet afternoon — with the working set apart from the cache it borrows. It also needs a breach policy: who is paged, what restarts, which counter proves it happened. The gap question: what measured peak does this limit assume, and on breach what happens and who is told?

ImportantWhen the domain mandates it

A batch pod with memory.max above its largest observed resident set plus headroom for the biggest input, and memory.events on a dashboard: the limit held, one breach paged a human, and the pod restarted clean. cpu.max sized so the interactive path kept its share, with cpu.stat throttling displayed rather than discovered.

WarningWhen it’s a guess dressed as engineering

Current usage plus ten percent, sampled on a quiet afternoon: the first legitimate spike exceeds it, direct reclaim eats the response time, then an OOM kill can take a pod that would have survived. The fairness variant looks principled and is worse: a cpu.max quota set “for fairness” with no definition of fair and no measurement of burst shape. A job needing a 100 ms burst each second is throttled at every period boundary, and the symptom is a mysterious 100 ms p99 stall nobody traces to the quota.

TipThe faithfulness test

What measured peak does this limit assume — and on breach, what happens and who is told?

  • If yes → the limit is a contract with a number and a policy. Re-measure the peak when the inputs change.
  • If no → the limit is a number, not a contract. Measure peak usage and working set, then write the breach policy.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Read memory.events and cpu.stat under real load.

Case study: vm.swappiness

vm.swappiness=0 read as “never swap” turns a slow box into a dead one, mid-transaction.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: The knob biases reclaim between anonymous pages and file-backed page cache: a high value moves anonymous memory toward swap sooner, a low value drops the page cache first and swaps anonymous pages later. It does not switch swapping off — on kernels since 3.5 even zero still evicts anonymous pages rather than OOM while swap exists. The trade is warm file data against the reclaim order of process memory.

The kernel knowledge gap it signals

The setting presumes two numbers about your workload: the anonymous working set at peak, and how much file traffic is re-read after eviction. A database reaching files directly answers differently from one reading through the page cache, and neither number lives in the kernel. The gap question: what is the measured anonymous working set against RAM, and what does the box do on the first full reclaim walk?

ImportantWhen the domain mandates it

A database box whose anonymous working set was measured to fit in RAM at peak, with scan, page-steal and swap-in rate on a graph. Low swappiness kept the working set resident at the price of file-cache warmth, and any swap-in would have appeared on the latency path immediately.

WarningWhen it’s a guess dressed as engineering

Zero treated as an off switch. The box has swap, so zero still pages out — but only once the file cache is gone. The workload grows past RAM, direct reclaim storms as swap fills, and the OOM killer lands mid-transaction once swap runs out too. The escalation is turning swap off entirely, which removes the valve and the slow degradation it buys, so the failure changes from slow to sudden.

TipThe faithfulness test

What is the measured anonymous working set against RAM — and what does the box do on the first full reclaim walk?

  • If yes → the value follows from two measured numbers. Watch swap-in rate on the latency path, not just the swap used column.
  • If no → the value is a slogan, not a setting. Measure peak anonymous usage, then decide whether swap is the valve or the crutch.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Read scan, page-steal and swap-in through one real peak.

Case study: Transparent huge pages (the stall on the allocation path)

A database on 128 GB of RAM stalls 11 ms once a minute, and no query is running when it does.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: THP backs a 4 KB request with a 2 MB page, so one TLB entry covers 512 times more memory. The bill arrives at allocation: when no free 2 MB block exists, the kernel compacts to assemble one, and the thread that asked waits. enabled=madvise limits big pages to regions marked MADV_HUGEPAGE; defrag=madvise keeps compaction off the allocation path.

The kernel knowledge gap it signals

The knob encodes a priority you must state: throughput on a large footprint, or bounded pause on a shared host. Neither value is the right default — both are properties of your workload and your latency budget. Two boxes want opposite settings, yet the config file is identical. The gap question: which latency number improved on this box — and what did throughput do in the same measurement window?

ImportantWhen the domain mandates it

A jitter-sensitive database shows the stall in its worst-case latency: with THP forced on, the slowest query moved from 0.4 ms to 11 ms; set to madvise, it left the tail and throughput stayed inside the noise. A big-heap batch job that never reports the stall keeps THP on and collects the TLB win.

WarningWhen it’s a guess dressed as engineering

Disabling THP fleet-wide because a tuning guide said so. Defensible on the database, wrong on the analytics job two racks over, which quietly loses its TLB win and pays 4 KB walks over a heap it touches constantly. The mirror trap is worse: THP left on for the database, where the millisecond pauses stay unexplained for a year because nobody connects them to the knob.

TipThe faithfulness test

Which latency number improved on this box — and what did throughput do in the same measurement window?

  • If yes → both numbers are yours, so the trade is a decision. Re-read defrag when the allocation pattern changes.
  • If no → the tweak is a copied default. Toggle THP on one box, same workload, and read p99 and throughput together.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Measure the compaction stall (thp in /proc/vmstat) against your own latency budget.

Case study: Memory overcommit (the promise the kernel cannot keep)

At 02:10 a cache forks to write its snapshot, and the OOM killer takes the parent, not the child.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: vm.overcommit_memory decides what the kernel answers to an address-space request it has no pages for: 0 is heuristic, 1 always says yes, 2 refuses anything past CommitLimit — swap plus overcommit_ratio percent of RAM. The trade: optimistic promises against a hard commitment. The fork path needs the second: with copy-on-write the child’s pages materialise when the parent writes, so a fork the kernel grants must be backed when the writes arrive.

The kernel knowledge gap it signals

How much your service forks, how much it writes after forking, and what swap you sized are facts about your system, not the kernel. A snapshot rewrite and a preforking server both duplicate pages; a single-process allocator does not. The gap question: which process forks how much, measured — and who survives the first failed allocation, the requester or a random victim?

ImportantWhen the domain mandates it

A fork-heavy service runs mode 2 with CommitLimit sized to twice the snapshot — the fork charges the COW child in full: the fork fails fast if it cannot be served, and the snapshot is protected instead of dying at 02:10. A single-purpose box whose application counts its own allocations runs mode 1, where the kernel stops second-guessing a plan the process made.

WarningWhen it’s a guess dressed as engineering

Heuristic mode, no swap, a fork-heavy service. It survives a year because the parent’s dirty pages stay small until the dataset grows; then one night the fork is refused mid-snapshot, or the killer picks its victim by score. The cousin trap is the operator who says “we have swap” while the ratio ignores how the check counts: swap plus a percentage of RAM, not free memory.

TipThe faithfulness test

Which process forks how much, measured — and who survives the first failed allocation, the requester or a random victim?

  • If yes → the mode matches fork behaviour. Re-check the ratio when RAM or swap changes.
  • If no → you are betting the snapshot on a heuristic. Count the forks, then size swap to the largest copy.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Measure peak anonymous memory and fork frequency.

Case study: Dirty writeback (the flush wall)

A log writer stalls 1.8 seconds every few minutes, and the CPU sits at 30% the whole time.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: vm.dirty_background_ratio is the share of RAM at which the flusher starts writing dirty pages; vm.dirty_ratio is the share at which a writer must write its own pages and block. Between them the kernel absorbs bursts — a delay, not a capacity. A large buffer smooths short bursts and turns the overflow into one long stall: every writer waits at the wall.

The kernel knowledge gap it signals

The ratios mean something only against two facts you hold: the write rate this box sustains, and whether a tail-latency budget shares the box with the flusher. In a container the percentage is of host RAM, not of the limit — inherited, never sized. The gap question: what is the measured write pattern of this box — and does any tail-latency budget share the box with the flusher?

ImportantWhen the domain mandates it

A team measured the pause first: writers blocked 1.8 s when dirty pages crossed the hard ratio, and the flusher had started too late. Lowering dirty_background_ratio turned one cliff into a sawtooth with no stall above 20 ms, at the cost of more small writes. Latency-sensitive writers get small ratios; a bulk staging disk keeps large ones.

WarningWhen it’s a guess dressed as engineering

Raising dirty_ratio “to buffer more”, because the stall looked like a capacity problem. It is seductive: the pause leaves the test window and can return later and taller, since the same megabytes must still reach the disk in one burst. Worse is the inherited default: 20% of RAM on a machine with forty times the memory of the guide that wrote it, buffering 40 GB before stopping for minutes.

TipThe faithfulness test

What is the measured write pattern of this box — and does any tail-latency budget share the box with the flusher?

  • If yes → the ratios match a write rate you can state. Re-check them when RAM or the writer changes.
  • If no → you are buffering against a wall you never measured. Size both ratios from a write rate you can state.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Measure the peak write rate and the worst pause together.

Case study: NUMA policy (bandwidth against locality)

A scan reads 40 GB at 3 GB/s, the profiler blames the code, and numastat says 62% of the allocations are remote.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: On a multi-node box an access is local or remote; remote costs latency and shares an interconnect. numactl --interleave spreads allocations for bandwidth; --membind keeps pages on one node for the lowest access time. The trade: whole-machine bandwidth, or latency for one working set. vm.zone_reclaim_mode still makes a node reclaim its own pages instead of allocating remotely; since 5.9 it defaults to 0.

The kernel knowledge gap it signals

Which share of accesses must stay local belongs to your access pattern, not the machine. A join walking a 20 GB index wants locality; a 200 GB table scan wants bandwidth and does not care where the bytes live. The gap question: what share of this workload’s allocations is remote, measured — and did the policy move that number?

ImportantWhen the domain mandates it

A team read numastat, saw 62% remote on a bandwidth-bound scan, and interleaved it: throughput reached the aggregate and the remote share stopped mattering, since bandwidth was the goal. For the database the same measurement pointed the other way — bind to the node sharing its interrupts, the remote share falls, the p99 follows.

WarningWhen it’s a guess dressed as engineering

Interleaving everything “for balance”. It reads like fairness and is wrong for a database whose working set fits one node: every page can now be remote, the free locality is gone, and the slowdown shows up as unexplained query time. The companion trap is a host that inherited zone_reclaim_mode=1 from a template for a two-node machine — stalls that nobody traced to a knob older than the hardware.

What share of this workload’s allocations is remote, measured — and did the policy move that number?

  • If yes → the policy answers a number you can state. Re-read numastat after a placement change.
  • If no → the policy is a preference. Measure the remote share before and after.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Map the working set to nodes, then name the resource you buy.

Case study: Kernel same-page merging (density bought with CPU)

Forty containers run the same base image, the host reports 22 GB used, and the sum of their limits is 60 GB.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: KSM scans pages marked MADV_MERGEABLE, hashes them, and merges identical ones into one copy-on-write page; the first write faults and copies. pages_to_scan and sleep_millisecs set the rate. The trade: RAM density per host, paid in CPU for hashing and in fault latency at every write to a shared page.

The kernel knowledge gap it signals

Whether density is the product or a side effect decides this knob. A fleet of near-identical guests selling memory per tenant buys density; a database host selling latency does not. You must also know the scan cost against your CPU budget, and how much is shared: pages_sharing counts the duplicate mappings, pages_shared the unique merged pages. The gap question: what does the dedup save on this host, and what CPU does the scan cost — measured in the same units, over the same week?

ImportantWhen the domain mandates it

Forty identical images measured 0.8 GB saved per guest, with the scan under a few percent of one core: density was real and priced. They graph the sharing ratio beside the scan cost: a rising ratio with rising CPU is the point, a rising ratio with falling throughput the warning.

WarningWhen it’s a guess dressed as engineering

Switching KSM on for a latency-sensitive database host because memory is tight. The premise is sound — identical pages are wasted pages. What it misses: a database writes constantly, merged pages copy on every write, and the churn becomes background load on a machine whose tail latency is its purpose. Nothing on the dashboard attributes it: the fault appears as a slower query, the scan as system CPU.

TipThe faithfulness test

What does the dedup save on this host, and what CPU does the scan cost — measured in the same units, over the same week?

  • If yes → density is a priced decision. Watch the ratio as the workloads diverge.
  • If no → you bought an unmeasured discount. Budget the scan’s CPU share on one host before the next.
  • If you can’t answer → unclear. You haven’t found the tweak wrong — you’ve found incomplete system knowledge. Measure saved bytes and scan cost on one host for a week.

Case study: The free-page reserve (headroom against the burst)

A 512 GB host with 200 GB free spends 300 ms in direct reclaim, and the workload has not grown.

Setting a kernel knob? Ask “which measured fact does this tweak answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the config line is a superstition. If you can, the tweak is knowledge embodied — the system catching up to what the workload demands.

Mechanism: vm.min_free_kbytes reserves free pages for atomic allocations that cannot sleep or reclaim. The reserve must cover the largest burst between wakeups, and every kilobyte of it is page cache the workload cannot use. The default is four times the square root of lowmem, the directly mapped zone, and is capped at 256 MB, so on a large host it grows far slower than the burst does.

The kernel knowledge gap it signals

How large a burst arrives between kswapd runs is a fact about your drivers and interrupt load, documented nowhere. The reserve also subtracts from the cache your reads depend on, so it is never free. ImportantWhen the domain mandates it

Strict mode where the topology is single-homed and the claim is true: a plain application host, a single-uplink bastion whose drop counters stayed flat across a month, the spoofed-source probe rejected at the door. The hardening is defensible — a checklist asks for it. Case study: the adaptive tick (nohz_full, rcu_nocbs)

A trading gate passes at one tick per second — while one core absorbs every displaced timer and RCU callback.

Mechanism: nohz_full names cores whose running task sees no periodic timer tick; rcu_nocbs moves that core’s RCU callbacks elsewhere; isolcpus keeps the scheduler off them. All three are boot parameters, not sysctls, so the decision never appears in a config review. You buy undisturbed userspace with a housekeeping burden that must land somewhere.

The kernel knowledge gap it signals

A tick-free core is worth its cost only where the tick injects jitter the workload can feel — a market-data loop, a control path, an audio buffer. The rest of the machine still needs a core for timers, interrupts, RCU callbacks, and the scheduler — one core now carrying the work of fifteen. So the change moves a known load onto an unknown capacity. What jitter did the tick actually inject, measured — and what runs on the core left holding the housekeeping?

ImportantWhen the domain mandates it

A market-data loop on a 16-core box measured 40 µs worst-case wakeup with the tick and 6 µs without; nohz_full plus isolcpus held it there, and the housekeeping core sat at 30% at peak — the cost stated before the line shipped.

WarningWhen it’s a guess dressed as engineering

nohz_full enabled for a vanity number, “one timer tick per second”, on a workload that never measured tick jitter. The mechanism is real, the metric impressive — on a dashboard tied to no latency budget. Meanwhile one core takes the migrated timers and RCU callbacks, plus whichever IRQs you steer there, and can saturate at peak: the spikes return from a new direction, and the team concludes tick suppression “does not work”.

  • If no → you moved the work and kept the risk. No nohz_full until a latency histogram shows the tick.
