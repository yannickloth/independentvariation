Algorithms as Knowledge-Gap Indicators

A series of short posts that read each algorithm as a claim about the operation mix, the scale, the ordering, and the exactness the domain demands.

Every algorithm below rests on a claim about the workload — the operation mix, the scale, the ordering, the exactness the domain demands. Each post names the algorithm, states the claim, and asks whether the facts are known or hoped.

Pick a post on the left. It opens on the right.

Choosing an algorithm or a data structure? Ask “which facts does this choice encode — the operation mix, the scale, the ordering, the exactness the domain demands, among others?” If you can’t answer, you’ve found a knowledge gap: the structure pays for a prediction nobody wrote down. If you can name those facts, the structure is the knowledge embodied — the code catching up to what the domain decided.

Case study: Linear scan

Construct: A linear scan examines elements in sequence until it finds the match or the collection ends: O(n) per lookup, O(1) memory, no index assumed. It encodes one claim — the collection stays small enough that the per-lookup constant dominates every alternative.

The algorithmic knowledge gap it signals

For the scan to be knowledge rather than inertia, the domain must supply the bound: seven days in a week, a status set closed by a state machine. Where that rule holds, the constant wins: 200 lookups over 50 rows cost 10,000 comparisons, with no build, memory, or write-path cost. The gap question is whether the bound is a domain fact or a hope about tomorrow’s data.

ImportantWhen the domain mandates it

The bound is small, stated, and enforced elsewhere: ISO country codes, a closed set of order states, a fixed feature-flag list. Any growth past the stated bound breaks a validation before it reaches the scan.

WarningWhen it’s a guess dressed as engineering

The collection is unbounded and already in the thousands, kept alive by “optimize later.” The subtler form is a scan inside a loop: checking membership per row, or deduplicating against a list, gives O(n²) — a hundred million comparisons where no line looks wrong. The set grew from five statuses to four thousand tenant codes, and nothing re-examined the scan, because the claim was never written down.

TipThe faithfulness test

Can you state the bound on the size that makes the scan acceptable — and is it a domain fact or a hope?

  • If yes → the bound is a domain fact; with it enforced, the scan is correct. Record the number where a check can break.
  • If no → the bound is a hope, so the bill grows with the collection and the caller cannot see it. An index moves that cost to the write path.
  • If you can’t answer → unclear. You haven’t found the scan wrong — you’ve found incomplete domain knowledge. Measure the set’s size and its growth rate, then ask which rule could close the set.

Case study: Binary search

Construct: Binary search halves the search interval per step: O(log n) per lookup, O(1) memory. It is correct only under an invariant — the collection is ordered, and it stays ordered at every read. It encodes the claim that someone produces the order and someone restores it on every write.

The algorithmic knowledge gap it signals

Sorted order is not free; it is a maintained property with an owner. Either the domain produces it as a side effect of its own rule, or a write path pays to restore it after each insert. The gap question is not whether the array is sorted today but who keeps it sorted under insertion.

ImportantWhen the domain mandates it

The domain emits order itself: an append-only ledger ordered by posting timestamp, a version index whose numbers increase monotonically. The sort costs nothing extra, because it is what the domain already did.

WarningWhen it’s a guess dressed as engineering

Two traps, both competent-looking. Sorting on every lookup to search once costs O(n log n) per query to save O(log n) — worse than the scan it replaced. The second is the classic bug: sort once at construction, then let inserts happen. The invariant has no owner and nothing revalidates, so the first write path added after construction — an admin endpoint, a batch import, a repair script — makes every later lookup plausibly wrong.

TipThe faithfulness test

Does the domain both produce the sorted order and maintain it under insertion — or is the order a bet?

  • If yes → the order is a domain product. Binary search is the code catching up. Verify the insert path is the only write path.
  • If no → name which half is missing. Order produced, one write path escaping: close it. No producer at all: sort once where writes end, or keep an ordered structure.
  • If you can’t answer → unclear. You haven’t found binary search wrong — you’ve found incomplete domain knowledge. Measure the lookup-to-insert ratio, then ask whether any domain rule orders the keys.

Case study: Quicksort

Construct: Quicksort partitions around a pivot and recurses on each side: O(n log n) expected, O(n²) worst, in place, not stable. One call encodes four claims — no user chooses the keys, the average case is what production sees, equal keys carry no order, and the sort is a one-shot over data already in memory.

The algorithmic knowledge gap it signals

The expected case is a prediction about the input distribution, and a prediction is not knowledge until someone states where the input comes from. Four decisions hide inside one call. The gap question is whether that distribution is a domain fact: who produces these records, and can a user shape them.

ImportantWhen the domain mandates it

A batch the system itself assembled, sorted once and discarded. Distinct keys, so equal-key order cannot mean anything. No user reaches the key sequence, and a randomized pivot is accepted. Sorting one report’s rows by order id is the shape: one shot, in memory, no adversary, no ties.

WarningWhen it’s a guess dressed as engineering

Line items sorted by amount when the input order was the customer’s line numbering: ties shuffle between runs and the diff inverts. A deterministic pivot over keys a user can submit is an O(n²) denial of service with extra steps. Re-sorting a million rows inside a 50 ms request path, where 25 million comparisons no longer fit the budget. Each is defensible alone, and each is a bet on benign input, invisible ties, or batch cadence.

TipThe faithfulness test

Is equal-key order truly irrelevant, and is the input distribution a domain fact or a hope?

  • If yes → quicksort is correct and cheap. Pin the pivot policy so the average case is not left to chance.
  • If no → choose stability where ties matter, a worst-case bound where input is reachable, incremental insertion where updates are the rhythm.
  • If you can’t answer → unclear. You haven’t found quicksort wrong — you’ve found incomplete domain knowledge. Sample the input distribution, then ask whether any consumer compares equal-key order.

Case study: Stable sort

Construct: A stable sort preserves the relative order of equal keys. Mergesort is stable at O(n log n) with O(n) extra space; heapsort is O(n log n) in place and unstable; the textbook quicksort partition is unstable. Stability encodes one claim: the order of equal keys is a domain fact, and something downstream reads it.

The algorithmic knowledge gap it signals

Ties are rarely ties. When two records compare equal on the sort key, a second criterion decided their order earlier — submission time, arrival sequence, posting order — and the domain already ruled on it. Stability guarantees that the earlier ruling survives the sort. The gap question is whether that criterion is a written rule or an accident of how the data arrived.

ImportantWhen the domain mandates it

Multi-level ordering where a domain rule set the earlier order: sort by name within department, preserving the sequence the intake rule produced. Latest-first within equal priority, where the sequence carries the tie. The buffer costs O(n) and the domain states what it buys.

WarningWhen it’s a guess dressed as engineering

Both directions look plausible. Paying for stability where equal keys cannot exist — sorting by a unique id, where the extra O(n) buffer buys nothing. And the subtler one: enshrining an accident. The tie order arrived from a hash map’s iteration or from whatever order the file had, stability preserved it, a test asserted it, and now an incidental upstream order is a contractual guarantee nobody designed.

TipThe faithfulness test

Does anyone downstream depend on the order of equal keys, by a rule the domain states?

  • If yes → stability is domain knowledge. Document which criterion the tie order encodes, and where it comes from.
  • If no → use the unstable sort, keep the memory, and stop pretending the tie order means something.
  • If you can’t answer → unclear. You haven’t found stability wrong — you’ve found incomplete domain knowledge. Find who reads the output, then ask whether that tie order came from a rule or from how the rows happened to arrive.

Case study: Counting and radix sort

Construct: Counting sort tallies each key into a table indexed by the key, then writes the output in key order: O(n + k), where k is the size of the key universe. Radix sort repeats that per digit at O(d(n + b)) for d digits over a b-symbol alphabet. Both encode one claim: the keys come from a small, known, closed universe.

The algorithmic knowledge gap it signals

Comparison sorting assumes only a total order on the keys; these assume the key universe itself. The table’s size is a written claim about which values the domain can produce, and an alphabet bound is a claim about key width. The gap question is whether that universe is closed by a rule you can state, and who is notified when it opens.

ImportantWhen the domain mandates it

Ages from 0 to 120, bounded by biology. IP octets from 0 to 255. Country codes closed by a published list. A fixed-width integer ID, where alphabet and width are facts of the type. A validation rule that already rejects anything outside the range — the constraint restated as an array.

WarningWhen it’s a guess dressed as engineering

The table sized for a universe that grew: twenty status codes, then one tenant-specific code numbered 4000, and the array is now two hundred times the data. Direct indexing over an open identifier space allocates a billion entries for a thousand user IDs. Keys of unfixed width, such as arbitrary strings, make the digit count depend on the data. Each works on test data.

TipThe faithfulness test

Is the key universe closed by a domain rule you can state — and who is notified when it opens?

  • If yes → counting sort fits; radix also needs a fixed key width. Assert both in code, so growth fails loudly instead of allocating.
  • If no → the table is a bet on a universe you do not control. A comparison sort costs O(n log n) and needs no such claim.
  • If you can’t answer → unclear. You haven’t found counting sort wrong — you’ve found incomplete domain knowledge. Measure the key cardinality and range over a real sample, then find the rule that could close the universe.

Case study: Topological sort

Construct: A topological sort orders the vertices of a directed acyclic graph so every edge’s source precedes its target, in O(V + E). It encodes a strong claim: the domain’s before/after relation is a partial order — asymmetric, transitive, acyclic — and pairs with no order between them are genuinely unordered, not missing information.

The algorithmic knowledge gap it signals

A partial order cannot be inferred from observations; it must be declared — in policy, in a document the domain owns. Every edge is a domain rule; every absent edge is a claim too — that either order is acceptable — unless transitivity already decided the pair. The gap question is whether an expert can name the pairs, and which unordered pairs the domain leaves free.

ImportantWhen the domain mandates it

Build steps whose dependencies come from declared imports. Migration ordering a database administrator can draw on a whiteboard. An approval chain written in policy. The graph is a domain artifact, the expert draws it, and the cycle check runs as a domain-consistency check — a contradiction detector, not an inconvenience.

WarningWhen it’s a guess dressed as engineering

Precedence invented to make the sort succeed: a tie between two unordered tasks, broken by list position or by ID, so the run completes and the order looks settled. Then the second trap — suppressing the cycle. Catch the exception, log a warning, fall back to declaration order, ship. The system now hides a contradiction, and the wrong order looks like a right one: no failure, no alert.

TipThe faithfulness test

Can the domain expert name the before/after pairs — and for unordered pairs, is “either order is fine” the domain’s answer?

  • If yes → the sort embodies a real partial order. Keep the cycle check as a domain check, never as noise to route around.
  • If no → any acyclic output is luck. A cycle means two domain rules conflict; resolve the rules, not the graph.
  • If you can’t answer → unclear. You haven’t found the sort wrong — you’ve found incomplete domain knowledge. Enumerate the pairs with the expert, and treat every cycle as a question about requirements.

Case study: Breadth-first search

Construct: BFS explores a graph in order of hop count: it visits every node at distance k before any node at distance k+1, in O(V + E) time. The queue is the whole mechanism, and a queue can only count edges. So the algorithm encodes one claim — every step costs the same, and the smallest number of intermediate stops is the domain’s notion of best.

The algorithmic knowledge gap it signals

Unit weights are a domain statement, not a default value. The claim says two routes of equal length are equally good, and that nothing distinguishes the third step from the first. The gap question is whether the domain ever decided that.

ImportantWhen the domain mandates it

The steps are genuinely interchangeable. Degrees of separation, fewest clicks to a checkout, minimum moves in a puzzle, fewest screens in a flow — the unit is an action, and the domain counts actions. BFS is then exact, at O(V + E).

WarningWhen it’s a guess dressed as engineering

The weights exist — in a price table, a contract, an SLA — and the traversal ignores them because a queue was easier to write and BFS is the traversal everyone knows. It returns a real path with a plausible length, so the team reports “the cheapest route” — the domain asked which route costs least, and the code answered which route is shortest. The gap stays invisible until finance compares the two routes and finds the shipped one more expensive.

TipThe faithfulness test

Does the domain count steps — or price them? Who said all steps are equal?

  • If yes → hops are the domain’s unit. Check that no edge in the data carries a weight the traversal silently drops.
  • If no → it is a shortest-hop answer to a shortest-cost question. Read the weights, or record in writing that hops are what the domain measures.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. Find two routes of equal hop count that differ in domain value, and ask the domain owner which one they would ship.

Case study: Depth-first search

Construct: DFS follows one branch to its end before it backtracks, with a visited set to stop revisiting and a stack of depth equal to the longest path. It costs O(V + E) and returns reachability; ranking is not its product. The algorithm encodes one claim: existence or completeness is what matters, not which path is best. The first path it finds is a valid path and nothing more.

The algorithmic knowledge gap it signals

Accepting any valid answer is a strong domain decision. Either the question was “does one exist”, “is there a cycle”, or “enumerate them all” — or the domain compares answers and needs the best one. The gap question is which of those the domain asked, because DFS is honest about existence and enumeration and silent about which is best.

ImportantWhen the domain mandates it

The domain wants the full set or the bare yes. Cycle detection on a dependency graph, all reachable accounts for a permission audit, every descendant of a category node, a topological order from postorder where the graph is acyclic. The domain never asks which answer, because every member of the set is equally wanted.

WarningWhen it’s a guess dressed as engineering

DFS returns a path, the path is valid, and the product presents it as the route. Nobody asks whether a better one exists until a customer compares today’s route with yesterday’s and finds it longer. The trap is seductive because the output is correct in the only sense the code checks. The second trap is the visited rule keyed on the wrong field: a node reached by two paths is silently omitted, and the set is wrong in a way no test names.

TipThe faithfulness test

Is the question “does one exist / enumerate all” — or “which is best”? Does the domain accept any valid answer?

  • If yes → existence or enumeration is the question. Check that the visited rule covers cycles and the depth covers the data.
  • If no → an arbitrary valid path is being read as an optimal one. Say which answer the domain compares, then compute the comparison.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. Ask whether two valid answers are ever compared, and by what rule.

Case study: Dijkstra’s shortest path

Construct: Dijkstra settles nodes in order of tentative distance, using a priority queue: O((V + E) log V) with a binary heap, and correctness requires non-negative weights. It encodes three claims at once — the weights are numbers the domain recognizes, costs add along a path, and the sum is what “best” means. Take away the first or the third and it still returns an optimal answer to a question nobody asked; take away additivity and the answer is optimal for nothing.

The algorithmic knowledge gap it signals

A weight is a unit before it is a number. Minutes, euros, kilometres: each carries a decision that units are comparable, and that two routes cost the sum of their parts. The gap question is whether the domain made that decision in public, or a developer made it privately.

ImportantWhen the domain mandates it

The weights are quantities the domain already trades in. Route planning over measured minutes, cost-optimal planning over invoice lines. Someone can check the unit with a stopwatch or a bill, and re-derive it when the contract changes. Non-negativity holds because a refund is not a journey.

WarningWhen it’s a guess dressed as engineering

The weights are invented: 0.5 because that partner is “preferred”, 1.0 because that route is “strategic”. The algorithm is textbook-correct and returns a provably optimal answer to an objective no one owns. The harder version is multi-attribute — cheapest and fastest at once — collapsed into one number that fixes an exchange rate between money and time nobody can defend.

TipThe faithfulness test

Can someone name the unit of the weights, and defend addition as the way they combine?

  • If yes → the weights are domain quantities. Check non-negativity, and record where each weight comes from.
  • If no → it is an optimizer over an invented objective. Name the attributes separately and let the domain rule compare them.
  • If you can’t answer → unclear. You haven’t found Dijkstra wrong — you’ve found incomplete domain knowledge. Find who owns the trade-off, then ask what one unit of weight buys.

Case study: A* search

Construct: A* orders its frontier by f(n) = g(n) + h(n): cost so far plus an estimate of cost remaining. It encodes two claims. The domain supplies that estimate, and the estimate is trusted: admissible, it never overestimates the remaining cost, so optimality holds; consistent — never overestimating by more than one edge — so no node is reopened, when efficiency is required too. The heuristic is domain knowledge expressed as a number, or it is a tuning knob.

The algorithmic knowledge gap it signals

h is a prediction, and every prediction needs a warrant. A warrant is a domain fact that bounds the remainder from below in the cost’s own unit: the straight line between two points, because no road is shorter than the line joining its ends. The gap question is where the estimate came from, and which fact keeps it from overshooting. Without that fact, faster search is bought by giving up the answer.

ImportantWhen the domain mandates it

A principled estimate exists and someone can derive it: straight-line distance for road networks, the triangle inequality doing the proof.

WarningWhen it’s a guess dressed as engineering

The heuristic is guessed to make the search fast. It is fast, and the answers are plausible, so the returned route ships. The optimality claim stays in the comment above the function while the estimate quietly overestimates in the one region of the graph that matters. The optimality claim leaves without a test failing, because no test compares the result with the true optimum.

TipThe faithfulness test

Can you name the domain fact that bounds the remaining cost from below — and does it hold everywhere the search runs?

  • If yes → A* is optimal, and the estimate is domain knowledge in numeric form. The fact you named is its warrant.
  • If no → say where the fact stops holding. No fact at all: drop the optimality claim. A fact that holds in part: scope the claim to that part.
  • If you can’t answer → unclear. You haven’t found A* wrong — you’ve found incomplete domain knowledge. Compare h against true remaining cost on instances you can solve exactly.

Case study: Greedy algorithms

Construct: A greedy algorithm takes the locally best option at each step and never reconsiders. Interval scheduling by earliest finishing time is optimal; coin change is optimal only when the coin system is canonical; first-fit packing carries no optimality guarantee and is often good enough. The algorithm encodes a claim about the input’s structure: that the local best choice leads to a globally acceptable outcome.

The algorithmic knowledge gap it signals

That claim is a theorem about the domain, not a property of the code. It survives when two choices can always be swapped without loss — as the 1, 2, 5, 10 coins allow and 1, 3, 4 do not. The gap question is whether the domain has that structure, or has issued a policy accepting a suboptimal answer. Both are legitimate. Neither is “it worked on our examples”.

ImportantWhen the domain mandates it

The structure holds, or the policy is explicit. Interval scheduling by earliest finish, where the swap argument is one paragraph. A minimum spanning tree, where an edge can be added only if it joins two unconnected parts. First-fit packing where an operations rule accepts wasted capacity above a threshold.

WarningWhen it’s a guess dressed as engineering

The counterexample is one step away. A non-canonical coin system invented by a loyalty programme. Scheduling with prerequisites, where the earliest-finishing task is not the one that unblocks the rest. Greedy on this shape is seductive because it is O(n log n), short, and correct on every example it was shown — and the examples were chosen by the person who wanted it to work.

TipThe faithfulness test

Can you state why local optimality survives to the global level — or has the domain explicitly accepted a possibly-suboptimal answer?

  • If yes → the structure holds, so optimality survives. If the policy was merely accepted, say so, and never call it proved.
  • If no → it is a heuristic wearing a proof’s clothes. Search for the counterexample, or compute the optimum.
  • If you can’t answer → unclear. You haven’t found greedy wrong — you’ve found incomplete domain knowledge. Brute-force the small inputs; one counterexample settles it.

Case study: Dynamic programming

Construct: DP solves a problem by combining solutions to overlapping subproblems over a state space: edit distance over prefix pairs in O(mn), knapsack over items times capacity in O(nW). It encodes two claims — the subproblems genuinely overlap, and optimal substructure holds, meaning the best answer assembles from the best answers to its parts — over a state space the domain recognizes. The state definition is the domain model. Two axes of a table are two distinctions the domain is willing to pay to keep apart.

The algorithmic knowledge gap it signals

Writing the state is a modelling act, and it is the whole decision. Items times capacity says the domain cares which items and how much room is left, not arrival order. Positions in one string times positions in the other says the strings are compared as sequences. The gap question has two halves: can the axes be named in the domain’s vocabulary, and do the subproblems genuinely overlap — the same state reached by several routes.

ImportantWhen the domain mandates it

Optimal substructure is real, and the state is a domain object. Edit distance, knapsack where capacity is a measured space. The table is large because the domain is that large, and the size is the honest cost of an exact answer.

WarningWhen it’s a guess dressed as engineering

The state carries distinctions the domain never asked about: the identity of the request, the tenant. The table then grows with traffic instead of with the problem, and the explosion gets blamed on “combinatorics”. Size is read as rigour: the table is big, so the state is assumed to have been thought through.

TipThe faithfulness test

Can you define the state in the domain’s words, and say why the subproblems overlap — or is the table just where the complexity went?

  • If yes → the state is the domain model. Check each axis against a question the domain actually asks.
  • If no → drop the axis, or drop the table. Either the distinction is not the domain’s, or the subproblems do not repeat.
  • If you can’t answer → unclear. You haven’t found DP wrong — you’ve found incomplete domain knowledge. List the state’s axes, then ask the domain owner which of them it distinguishes.

Case study: Divide and conquer

Construct: Solve the problem by splitting it into subproblems, solving each, and combining the answers. The choice encodes two claims the framing list does not name: the subproblems share no state, and the combine is cheaper than the work the split removed. Merge sort earns Θ(n log n) this way — merging two sorted halves is a linear pass, and there are log n such passes.

The algorithmic knowledge gap it signals

The domain must state that the split follows a real separation: the halves share no state, and no rule couples one half’s answer to the other’s. Sorting halves works because the position of one value does not depend on the other half — a domain fact about total orders, not a property of the code.

ImportantWhen the domain mandates it

The domain genuinely decomposes. Records partition by account, and one account’s aggregate is independent of every other’s, so combining is an addition over disjoint keys. A map covers disjoint regions, so each region’s answer stands alone. The combine is a sum, a max, or a union — cheap next to the piece work.

WarningWhen it’s a guess dressed as engineering

The halves are only apparently separate. Both write the same counter or session record, so the “independent” subproblems serialize at the combine and the split buys latency it cannot deliver. Or the merge dominates: a combine that passes over the whole output at every level turns the algorithm into its own combine step with recursion attached. The combine is where the claim is priced: eight partial sums is eight additions, eight merged runs is a pass over the whole output.

TipThe faithfulness test

Is the independence of the pieces a domain fact — and is combining cheaper than the work the split removed?

  • If yes → the split follows the domain’s own separation. Watch the combine as the data grows; it scales with the whole, not with a piece.
  • If no → say which claim failed. Coupled state: the pieces serialize. Dominant combine: the split gave back the work it removed.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. Time the combine against the total. If the combine is the majority, the split is not the decomposition.

Case study: Backtracking

Construct: Build a candidate one decision at a time and abandon a partial candidate the moment a constraint fails, then try the next option at that depth. The choice encodes one claim: the domain’s constraints are checkable on incomplete candidates, and they prune enough that the remaining search is affordable. The worst case stays exponential — O(b^d) for branching b and depth d — pruning lowers constants and effective depth, never that bound.

The algorithmic knowledge gap it signals

The domain must supply the rule that kills a prefix. A partial timetable is already wrong when two lectures claim one room at one hour, and that check is local and cheap. The recursion only carries the domain’s constraint structure; without such a rule the search has no reason to stop anywhere.

ImportantWhen the domain mandates it

Real constraint propagation exists. Scheduling with hard room and lecturer conflicts, where a conflict is decidable from the assigned prefix. Dependency resolution, where a version conflict is visible before the full set is chosen.

WarningWhen it’s a guess dressed as engineering

Brute force wearing the name. The recursion walks every subset and the “constraint check” runs only at the leaf, so nothing prunes and the run time grows with the whole space. Pruning that is unsound returns a wrong answer faster, which is worse than being slow.

TipThe faithfulness test

Does a domain rule kill a partial candidate early, near the root rather than near the leaf?

  • If yes → the search mirrors the domain’s constraint structure. Check next that the rule is sound and that it fires near the root, not near the leaf.
  • If no → it is enumeration with a stack. Bound the space before you run it, or accept that the run time grows with the whole space.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. Time a run at n items and at n+1. If the time doubles per added item, nothing is pruning.

Case study: Sliding window and two pointers

Construct: Keep a contiguous span between two indices, plus a rule that decides whether the span is valid. Both indices move forward only, so each element enters and leaves at most once and the pass is O(n) instead of O(n·k) for rescanning every window of size k. The choice encodes two claims: the answer is a property of a contiguous span, and validity is monotone in span length, so shrinking is the correct repair.

The algorithmic knowledge gap it signals

The domain must state the span rule and its bound: at most K distinct items, no more than X consecutive failures, sessions no longer than T. The algorithm assumes such a rule exists and that adjacency in the data means something. Where the domain never stated a span, the window has nothing to be faithful to.

ImportantWhen the domain mandates it

The domain states the span. Rate limits over the last T seconds. A rolling count or sum over five minutes, where shrinking the span is a subtraction. A circuit breaker opening after N consecutive failures, where “consecutive” is a domain word. Run-length constraints in validation.

WarningWhen it’s a guess dressed as engineering

The window sits over data whose relevant pairs are not contiguous. Two transactions that correlate may lie a month apart with unrelated rows between them. The size is often chosen because the algorithm needs one — 100 rows because 100 is round — so any pair separated by 101 rows is invisible. And non-monotone validity breaks it silently: if adding an element can restore validity, shrinking is the wrong repair and valid answers are skipped.

TipThe faithfulness test

Does the domain state the window rule and its size — or do the algorithm’s needs supply them?

  • If yes → the window is the domain’s own span rule and the bound is a number the domain stated. Check the ordering: a window means something only if adjacency means something.
  • If no → the window is a reading habit. The span is a pair the data never promised to keep adjacent, and the size is arbitrary.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. Ask what makes two records adjacent in this ordering. If nothing does, no window is faithful.

Case study: Quickselect and order statistics

Construct: Partition around a pivot and recurse only into the side containing rank k, discarding the rest. Average O(n), worst case O(n²) with bad pivots, O(n) guaranteed with median-of-medians. The choice encodes one claim: the domain consumes the k-th order statistic — the median, the top-k set, the percentile — and the ordering of the other n−1 values is work nobody reads.

The algorithmic knowledge gap it signals

The domain must state k and state that only the k-th value is consumed. A p99 SLA threshold is such a statement. So is a median with no requirement on the rest of the distribution. Where the domain never said which statistic it acts on, selection is a guess about what the reader will want.

ImportantWhen the domain mandates it

Percentile SLAs at p99, with a randomized or median-of-medians pivot, where nothing else is read. Median response time reported as one figure. Top-N by score where the set matters and order within it does not. Each case pays O(n) for one answer and never asks for the rest.

WarningWhen it’s a guess dressed as engineering

The median is computed, then the same report paginates and ranks the rows, so the sort happens anyway and the selection was a wasted extra pass. Or k is unstable: page size sets k, so the domain re-asks with a different k on every request, and each request pays O(n) over the same 50 million rows a hundred times a minute — where one sort and one index would have answered every k. Right per call, wrong per workload.

TipThe faithfulness test

Is the partial answer genuinely what’s consumed — or does the next step need the full order?

  • If yes → selection is the answer. Check next whether k is stable across requests, since that decides pass-per-request against sort-once.
  • If no → the full order is the real product. Sort or index once and answer every k from it.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. Trace the value one step downstream; that step decides.

Case study: Reservoir sampling

Construct: Keep k items from a stream of unknown length so that every item seen so far is in the sample with probability k/n. The classic form holds the first k, then keeps the i-th item with probability k/i in place of a uniformly chosen one. The choice encodes one claim: a uniform sample answers the question, and a census is neither needed nor possible.

The algorithmic knowledge gap it signals

The domain must pose a question about the population and accept a sampling error. For a proportion, the 95% margin is 1.96 × 0.5/√k, so a thousand items give about ±3% — a number someone states and accepts, not one discovered later. Where the domain asks about a particular item, no sample size helps.

ImportantWhen the domain mandates it

Population-level questions with a stated error. The fraction of requests that fail, to a margin someone wrote down. The share of requests slower than 300 ms. In each case the answer is a rate over the population, the error is written beside it, and no individual item is the subject. A distribution’s shape is a different question, and a reservoir answers it only at the quantiles it can support.

WarningWhen it’s a guess dressed as engineering

Fraud review, compliance audit, incident triage: the question is per item, and the rare event is exactly what a uniform sample misses. At one event in 10,000 and a sample of 1,000, the chance of missing it is about 90%. Then sample statistics get reported as facts — “the sample shows no failures” becomes “there were no failures”. Uniform inclusion is itself a claim: where rare events matter, stratified sampling — sampling within each group — is the right instrument, not the cheap one.

TipThe faithfulness test

Is the question about the population — and is the sampling error a stated, accepted bound?

  • If yes → a sample of stated size answers it, and the error is a number someone wrote down beside the metric.
  • If no → say which half failed. Per-item question: no sample size answers it. Population question with no stated bound: state one and accept it.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. Ask what decision the number feeds. If one missed item changes that decision, the question is per item.

Case study: Streaming approximate algorithms

Construct: HyperLogLog estimates cardinality from the longest run of leading zeros in each of m registers; with 16,384 registers of six bits, 12 KB, the standard error is 1.04/√m, or 0.81%. Count-Min Sketch estimates item frequencies from d arrays of counters and only ever over-counts. Both encode one claim: an estimate carrying a stated error bound is acceptable, and exactness is not a requirement.

The algorithmic knowledge gap it signals

The domain must accept a bound and name the decisions the number feeds, so the acceptance is explicit rather than accidental. Where nobody can say which decision reads the number, nobody can say whether 0.81% is acceptable, and the Count-Min is a guess about tolerance.

ImportantWhen the domain mandates it

Dashboards, alert thresholds, and capacity planning, where 9,980 and 10,000 distinct users lead to the same decision. Cardinality of a label set when the question is “ten series or ten thousand”. Trend detection, where the movement matters and the last digit does not.

WarningWhen it’s a guess dressed as engineering

Billing and reconciliation counts: the approximate answer becomes a money number someone acts on. A 0.81% standard error on four million events is 32,500 events at one sigma, 65,000 at two, and at a per-event price that is an invoice line. Count-Min only over-counts, so a “block above 1,000 requests” rule fires early and never late — maybe fine, never chosen. Often the bound is unstated: a Count-Min sized for 1% error then answers a decision that needs 0.01%.

TipThe faithfulness test

Does an error of the stated size leave every decision that reads this number unchanged?

  • If yes → the estimate is the knowledge and the error is its contract. Put the bound next to the number.
  • If no → the number became a fact by accident. Exact counting is the repair, and it costs the memory that made the sketch attractive.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. List the consumers of the number. If any of them acts per item, the estimate is the wrong tool.

Case study: Consistent hashing

Construct: Consistent hashing places nodes and keys on a hash ring, and a key belongs to the first node at or after its position. Adding a node splits one arc, so roughly 1/n of the keys move instead of (n−1)/n. The choice encodes one claim: membership changes, and remapping the whole key space on each change costs more than the ring costs to keep.

The algorithmic knowledge gap it signals

For the ring to be knowledge, the domain must have decided that the node set is dynamic. It must also decide that the remap cost matters: at ten nodes a full remap loses ten of every eleven warm entries, and that loss must outweigh the ring’s complexity. The gap question: does membership actually change here, and what does one change cost?

ImportantWhen the domain mandates it

A cache tier or shard cluster that scales with load, where nodes join on a capacity schedule and leave on failure. The misses that follow a join are bounded by the fraction that moved. The domain owns the fact: capacity is elastic, and churn is its normal state.

WarningWhen it’s a guess dressed as engineering

Three nodes, provisioned by hand, in a deployment that has not scaled in two years — and has no plan to. The ring remains. So do the virtual nodes (several ring positions per node), the rebalancing tool, and the key-placement debugging. None answers a question this deployment asks. The seductive form runs the other way: a fleet that scales weekly, where the team skips the ring because “we only have a few nodes,” and pays a full remap every Monday.

TipThe faithfulness test

Does membership actually change on this system — how often, measured? Is the remap cost real here or inherited from another system’s scale?

  • If yes → the ring is the knowledge. Record the churn rate and the fraction of keys each change moves.
  • If no → it is a fixed placement carrying a ring’s maintenance bill. Take modulo, or a static table.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. Count the membership changes in the deploy log over six months.

Case study: Join algorithms (nested loop, hash join, sort-merge)

Construct: A nested loop reads the outer input once and the inner input once per outer row: n × m reads without an index on the inner side, about n × log m with one. A hash join builds a table on one input and probes with the other in linear time, and needs the build side to fit in memory. A sort-merge join sorts both inputs and merges them, which is also the one that serves range predicates. All three encode the same claims: which input is small, how much of it survives the filters, and which of an index, a memory budget, or sorted input the domain supplies.

The algorithmic knowledge gap it signals

For the plan to be knowledge, someone must know that the domain produces tables at these sizes, and that these predicates keep this fraction of rows. The gap question is the size ratio and the selectivity — the fraction of rows each filter keeps — on this data, with these filters, not a ratio a benchmark reported for another schema.

ImportantWhen the domain mandates it

The sizes are measured on the real tables: a 50-million-row fact table joined to a 2,000-row currency dimension, where building the hash on the dimension and probing with the fact reads each table once. The domain supplies the ratio, and the plan follows from it.

WarningWhen it’s a guess dressed as engineering

The plan carries yesterday’s statistics. “The filter makes it small” states a selectivity nobody measured, and the estimate holds until one customer’s data arrives. It all works in development, on ten-thousand-row fixtures, where every plan is fast and every plan is wrong for the same reason: nothing was measured at production size.

TipThe faithfulness test

Has the small side been measured on this data, with these filters — and recently enough to trust?

  • If yes → the plan follows, if the build side fits memory and the index exists. Recheck counts after each backfill.
  • If no → the plan pays for an unmeasured prediction. Read the actual row counts, then choose.
  • If you can’t answer → unclear. You haven’t found the join wrong — you’ve found incomplete domain knowledge. Run the join with EXPLAIN ANALYZE and compare estimated to actual rows per node.

Case study: Recursion instead of iteration

Construct: Each recursive call takes a stack frame: parameters, locals, return address. The stack is finite — typically 8 MB on Linux for the main thread, around 1 MB default on a JVM thread, and Python stops itself at 1,000 frames. Recursion therefore encodes one claim about the input: the depth is bounded, and the bound is comfortably under what the stack holds.

The algorithmic knowledge gap it signals

The depth bound is a claim about the shape of the input, not about the code. For recursion to be knowledge, the domain must have decided that shape: a grammar with a declared maximum nesting, a hierarchy with a known height, a tree the system itself builds. The gap question: is that shape a domain fact, or a property of the fixtures the tests happened to use?

ImportantWhen the domain mandates it

An org chart eight levels deep. A category tree whose schema declares four levels. Balanced tree traversal, where depth is log n and n is bounded by memory anyway. An expression tree the parser builds from its own grammar, so its depth is bounded by the nesting the language defines. Here the bound is a domain fact, and the recursion states it.

WarningWhen it’s a guess dressed as engineering

Recursion over user-supplied nesting: JSON from an API, reply threads, folder hierarchies, XML from a third party. The producer decides the depth and has published no limit. Recursion is clearer to read, the tests use shallow fixtures, and the single input that breaks it arrives from one customer’s import at 3 a.m. The guard is worse than the recursion: a depth limit of 1,000 chosen because the test passed at 900 is an enforcement of a number nobody owns.

TipThe faithfulness test

Does the domain bound the depth, with a limit you can cite?

  • If yes → the recursion states the bound. Record it next to the function that relies on it.
  • If no → the recursion bets on a bound nobody owns. Iteration pays in clarity; a guard pays in a number you must justify.
  • If you can’t answer → unclear. You haven’t found the recursion wrong — you’ve found incomplete domain knowledge. Measure the deepest input the producers actually send.

Case study: Batch versus incremental recomputation

Construct: Batch recomputes the whole answer from the whole input. Incremental applies only the delta to the answer already held. The choice encodes two claims the framing list does not name: how often the input changes, and how stale the answer may be.

The algorithmic knowledge gap it signals

Both claims are domain facts. The ledger posts at 23:00 and prices change hourly — that is a change rate. The report is read at 07:00 by a controller who accepts yesterday’s close — that is a staleness tolerance. Neither is a property of the code. The gap question: has anyone stated the freshness number, and has the person who reads the number accepted it?

ImportantWhen the domain mandates it

Nightly totals for a morning report, where the freshness is stated and accepted in writing. Incremental maintenance where reads outnumber writes by orders of magnitude and each change touches a small fraction of the answer, so the delta path pays for itself. In both cases the change rate and the tolerance were named before the mechanism was chosen.

WarningWhen it’s a guess dressed as engineering

The mirror image of the hook is the seductive one: a change log, incremental tables, and a reconciliation job for a report a nightly forty-minute batch already answered, because nobody measured that the input changes twice a day. Behind both sits the same artifact — a “real-time” requirement that traces to no business rule, defended by the fact that it sounds like a requirement.

TipThe faithfulness test

Has someone accepted how stale the answer may be — and is the input’s change rate measured?

  • If yes → choose the cheaper mechanism that meets both numbers.
  • If no → the choice is a preference, not engineering. Write the two numbers down first.
  • If you can’t answer → unclear. You haven’t found the choice wrong — you’ve found incomplete domain knowledge. Count the writes per day, then ask the reader what staleness they would notice.
