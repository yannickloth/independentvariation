SQL Statement Semantics

SQL statement semantics as knowledge claims.

A query’s shape claims something about the domain — what exists, what counts, what order means, what NULL means. Each post states the claim and the fact it needs.

Pick a post on the left. It opens on the right.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Case study: Three-valued logic (NULL in a comparison)

A revenue report comes up short by 2,190 orders. The table also holds 2,190 rows whose status is NULL, and no clause of the query ever mentions them.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: NULL is not a value; it marks the absence of one, so it equals nothing, not even itself. Every value comparison with NULL yields UNKNOWN, and WHERE keeps only TRUE. status <> 'cancelled' is TRUE for shipped, FALSE for cancelled, UNKNOWN for NULL — and NOT (status = 'cancelled') is UNKNOWN as well. Neither predicate covers the NULL rows.

The SQL knowledge gap it signals

The query splits the table’s rows into three parts while the writer holds a two-part mental model. Writing the filter requires knowing whether the column is nullable, and what the NULL means here: not yet decided, not applicable, or unknown to the source system. Under “unknown”, excluding those rows is a lie about coverage.

The gap question: for each comparison in this query, where do the NULL rows go?

ImportantWhen the domain mandates it

WHERE status <> 'cancelled' OR status IS NULL — the writer knew the NULL rows were in scope and said so in the statement. The standard goes further: IS DISTINCT FROM treats NULL as a value, so each such comparison answers TRUE or FALSE.

WarningWhen it’s a guess dressed as engineering

The exclusion query that drops every NULL-status row. It is seductive because the query is well-formed, the filter reads like the English requirement, and a NULL status is invisible in the output. The count then falls short by exactly the unknowns, and the complementary report falls short by the same rows, so the two totals never reconcile to the table and nobody can say why.

TipThe faithfulness test

For each comparison in this query: where do the NULL rows go — stated, or unknown?

  • If yes → the row set is closed and the aggregate is meaningful. Check the aggregates next: COUNT(col) skips NULL, COUNT(*) does not, AVG divides by the non-NULL count.
  • If no → the comparison is a filter with an unstated third outcome, answering a question nobody asked. Add IS NULL, or make the column NOT NULL so the guess cannot recur.
  • If you can’t answer → stop. Find the column’s nullability, then count the NULLs before trusting any total. The choice waits until that is on file.

Case study: LEFT JOIN demoted by a WHERE clause

A LEFT JOIN kept all 9,400 customers. One WHERE condition on the right table removed 1,340 of them, and the join became an inner join without anyone editing the join.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: A LEFT JOIN promises at least one output row per left row even when the right side has no match, padding the missing right columns with NULL. A WHERE condition on a right-table column then tests those padded rows too: b.type = 'purchase' is UNKNOWN when b is NULL, so the row is discarded. The keyword still says LEFT; the result is INNER.

The SQL knowledge gap it signals

The writer must know whether the domain needs every left row: every customer including those who never ordered, every account including those with no transactions. Missing purchases appear as gaps in the output; missing customers do not.

The gap question: does any WHERE condition on the right table exist — checked — and did anyone intend an INNER JOIN?

ImportantWhen the domain mandates it

Right-table conditions live in the ON clause, where the promise survives: the left row stays and the right columns come back NULL. The deliberate anti-join WHERE b.id IS NULL asks the outer join’s question directly.

WarningWhen it’s a guess dressed as engineering

LEFT JOIN orders b ON b.customer_id = c.id WHERE b.type = 'purchase'. Every customer without a purchase vanishes and the count drops to the match count. It is seductive because the LEFT JOIN looks like the careful choice, the author believes the guarantee is preserved, and no error is raised: the query returns a smaller, well-formed, plausible table. The shortfall is exactly the left rows with no right row of type purchase.

TipThe faithfulness test

For each LEFT JOIN: does any WHERE condition on the right table exist — checked — and did anyone intend an INNER JOIN?

  • If yes → the outer join is an inner join wearing an outer join’s name. Move the condition into ON, or delete the LEFT keyword and stop claiming a guarantee the query does not give.
  • If no → every left row survives — the rows are the join’s full result, not a filtered one. Check that consumers expect NULLs there.
  • If you can’t answer → stop. Compare COUNT(*) with COUNT(b.id): the difference is the left rows with no right. The choice waits until that is on file.

Case study: NOT IN against a set that contains NULL

The exclusion query returned zero rows for three weeks. The blocklist held 40 values, one of them NULL.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: NOT IN is shorthand for a conjunction of inequalities. id NOT IN (1, 2, NULL) means id <> 1 AND id <> 2 AND id <> NULL. The last conjunct is UNKNOWN for every id, UNKNOWN absorbs the conjunction, and no row can satisfy the predicate. The answer is empty for every id — unsatisfiable, not merely over-selective.

The SQL knowledge gap it signals

The writer must know whether the subquery’s column can return NULL: a nullable foreign key, an optional attribute, or a LEFT JOIN inside the subquery each produce one. The negation is only safe when that column is provably total, and “nobody inserts NULL there” is a belief, not a proof.

The gap question: can the subquery return NULL — proven — or should this be NOT EXISTS?

ImportantWhen the domain mandates it

NOT IN over a subquery column declared NOT NULL, where the constraint is the proof rather than the hope. Or NOT EXISTS for the negation: it tests row existence, not value equality, so a NULL in the subquery cannot match and the intended answer survives.

WarningWhen it’s a guess dressed as engineering

The exclusion list that gains one NULL row — an import left a cell blank, or a LEFT JOIN in the subquery padded one in. It is seductive because the query is idiomatic, the list is short and looks curated, and the empty result reads as “nothing was excluded” or “the filter cleaned everything” — when it is the correct answer to an accidental question: is this id different from every listed value, including an unknown one?

TipThe faithfulness test

For each NOT IN: can the subquery return NULL — proven — or should this be NOT EXISTS?

  • If yes → any NULL in the list disables the whole predicate. Rewrite as NOT EXISTS, then compare the row counts before and after.
  • If no → the NOT NULL constraint is doing the work, so check it survives every load path: staging tables, imports, and backfills each need it.
  • If you can’t answer → stop. Read the subquery column’s definition and every writer of it, then count its NULLs directly. The choice waits until that is on file.

Case study: GROUP BY as a grain claim

A revenue report groups by region and prints a sales rep’s name beside the total. The named rep did not earn the total — the query picked an arbitrary row.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: GROUP BY states the grain of the answer: one output row per distinct combination of the grouped columns. Every selected column must therefore be grouped, aggregated, or functionally dependent on the grouped columns; standard SQL rejects the rest. MySQL with ONLY_FULL_GROUP_BY off, and SQLite by default, accept it and return a value from an arbitrary row of the group.

The SQL knowledge gap it signals

The writer must know the grain of the business question: one row per region, per region per month, per rep per month. The grain is a domain fact, not a formatting choice — a total is defined at a grain, and the label beside it must live at the same one.

The gap question: what is one output row of, exactly — stated — and is every column grouped, aggregated, or dependent?

ImportantWhen the domain mandates it

Every selected column is grouped or aggregated, and the groups match the report’s claim: one row per region per month, said in the header and true in the query. Then every label in a row belongs with the number.

WarningWhen it’s a guess dressed as engineering

The lenient GROUP BY returning an arbitrary row’s value for the ungrouped column. It is seductive because the query runs, the total is right, and the name belongs to a real rep who does sell in that region — so nothing looks broken. The report is a total joined to a person who did not earn it, and the name can move when the plan does.

TipThe faithfulness test

For this query: what is one output row of, exactly — stated — and is every column grouped, aggregated, or dependent?

  • If yes → the aggregate is defined at a named grain. Check it is the report’s grain, not a coarser one summed into a finer label.
  • If no → the query aggregates at a grain nobody wrote down, and the ungrouped column is a pick, not a fact. Add it to GROUP BY, or replace it with an aggregate the domain permits.
  • If you can’t answer → stop. Find the table’s key, then name the business entity one output row denotes. The choice waits until that is on file.

Case study: HAVING versus WHERE

A row filter moved into HAVING drops whole groups or counts the excluded rows, so the total is wrong either way.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: WHERE evaluates rows before grouping; HAVING evaluates groups after aggregation. Two grains: the row and the group. The shape claims which grain the rule belongs to.

The SQL knowledge gap it signals

The writer must know whether “more than three orders” filters rows before counting them, or counts a customer’s orders and tests the total. Both readings yield a number; only one is the question. A condition that each row meets or fails belongs before the count, because afterwards it changes what is counted.

The gap question: which grain does this rule belong to — the row or the group?

ImportantWhen the domain mandates it

WHERE on the raw rows: shipped orders only, one region, a closed range. HAVING on the aggregate’s meaning: accounts whose summed balance exceeds the limit, customers with more than three orders. The test is the subject, not the grammar: does the condition speak about one row or about the group? One row is WHERE; a group is HAVING.

WarningWhen it’s a guess dressed as engineering

The aggregate condition pushed into WHERE, which standard SQL rejects — it moves to HAVING to make it run, and the row condition follows. MySQL without ONLY_FULL_GROUP_BY, and SQLite, accept HAVING status = 'shipped' on an ungrouped column, evaluate it on one arbitrary row of the group, and drop the whole group on that row’s value. The mirror image: HAVING used as “WHERE for grouped queries,” filtering groups by a fact about their members while the writer thinks they filtered rows. It runs, the totals look plausible, and they span rows the rule meant to exclude.

TipThe faithfulness test

For each filter: does it constrain the rows or the groups — stated — and is that the question being asked?

  • If yes → the clause records the grain. Check that the filters before the count are the ones the count’s definition assumes.
  • If no → the count is taken over the wrong grain. Move each condition to the clause matching its subject.
  • If you can’t answer → stop. Write each metric as one sentence, then place each condition against the noun it constrains. The choice waits until that is on file.

Case study: No ORDER BY, no ordering guarantee

A report has come out sorted for six years. A parallel plan appears, no code changes, and rows arrive in a different order.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: A table is an unordered multiset: rows have no position, and no operator reading them promises a sequence. Without ORDER BY the engine returns rows in whatever order the plan produces — index scan, hash build, worker arrival. The statement claims nothing about sequence, so a consumer reading sequence relies on an unstated fact.

The SQL knowledge gap it signals

The writer must know whether sequence is part of the answer or only part of the reading habit. Order belongs to the question, not the storage. A client rendering rows top to bottom turns an accident into an expectation the database never agreed to.

The gap question: does any consumer of these rows depend on their sequence?

ImportantWhen the domain mandates it

Every consumer depending on sequence states it: the API page, the feed, the ledger statement, the migration applying changes in order. Order belongs on the outermost query — ORDER BY in a subquery or view is not carried outward as a contract, and engines that keep it do so by accident.

WarningWhen it’s a guess dressed as engineering

The report that always came out sorted, until the parallel plan or the new index. Nothing was tested, because the test asserted rows exactly as its environment produced them — a green suite proving the plan, not the query. The failure reads as an intermittent bug, and the fix gets filed against the export layer.

The sharper variant: LIMIT 10 with no ORDER BY, labelled “top ten.” It returns ten rows, not the ten highest, and they can change with the plan.

TipThe faithfulness test

For each query whose consumer cares about order: is ORDER BY written — or is the order an accident being trusted?

  • If yes → the sequence is a stated claim. Check that the sort key is unique, or that a tie-breaker follows.
  • If no → nothing was promised. Add ORDER BY at the outermost query, or drop the consumer’s dependence on sequence.
  • If you can’t answer → stop. List the consumers, then mark which would change output on shuffled rows. The choice waits until that is on file.

Case study: Ties without a tie-breaker

One row appears on page two and again on page four. Its neighbour appears on no page, and the SQL is correct.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: ORDER BY created_date imposes a partial order: rows sharing a date are equal, and the engine may return them in any sequence. LIMIT and OFFSET re-execute the whole query per page, so a tie straddling a page boundary can be cut at a different place each time — the same row can surface twice, or slip between two pages and land nowhere. Pagination needs totality: no two rows compare equal.

The SQL knowledge gap it signals

The writer must know whether the sort key is unique, or which second column makes it so. Timestamps, prices, scores, and truncated dates can be non-unique in practice; a tie can be rare in staging and routine the day one batch writes two records. Pagination claims something about every pair of rows, so one duplicate breaks it.

The gap question: is the sort key unique, or is there a stated tie-breaker?

ImportantWhen the domain mandates it

A unique tie-breaker appended — ORDER BY created_date, id — makes every page disjoint and complete while the table holds still, and the proof is one line: distinct sort tuples. Keyset pagination goes further, seeking WHERE (created_date, id) > (?, ?) instead of counting rows to skip, so the boundary is a value, not an offset, and ties cannot shift it, giving up the jump to a page number.

WarningWhen it’s a guess dressed as engineering

ORDER BY created_date LIMIT 20 OFFSET n. It looks right on every page a developer opens: stable while the plan is stable, and ties near boundaries are absent in a small table. OFFSET reads like a cursor resuming where the last page stopped; it is a skip count computed by re-running the query and re-deciding ties. Add a second non-unique key, and the illusion holds while the guarantee does not.

TipThe faithfulness test

Is the sort key unique — or is there a tie-breaker — stated, so pagination is provable?

  • If yes → the order is total. Check that the tie-breaker is unique on the data, not only on today’s sample.
  • If no → pages overlap and leak by construction. Append a unique column, or switch to keyset pagination.
  • If you can’t answer → stop. Compare COUNT(*) with COUNT(DISTINCT sort_key) on the real table. The choice waits until that is on file.

Case study: ROW_NUMBER versus RANK

Two players tie for first. The report numbers them 1 and 2, the medal table shows two golds, and the ceremony disagrees with both.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: All three number rows in a partition, each claiming something different about equality. ROW_NUMBER promises distinct consecutive integers, so equal keys get an order the engine picks and a plan change re-picks. RANK promises equal ranks for equal keys and skips what a tie consumes: 1, 1, 3. DENSE_RANK promises equal ranks with no gap: 1, 1, 2. Three claims about ties: none, equal with a gap, equal without.

The SQL knowledge gap it signals

The writer must know what a tie means before choosing. Two rows with the same score: same standing, or a deterministic order that must be provable, or labels for a list? Top-N needs exactness: a unique tie-breaker belongs in the ORDER BY. Standings need the opposite — equality preserved, gaps included: after two joint firsts no row is second.

The gap question: what does a tie mean here, and does the function chosen say the same thing?

ImportantWhen the domain mandates it

Arbitrary-but-total for top-N per group: ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC, id DESC) = 1 picks the latest order reproducibly: a unique column breaks ties. RANK where shared standing is the truth: competition results, exam grades, severity bands.

WarningWhen it’s a guess dressed as engineering

ROW_NUMBER used as “the ranking” for a leaderboard. Tied players are numbered 1 and 2 by storage order; the report stays stable until the table is rewritten or the plan changes, then the medals can swap between two people with identical scores.

The mirror trap: RANK for top-N returns eleven rows for WHERE rank <= 10 once a tie straddles the cut.

TipThe faithfulness test

For each ranking query: what do ties mean to the domain — and does the function chosen say the same thing?

  • If yes → the numbering encodes the domain’s tie rule. Check that the window’s ORDER BY is unique where exactness is demanded.
  • If no → the numbering imposes a tie rule nobody stated. Switch function, or add the tie-breaker the domain recognizes.
  • If you can’t answer → stop. Count duplicate sort keys, then ask what equality means. The choice waits until that is on file.

Case study: DISTINCT as a bug mask

A join returns 4,000 rows where the domain expects 1,000. Someone adds DISTINCT, the count drops back to 1,000, and the fan-out (row multiplication) that produced the extra rows stays in the query.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: DISTINCT compares each complete result row against every other complete result row and discards the duplicates. It claims that the data can produce identical rows and that the result must not contain them. That claim concerns the output alone: the duplicates are removed after the join multiplied them, so the count a reader sees no longer measures what the join did.

The SQL knowledge gap it signals

The writer must know which of two facts holds: the duplicates came from the data, or they came from the join. If the join generated them — a missing condition, a fan-out on a one-to-many key — the query now returns a correct count over an incorrect row set. The gap question: what in the data makes these rows identical?

ImportantWhen the domain mandates it

Counting uniques. “How many distinct customers ordered this month?” The column holds duplicates because one customer orders many times, and the question asks for customers, not orders. DISTINCT is that question, written down. The same holds for a list of distinct shipping countries, or distinct product ids across a set of invoices.

WarningWhen it’s a guess dressed as engineering

DISTINCT appended after a row count “came out too high.” The dedup restores the number, the review passes, and the missing join condition stays. The duplicates are now invisible: a region total sums correctly because each duplicated row collapsed, and nobody sees that one order was joined to four addresses. The keyword reclassifies a wrong join as a property of the data.

TipThe faithfulness test

Was DISTINCT written because the domain counts uniques — or because the join produced too many rows?

  • If yes → the keyword is the domain’s question. Check that distinctness is stated over the columns that matter, and that the dedup is not collapsing rows the domain counts twice.
  • If no → the join is the defect. Remove DISTINCT, then fix the condition or the grain (what one row denotes).
  • If you can’t answer → stop. Count rows before and after each join, and name the key that should be unique. The choice waits until that is on file.

Case study: UNION versus UNION ALL

Two branches that cannot return the same row. One keyword still sorts or hashes the whole result on every run to prove that they don’t.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: UNION combines the branches, then removes duplicate rows across the combined result — typically through a sort or a hash — and returns each surviving row once. It claims that the branches can produce identical rows and that the result must not contain them. UNION ALL concatenates the branches and claims nothing about overlap; every row from every branch appears.

The SQL knowledge gap it signals

The writer must know whether the branches can overlap. They can when one source is queried twice under predicates that do not exclude each other, or when a current table and an archive table share key values. They cannot when the branches read disjoint sources, or one source under mutually exclusive predicates — and the projection keeps the rows apart. The gap question: can branch A and branch B return the same row?

ImportantWhen the domain mandates it

A partial migration leaves the current orders table and the archive table with overlapping id ranges, and a mailing list needs each customer once. Or one branch selects buyers, another selects complainants, and a recipient must appear once. The branches genuinely can return the same row.

WarningWhen it’s a guess dressed as engineering

UNION between branches that are disjoint by construction: one predicate on status ‘open’, one on status ‘closed’, both over the same table, and status in the select. Every run pays a sort or hash over the full result to remove duplicates that cannot exist. The inverse trap is quieter: UNION ALL over a current table and a history table that started to overlap after a re-import. Then one customer is counted twice, and the total is wrong with no error to show for it.

TipThe faithfulness test

Can these branches return the same row — proven — and was the dedup cost accepted knowingly?

  • If yes → UNION states the domain’s rule. Check the cost against the result size, since the dedup — sort or hash — is paid on every run.
  • If no → UNION ALL, and say in the query why the branches are disjoint.
  • If you can’t answer → stop. Read the predicates: the disjointness you rely on is either written down or it is not. The choice waits until that is on file.

Case study: The scalar subquery

A lookup starts returning two rows, and the query does not return the first one. It fails at runtime, on the one row that broke the assumption.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: A scalar subquery stands where one value is required: in the SELECT list, or in a comparison. It claims the inner query returns at most one row for that position, and most engines enforce it: two rows raise a cardinality violation (SQLite takes the first). Zero rows yield NULL, so “none” arrives as a value and the claim stays at most one, never exactly one.

The SQL knowledge gap it signals

The writer must know what holds the inner result to one row. Three things can: a constraint, such as a unique index on the lookup key; an aggregate, such as MAX, which collapses any number of rows to one; or hope. The gap question: for each scalar subquery, which of the three?

ImportantWhen the domain mandates it

An aggregate over a set: the highest price in a price history, the maximum approval date for an order. A lookup by primary key, where the constraint guarantees the cardinality. A correlated subquery reading a unique index per outer row. In each case the guarantee is written where the engine and a reader can both inspect it.

WarningWhen it’s a guess dressed as engineering

The lookup runs on a business key only believed unique — an email address, a SKU, a national identifier — and stopped being unique when an import merged two systems. It works for a year. Then production fails on the single duplicated row in a query nobody changed. The seduction is the first thousand runs: a working query looks like a proven claim. Where the inner query carries a LIMIT 1, the failure disappears and the query picks a row arbitrarily — worse than the error.

TipThe faithfulness test

What guarantees at most one row — a constraint, an aggregate, or hope?

  • If yes → the claim is grounded. Check that the constraint still holds in the data, not only in the schema.
  • If no → the subquery is a bet. Add the constraint, add the aggregate, or make the multi-row case explicit in the query’s shape.
  • If you can’t answer → stop. Group the inner key and count the rows where the count exceeds one. The choice waits until that is on file.

Case study: Implicit type coercion in comparisons

A varchar column compared to a number turns an index lookup into a full scan — and the stored value into something nobody wrote.

Writing a SQL statement? Ask “which claim does this query make about the data — what exists, what counts, what order means, what NULL means?” If you can’t answer, you’ve found a knowledge gap: the query enforces a guess. If you can, the query is knowledge embodied — the statement catching up to what the data actually contains.

Construct: When a comparison puts two different types side by side, the dialect’s coercion rules decide whether they compare at all. The statement claims these values are comparable, and that one side converts to the other’s type without loss. Two costs follow. The conversion happens per row, so an index on the converted column cannot be read. The conversion may also change the value.

The SQL knowledge gap it signals

The writer must know the declared type of both sides and whether the conversion keeps the meaning. The gap question: are both sides the same type, stated in the query — or is the engine translating a claim nobody wrote?

ImportantWhen the domain mandates it

A cast at a boundary where the types genuinely differ, with the conversion named. A legacy text column of identifiers is cast once, on the parameter side, so the indexed column keeps its type and the cost is one conversion. A date literal written as DATE ‘2027-01-01’, not left as a string. The conversion is visible, so a reader can check it.

WarningWhen it’s a guess dressed as engineering

An order reference stored as varchar, compared to a numeric parameter. Every row is converted, the index goes unread, and the query scans the table while looking identical to an indexed one. Dates stored as strings are the quieter variant: lexical order matches calendar order only while every row is zero-padded and formatted alike. One ‘2027-2-1’, or a locale format, silently reorders the result. Dialects disagree, and that changes the claim. PostgreSQL raises an error. MySQL converts the string to a number — zero when it has no numeric prefix — so = 0 matches every row without one.

TipThe faithfulness test

Are both sides the same type — stated in the query — or is the engine translating a claim nobody wrote?

  • If yes → the comparison is grounded. Check that the cast sits opposite the indexed side.
  • If no → state the type, or cast deliberately at the boundary, knowing the cost.
  • If you can’t answer → stop. Read the column definitions, then the parameter types, and compare them. The choice waits until that is on file.
