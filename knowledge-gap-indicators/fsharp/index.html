F# Constructs

F# constructs as compiled knowledge claims.

Computation expressions, units of measure, type providers — compile-time knowledge drawn from data. Each post names what the construct knew, and when it knew it.

Case study: Computation expressions

Two builders both called “result”: one stops at the first failed step, one collects all of them. The call sites look identical.

Writing an F# construct? Ask “which fact does the type carry — units, effects, exhaustiveness — and when is it checked?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: A computation expression is a builder object plus syntax. let! x = e desugars to builder.Bind(e, fun x -> ...) (or a fused Source form when the builder defines one), return to Return, and! to MergeSources or a BindN, whatever the builder defines. The builder decides what a bind means — stop on first error, accumulate all, await, retry — and the syntax hides that decision behind let!.

The F# knowledge gap it signals

Know your workflow’s failure semantics first: does one failed step end the run, or must every failure report in one pass? A payment authorization stops: the second step is invalid once the first refused. A form validation reports all fields; no user should submit five times to learn five things. Both look like let!, and only the author knows which this is.

The gap question: for this workflow, what does one failed step mean — stop, accumulate, retry — and does the builder actually do that?

ImportantWhen the types encode reality

Steps as sequential obligations: read the order, charge the card, write the receipt. Any failure aborts, and a short-circuiting Bind is exactly that rule. Or a validation builder where and! accumulates every violation into one pass.

WarningWhen it’s a guess dressed as engineering

The computation expression was adopted “for readability”. The builder comes from a library because let! beats nested matching, and nobody reads its Bind. A record then fails two rules, the short-circuiting builder returns the first, and the second error waits for the next submission. The syntax matches an accumulating builder’s, so review sees nothing. The elegance was real; the failure semantics were never decided.

TipThe faithfulness test

For this workflow: what does one failed step mean — stop, accumulate, retry — and does the builder actually do that?

  • If yes → the syntax carries the domain’s rule. Check the builder’s Bind, not the call sites.
  • If no → the construct asserts a failure rule your domain lacks. Swap the builder, or handle what it drops.
  • If you can’t answer → stop. Write down what happens to the other steps when one fails, then read Bind against it. The choice waits until that is on file.

Case study: Units of measure

A length in metres plus a length in feet refuses to compile — and the same two numbers, cast to float for a library call, add up silently.

Writing an F# construct? Ask “which fact does the type carry — units, effects, exhaustiveness — and when is it checked?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: [<Measure>] type m makes float<m> a dimensioned number, and arithmetic keeps the dimension: metres times metres is float<m^2>, metres plus feet is a type error. The check runs entirely in the compiler — the units are erased, so nothing exists at runtime and nothing re-checks it later. Conversions become explicit factors like 0.3048<m/ft>.

The F# knowledge gap it signals

Dimension is a claim about the quantity itself, and the author must know which quantities have one: is this number a length, a duration, a rate, a count, money? float<m/s> and float<kg/s> are both “a rate” and are not interchangeable. A type says which.

The gap question: which numbers in this system carry units — typed — and at which boundary do the units disappear?

ImportantWhen the types encode reality

A measured calculation: structural spans in metres against a specification table in feet, with the conversion written once as 0.3048<m/ft>. The mixup that ships elsewhere is a compile error here, at the line. Dosages, flow rates, fuel per distance behave alike.

WarningWhen it’s a guess dressed as engineering

The dimensional claim stops at the interop edge. The core is typed, then a DTO needs double Length for JSON, a column is float, a plotting call takes plain floats — and the unit is stripped by a cast to float, at the boundary, where no reviewer looks twice. The metre/foot mixup now lives exactly where the compiler was told to stop caring, and the runtime has no units left to disagree with.

TipThe faithfulness test

Which numbers in this system carry units — typed — and at which boundary do the units disappear?

  • If yes → the compiler guards the interior. List the boundaries and check each conversion factor by hand.
  • If no → the numbers are plain float and the dimensional claim lives in a comment or a variable name. Add the measures, starting at the boundary that hurts.
  • If you can’t answer → stop. Walk the data path and name the unit of every stored number. The choice waits until that is on file.

Case study: Type providers

A column gets renamed upstream. The build stays green, because it read a sample file committed in March.

Writing an F# construct? Ask “which fact does the type carry — units, effects, exhaustiveness — and when is it checked?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: CsvProvider<"sample.csv"> reads that file at compile time and generates a row type with the columns it found; an OpenAPI or SQL provider does the same from a document or a live schema. Your code is then checked against those types, so a misspelled column fails the build. But the schema was read once, at that build — and erased providers leave nothing at runtime to re-check it.

The F# knowledge gap it signals

The author must know whether the schema is a contract they control or a snapshot they observed. A provider turns an observation into a type: as true as the document read, as durable as the next change to it. The knowledge is not “these columns exist” but “these columns exist in version N, which is what production serves”.

The gap question: when was this type last generated — and from which version of the schema?

ImportantWhen the types encode reality

A contract that is stable and fetchable at build time: the provider regenerates in CI against the current schema document, so a renamed column or an added field breaks the build instead of a nightly job. The generated type is that agreement, dated.

WarningWhen it’s a guess dressed as engineering

The committed sample. Someone checked in a CSV, or pointed the provider at last quarter’s schema document, and every build since has asserted that old shape. Then the API renames a field: the build reads the stale document, compiles clean, tests pass on recorded fixtures, and the runtime serves the new one. The failure arrives as a null under the old field’s name — right type, missing value, no exception — and “it compiles” had felt like validation.

TipThe faithfulness test

When was this type last generated — and from which version of the schema?

  • If yes → the type is a claim about a named version. Pin it in the build and fail when the source document moves.
  • If no → the type is a claim about a snapshot nobody tracks. Regenerate, or drop the provider and validate where the data enters.
  • If you can’t answer → stop. Find the file or URL the provider reads, and date it. The choice waits until that is on file.

Case study: Discriminated unions and the incomplete-match warning

A union gains a case, the build prints four warnings among three thousand lines, and the missing arm throws at 2 a.m. in production.

Writing an F# construct? Ask “which fact does the type carry — units, effects, exhaustiveness — and when is it checked?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: A multi-case reference-type discriminated union compiles to a tagged class hierarchy; a match compiles to a tag test with the arms inlined. Incompleteness is FS0025 — a warning, not an error — so a match that omits a case compiles clean and throws MatchFailureException when that case arrives. The trade: the type carries the whole case set, and the compiler reports the mismatch only at the volume you configured.

The F# knowledge gap it signals

The developer must know the case set is closed, that every consumer was rebuilt against it, and that no wildcard arm stands in for cases not yet written. The wildcard is where the next case is swallowed: the warning disappears and the new case takes the fallback branch. An old binary does not warn at all — it throws.

The gap question: does an unmatched case break this build — configured — or only a production run?

ImportantWhen the types encode reality

FS0025 promoted to an error in the project file, and no wildcard arms on the union. A new case then breaks the build in every consumer that has not handled it: the compiler enumerates the sites you would otherwise grep for, and both stay in lockstep.

WarningWhen it’s a guess dressed as engineering

A developer adds the case, the warning lands in the log, and nobody reads it. Four matches have no arm for the new case — the warning was their only check. The build stays green, and the one path that reaches the case throws in production.

TipThe faithfulness test

Does an unmatched case break this build — configured — or only a production run?

  • If yes → the union is the authority on its case set. Check which arms are wildcards; those are the ones the next case will not reach.
  • If no → the exhaustiveness claim is prose, not a checked fact. Promote FS0025 to an error and rebuild every consumer.
  • If you can’t answer → stop. List every match over the union, then the arms that name no case. The choice waits until that is on file.

Case study: Immutability by default

One unguarded mutable field turns a record you could hand to ten threads into a record you must hand to one.

Writing an F# construct? Ask “which fact does the type carry — units, effects, exhaustiveness — and when is it checked?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: A record compiles to a class with get-only fields, and a list to a linked chain no operation modifies; a change produces a new value. The trade: the compiler checks nothing about sharing. It makes mutation hard to write, then trusts you to know what is actually shared. Declare one field mutable and the type is immutable in shape, mutable in fact, and nothing warns.

The F# knowledge gap it signals

The developer must know which values more than one owner reads at once, and which of those hold state that changes once another thread can see it. Immutability by default keeps that question cheap only while it holds — and one unguarded mutable field ends it.

The gap question: which types in this module contain mutable state — listed — and is each one’s sharing story stated?

ImportantWhen the types encode reality

Records updated by explicit with expressions, so a change yields a new value and the old one stays valid for every reader holding it. Lists shared by prepending, where the tail is reused without a copy and both owners hold it safely.

WarningWhen it’s a guess dressed as engineering

The record is immutable except for one field, declared mutable to avoid threading an update through six call sites — a real saving, and why the trap works. Two threads now share the instance and the field crosses a thread boundary with no synchronization and no symptom until the read lands stale. The mutable list says it louder: a ResizeArray handed to two owners, both appending, one growing under the other’s loop.

TipThe faithfulness test

Which types in this module contain mutable state — listed — and is each one’s sharing story stated?

  • If yes → the default is doing its job and the exceptions are deliberate. Check that each mutable field is confined to one owner or guarded.
  • If no → the type says immutable and the program says otherwise. Confine the mutation to one owner, or make the sharing explicit and synchronized.
  • If you can’t answer → stop. List the mutable fields, then the threads that reach them. The choice waits until that is on file.

Case study: Async of T versus Task of T

An async workflow that never runs throws nothing — it is a value built, passed on, and dropped.

Writing an F# construct? Ask “which fact does the type carry — units, effects, exhaustiveness — and when is it checked?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: An async workflow compiles to a function taking a cancellation token and a callback that resumes it — cold: nothing runs until something starts it. A Task is hot when its factory starts it: work begins there, and the bare constructor leaves it cold until Start(). Both are generic over the result: the type says “this produces a T” and nothing about who starts it or whether cancelling reaches the work. The trade: coldness with an implicit token against immediacy with an explicit one.

The F# knowledge gap it signals

The developer must know which token the work observes — a fact no signature records. Async threads cancellation through the workflow context, so a started workflow inherits the token given to Start; a Task observes only the token its factory was given. Convert and the answers diverge.

The gap question: for each async value, who starts it, and does cancellation cross the Async and Task boundary — verified?

ImportantWhen the types encode reality

One world per Async/Task seam, chosen once and named. Async inside the domain where composition and inherited cancellation matter, converted where a .NET library returns a Task — named, so a reader sees the task is already hot. Startup is one explicit Start at the top, and its token is the one the workflow observes.

WarningWhen it’s a guess dressed as engineering

Start called inside a function to make sure the work happens: it fires, returns, runs under Async’s default token, so the caller’s cancellation never reaches it. Or the reverse — an async wrapper awaited around a Task created without a token, so cancelling the workflow is a request the Task never received.

TipThe faithfulness test

For each async value: who starts it, and does cancellation cross the Async and Task boundary — verified?

  • If yes → the boundary is explicit and the token path is real. Check the one place startup happens, and that it is not repeated deeper.
  • If no → the workflow may never run, or may never stop. Make startup explicit, and pass the token into every factory that creates a Task.
  • If you can’t answer → stop. Trace each value from its creation to its Start or await. The choice waits until that is on file.
