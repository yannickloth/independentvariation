The C# Language

What the C# compiler does with your claims.

LINQ deferred execution, iterator blocks, expression trees — where evaluation happens is where the claim lives. Each post locates the evaluation and asks what it assumes.

If you can, the construct is knowledge embodied — the execution matching what the domain decided.

Case study: LINQ deferred execution

A query runs twice, the collection changes in between, and the count stops matching the items it counted.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: A LINQ chain over IEnumerable compiles to a tower of iterator objects, one per operator, not to a loop. Nothing reads the source until something calls MoveNext. The trade: you get a composable description that always reflects the source as it is at that moment, and you pay for it by re-running the whole pipeline on each enumeration.

The C# knowledge gap it signals

The result is a function of the source at enumeration time, not at the line the query sits on. To know what the code does, you must know every site that enumerates it, how often each runs, and whether anything writes to the source between them. The variable looks like a value and behaves like a method.

The gap question: how many times is this query enumerated, and can the source change between the enumerations?

ImportantWhen the types encode reality

A pipeline built in stages — filter in one method, project in another, order in a third — materialized once at the end. Deferral is what lets the stages compose without a list per stage, and the result equals the query.

WarningWhen it’s a guess dressed as engineering

The query held as a value. It is logged, counted, and iterated by a foreach, and the source is a list something else appends to: the count disagrees with the items, and the report states a total from before the last write. Or it is enumerated inside a loop over ten thousand rows, and each row re-reads the store — N+1 produced by deferral, in code that reads as one query assigned to one variable.

TipThe faithfulness test

How many times is this query enumerated — counted — and can the source change between them?

  • If yes → one enumeration, and no writer between. The deferral is the composition and costs only what you planned. Check the source’s lifetime next.
  • If no → the query was a description where you needed a result. Materialize where it is consumed, and the second execution disappears.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Count the enumeration sites, then find every writer to the source.

Case study: IQueryable versus IEnumerable

One AsEnumerable() mid-chain, and every filter after it reads rows the database already sent.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: They share extension-method names, not methods, and compile to different artifacts. IEnumerable<T> binds to Enumerable: each operator becomes an iterator object over the sequence. IQueryable<T> binds to Queryable, so each operator appends a node to an expression tree that a provider reads and translates — the filters become one statement in another language. The trade: the query travels to the data, at the price of every operator being translatable.

The C# knowledge gap it signals

The type of the sequence is the claim about where the work runs. Reading a chain, you must know which operators the provider can translate, whether an untranslatable one throws or falls back to memory, and where the type changed. Same syntax, two locations, nothing in the line announcing the switch.

The gap question: does each chain’s type say where it runs, and is the location the one you need?

ImportantWhen the types encode reality

Each segment declares its type: the repository hands back IQueryable for the part the store can answer — filter, project, order, page — and the method that needs a regex, a compiled delegate, or a domain object materializes explicitly. The declaration reads as a map of execution.

WarningWhen it’s a guess dressed as engineering

An AsEnumerable(), a ToList(), or a helper taking IEnumerable<T> inserted mid-chain to satisfy a signature. It compiles, returns the right rows, and the rest of the query runs in memory: the filter that should have shrunk the result set scans it, and the cost grows with the table. In review it reads as a style preference: both sides are sequences.

TipThe faithfulness test

For each LINQ chain: does its type say where it executes — and does the execution location match the claim?

  • If yes → the type transition is deliberate. Check that the operators left on the provider side are translatable, and watch the fallbacks.
  • If no → the sequence acquired a type nobody chose. Move the materialization to the type transition, and widen the helper to IQueryable; keep the filter with the data.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Print the expression tree and read the provider’s translation.

Case study: Iterator blocks (yield return)

The null check in your iterator throws three frames from the caller, inside someone else’s foreach.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: A method containing yield return is not compiled as an ordinary method. The compiler emits a class implementing the returned interface — IEnumerable<T> or IEnumerator<T> — with fields for the current item and a state number; your body becomes MoveNext, resumable at each yield. The trade: a lazy, resumable sequence, against a body that has not run at all when the call returns.

The C# knowledge gap it signals

The call returns the state machine, not a value: the arguments are captured now, and the body, guard included, waits for the first MoveNext. A guard belongs to the consumer’s schedule, not the caller’s. To know when the guard fires, you must know who enumerates, and when — knowledge your signature does not carry.

The gap question: which of these iterator methods validate their arguments, and does that validation run when the caller expects it?

ImportantWhen the types encode reality

An iterator paired with a wrapper: the public method validates eagerly — null guard, range check — then returns the private iterator. The guard runs at call time, in the caller’s frame, and the body stays lazy. The split is the knowledge.

WarningWhen it’s a guess dressed as engineering

The guard inside the yield method, because that is where the parameter is used. It looks defensive, reads as validation, and fires at the first MoveNext — after the caller’s try block has closed, in another layer’s foreach. A unit test asserting a throw on construction fails while the guard is present. Worse, the method is called for a side effect — a logger, a connection opened in the body — and none of it happens: nobody enumerated.

TipThe faithfulness test

Which iterator methods validate their arguments — and does that validation run when the caller expects?

  • If yes → eager guards, lazy body. Make sure the guard set is complete, then check what the body does on disposal — the last resumption it triggers.
  • If no → the validation is on the consumer’s schedule. Split the method, keeping the body lazy.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. List the callers, then mark where the first MoveNext happens.

Case study: Expression trees (code as data)

A pricing rule is written once as C#, handed to a database as SQL, and never runs in the process that wrote it.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: Expression<Func<Order, decimal>> compiles to IL that builds a tree, not to IL that runs the rule. The compiler emits a tree of node objects — ParameterExpression, MemberExpression, BinaryExpression — that a library reads, rewrites, and hands to another engine. The trade is inspection for expressiveness: a statement body, an assignment, or an await in the lambda is a compile error, so the code-as-data boundary announces itself at the lambda and nowhere else.

The C# knowledge gap it signals

The type claims a second engine can reproduce this code. That claim is about your program, not about C#: only you know whether the rule means anything apart from the machine evaluating it. The compiler checks the tree’s shape; it never checks that two engines agree on what the shape means.

The gap question: does every expression survive translation — verified — or is something lost in transit?

ImportantWhen the types encode reality

A rule that must run twice: expr.Compile() over one order in memory, the same tree translated to SQL over a million rows. Both engines read the rule as data, so one edit reaches both — the disagreement, when it comes, comes in the translation.

WarningWhen it’s a guess dressed as engineering

A call the provider cannot translate: a culture-sensitive ToString(), a local helper, a DateTime comparison with an unstated Kind. Sometimes it throws — loud, survivable. Sometimes it translates to different semantics: collation (the database’s text-comparison rules), null ordering, decimal rounding. Zero test failures, because both sides pass their own tests.

TipThe faithfulness test

For this code-as-data boundary: does every expression survive translation — verified — or is something lost in transit?

  • If yes → the tree is the domain’s rule, portable by construction. Check each provider’s translation of collation, null ordering, and date handling against the local delegate.
  • If no → the code is a delegate wearing a tree’s type. Write it as a delegate and run it where it was written.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Enumerate the tree’s node types, then the provider’s translation table, and diff the two.

Case study: Extension methods (the static call in member clothing)

The call reads like a member on your own type, resolves to a static method a using brought in, and accepts null as a legal receiver.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: value.Normalize() compiles to TextExtensions.Normalize(value), the receiver as first argument. No virtual dispatch: binding is fixed at compile time by the namespaces in scope, and an instance member of that name always wins. The trade is methods on a type you do not own, paid for with scope resolution — and a this parameter that may arrive null.

The C# knowledge gap it signals

The syntax claims the operation belongs to the type. Whether it does is your program’s fact, not C#’s. The compiler resolves by scope — innermost level first, then outward, and ties inside a level are ambiguous — so a call site rebinds after a using someone added for another reason.

The gap question: is the receiver checked — and would the reader know this is a static method, not a member?

ImportantWhen the types encode reality

Extensions in one namespace per concern, imported only where it applies — WhereActive on IQueryable<User> — each guarding this with ArgumentNullException.ThrowIfNull, so the call fails at the entry point it really has.

WarningWhen it’s a guess dressed as engineering

maybeNull.OrEmpty(). The syntax reads like a safe member call, so nobody asks whether the receiver could be null — and without a guard the NullReferenceException is thrown inside the extension, not at the call site.

The silent one: a later package version adds a real member of that name, every call site recompiled against it binds to the instance method (same syntax, different body), and behavior changes with no diff in your repository.

TipThe faithfulness test

For each extension call: is the receiver checked — and would the reader know this is a static method, not a member?

  • If yes → a deliberate widening of a type you do not own. Keep the guard, keep the namespace narrow.
  • If no → a static helper wearing instance syntax: bound by scope, invisible to dispatch, unguarded on null. Make it an explicit static call, or a type you own.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. List the using directives each file needs, then check whether the type already ships that member.

Case study: Nullable value types (absence as a value)

A total goes null at one unguarded multiplication, and the invoice ships with a zero nobody chose.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: int? is Nullable<int>: a bool and an int in one struct. The compiler lifts every int operator, and the families disagree. Lifted arithmetic returns int? — null + 5 is null, and the null spreads. Lifted comparison returns bool — null < 5 is false, and so is null >= 5. The trade is declared absence, with operators that answer silently instead of throwing.

The C# knowledge gap it signals

Whether “no value” is a fact about this number is your program’s knowledge, not the type’s. The type admits absence and steps aside: it never asks what absence means for a sum or a threshold.

The gap question: where does null enter this computation — listed — and is each entry point a stated decision or a lifted operator nobody chose?

ImportantWhen the types encode reality

A measurement that may not exist: a sensor reading. HasValue guards the branch that needs a number, ?? throw kills the path that must have one, and GetValueOrDefault(fallback) writes the substitute down, because 0 is a legal price.

WarningWhen it’s a guess dressed as engineering

The arithmetic chain. subtotal * discountRate * taxRate, every factor nullable: one null and the result is null, flowing until a ?? 0m makes it a zero someone signs.

The comparison is worse. if (x < threshold) Alert(); never fires when x is null; as if (!(x < threshold)) Alert(); it fires on every missing reading. Two branches, opposite failures, one absent value.

TipThe faithfulness test

Where does null enter this computation — listed — and is each entry point a stated decision or a lifted operator nobody chose?

  • If yes → absence is modeled with declared semantics. Check that every ?? fallback is a domain decision, not a zero-fill.
  • If no → a lifted operator chose for you: null propagates through arithmetic and becomes a bool through comparison. Test HasValue at the entry; never compare a nullable to a threshold without deciding what absence means.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. List every ?? and lifted operator on the path, and name the null each handles.

Case study: Generic constraints

“where T : IComparable<T>” tells the compiler every T can be compared — and the path that crosses as object passes a type that cannot.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: A where clause compiles to metadata on the method, not to a check inside the body: the runtime verifies it when a concrete type argument closes the method, and the compiler verifies it at every call site that names one. Both checks are free and total — and scoped to the generic door: the call path that names a type argument. A path that never closes the method never instantiates it.

The C# knowledge gap it signals

A constraint is a claim about every type that closes this method: comparable, constructible, a reference type, non-null. The developer must know which of those the body actually uses — a new() constraint on a method that never calls new states a requirement the algorithm does not have. The gap question: which types reach this code, and do they all arrive through the constrained door?

ImportantWhen the types encode reality

The constraint states exactly what the algorithm does with T and nothing more: IComparable<T> on a sort, new() on a factory, class where the null check depends on it. Every call site becomes a proof obligation the compiler discharges, and the signature documents the requirement.

WarningWhen it’s a guess dressed as engineering

Developers trust the constraint past the generic door. The same algorithm is reached through object and through a non-generic interface. On those paths the promise is checked nowhere, so the failure surfaces as an InvalidCastException deep in a library that “cannot” receive it. The constraint was never wrong. The door beside it was unguarded.

TipThe faithfulness test

For each constraint: does every caller reach this code through the checked path — or is there a door that skips the check?

  • If yes → it is enforced where the traffic is. Check next that no constraint claims more than the body uses.
  • If no → it guards a fraction of the callers. Close the non-generic door, or validate at it — a check you now maintain by hand.
  • If you can’t answer → unclear. You haven’t found the constraint wrong — you’ve found incomplete knowledge of your own call graph. List every entry into the method, generic and not.

Case study: checked and unchecked arithmetic

Two positive amounts sum to a negative total, nothing throws, and the report prints that total as a number.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: Integral arithmetic is unchecked by default: the compiler emits the wrapping add and multiply, and an overflow disappears in silence. A checked block or expression emits the overflowing forms, and the runtime raises OverflowException as the result leaves the type’s range. The trade: a condition the program can detect, against a number it cannot tell from a correct one. Decimal throws on overflow; int and long wrap.

The C# knowledge gap it signals

The developer must know the stated upper bound of the operands, and whether the code enforces it before the arithmetic runs. A bound in a comment is not enforced; a bound validated where input enters is. The gap question: what is the largest value this expression can reach, given every input path into it?

ImportantWhen the types encode reality

Checked context on the arithmetic whose operands are user-sized: amounts in cents, record counts, buffer indexes. There the domain already fixed a bound — the invoice maximum, the page size — and checked arithmetic turns that stated bound into a failure at the exact expression that breached it.

WarningWhen it’s a guess dressed as engineering

The sum that silently wrapped. Every test uses small numbers, the default emits no overflow check, and nothing warns. A year of correct totals ends negative, found only when the figure fits no report. The wrapped value sat inside the type, plausible, and traveled through three aggregates before anyone read it as impossible. The code never stated what it assumed about magnitude, so the language assumed nothing.

TipThe faithfulness test

For this arithmetic: what is the stated upper bound of the operands — and does the code enforce it, or wrap around it?

  • If yes → the bound is a fact the code holds. Check next that validation sits on every path, not only the parsed one.
  • If no → the range is an assumption, not knowledge. State the bound and validate it where input enters — checked only throws at the breach.
  • If you can’t answer → unclear. You haven’t found the arithmetic wrong — you’ve found incomplete knowledge of your own program. Measure the largest operands in production; compare them to the type.

Case study: string comparison

The same identifier matches on your laptop and fails on a server whose locale is Turkish, with no code change.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: Equality is ordinal: == on string compiles to String.Equals, which compares characters exactly and consults no culture. Ordering is not: string.Compare and CompareTo default to the current culture, so they return 0 for some strings that are not byte-equal, and produce an order that moves with the host’s locale. Casing sits between them: ToUpper() reads the current culture too. Three truths — byte, culture, case rule — and one operator that picks the first.

The C# knowledge gap it signals

The developer must know what the string is: identifier, key, or a label a human reads. An identifier needs byte truth; a sorted display list needs the reader’s culture; a case-insensitive login needs a case rule. One type serves all three, so the mode is a claim the code never checks. The gap question: which truth does this comparison claim, and is that the truth this key needs?

ImportantWhen the types encode reality

The mode is chosen per use: Ordinal for identifiers, keys, file paths; OrdinalIgnoreCase where case carries no meaning but characters do; culture rules only where a human reads the difference, as in a sorted list for a German UI. Then each comparison states its fact.

WarningWhen it’s a guess dressed as engineering

The Turkish-i problem. An identifier is normalized with ToUpper() and no invariant culture, so the lowercase i becomes İ on a tr-TR host and the key stops matching itself. The developer never chose a culture; ToUpper() chose the host’s. Beside it, Compare(a, b) == 0 used as equality: two distinct keys declared identical because the culture ignores the difference, and a duplicate slips past the uniqueness check meant to catch it.

TipThe faithfulness test

For each string comparison: which truth does it claim — byte, culture, or case — and is that the truth this key needs?

  • If yes → the mode is knowledge. Check next that the culture you get is the one you meant, not the host’s.
  • If no → the comparison is a default, not a decision. Name the mode at the call site and remove the ToUpper().
  • If you can’t answer → unclear. You haven’t found the comparison wrong — you’ve found incomplete knowledge of your own key. Ask what the string identifies, then who reads it.

Case study: the event keyword

One assignment to a public delegate field erases every subscriber; no compiler error marks the line.

Writing a C# construct? Ask “when does this code actually run — now, on enumeration, at the provider — and what claim does its type make?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: A field-like event compiles to a private delegate field plus two public accessors, add and remove. Any code may subscribe; only the declaring type may invoke or reassign it, and the compiler enforces both. A public delegate field compiles to no accessors at all: read, invoke, assign, all legal from anywhere. The trade is one rule — who may raise this — held by the compiler or by convention.

The C# knowledge gap it signals

The developer must know two facts about their own program: which object owns the decision to raise, and which object outlives which. The second is a lifetime fact. Every subscription is a reference from publisher to subscriber, so a long-lived publisher holds every subscriber that never unsubscribed. The gap question: who may invoke this, and does each subscriber unsubscribe when its own lifetime ends?

ImportantWhen the types encode reality

Events with subscribe and unsubscribe written as a pair: handler added in a constructor, removed in Dispose or on detach. The publisher is the only raiser, so every raise site sits in one file. The lifetime relation is stated, not assumed: the window subscribes to the store and unsubscribes before it closes.

WarningWhen it’s a guess dressed as engineering

A public delegate field: any caller invokes it, any caller assigns it, wiping every other subscriber. The event semantics exist in a comment; the bytecode has none. Beside it, the subscriber that never unsubscribed: a view model on a singleton, closed, alive because the singleton holds its handler. The leak grows an object per navigation, and the retained object still receives events after its window closes.

TipThe faithfulness test

For each event: who may invoke it — enforced — and does every subscriber unsubscribe when its lifetime ends?

  • If yes → the rule and the lifetime are both knowledge. Check next that the unsubscribe runs on the failure path too.
  • If no → you hold the semantics in convention. Replace the field with an event, and detach when the subscriber closes.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own object graph. Draw the publisher and its subscribers, then mark which dies first.
