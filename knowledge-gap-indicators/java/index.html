The Java Language

What javac and the JVM do with your claims.

A language claim meets the compiler: erasure, boxing, pattern matching. Each post compares the claim with the compiled reality.

Pick a post on the left. It opens on the right.

Writing Java? Ask “what survives compilation — and which claim of mine does the compiler erase, box, or defer?” If you can’t answer, you’ve found a knowledge gap: the source says one thing and the bytecode another. If you can, the construct is knowledge embodied — the compiled reality matching what the domain decided.

Case study: Type erasure

A method declares List<String>, the bytecode declares List, and the String is gone before the first call — the only trace is a checkcast where you read the element.

Writing a Java construct? Ask “what does javac and the runtime actually do with this claim — what survives compilation, what is erased, what is checked and when?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: A type argument is checked by javac, then discarded: List<String> compiles to List, T to its bound or to Object. A checkcast at each read is what remains. The trade: a type check that costs nothing at runtime, since no type is left, against interoperability with pre-generics code — raw types, wildcards, unchecked conversion at every old boundary.

The Java knowledge gap it signals

Whether any decision depends on T at runtime. Arrays of T, instanceof T, static state shared across type arguments, overloads that differ only in a type argument — each wants T to be a runtime fact, and javac declines.

The gap question: which decisions in this code depend on T at runtime, and does any of them survive compilation?

ImportantWhen the types encode reality

A repository over T whose methods accept and return T. Nothing inside branches on what T is, so nothing needed it at runtime: the type argument documents intent at each call site, and the compiler checks the wiring.

WarningWhen it’s a guess dressed as engineering

A (T) cast under @SuppressWarnings, no Class token at the entry: the cast checks nothing, so a wrong type argument throws ClassCastException at the first read — far from the mistake, and the trace names the reader, not the writer.

The overload pair differing only in its type argument does not compile, same erasure. The seductive repair collapses both into one List<?> or raw List method: it compiles, accepts both, and enforces the distinction nowhere.

TipThe faithfulness test

Which decisions in this code depend on T at runtime — listed — and does any of them survive compilation?

  • If yes → T is a runtime fact. Hold the Class token, check where values enter, and keep the unchecked cast to one line.
  • If no → T is a compile-time label. Keep it out of fields, arrays, and instanceof; the erasure costs you nothing.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. List every instanceof, array creation, and ClassCastException catch, and trace each to the type argument it leans on.

Case study: Boxing and unboxing

Two user ids compared with == return false, both 1000 — the same comparison passed last year, when every fixture used an id below 128.

Writing a Java construct? Ask “what does javac and the runtime actually do with this claim — what survives compilation, what is erased, what is checked and when?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: javac inserts Integer.valueOf wherever a primitive meets a reference type, intValue wherever a wrapper meets a primitive. valueOf must cache −128..127, so small values share identity; with default JVM settings, larger ones do not. The trade: wrappers let a primitive enter a generic collection or state absence as null, against a possible allocation per conversion past the cache and an == that compares references while reading like a value.

The Java knowledge gap it signals

Where the program stops doing arithmetic and starts handling an object. The conversion is silent both ways: in a loop condition, in a ternary whose branches differ in type. A developer who does not know which values are objects knows neither their allocation rate nor the meaning of their ==.

The gap question: where does boxing happen in this loop, and does any == compare boxed values?

ImportantWhen the types encode reality

Primitives for the computation, wrappers only where the domain hands you objects. A total as a long, a counter as an int; the box appears once, where the value enters a Map<Long, Order>. The collection needs objects; the arithmetic does not.

WarningWhen it’s a guess dressed as engineering

Long sum = 0L, then sum += values.get(i) in a hot loop: each iteration unboxes, adds, and boxes a fresh Long past the cache — one allocation per element, invisible in the source.

The comparison trap is quieter. == on two separately boxed Integers is true only while the cache covers the value, so the suite proves it works and the first real order number disproves it. equals was right on every value; == only on what the fixtures used.

TipThe faithfulness test

Where does boxing happen in this loop, measured by allocation — and does any == compare boxed values?

  • If yes → the box is in the loop, or the comparison is on identity. Hoist the accumulator to a primitive, box once at the exit, change == to equals.
  • If no → boxing sits where objects genuinely begin. The cost is the boxing’s cost, not the loop’s.
  • If you can’t answer → unclear. You haven’t found the wrapper wrong — you’ve found incomplete knowledge of your own program. Measure allocations per iteration, then list every == on wrappers.

Case study: Pattern matching for switch over a sealed hierarchy

A fifth payment state ships; eleven switches keep compiling. Each has a default that throws “unreachable”.

Writing a Java construct? Ask “what does javac and the runtime actually do with this claim — what survives compilation, what is erased, what is checked and when?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: A sealed interface states its permitted implementations are a closed set. A pattern switch that names every permitted type is proved exhaustive by javac, no default needed — the switch final since 21, the seal since 17. The trade: completeness checked wherever the switch is recompiled, against a default that ends the check.

The Java knowledge gap it signals

Whether the domain closes the set, and whether every consumer sits inside the proof. Exhaustiveness is a property of switch and seal read together at one compile, not of the switch alone. Know which switches are load-bearing, and whether the default is a case or an exemption.

The gap question: does every switch over this hierarchy prove completeness — or does a default clause end the proof?

ImportantWhen the types encode reality

A payment state machine as a sealed interface, one record per state, switches that name every case and carry no default. Adding a state is a compile error in every consumer, named in one build: eleven files, or the one that forgot.

WarningWhen it’s a guess dressed as engineering

A default that throws IllegalStateException(“unreachable”) passes review and converts a compile-time promise into a runtime one: the compiler calls the switch total, stops reporting the missing variant, and the new state reaches a branch nobody wrote. A consumer compiled against the old seal has no arm for the new variant and throws MatchException on it — correct, and late.

TipThe faithfulness test

Does every switch over this hierarchy prove completeness — or does a default clause end the proof?

  • If yes → the compiler owns the list of cases. Add the variant, let the build name every file, and keep the seal closed.
  • If no → the default is where new variants go to be forgotten. Delete it from the exhaustive switches, or narrow the switch to the type it handles.
  • If you can’t answer → unclear. You haven’t found the switch wrong — you’ve found incomplete knowledge of your own program. List every switch on the hierarchy, mark which carry a default, and check which files built on the seal.

Case study: var and type inference

One var on a factory result, and nothing on that line says what the variable holds.

Writing a Java construct? Ask “what does javac and the runtime actually do with this claim — what survives compilation, what is erased, what is checked and when?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: var changes nothing at runtime. javac infers the initializer’s static type, writes it into the class file as an ordinary local-variable entry, and rejects the sites where no standalone type exists: null, a lambda, a method reference, a bare array initializer. What moved is the declaration — the type claim now lives in the expression on the right, and only there.

The Java knowledge gap it signals

The developer must know the initializer’s static type, not its runtime type, and where the two diverge. javac holds that fact; the reader no longer does. A file full of var resolves its types one hover away — fine for whoever has the IDE open, invisible in a diff, a review, or a stack trace.

The gap question: for each var, can the reader reconstruct the type from that line alone?

ImportantWhen the types encode reality

var orders = new ArrayList<Order>(); — the constructor names the class, so var keeps it and drops the interface. The same holds for var names = new HashSet<String>(ids); and any initializer whose right-hand side is a constructor call, a cast, or a literal. The reader reads the type where it is written.

WarningWhen it’s a guess dressed as engineering

var report = ReportBuilder.of(tenant).withRange(range).build(); The line states a name and a pipeline. The type is whatever build() returns — a decision inside another file that can change without touching this line. List.of() is the sharper trap: var gives E no target to infer from, so it falls back to Object — List<Object> where the team assumed List<Order>. It compiles; the type claim is quietly weakened.

TipThe faithfulness test

For each var: can the reader reconstruct the type from that line alone — or must they open another file?

  • If yes → the inference is local knowledge. Check that the inferred type is the interface you meant, not Object.
  • If no → the type claim left the code the reader has. Write the type on the left, or make the factory’s return visible on the line.
  • If you can’t answer → unclear. You haven’t found var wrong — you’ve found incomplete knowledge of your own program. List the declarations a reviewer could not name.

Case study: String concatenation

The report takes 9 seconds to build, and the only fault is a + inside a loop.

Writing a Java construct? Ask “what does javac and the runtime actually do with this claim — what survives compilation, what is erased, what is checked and when?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: a + b reads like arithmetic and compiles to a call, constants aside: since JDK 9 javac emits invokedynamic against StringConcatFactory, binding a makeConcatWithConstants handle that builds the result in one allocation. One expression is efficient and exact. Inside a loop, each s += row concatenates onto the whole prefix, so N iterations copy 1 + 2 + … + N row-lengths — quadratic work the source never announces. The JIT does not remove it: each result is live into the next iteration, and each iteration allocates a new String.

The Java knowledge gap it signals

The developer must know the iteration count’s growth, not just the syntax. Concatenation cost is invisible at one call site and cumulative at N. The gap is a claim about the data: how many iterations, and how long the accumulated string gets. Nobody wrote that down; the code pays.

The gap question: is any concatenation inside a loop whose iteration count grows with the data?

ImportantWhen the types encode reality

A log line, an exception message, a cache key of three fields, a URL built once per request. One concatenation, one allocation, and javac’s invokedynamic path is as good as the StringBuilder you would write by hand. The string is built here, once, from parts known here.

WarningWhen it’s a guess dressed as engineering

+= in a loop assembling a report over rows from a table. The line reads like an append, and every append copies everything already appended. Ten thousand rows of eighty characters copy four billion characters. The variant that hides best is concatenation inside a toString() called from a loop: the loop looks innocent, the copying lives in another class.

TipThe faithfulness test

Is any concatenation inside a loop whose iteration count grows with data — measured?

  • If yes → count the characters copied: iterations × average accumulated length. Use a sized StringBuilder or StringJoiner, passed in rather than returned from inside the loop.
  • If no → one expression, one allocation. Leave it.
  • If you can’t answer → unclear. You haven’t found + wrong — you’ve found incomplete knowledge of your own program. Find the loops, then the rows each iterates.

Case study: The enhanced for loop

A loop removes an order from an ArrayList it walks, and the next next() throws.

Writing a Java construct? Ask “what does javac and the runtime actually do with this claim — what survives compilation, what is erased, what is checked and when?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: for (Order o : orders) over a collection compiles to an Iterator: javac calls hasNext() and next() for you, so the loop has no index and no direct handle on the list. The ArrayList iterator compares a modification counter on next() and throws ConcurrentModificationException when the structure changed under it. The trade: the loop claims “walk every element” only while the structure holds still.

The Java knowledge gap it signals

The developer must know three facts: whether the collection is structurally modified inside the loop, whether that change is a removal or an addition, and whether this walk is the only reader. Removal is a claim about structure — the list shifts and the iterator cannot see it. Fail-fast is best effort, not a guarantee, and not thread safety.

The gap question: which loops mutate the collection they walk?

ImportantWhen the types encode reality

iterator.remove() after next() — the removal goes through the structure that owns the position, so the iterator stays consistent. Or collect the doomed elements and call removeAll after the loop: the walk stays pure, the mutation happens once.

WarningWhen it’s a guess dressed as engineering

orders.remove(o) inside the for (Order o : orders) loop. Single-threaded, no other thread — and it throws on the next advance, because the claim is structural, not concurrent. The silent version is worse: on a CopyOnWriteArrayList the iterator holds a snapshot, so the removal never appears and the loop processes an already-deleted element. No exception, and the report is wrong by one row.

TipThe faithfulness test

Which loops mutate the collection they walk — listed — and does each one use the mutation path the structure defines?

  • If yes → the mutation goes through Iterator.remove() or after the loop. Check that each remove() follows a next() and that no second remove() follows it.
  • If no → the loop mutates through a path the iterator does not track. Move the mutation out, or use an indexed loop whose index you correct on removal.
  • If you can’t answer → unclear. You haven’t found the for-each wrong — you’ve found incomplete knowledge of your own program. List the loops, then the collections each writes to.

Case study: Default methods on interfaces

A default method ships in a minor release, and a class nobody edited returns the wrong answer.

Writing a Java construct? Ask “what does javac and the runtime actually do with this claim — what survives compilation, what is erased, what is checked and when?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: A default method carries its body inside the interface. Implementors compile unchanged: they do not override it, and invokeinterface falls through when the class declares none. Binary compatibility usually holds: old class files inherit behavior they never compiled. The trade: evolution without breaking implementors, against behavior arriving on types that never opted in.

The Java knowledge gap it signals

The developer must know whether a behavior is universal across every implementor the interface will ever have, and whether the body needs state the interface cannot hold. A default sound across all implementors relies only on the interface’s contract; otherwise declare it abstract.

The gap question: for each default method, do all implementors honestly satisfy its claim?

ImportantWhen the types encode reality

Comparator.thenComparing, reversed, Iterator.remove throwing UnsupportedOperationException, List.sort. Each body follows from the interface’s contract alone, so any correct implementation behaves as the default expects and the default adds no assumption. thenComparing says “every comparator chains this way”, true by the meaning of comparator.

WarningWhen it’s a guess dressed as engineering

A default that assumes implementor state. default String describe() { return name() + " " + version(); } where half the implementors return null from name(), so the default prints “null 2.1” for years. Or default boolean isEmpty() { return size() == 0; } where some implementations compute size() by traversal: an O(1) check becomes a full scan. Every implementor inherits a claim it never read.

TipThe faithfulness test

For each default method: do all implementors — present and future — honestly satisfy its claim?

  • If yes → the body is derivable from the interface’s contract. Keep it free of assumptions about state.
  • If no → the behavior belongs to some implementations only. Make it abstract — it breaks implementors — or move it to an interface the willing implementors extend.
  • If you can’t answer → unclear. You haven’t found the default wrong — you’ve found incomplete knowledge of your own program. List the implementors, then the methods the default calls.

Case study: Annotation retention

A validator that checks every request, a green build, and validation that never ran once.

Writing a Java construct? Ask “what does javac and the runtime actually do with this claim — what survives compilation, what is erased, what is checked and when?” If you can’t answer, you’ve found a knowledge gap: the construct enforces a guess. If you can, the code is knowledge embodied — the language catching up to what the program means.

Mechanism: @Retention decides which artifact holds the annotation. SOURCE is read by the compiler and processors, then discarded. CLASS is the default: written into the class file, invisible to the reflection API. RUNTIME is written into the class file and materialized by reflection. The trade is one enum constant: a framework that reflects sees the annotation only if you said RUNTIME, and javac warns nothing if you did not.

The Java knowledge gap it signals

The developer must know two things: which reader sees this annotation, and when — compile time through a processor, or runtime through reflection. Retention is that claim. Omitted, it defaults to CLASS — invisible to the reflection API your validator uses.

The gap question: for each annotation, which retention was chosen deliberately, and which framework is supposed to see it?

ImportantWhen the types encode reality

@Retention(RetentionPolicy.RUNTIME) on annotations a framework reflects over: a validation constraint, a JSON field mapping. The reader exists at runtime; the declaration says so. Compile-time annotations — @Override, @SuppressWarnings — carry SOURCE and vanish, correctly: no runtime reader needs them.

WarningWhen it’s a guess dressed as engineering

A custom @PositiveAmount without @Retention. It compiles, it reads well in review, and it defaults to CLASS. The validator loops over field.getAnnotations(), finds nothing, and passes every field — silently, on every request, for months. The failure looks like success: no exception, no log line, a check iterating zero times.

TipThe faithfulness test

For each annotation: which retention was chosen — deliberately — and which framework is supposed to see it?

  • If yes → the retention names its reader. Assert it: reflect over one annotated element; fail if the annotation is absent.
  • If no → the annotation is a comment the compiler keeps. Add @Retention, or delete it and the dead validator with it.
  • If you can’t answer → unclear. You haven’t found the annotation wrong — you’ve found incomplete knowledge of your own program. Find the code that reads it, then when that code runs.
