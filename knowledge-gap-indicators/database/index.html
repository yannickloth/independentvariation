Database Constructs as Knowledge-Gap Indicators

A series of short posts that read schema constructs and storage mechanisms as encoded facts about the domain.

Every construct below encodes a fact — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be. Each post names the construct, states the encoding, and asks whether the fact is the domain’s or the developer’s.

Pick a post on the left. It opens on the right.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Case study: Natural vs surrogate primary key

Two customers, same email, same address, same person — and the database is happy, because both rows carry a different id.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A natural key is an attribute the domain already treats as unique and stable: a serial number, an ISBN, a national identity number. A surrogate key has no domain meaning, so identity survives a change to real attributes. Both enforce a unique column; only the natural key makes the domain’s uniqueness claim.

The database knowledge gap it signals

Identity is a domain decision before it is a column choice. The domain names an attribute that is unique and never reused, or admits it has none. With none, a surrogate is honest — but the sameness rule still needs a home: a UNIQUE constraint over the columns a human compares. The gap question: is the sameness rule written anywhere the database can enforce it?

ImportantWhen the domain mandates it

An attribute the domain already guards: a serial number stamped on a device, an IBAN, a legally issued invoice number. Nobody reuses it, so it is the identity. Equally sound: customer_id BIGSERIAL with UNIQUE (email_normalized) WHERE email_normalized IS NOT NULL beneath it.

WarningWhen it’s a guess dressed as engineering

Add id, declare it the key, leave email an ordinary nullable column because emails change. Nothing fails, and the reasoning is sound: surrogate keys are more stable. Then the form double-submits on a flaky connection and the CRM export loads twice. Merging means rewriting foreign keys, and the id has leaked into invoice numbers and URLs — so it becomes the identity nobody can change while the human’s own identity stays unconstrained.

TipThe faithfulness test

Can someone name the rule that makes two rows the same customer — and is that rule enforced anywhere?

  • If yes → identity is a domain fact with an owner. Verify the constraint exists in the schema, not only in a service method.
  • If no → the rule exists with no enforcement. A UNIQUE constraint on the natural candidate is the repair — and it rejects the emails that legitimately change.
  • If you can’t answer → stop. Ask whoever merges customer records today which columns they compare. The choice waits until that is on file.

Case study: Normalization vs denormalization

The product price lives in two tables. The catalog job updates one of them. The customer finds the other.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: Normalization stores each fact once, in the table whose key determines it, so every fact has one home, and a change has one place to happen. Denormalization stores a copy so a read avoids a join. The first encodes “this fact changes and must not diverge”; the copy encodes “this read dominates, and someone reconciles it”.

The database knowledge gap it signals

A copy is a prediction about the read-to-write ratio, plus an owner for the day the copies disagree. The choice needs both: a measured read pattern, and a named reconciler — refresh job, trigger, event consumer — with a stated staleness bound. The gap question: what ratio was measured, and who owns the reconciliation?

ImportantWhen the domain mandates it

Boyce-Codd normal form — one home per fact — wherever facts change: price, address, status. Denormalize where one read dominates and the maintenance is real: an order_total kept by a trigger, a search index rebuilt from the event stream, a report table refreshed on schedule.

WarningWhen it’s a guess dressed as engineering

“Denormalize for performance”, applied before anyone measured. The plan shows a join over a million rows, and a stored order_total recomputed on every line-item change looks cheaper. The copy lacks two things: a measured ratio and an owner. Then the trigger misses the refund line, the reconciliation job writes its own version, and finance reads whichever ran last. Two mechanisms now maintain one total, and nothing compares their answers.

TipThe faithfulness test

Does a measured read dominate — and is a reconciler named for the copies?

  • If yes → a measured pattern and a named reconciliation exist. Verify the staleness bound is written where readers can see it.
  • If no → say which half failed. No measured read: normalize. Read measured, no reconciler: name the reconciler before keeping the copy.
  • If you can’t answer → stop. Instrument the read and write counts for a week, then name who owns reconciliation. The choice waits until that is on file.

Case study: Nullability

The report counted 4,112 non-rejected customers. Another 611 were never counted at all — their status was NULL, and WHERE status <> 'rejected' had dropped them.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A nullable column admits absence: the row exists without a value. The model gives absence one representation, NULL, and one consequence — three-valued logic: any comparison against NULL is unknown, apart from IS NULL and IS DISTINCT FROM. The column encodes “absent”, never which kind of absence.

The database knowledge gap it signals

Absence has at least three meanings a schema must separate: not known yet, not applicable, not yet reached in a process. NULL stores none of them. The domain must say, per column, which one applies — and whether “not yet” is a state the process will leave. The gap question: which absence does this column carry, and did anyone decide?

ImportantWhen the domain mandates it

shipped_at NULL means “not yet shipped”: a state the fulfilment process leaves, so WHERE shipped_at IS NULL is exactly the open-orders query. terminated_on NULL means “still active”, and the domain says so.

WarningWhen it’s a guess dressed as engineering

Nullable as the default for every column not supplied at insert. It never rejects a valid row, so it never fails a test. Now status is NULL for three populations: the row the webhook created before the state machine ran, the row imported from a legacy system with no status, and the row where status does not apply. The logic then works silently — <> 'rejected' is unknown for NULL, so those rows vanish from the count; NOT IN against a subquery yielding one NULL returns no rows at all. The report undercounts while every query looks correct.

TipThe faithfulness test

Does every nullable column carry one decided absence — and does every query agree on which one?

  • If yes → absence is a modeled state. Check the <> and NOT IN filters against it.
  • If no → say which half failed. Undecided absence: make it NOT NULL or split it. Decided absence, disagreeing queries: fix the queries, not the column.
  • If you can’t answer → stop. Count NULLs per column and per source; the split counts your hidden meanings. The choice waits until that is on file.

Case study: Soft delete vs hard delete

A customer asked to be forgotten. The row is still there, with deleted_at set, an email and an address — and erasing it would break last year’s revenue report.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: Soft delete keeps the row and marks it: a deleted_at timestamp, an is_active flag. Hard delete removes it. The retained row encodes “the domain must still reason about this thing after it stops being current” — history, audit, and the records that cite it.

The database knowledge gap it signals

Forgetting is a rule from outside the schema. Accounting retains invoices for a decade, a regulator names the period, an erasure obligation says personal data must go. These conflict; only the domain resolves it per table. A tombstone — the retained row with its flag — must redact the personal fields to serve an erasure request; whether keeping them is lawful is a judgment the schema cannot make. The gap question: does the domain forget this thing, and who states the retention rule?

ImportantWhen the domain mandates it

deleted_at where the domain states the rule, deletion is a modeled state, and one filtered view is the only way to read the table: an invoice voided rather than removed, because the ledger must still balance; a user archived because their orders cite them. The rule lives outside the schema, and a named process owns the purge.

WarningWhen it’s a guess dressed as engineering

deleted_at added as a habit — “we never really delete, it is safer”. It is safer, and that is the trap: nothing fails, no data is lost, the choice looks conservative. Then every query must remember WHERE deleted_at IS NULL forever, including ones written next year. One forgotten filter leaks tombstones into a production report. Meanwhile the personal data is still physically present, so the erasure request is refused for a reason the schema cannot express.

TipThe faithfulness test

Must the domain still reason about this thing after it stops being current — and who states the retention rule?

  • If yes → retention is a domain fact with an owner. Verify a purge process exists and that queries filter through one shared view.
  • If no → delete for real, or split the live table from an archive whose access is deliberate.
  • If you can’t answer → stop. Ask legal and finance how long each table must keep a row. The choice waits until that is on file.

Case study: ENUM, lookup table, or free text

“U.S.”, “USA” and “us” were the top three countries by customer count. One country, three rows, and no way back to one.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: An ENUM closes a column to a fixed set; an FK lookup restricts it to the rows present; free text constrains nothing. The closed form encodes “the process owns this set and can enumerate it” — values are states a workflow moves through, not labels the world invents.

The database knowledge gap it signals

The domain decides whether the set is closed by rule or open by nature. Payment states are closed: the gateway returns a fixed list, and a new one is a version change. Lead sources are open: the world adds one whenever a campaign runs. The gap question: is this set closed by a rule, or open by nature?

ImportantWhen the domain mandates it

Payment states — pending, authorized, captured, refunded, failed — as an enum or a lookup table with an FK: the process owns the transitions, and a typo breaks reconciliation.

WarningWhen it’s a guess dressed as engineering

An enum for a set the world extends: categories, lead sources, product families. It ships well — fast, typo-proof, cleanly aggregated. Then a value arrives that the enum lacks, and adding it is a migration: a deploy coordinated with the reporting team. After six rounds someone adds other and stops. A year later 40% of rows say other, and the constraint enforces only that the real category lives in a free-text note. The inverse trap: free text where aggregation is required, so the country report needs a hand-written mapping table.

TipThe faithfulness test

Can someone state the complete value set today — and who is consulted when a new value is needed?

  • If yes → the set is closed by rule. Verify the owner exists and that a new value arrives through that owner, by a deploy if the rule says so.
  • If no → say which half failed. No complete set today: the set is open, so store it as data. Set known, no intake path: build the path and keep the constraint.
  • If you can’t answer → stop. List the production values and count the variants. The choice waits until that is on file.

Case study: Valid-time columns

The audit asked what a SKU cost on 14 March. The table answered with today’s price, on one row per SKU: valid_from and valid_to were never added, because nothing asked for a past price until the audit did.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: valid_from and valid_to state the interval over which a row’s fact held, keeping superseded rows instead of overwriting them. The interval encodes “the domain asks about the past”, and it carries a rule the columns alone do not: per entity — per SKU, say — no overlapping intervals.

The database knowledge gap it signals

Keeping history is a different claim from current state, and it costs an interval per fact and an integrity rule no writer may violate. The domain must say who closes an interval when a new one opens. The gap question: which decisions were made by reading an old price?

ImportantWhen the domain mandates it

Domains that reason over the past by rule: rate cards, insurance cover evaluated on the incident date, audits of the configuration then. The interval is the domain’s own fact; an enforced exclusion constraint closes the old one as it opens the new one.

WarningWhen it’s a guess dressed as engineering

Temporal columns added for one report. Nothing enforces the intervals; they are maintained by hand, by whoever remembers. Three failures follow. Overlaps: a rate change inserts the new row and forgets to close the old one, so it has two open intervals and queries pick one at random. Gaps: a backdated correction closes the old interval too early, or the new rate starts late, so “price on that date” returns no row. And the current-row convention differs per query — valid_to IS NULL here, a sentinel there — so two teams get two answers from one table.

TipThe faithfulness test

Does anyone ask about the past in domain terms — and who maintains the integrity of the intervals?

  • If yes → history is a domain fact. Verify one shared definition of “current” and an enforced no-overlap rule.
  • If no → say which half failed. Past queried, no interval owner: name the owner and enforce no-overlap. Past not queried: keep current state only.
  • If you can’t answer → stop. Ask which decisions were made by reading an old price, then count open intervals. The choice waits until that is on file.

Case study: Foreign keys, CHECK, UNIQUE

A migration set amount = -1 on 340 ledger rows. Nothing raised an error. The application would have rejected it — the migration never went through the application.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A constraint is a rule the database evaluates on every write, from any client. Someone can still defer it, disable it, or outrank it. Three shapes: a foreign key forbids a reference to a missing row, CHECK a value outside a predicate, UNIQUE a duplicate. Each encodes “an invariant of the fact”, not a step in one code path.

The database knowledge gap it signals

Every rule has a population of writers: the API, the import, the migration, the hotfix, the second service, the analyst with a console. Application validation covers one of them, and the rest arrive later. The question is not whether the app checks, but who may break the rule. The gap question: if a bug or a second writer bypasses the app, what stops this rule from being violated?

ImportantWhen the domain mandates it

A ledger entry’s account_id references accounts(id): a posting to a nonexistent account must not exist, whatever wrote it. CHECK (amount > 0), UNIQUE (invoice_number).

WarningWhen it’s a guess dressed as engineering

Rules kept in application code “for flexibility”. The reasoning is defensible: validation belongs near the domain logic. It holds while one writer exists. Then the reconciliation script runs at 2 a.m. and writes rows the service never sees; a partner CSV import bypasses every check; a second service ships its own copy of the rules. The constraint dropped for a bulk load “temporarily” is never restored, and nobody notices while production data is valid.

TipThe faithfulness test

If a bug or a second writer bypasses the app, does the database still stop this rule from being violated — and is that acceptable?

  • If yes → the rule is a domain invariant with a database owner. Verify no writer holds a privilege that skips it.
  • If no → the rule is unenforced, or not acceptably. Name the writers you accept; their number is a chosen risk.
  • If you can’t answer → stop. Enumerate every path that writes this table, including scripts, then compare the rule sets. The choice waits until that is on file.

Case study: JSON columns and EAV versus typed columns

Every order carries a metadata JSON column. Counted over one month, nine in ten rows repeated the same twelve attributes, and every report reached them by path.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A JSON column, or an EAV table — one row per attribute, no declared columns — stores a shape the schema does not declare. The database reads the stored shape as text: a type, a CHECK, and statistics arrive only with an extracted column. It encodes “the shape is open and decided outside this schema” — a claim about who controls the data.

The database knowledge gap it signals

Openness has a source. A provider webhook payload is open because the provider decides its shape. A domain attribute you have not named yet is not open — it is unknown, and the schema records your uncertainty as a permanent storage format. The gap question: who outside this system decides the shape?

ImportantWhen the domain mandates it

A webhook payload stored opaque inside a typed envelope: event_id, type, received_at, payload as JSON. The envelope is typed and constrained because the domain owns those facts; the payload stays opaque because the provider owns its shape.

WarningWhen it’s a guess dressed as engineering

Core attributes moved into JSON because a column “felt permanent”. Each step was reasonable: the attributes differ per category, adding columns meant a migration, and JSON was there. Soon metadata->>'colour' sits in a dozen queries, and those numbers are strings, so ‘10’ sorts before ‘9’. No type, no constraint, no statistics — on engines that keep none for expressions, the planner guesses. And the schema cannot be diffed: two environments with “the same” schema hold different shapes in one column.

TipThe faithfulness test

Is the shape genuinely open from outside the system — or is this a domain attribute you postponed naming?

  • If yes → the payload is opaque by contract. Verify a typed envelope around it and a version check at every read.
  • If no → the shape was never open; it was undecided. Extraction costs the migration the untyped column avoided, and it is the only place the type can live.
  • If you can’t answer → stop. Count the distinct paths used in queries; that list is the schema you have not written. The choice waits until that is on file.

Case study: Views vs tables

Two revenue reports disagree by 4% and both are labelled revenue: one sums the table, the other a view an analyst filtered last year, and no one can say which number finance signs.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A table stores facts; a view stores a definition — a query text plus the name and owner that govern it. Its rows are computed at read time, so it encodes a claim about meaning: this derived fact has one definition, many readers, and one owner who changes it in one place. It predicts the derivation is cheap enough to recompute per read, and that nobody needs the result pinned.

The database knowledge gap it signals

A named view is a domain term wearing SQL. Someone decided what “active” means, which rows qualify, and who may change the rule — before CREATE VIEW ran. If that decision lives only in the WHERE clause, the schema enforces a guess. Is this a governed term, or a query that happened to get saved?

ImportantWhen the domain mandates it

The domain already names the question. Support, billing, and the churn model all need “active customers”; the finance team owns the definition; a policy change — refund window, trial length — edits the view once, and every consumer that holds no copy moves in the same deploy.

WarningWhen it’s a guess dressed as engineering

Both traps look like good practice. The first is view stacking: v_active on v_orders_recent on v_orders_clean, twelve layers deep, each hiding one filter. On engines that flatten the nested views into one query it works until the plan degrades, and the debugger then has twelve places to look. The second is drift: active was one filter, then silently became “has an order in 90 days.” Who decided 90, and which of the two views is the term now?

TipThe faithfulness test

Is this a named domain question — or a query that got a name because it was pasted twice?

  • If yes → the view is the domain’s vocabulary. Check that one owner can change the definition, and that no caller re-implements the filter locally.
  • If no → it is a saved query. Keep it inside the module that needs it, or make it a table if the derivation is expensive.
  • If you can’t answer → stop. Count how many callers duplicate the filter, then ask who signs off when the meaning changes. The choice waits until that is on file.

Case study: Materialized views

The finance dashboard says €1.24M. The ledger says €1.31M. Both numbers are right: the dashboard is a materialized view six hours old, and the freshness was never written down.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A materialized view stores the result; on most engines refresh is an explicit job — scheduled, triggered, or manual. It encodes two predictions: the question is asked far more often than the underlying rows change, and an answer of a stated age is acceptable to whoever acts on it.

The database knowledge gap it signals

Staleness is a domain fact with an owner and a decision boundary. Someone has to accept “up to six hours old” for this consumer, and name the decision that would flip at the edge of that window. Has anyone accepted that age in writing, for this report?

ImportantWhen the domain mandates it

The dashboard refreshes once at 03:00, the team acts on yesterday’s numbers, and no consumer reads the last day. The refresh cost is known — ninety seconds of I/O, measured — and the slot sits outside the load window. The staleness is printed on the page; the last successful refresh is monitored.

WarningWhen it’s a guess dressed as engineering

The materialized view added “to make the report fast,” with no freshness contract. Trap one: a decision that needs the last hour gets made on stale data, quietly and confidently. Trap two: the refresh window that outgrew its slot — minutes to forty as the data grew — and now overlaps the business day, blocking readers exactly when the report is read. A failed refresh is silent too: the view serves yesterday, then last week, and the number still looks plausible.

TipThe faithfulness test

Has someone accepted a stated staleness — with the decision that changes at the boundary named?

  • If yes → staleness is a stated domain fact. Check the refresh is scheduled, timed, and alerts on failure.
  • If no → a cache with no expiry contract. Someone must accept an age in writing; until then the age is whatever the refresh happened to produce.
  • If you can’t answer → stop. Measure the refresh duration against the change rate, then ask each consumer what age they would refuse. The choice waits until that is on file.

Case study: CTE vs subquery vs temp table

A 400-line query with eleven CTEs ran in 90 ms on an engine that inlined them; as temp tables, 40 ms, because stage five was read three times. The cost nobody measured: which of the eleven names a domain concept.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: WITH names a subquery — a common table expression. On engines that inline it (non-recursive, referenced once, unless you write MATERIALIZED), the name costs nothing. On older engines, or with MATERIALIZED, it is a fence: computed once, stored, and hidden from the rest of the query. A temp table is a stronger promise — the result is read more than once and the materialization is deliberate.

The database knowledge gap it signals

Readability, reuse, and a materialization boundary are three different claims, and the domain decides which it needs. Steps that mirror domain concepts — billing period, eligible cohort, prorated amount — are knowledge; eleven CTEs that exist because the query grew are not. Does each named step correspond to something the domain names?

ImportantWhen the domain mandates it

CTEs naming the steps of a domain computation, one step per concept, so a finance reviewer can read the query as the policy it implements: cohort, eligibility, proration. A temp table for a genuine multi-pass pipeline that reads stage one three times.

WarningWhen it’s a guess dressed as engineering

Cargo-culting “CTE for performance.” The folklore came from planners that fenced every WITH; on modern engines the measured plan shows the CTE is inlined. The engineer adds MATERIALIZED to force the old behavior, and it is slower only where the CTE is referenced once. Second trap: the single 400-line statement of nested CTEs, adopted for modularity, that no reviewer can hold in one reading.

TipThe faithfulness test

Does each named step correspond to a domain concept — and did you confirm on this engine’s plan that the fence is real?

  • If yes → the naming is domain knowledge. Keep the steps, then confirm with EXPLAIN ANALYZE on this engine version.
  • If no → say which half failed. Steps without domain names: collapse them. Named steps, unconfirmed fence: read the plan before trusting the boundary.
  • If you can’t answer → stop. Time each stage, read the plan, then ask which steps a domain expert names. The choice waits until that is on file.

Case study: Indexing (single and compound)

One insert-heavy table carries twelve indexes and pays about 40 ms per insert at its current size; at one index it paid about 4 ms. Nine of the twelve serve no query anyone can name.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: An index is a second access path over the key columns — sorted in a B-tree, hashed in a hash index — plus whatever the engine needs to reach the row. An index on one column serves predicates on that column at any value; a compound index serves a filter shape, and its column order is part of the claim — equality columns first, then the range. It encodes a claim about a named query and a write tax.

The database knowledge gap it signals

An index is a statement about the queries the domain asks: which lookups are named, what they filter and sort by, how often each runs. It also adds write amplification — extra writes per row.

ImportantWhen the domain mandates it

Every index traced to a real query, quoted. Orders filtered by tenant and date get a compound index on (tenant_id, created_at) — equality first, range second — and the ORDER BY needs no sort node. Each index has a caller, an owner, and a measured cost on the insert path.

WarningWhen it’s a guess dressed as engineering

“Index every column, just in case.” The table is insert-hot; twelve indexes each need maintenance per row; writes queue and latency climbs. Second: the compound index in the wrong column order, (created_at, tenant_id), which serves a date-only filter beautifully and cannot serve the tenant-and-date query by plain descent. Third: the unused index nobody dares drop, because whoever added it has left and its scan count has stayed at zero for a year.

TipThe faithfulness test

Can every index be traced to a named query — and is the write cost of each measured?

  • If yes → the index is the query’s shadow. Check the column order; before dropping a zero-scan index, check what it enforces.
  • If no → finish the audit, not the index. Remove the ones with no named query; measure the write cost of the ones that have one.
  • If you can’t answer → stop. Log the queries this table serves for a week, then compare their filter shapes to the index list. The choice waits until that is on file.

Case study: Clustering

A table clustered by id is read by customer_id. Ten thousand matching rows scatter across most of its pages, so the plan promises 12 ms and the wall clock reports 4 s.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A clustered index, an index-organized table, and CLUSTER all store rows in key order in the physical structure. A table carries one physical order at a time — one per partition where it is partitioned — so the choice encodes a claim that one read pattern dominates and the others can pay.

The database knowledge gap it signals

The domain must have a dominant read path, measured: what queries this table, in which order, how often, and whether that order survives three more features. What does the domain read together — and is that the order you chose?

ImportantWhen the domain mandates it

Orders read by customer and date range: cluster on (customer_id, placed_at); on an engine that maintains clustering the matching rows sit in one contiguous run, so readahead works and the query reads only the pages holding them. A time-series table read by timestamp window, clustered on it. The competing paths were counted and are rare enough to pay for.

WarningWhen it’s a guess dressed as engineering

Clustered on the generated id because ids are “the key,” while every query filters customer_id: reads stay scattered and the clustering buys only rewrite cost. The subtler trap is treating re-clustering as one-time. On engines that maintain clustering (SQL Server), an insert into a random key position splits a page and leaves both halves half empty. On engines where CLUSTER is a one-time rewrite (PostgreSQL), new rows land wherever there is free space, rows per page drift toward random at a rate set by inserts against size, and the rewrite takes an exclusive lock.

TipThe faithfulness test

Is the dominant read path counted — and does that read order hold as features are added?

  • If yes → the physical order matches how the domain reads. Check the key’s insert order does not churn, or schedule the rewrite and watch the drift.
  • If no → say which half failed. No counted path: the cluster key is decorative, so keep the heap and a secondary index. Counted path that drifts: schedule the rewrite, or accept the drift.
  • If you can’t answer → stop. Measure rows-per-page for the dominant filter, then ask which order survives the roadmap. The choice waits until that is on file.

Case study: Sharding and partitioning

A query that took 20 ms takes 320 ms after sharding. It reads one row per tenant, so it now opens sixteen shards in turn and pays each one’s latency.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A shard key routes each row to one shard at write time. Choosing it pre-commits every query path: a query that carries the key reaches one shard, a query without it fans out and pays the slowest. It predicts the domain’s unit of access is that key, that the key has many distinct values, the distribution is even, and cross-unit queries are rare.

The database knowledge gap it signals

Two facts outside the framing list decide this: the load that made one database insufficient, and the measured skew of the key.

ImportantWhen the domain mandates it

B2B software where one database is measurably out of room and every query filters tenant_id: the key is carried by construction, and moving a tenant is an explicit migration, not an accident. Table partitions for retention — no shard key needed — where dropping a month is a metadata operation, not a million-row delete.

WarningWhen it’s a guess dressed as engineering

Hashing user_id when the domain’s unit is the account: no query carries the key, so every report fans out and joins across shards in application code, and shared-nothing (each shard independent) behaves like a slow single database. Second: a key chosen for assumed evenness that the queries do not carry. Third: the skewed key found in production. One tenant holds 40% of the rows, its shard is the bottleneck, and re-sharding means moving live data while serving traffic.

TipThe faithfulness test

Do the domain’s queries carry this key — and what is the measured skew, not the assumed evenness?

  • If yes → the key is the domain’s unit. Verify cross-shard queries are enumerated, and that a resharding plan exists.
  • If no → say which half failed. Queries do not carry the key: change it. Carried but skewed: split the hot tenant, or isolate it.
  • If you can’t answer → stop. Count how many queries carry the candidate key, then measure the top-tenant share of rows. The choice waits until that is on file.

Case study: Function vs stored procedure vs query

A month-end close moves forty thousand postings, and one endpoint in a small service posts without calling the procedure that owns the rule, so one debit lands without its credit and the trial balance is off by €4,200.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A procedure is a named body of SQL the server compiles and keeps; a function returns a value inside a query; an inline query lives only in the client that sent it. The first two give one rule one home, and claim that the invariant holds for whoever writes.

The database knowledge gap it signals

A rule in the schema asserts that this writer is not the only writer, now or later. That is a fact about the domain, not about speed: no caller may be trusted to remember the rule. The gap question: which writers must obey this rule, and who can currently write without it?

ImportantWhen the domain mandates it

Double-entry posting: a debit and its credit must land in one transaction, the sum must be zero, and the rule must hold for the API, the importer, and the service nobody has written yet. One posting procedure covers every caller that uses it, and revoked write grants cover the rest — plus computation that must not travel: sum a hundred million rows in the server, return one number.

WarningWhen it’s a guess dressed as engineering

“Put it in a procedure, it is faster” seduces because it is sometimes true; the trap is the unowned one — a rule the write paths never mention. The app grows a discount rule, the procedure grows one too, and two truths drift until a customer is charged twice. The inverse dogma fails alike: “no procedures, ever,” so five services re-implement the balance rule, and the hundred-million-row sum never travels.

TipThe faithfulness test

If a second application writes to this table tomorrow, do the same rules survive — and does a reviewer see them?

  • If yes → the rule is domain-owned, and placement follows. Check one copy exists, the same body runs for every writer, and no grant bypasses the procedure.
  • If no → one client’s habit, not a schema fact. Keep the logic in the application, in version control, with tests.
  • If you can’t answer → stop. List every current and planned writer, then ask which rules the domain requires of each. The choice waits until that is on file.

Case study: Row-level triggers

A balance is corrected at 09:25 and wrong again at 09:33, and the cause is a trigger that recomputes it from a rule nobody on the team had read.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A row trigger is a body of SQL the database fires by itself, once per row a statement touches; a statement-level trigger fires once per statement and does not carry the per-row cost below. It encodes knowledge no caller invokes: the table declares the consequence, for anyone who writes.

The database knowledge gap it signals

A trigger says no writer may be trusted to remember the rule and, while enabled, none may opt out — a strong, sometimes true claim. The rule gains no name at any call site, which is where accountability sits. The gap question: would a developer who never opens the table definitions (the DDL) predict that this happens?

ImportantWhen the domain mandates it

An audit row on every inserted, updated, or deleted row of a regulated table, written in the same transaction, so trail and fact cannot diverge. Or a derived column the schema owns and arithmetic determines — a line total, where the alternative is hoping six code paths agree.

WarningWhen it’s a guess dressed as engineering

A business rule in a trigger: recalculate loyalty on every order update. It looks stronger than a service call, and it is invisible to everyone reading the application: no call site, no signature, nothing in the trace. It fires per row, so a two-million-row load means two million firings; on engines that allow nested firing it cascades into other triggers. Then comes the week spent answering “who updated this row.”

TipThe faithfulness test

Could a developer who never opens the DDL predict that this happens — and does the rule survive that test?

  • If yes → the table owns the consequence, and it is visible where the table is defined. Check it covers every write path and stays cheap per row.
  • If no → an application rule hiding in the schema. Move it to the code that owns the decision.
  • If you can’t answer → stop. Measure the biggest write, then ask which rules the domain wants for every writer. The choice waits until that is on file.

Case study: Object-relational mapper (ORM) lazy loading (the N+1 query)

One page takes 40 ms in staging and 700 ms in production, and the number of queries per row is identical in both.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: A navigation property — a reference from one object to its related rows — loads on first touch, so the ORM issues one query per parent row and the query count becomes a function of the data. It encodes an unstated cardinality — this list is short, this relation is optional here — and defers the second query until someone asks.

The database knowledge gap it signals

Cardinality per parent — rows loaded per navigation — is a domain fact the schema almost never records, and it is a size, measured at the largest page the product offers. Nothing in the access decides it; the code assumes “a few,” and the assumption stays invisible until the list grows. The gap question: what is the real cardinality of this relation at production page size, and did anyone count it?

ImportantWhen the domain mandates it

Singular navigation. Load the order header, then load its lines when a person opens that order: one extra query for one row, and nothing paid for the orders nobody opens. The reader waits for one query, not two hundred.

WarningWhen it’s a guess dressed as engineering

Lazy loading inside a list render. Each row follows the relation, so one statement becomes two hundred, and the defect is invisible until a real list appears: staging has twelve rows, production has two hundred, and the page slows about seventeenfold with no error to grep. Then the fix: load everything up front, which multiplies rows at each join level until a three-level fetch returns the product of all three lists and the ORM de-duplicates them in memory. Both placements encode a cardinality guess; in neither was the number counted.

TipThe faithfulness test

For each navigation the ORM will follow, do you know the cardinality it loads — counted, at production page sizes?

  • If yes → the load matches the domain. Verify it against the largest page the product offers, not the sample data.
  • If no → it is an assumption about size, not a fact about the domain. Eager fetch is the other guess: it multiplies rows at each join level. Neither is a fact until the cardinality is counted.
  • If you can’t answer → stop. Log the query count per request and the row count per relation, at production scale. The choice waits until that is on file.

Case study: Isolation levels

Two withdrawals of 200 from an account holding 300 can both commit, and the balance can end at 100 — at the default level, with read-modify-write.

Choosing a schema construct or a database mechanism? Ask “which fact does this choice encode — what exists, what repeats, what must stay true, what gets read together, how fresh an answer may be, among others?” If you can’t answer, you’ve found a knowledge gap: the schema enforces a guess. If you can name those facts, the schema is the knowledge embodied — the code catching up to what the domain decided.

Construct: An isolation level names the standard anomalies the engine permits — dirty read (a value never committed), non-repeatable read (a row that changes mid-transaction), phantom (a row that appears on re-query). Each engine adds its own, such as lost update (one write erasing another). Choosing one claims the domain can absorb exactly these — a claim about the business, not a setting.

The database knowledge gap it signals

The domain must already know which anomaly costs money — not which level sounds safest. A level that forbids more than needed is paid in retries; one that forbids less is paid in wrong balances. The gap question: which interleaving would lose money here, and does the chosen level exclude it?

ImportantWhen the domain mandates it

Read committed where the domain needs only that independent rows stay independent: two agents editing different orders. Serializable, or an explicit row lock, where two reads feeding one write must not interleave — read both balances, then write both. There the domain can name the loss: an account debited twice, a seat sold twice.

WarningWhen it’s a guess dressed as engineering

Shipping the default and calling it correct. Read-modify-write in code — read 300, compute, write the absolute value back — can lose an update on engines that give each statement a fresh snapshot, with no error. On engines where a transaction reads one frozen snapshot, the second writer on the same row aborts while write skew — two rows, each written on the other’s stale value — still commits. The over-defence is equally competent: the strictest level everywhere, buying deadlocks and retries for anomalies that never mattered.

TipThe faithfulness test

Does the chosen level rule out the anomaly that would actually hurt this domain, on this engine? Name the transaction and the loss.

  • If yes → the level is chosen, not inherited. Check the engine enforces it, not merely that the standard lists it.
  • If no → you inherited a default. Name the money-losing interleaving first, then take the lowest level that excludes it.
  • If you can’t answer → stop. List the transactions that read then write, and ask which pair the business would refuse. The choice waits until that is on file.
