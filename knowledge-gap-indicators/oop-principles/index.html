OOP Principles as Knowledge-Gap Indicators

A list of short posts that read each pattern as a completeness check on domain knowledge.

The OOP principles read as completeness checks: each names a rule about what a module should hold and what a caller should know — and each holds only where a domain fact stands behind it.

Pick a post on the left. It opens on the right.

Encapsulation is a language mechanism — access control on fields and methods. Whether a boundary earns its keep is not a language question; it is a question about what callers depend on.

Case study: Encapsulation

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

Encapsulation is a language mechanism — access control on fields and methods. Whether a boundary earns its keep is not a language question; it is a question about what callers depend on.

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Parnas: Modules should hide a design decision behind an interface so that the decision can change without affecting clients. [1]

The domain knowledge gap it signals

An encapsulation boundary splits a type into what callers may depend on and what they never see. The real claim is not “something is hidden here” but “this interface is exactly what callers need.” That claim has content only if the team knows the callers’ needs — which parts the domain assigns to this thing, and which are one way of fulfilling them. The gap shows when the split is drawn by habit: the interface carries choices no caller asked about, or withholds something needed. Where the domain fixes a concrete detail, that detail belongs in the interface; an abstraction above it asserts a concept nobody decided.

ImportantWhen the domain mandates it (cohesion-increasing)

The team can point at each exposed operation and name the need it serves: “converting a payment uses the current rate” is a domain-assigned responsibility, and how the rate is stored is one way of fulfilling it. Callers depend on the responsibility, not the fulfillment, so reworking the internals touches no one.

WarningWhen the domain doesn’t (cohesion-reducing)

Encapsulation as a default virtue. Private fields with public getters and setters: the representation becomes part of the commitment, so an internal choice and the callers’ needs are fused — reworking the internals means renegotiating with every caller. Interfaces wrapped around things no caller needs: commitments with nobody to commit to. Where the domain mandates the concrete detail, the abstraction asserts a concept nobody decided; the concept is unwritten, and callers couple to the invention. The mirror failure: withholding what callers need produces workarounds — reflection, duplicated internals, paths that bypass the boundary. The mechanism runs without the knowledge.

TipThe faithfulness test

For each thing this type exposes: which need does it serve? For each thing it withholds: why may no caller reach it?

  • If you can answer both → applicable. The boundary is the code catching up to the knowledge.
  • If the answer is “private by default” → inapplicable. The mechanism runs without the principle.
  • If you can’t answer → unclear. You found incomplete domain knowledge, not a wrong pattern.

An extends clause is a claim: “this IS-A that, permanently, in the domain.” Usually it is code reuse wearing a taxonomy hat.

Case study: Inheritance / Subtyping

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

An extends clause is a claim: “this IS-A that, permanently, in the domain.” Usually it is code reuse wearing a taxonomy hat.

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Liskov and Wing: A subtype must be usable in place of its supertype without altering the correctness of the program. [2]

The domain knowledge gap it signals

Every extends freezes a classification into the code: the child is declared a kind of the parent, for all time. That claim has content only if the domain draws the distinction — if a domain expert would state the classification as a fact of the business, and if substitution holds under every change the domain can force. The gap shows when the hierarchy answers a question nobody asked the business: the taxonomy reflects how the code happens to be organised, not how the domain classifies. The square–rectangle trap is the textbook case; the everyday version is a parent class that exists only because two classes shared three methods.

ImportantWhen the domain mandates it (cohesion-increasing)

The classification is a domain fact with a forcing condition. Banking regulation distinguishes account types, and a savings account IS a bank account in the regulator’s own language — substitution is a legal truth, not a programming nicety. When the business itself reasons through the subtype (“any account may be frozen; savings accounts additionally accrue interest”), the hierarchy is the code catching up to the knowledge.

WarningWhen the domain doesn’t (cohesion-reducing)

Inheritance used to reuse implementation. Two classes share code, someone extracts a base class, and the child is coupled to every future change of the parent — while the code asserts a classification the domain has not stated; that knowledge is unwritten. The parent’s change reasons and the child’s diverge, but the hierarchy forces them to travel together: a change the domain aims at one concept lands on both. The taxonomy hat hides the actual structure, which was coincidence of code, not identity of concept.

TipThe faithfulness test

For a given extends: would a domain expert state this classification as a fact of the business — and does the subtype remain substitutable under every change the domain can force on the parent?

  • If yes to both → applicable. The hierarchy is the code catching up to the knowledge.
  • If the honest answer is “we wanted to share the code” → inapplicable. Reuse wearing a taxonomy hat.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Composition over Inheritance

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

Composition over inheritance is the flip side of yesterday’s post (#136). The domain question is: “is this a stable classification, or a role the thing plays?”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Gamma et al.: Favour object composition over class inheritance. [3]

The domain knowledge gap it signals

Choosing inheritance freezes a relationship as permanent taxonomy; choosing composition says the relationship is a role — attached, detachable, reassignment-capable. An employee is a person who plays the employee role; a discount policy is attached to an order, not what an order is. The gap shows when the structural choice was made for reuse or convenience without asking which reading the domain supports — the choice still encodes a claim about the business, and that claim is unwritten until the domain states it. Only one reading is true.

ImportantWhen the domain mandates it (cohesion-increasing)

Composition wins when the domain itself reassigns roles: a contractor becomes an employee; a customer is also a supplier; a policy attaches to this order today and that one tomorrow. Roles vary independently of the carrier’s identity, and composition encodes exactly that independence — a change in the role’s rules arrives without touching the thing that plays it. Inheritance stays honest in the opposite case (#136): the domain holds the classification fixed, and a changed relationship would mean a different thing entirely.

WarningWhen the domain doesn’t (cohesion-reducing)

Composition adopted as a blanket slogan. The relationship is a stable domain classification, but the code models it as an attachable role “for flexibility” — flexibility against a change no domain mechanism can force. The price is real: indirection, identity workarounds (the composed parts re-deriving what “the same thing” means), and a structure that invites the domain-illegal move — swapping a component the business considers constitutive.

TipThe faithfulness test

For a given relationship: can the domain change it without changing the thing’s identity?

  • If yes — the business reassigns, swaps, stacks roles → composition. The domain treats it as played, not inherited.
  • If the domain would say “it would then be a different thing” → the classification is stable; inheritance may be the honest encoding.
  • If you can’t answer → unclear. The structure is a guess about permanence the business never confirmed.

Case study: DRY (Don’t Repeat Yourself)

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

DRY says every piece of knowledge must have a single representation. It presupposes you know which duplications are the same domain rule — and which are coincidental text similarity.

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Hunt and Thomas: Every piece of knowledge must have a single, unambiguous representation within a system. [4]

The domain knowledge gap it signals

DRY is about knowledge, not text — but the only instrument the programmer has operates on text. Two fragments look alike, someone extracts the common code, and the extraction itself is a claim: “these are one rule, and a change to it must reach both.” That claim has content only if the domain agrees. The gap shows when the team merged by similarity without asking whether one domain decision stands behind both fragments — the merge couples two change drivers, and when one rule moves and the other must not, the shared abstraction breaks in production.

ImportantWhen the domain mandates it (cohesion-increasing)

Both fragments encode the same domain decision: the same VAT rule, the same rounding policy, the same eligibility criterion. The domain itself guarantees they change together — when the rule is revised, every place that applies it must move in lockstep, and a single representation is what makes that guarantee structural rather than hopeful. The deduplication is the code catching up to the knowledge.

WarningWhen the domain doesn’t (cohesion-reducing)

Merging by text similarity. Two price calculations that coincide today because the numbers happen to align; two validation blocks that share a shape but answer to different authorities. The duplication was the faithful structure — two rules, two drivers, two futures — and the merge planted a coupling no rule behind the fragments mandates; if each fragment answers to a different authority, each rule is unwritten and the merge hides both. Every later change now starts with an archaeology dig: which of the callers may follow this edit, and which must be peeled off first?

TipThe faithfulness test

For a candidate merge: if the domain rule behind fragment A changes, must fragment B change with it — always, by the domain’s own logic?

  • If yes → one knowledge, one representation. Merge.
  • If no → the duplication is faithful. Extracting couples two drivers.
  • If you can’t answer → unclear. The similarity is visible; whether it is one rule is exactly the knowledge you’re missing.

The Law of Demeter says a method may call its immediate collaborators only, never reach through them. “Who may know whom” is a coupling claim. An a.b().c() chain asserts a navigation path the domain may not mandate.

Case study: Law of Demeter

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

The Law of Demeter says a method may call its immediate collaborators only, never reach through them. “Who may know whom” is a coupling claim. An a.b().c() chain asserts a navigation path the domain may not mandate.

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Lieberherr and Holland: A method should talk only to its immediate collaborators, not to their collaborators. [5]

The domain knowledge gap it signals

Every reach-through chain asserts that the caller’s business genuinely depends on the far object along this route — that the path is a stable domain relationship, not an accident of object layout. Sometimes it is: an order’s customer’s billing address is a path the business itself reasons about. Sometimes it is digging: the caller exploits an implementation trail, following a route that exists only in the object graph. The gap shows when nobody can say which of the two a given chain is — the coupling exists, its legitimacy unexamined.

ImportantWhen the domain mandates it (cohesion-increasing)

The law earns its keep where the chain is NOT a domain path. Rewriting a.b().c() into a direct ask keeps the caller coupled only to the object whose job the operation is — so when the intermediate structure changes for its own reasons, the caller doesn’t move. The caller now depends on what the domain mandates (the outcome) and not on what it doesn’t (the route). Note the asymmetry: the law is a heuristic about structure; its violations are the signal worth auditing, one chain at a time.

WarningWhen the domain doesn’t (cohesion-reducing)

Mechanically eliminating every chain. Where the chain is a domain relationship the business itself reasons about, the rewrite replaces a recognised route with a direct ask nobody decided; where it was an implementation route, wrapper methods tunnel the same dependency and only move the coupling out of sight. The caller’s real dependence on the far object is hidden, not removed.

TipThe faithfulness test

For a given chain: is this path a relationship the domain itself recognises, or a traversal of an object graph that exists only as implementation?

  • If the domain recognises it → the coupling is mandated; keep it visible and direct.
  • If not → the path exists only as an implementation route; the chain couples the caller to structure the domain never mandated.
  • If you can’t answer → unclear. The navigation compiled, but nobody checked it against the map.

Speculative extension points are guessed change drivers. YAGNI is the discipline of refusing structure for a driver you cannot name — and it is not a license to ignore drivers you can.

Case study: YAGNI

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

Speculative extension points are guessed change drivers. YAGNI is the discipline of refusing structure for a driver you cannot name — and it is not a license to ignore drivers you can.

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: Build only what the requirements demand now; do not add speculative generality. [6]

The domain knowledge gap it signals

Every “we’ll need this to be flexible” asserts that the domain can force a variation here — a forcing condition exists, and the structure stands ready for it. The gap is anticipating variation no domain mechanism can force: a plugin point for providers the market does not contain, a config switch for a rule the business holds fixed, an abstraction layer against a change nobody can cause. The reverse gap is costlier: “you aren’t gonna need it” said about a variation the business has already announced — the seam was domain knowledge, and YAGNI was invoked to unsee it.

ImportantWhen the domain mandates it (cohesion-increasing)

No forcing condition exists for the anticipated change, and the team can say so honestly — not “we didn’t ask,” but “we asked, and the domain holds this fixed.” Deleting the speculative structure removes a coupling to a phantom driver: the code now covers exactly the variations the domain can produce, and nothing pays rent for the rest. YAGNI here is knowledge applied, not effort avoided.

WarningWhen the domain doesn’t (cohesion-reducing)

Two failure modes, same root. YAGNI invoked against a variation the domain demonstrably forces — a regulator who can change the rule, a market that adds channels, a pricing policy with a history of revision — because “we’ll add it when we need it,” as if adding structure under deadline pressure were free. The refusal asserts that no forcing condition exists; the domain has one, so the seam’s absence is a structure nobody decided. And the mirror: building for a forcing condition nobody can name. Both share one gap: the future change was decided without consulting the domain that owns it.

TipThe faithfulness test

For a given piece of flexibility (or a refused one): name the forcing condition that would make you use it.

  • If you can name the domain mechanism → the structure is knowledge, whether you build it now or deliberately defer it.
  • If the answer is “someday, maybe” → the structure is a guess; YAGNI applies.
  • If you can’t answer either way → unclear. The decision to build or not build is currently a coin flip dressed as engineering judgment.

Information hiding is Parnas’s rule: each module hides one decision that may change. Information hiding audits the whole decomposition: is the module structure the map of the domain’s forcing conditions?

Case study: Information Hiding (Parnas)

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

Information hiding is Parnas’s rule: each module hides one decision that may change. Information hiding audits the whole decomposition: is the module structure the map of the domain’s forcing conditions?

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Parnas: Decompose a system by hiding the design decisions most likely to change behind stable interfaces. [1]

The domain knowledge gap it signals

Parnas’s rule works at the system level: derive module structure from the inventory of decisions, grouped by what could force them to change. One module may hide several decisions — when the same conditions force them to change together — and one decision may not be split. The likelihood reading asks for a forecast that can never be checked when it is made. The recoverable reading lists decisions whose forcing conditions are demonstrable today — a regulator who has revised the rule. The gap shows as a break in the correspondence: co-changing decisions split across modules, or change-apart decisions hidden behind one wall.

ImportantWhen the domain mandates it (cohesion-increasing)

The correspondence holds both ways. Every module hides a cluster of decisions that share their forcing conditions, so one change event has one address; every decision with a demonstrable forcing condition lives in one such module. The structure is a complete map of the domain’s known forcing conditions.

WarningWhen the domain doesn’t (cohesion-reducing)

Two failures, same root. Decomposition by likelihood guess: boundaries drawn around decisions someone felt were change-prone, with no forcing condition anyone can name — speculation wearing Parnas’s hat. And decomposition by data shape or technical layer: all DTOs here, all controllers there, all “utilities” in a third drawer. Such a module hides no domain decision; its secret is a formatting convention. Meanwhile the genuinely volatile decisions — pricing policy, eligibility rules, regulatory thresholds — leak across five modules each, and the inventory of real forcing conditions is unwritten.

TipThe faithfulness test

Compare the modules with the decisions whose forcing conditions are demonstrable today. Are decisions grouped by shared forcing conditions?

  • If the correspondence holds both ways → applicable. The decomposition is the code catching up to the knowledge.
  • If co-changing decisions are split, or change-apart decisions share a wall → the correspondence breaks; that break is the gap.
  • If a module hides no decision → it is a drawer, not a module.

Behavior placement encodes where the knowledge lives. “Tell, don’t ask” is a claim that the object holding the data holds the knowledge to act on it.

Case study: Tell, Don’t Ask

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

Behavior placement encodes where the knowledge lives. “Tell, don’t ask” is a claim that the object holding the data holds the knowledge to act on it.

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Hunt and Thomas: Tell an object what to do rather than asking it for its state and acting on it yourself. [4]

The domain knowledge gap it signals

if (account.balance > amount) account.withdraw(...) looks harmless — but the overdraft rule just lived in the caller. Every “ask then decide” asserts that the decision belongs outside the object whose state feeds it; every “tell” asserts it belongs inside. Both are placement claims about domain knowledge, and both can be wrong. The gap shows when the placement was never reasoned about: rules drift into whichever file was open, and the object that owns the state no longer owns the rule that governs it — so a change to the rule hunts through every caller.

ImportantWhen the domain mandates it (cohesion-increasing)

The decision is a function of one object’s own state and constitutes one domain rule: overdraft policy on the account, eligibility on the application, validity on the certificate. Telling places the behavior where its change driver points — when the policy is revised, exactly one module moves, and no caller needs to know that anything changed. The placement is the code catching up to where the knowledge already lives in the business.

WarningWhen the domain doesn’t (cohesion-reducing)

Dogmatic “never return data.” Objects swallow decisions that belong to collaborators, growing into gods of their own state; or tell-methods sprout callback and lambda parameters so the caller can smuggle its decision back in through the tell — the knowledge moved syntactically while the dependency stayed exactly where it was. The deeper miss: a decision that consults several objects’ state is a collaboration, and no amount of telling removes that coupling — it only hides which object is actually deciding.

TipThe faithfulness test

For a given decision: which object’s state does the domain rule consult?

  • If one object’s → tell it. The rule lives where its data lives.
  • If several objects’ → the decision is a collaboration; place it explicitly (a policy, a service) instead of tunnelling it through a tell.
  • If you can’t say whose state the rule reads → unclear. The behavior is placed, but nobody knows by what knowledge.

An extension point is a pre-built seam where a new variation plugs in without editing existing code. It is legitimate only when the domain knowledge you have today selects the seam. Built for a hypothetical future variation, it is a bet nobody can check.

Case study: Extension Points

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

An extension point is a pre-built seam where a new variation plugs in without editing existing code. It is legitimate only when the domain knowledge you have today selects the seam. Built for a hypothetical future variation, it is a bet nobody can check.

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

The domain knowledge gap it signals

Every extension point — a plugin interface, a strategy slot, a template method — claims “the domain varies here, and not there.” No slogan tells you which point to build or when; a module can be extensible somewhere, never everywhere, so every seam is a bet about the location of change. The gap is the bet placed without the knowledge that settles it. Two failure signatures follow: seams on axes the domain holds fixed, and hardcoding on the axis it varies — the pricing formula’s shape changes while the seam sat at the rates.

ImportantWhen the domain mandates it (cohesion-increasing)

Current domain knowledge selects the seam — not clairvoyance, but a forcing condition the business can point to now: tax rules the jurisdiction already revises on a schedule, payment methods the market keeps adding, report formats a regulator has already changed twice. Build the seam where change has already shown itself. The next variation arrives as a new implementation plugged into the same seam, and the code already written stays untouched.

WarningWhen the domain doesn’t (cohesion-reducing)

Speculative extension points: abstractions for a second backend never funded, hooks for customizations never requested, strategies for jurisdictions never entered. Each wrong seam is worse than dead code — it looks deliberate and nothing flags it for removal, so the coupling accumulates as the codebase ages. And the inverse failure: the axis of demonstrated volatility was hardcoded, so every real change edits the code that was supposed to stay fixed.

TipThe faithfulness test

For a given extension point: which change has the domain already shown it can force along this axis — and is everything outside the seam safe from the changes shown elsewhere?

  • If you can point to demonstrated volatility → applicable. The knowledge selected the seam.
  • If the justification is “we might need it” → inapplicable. Speculation wearing a principle’s hat (#140 applies).
  • If you can’t answer → unclear. The structure bets on a change map nobody has drawn — that map is the missing knowledge.

Immutability is a language-level commitment that the domain treats a thing as replaceable rather than updatable. The DDD side of this was covered in #85 — this post adds only the OOP-language angle.

Case study: Immutable Value Objects

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

Immutability is a language-level commitment that the domain treats a thing as replaceable rather than updatable. The DDD side of this was covered in #85 — this post adds only the OOP-language angle.

Evans: Value objects should be immutable: rather than modifying one, you create a new one in its place. [7]

The domain knowledge gap it signals

Post #85 covered the identity question: a value object claims that identity doesn’t matter, that equality by content is the domain’s own notion of sameness. What remains for this folder is the mutation question. Making a class immutable asserts: “when this fact changes, the domain replaces it — the old one stops being true.” An address correction is a new address, not a mutated one; a price revision supersedes the old price. Where it goes wrong: immutability chosen for technical convenience — thread safety, cacheability — applied to facts the domain revises. Thread safety is a real requirement, but it does not decide whether a fact is replaced or mutated; the domain does. If the domain revises the fact, immutability asserts a replacement nobody decided — the rule is unwritten — and builders and copy-methods must emulate updates the business performs. And the inverse gap: mutable value-shaped objects whose shared aliasing silently couples changes that should be independent.

TipThe faithfulness test

For a value-shaped class: when this fact “changes” in the business language, does the old one stop being true — or does the same thing acquire a new state?

  • If the old one stops being true → replace, and immutability is the code catching up.
  • If the same thing acquires new state → this was never a value question; the identity question from #85 (and #86) decides the structure.
  • If the domain language has no answer yet → unclear. The keyword is written; the knowledge it encodes is not.

A static member claims more than a singleton (#13) does: not “exactly one instance” but “no instance at all — this knowledge belongs to the concept as such.”

Case study: Static Fields and Methods

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge.

A static member claims more than a singleton (#13) does: not “exactly one instance” but “no instance at all — this knowledge belongs to the concept as such.”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

The domain knowledge gap it signals

Every static is a placement claim: this fact or behavior exists independent of any particular thing — it holds for the type itself. That claim has content only if the domain speaks that way: a conversion constant the physics fixes, a rule that governs the concept rather than its instances, construction logic that is merely named creation (#91). The gap shows when static was chosen so the code could reach something without knowing which thing owns it — the knowledge lives nowhere, so it lives everywhere.

ImportantWhen the domain mandates it (cohesion-increasing)

The fact is genuinely instance-independent in the domain: a mathematical constant, a classification rule that holds for the type as such, a factory method that names a construction the business names (“Money.euros(amount)”). No instance could carry the knowledge, because no instance is what the knowledge is about.

WarningWhen the domain doesn’t (cohesion-reducing)

Two classic traps, same root. Static mutable state — the cache, the counter, the registry — asserts “the whole universe of discourse shares one of these.” Sharing scope is a domain decision. If the domain has not named it, the assertion is a claim nobody decided — the mandate is unwritten, not absent — and the result is a hidden global that couples every caller to one change driver. And the static utility class: behavior that acts on instances, parked at the type level — the class asserts a type-level fact the domain never stated. Even static final deserves suspicion: TAX_RATE = 0.21 hardcodes a domain decision with a forcing condition — the value is fixed so far, the speculative seam’s mirror image (#140, #143).

TipThe faithfulness test

For a given static member: does the domain state this fact without referring to any particular instance — or did the code lose track of which thing owns it?

  • If the domain speaks instance-free → applicable. The keyword encodes the knowledge’s true level.
  • If the knowledge consults one thing’s state → inapplicable. Place the behavior with the thing.
  • If it’s shared mutable state nobody justified → unclear at best. The coupling is real; the mandate for it was never checked.
