Vert.x and the Event Loop

The event-loop model as a blocking claim.

A design makes a claim about blocking: what may wait, what may never wait. Each post names the claim and asks what fact of the workload justifies it.

Pick a post on the left. It opens on the right.

Writing an event-loop handler? Ask “which claim does this design make about blocking — what may wait, what may never wait?” If you can’t answer, you’ve found a knowledge gap: the handler blocks on a fact nobody established. If you can, the design is knowledge embodied — the thread model catching up to what the workload decided.

Case study: Never block the event loop

One blocking call on an event loop thread stalls every request that loop is serving — not the one request that made it.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: Vert.x runs handlers on a small set of event loop threads, each serving many connections. A handler that waits — a JDBC query, a file read, a lock, a sleep in a retry — holds its loop for the whole wait. Vert.x’s documented rule: a blocked loop stops its connections cold. A handful of threads carry tens of thousands of connections, and one wait takes one of them out of service.

The Vert.x knowledge gap it signals

The loop is a claim about every call a handler makes: none waits. It holds only if someone checked each one — the driver, the cache client, the name lookup, the log appender, the synchronized block. The team must know which calls in its own code can wait, and for how long. The framework cannot.

The gap question: for each call on a loop thread, is it proven non-blocking — and how was that proven?

ImportantWhen the domain mandates it

An audited blocking inventory: database calls, file IO, locks, synchronized blocks, third-party clients — every entry listed, every one moved to a sized worker pool or a reactive client, at the cost of threads. The load test that would expose a stall runs clean at peak, and loop task durations stay in microseconds.

WarningWhen it’s a guess dressed as engineering

One JDBC call left on a loop thread. At low concurrency it is invisible: the query returns in 3 ms and the loop looks healthy. Under load the same 3 ms occupies a thread a hundred connections share, so throughput collapses while CPU sits near idle and latency spikes look random. The framework gets the blame, then the database.

TipThe faithfulness test

For each call on a loop thread: is it proven non-blocking — and how was that proven?

  • If yes → no wait remains on the loop. Check the proof names each call site, then reread task durations at peak.
  • If no → some call may wait, and every request on that thread pays. Move it to a worker or a reactive client, and state which.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. Measure handler time on the loop and its p99 task duration.

Case study: Worker verticles and executeBlocking

executeBlocking moves your blocking work off the event loop into a pool of twenty threads — where it may also run one task at a time.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: Vert.x offers two ways off the loop. A worker verticle is deployed with the worker flag and receives messages on the worker pool. executeBlocking hands one task to that same pool and returns a Future. Both draw on twenty threads by default, and executeBlocking is ordered by default, so tasks from one context run one at a time. Blocking work leaves the loop; its concurrency and ordering move into two settings nobody wrote down.

The Vert.x knowledge gap it signals

The offload does not remove the limit; it relocates it to two settings: pool size and ordering. The worker pool is the concurrency limit for everything that blocks, and its queue is where latency accumulates. Ordering is the second half: an ordered flag serialises independent work, and dependent work marked unordered returns out of sequence.

The gap question: which code blocks — measured — and what pool size keeps the worker queue bounded?

ImportantWhen the domain mandates it

Blocking segments offloaded deliberately — a legacy driver, a render, a filesystem sweep — onto a named pool sized from measured concurrency. Each path states its ordering requirement, and queue depth is watched at peak.

WarningWhen it’s a guess dressed as engineering

executeBlocking wrapped around everything to make handlers safe. The pool becomes an unsized thread pool, raised to a hundred threads to stop queueing. Ordering flips quietly: a path that needs sequence is marked unordered, or one that could parallelise keeps the default and serialises, and the results arrive in an order nobody can re-sequence. It reads as non-blocking and behaves as an unmeasured pool.

TipThe faithfulness test

Which code blocks — measured — and what pool size keeps the worker queue bounded?

  • If yes → the offload is a stated fact. Confirm the pool covers concurrent blocking segments at peak, and each path’s ordering flag matches its callers.
  • If no → both the pool and the order are guesses. Size the pool from measured concurrency, and state per path whether results may arrive out of sequence.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. Measure each blocking segment’s hold time, and how many are in flight at peak.

Case study: Event loop count

A pod with a two-CPU request and no CPU limit starts sixteen event loops, because the JVM sees the host’s eight cores and the default doubles them.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: Vert.x sizes its event loop pool, by default, at twice the processors the JVM reports, and each loop is one thread carrying many connections. The number is the process’s unit of parallelism. Too few loops and the cores idle; too many and the threads compete for a quota they never had. The processor count the JVM reports follows the cgroup quota — a CPU request without a limit leaves it reading the host.

The Vert.x knowledge gap it signals

The setting encodes a claim about CPU: this process owns that many cores, and all of them may serve handlers. In a container that claim must come from the cgroup, not the host, and even then it is half the fact — workers, GC and any sidecar draw on the same quota. The team must know the quota, then decide how much of it the loops may claim.

The gap question: how many loops does this process actually run — and does that match the quota rather than the host?

ImportantWhen the domain mandates it

The loop count is set explicitly from the CPU quota and logged at startup beside the worker pool size. Utilization stays low at peak, and task durations stay short — a blocked loop also runs idle.

WarningWhen it’s a guess dressed as engineering

A two-CPU request without a limit running sixteen loops because the host has eight cores and the default doubles them. Nothing fails outright: latency spikes at random, the throttling counter climbs, and every trace blames the database. Or the quota shrinks in a later release and the loop count is never revisited, because the two numbers live in different repositories.

TipThe faithfulness test

How many loops does this process actually run — and does that match the quota rather than the host?

  • If yes → the loop count is a stated fact. Check that workers and heap were sized against the same quota, then watch throttling.
  • If no → the loops compete for CPU they do not have. Set the count from the quota, leaving headroom for workers and GC.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. Read the loop count at startup, the quota from the cgroup, and the throttling counter under load.

Case study: Backpressure

A slow client never raises an error. It just grows the server’s outgoing buffer until the heap does.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: A write returns before the bytes leave. Each connection holds a queue of pending writes, and writeQueueFull turns true when that queue passes its maximum; a drain handler fires when it falls back to half. Check the queue and it stays bounded while a consumer catches up; skip the check and that queue is the heap.

The Vert.x knowledge gap it signals

Backpressure claims some producer can outrun some consumer. That is a fact about the workload — a result set streamed to a mobile client, a fan-out to a reporting replica — and it is invisible in a test where the client reads at server speed. The team must know which paths produce faster than they consume, and which sources can be paused.

The gap question: what bounds the in-flight bytes to a slow consumer — stated — and is it tested with a throttled peer?

ImportantWhen the domain mandates it

Streaming writes where every path checks the queue, sets a drain handler that resumes, and pauses the source while the queue is full. Bytes in flight per connection stay at the bound, memory is flat against a deliberately throttled consumer, and the bound is a chosen number.

WarningWhen it’s a guess dressed as engineering

Rows written without a queue check, because the local client was fast. The slow client’s buffer grows to the whole result set, a hundred such clients finish the heap, and the crash points at an allocation unrelated to the peer. The second variant: an upload read into memory because nothing paused the request. The code reads as streaming, because each chunk is written.

TipThe faithfulness test

What bounds the in-flight bytes to a slow consumer — stated — and is it tested with a throttled peer?

  • If yes → backpressure is a stated bound. Check it is enforced on every write path, and the throttled-peer test runs in the suite.
  • If no → the bound is the heap. Add the queue check and drain handler, pause the source while the queue is full, and state the maximum.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. Measure bytes buffered per connection against a throttled consumer, and the largest result it can stream.

Case study: Deployment instances per verticle

An in-memory counter deployed with eight instances is eight counters, and seven of them count for nobody.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: setInstances deploys N copies of a verticle across the event loop threads; each copy has its own fields. The count is a parallelism claim: N instances may serve handlers at once, and no two share an instance field — static state is common to all of them. Instances buy throughput, and every field becomes per-instance state whether meant or not.

The Vert.x knowledge gap it signals

The setting asserts two facts: the work per message is independent, and nothing the verticle holds may be visible to another message on another thread. Both are properties of the workload. The team must know what state the verticle holds and who reads it, then choose the count from that answer, not the core count.

The gap question: does this verticle hold state — and is the instance count consistent with that answer, by design?

ImportantWhen the domain mandates it

Stateless verticles at N instances, the count set from the CPU quota because the parallelism is real. Stateful ones held at a single instance, or their state moved to a shared store or map, with each field’s scope written beside the deployment.

WarningWhen it’s a guess dressed as engineering

An in-memory counter — a rate limiter, a cache, a session map — deployed with eight instances because scaling out looked right. Every increment lands in one instance, the dashboard reads one of the eight, and the tests pass on a laptop at one instance. The number is wrong by a factor of eight and nothing throws. The other variant is as quiet: one instance for safety, so one thread carries the traffic.

TipThe faithfulness test

Does this verticle hold state — and is the instance count consistent with that answer, by design?

  • If yes → instances and state agree. Check that no field assumes a single writer across messages, and the count still matches the CPU quota.
  • If no → the count and the state contradict. Either take the state out of the instance, or set the count to one and say why.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. List every field on the verticle, mark each mutable or constant, and name which component reads it.

Case study: The event bus and its scope

A clustered event bus delivers a message once and keeps nothing — and three services treat it as a queue that survives a restart.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: Vert.x has one EventBus API and two scopes. Local passes messages between verticles inside one JVM, often by reference. Clustered sends the same call over a network transport. The scope changes the route, not the promise: at-most-once, no bus persistence, no bus redelivery after a node dies. The calling code is identical.

The Vert.x knowledge gap it signals

The bus promises ordering between one sender and one receiver, and that a registered handler runs. No arrival is promised. Whether a lost message is acceptable is a fact about the workload, never about the bus. The gap question: does any consumer here need the message to arrive after a crash?

ImportantWhen the domain mandates it

Intra-process decoupling. A verticle announces an order was placed; three local handlers update their own state; a lost event costs nothing because that state rebuilds from the database. The claim is local and best-effort, and the bus is exactly that claim.

WarningWhen it’s a guess dressed as engineering

The clustered bus as a work queue. Work goes to a worker verticle on another node, the sender moves on, nothing records the job. The node restarts mid-job and the work is gone, because no retry was ever designed. It has a bus, an address, and a handler, so it reads as messaging. It is a fire-and-forget network call to an address, with no ledger.

TipThe faithfulness test

For each bus message: what delivery guarantee does it need — stated — and what does this bus actually provide?

  • If yes → the bus is the shape the claim requires. Confirm no consumer’s correctness rests on redelivery, and that a lost message is recoverable from another source.
  • If no → a broker buys durability at the cost of a component to run. Keep the bus for best-effort paths; route durable messages to the broker.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. List every message this bus carries and mark each one durable or best-effort.

Case study: Shared data, local versus cluster-wide

One network hop per read, times your request rate: the cluster-wide “cache” now answers over the network what the heap answered for free.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: Vert.x SharedData offers a local map and a cluster-wide map behind one API. The local map reads in heap with no encoding. The cluster-wide map serialises every value and crosses the cluster manager on each operation, so a read is a roundtrip and a write is a roundtrip plus replication.

The Vert.x knowledge gap it signals

The choice is a claim about who needs the truth. Local says: this process is the only reader whose freshness matters. Cluster-wide says: every node must see the same value, and the domain pays a hop for it. The gap question: must a node see a write made on another node, or must it read fast?

ImportantWhen the domain mandates it

Hot read paths use the local map: a per-node lookup table, flags refreshed by an event, a counter only this node’s handlers touch. Nobody asked for cross-node consistency, so the local map states the fact. The cluster-wide map earns its hop where staleness is a bug — a leader flag, a token held by exactly one node, a drain switch whose wrong value corrupts work.

WarningWhen it’s a guess dressed as engineering

The cluster-wide map used as a cache. Someone adds a lookup table to shared data to stop hitting the database, and every read becomes serialisation plus a hop, inside the handler that could have read the heap. Latency budget spent on lookups, plus a codec cost nobody measured. It reads as a cache and bills as a remote call.

TipThe faithfulness test

Who reads this map, how often, from where — measured — and does it need cross-node truth or local speed?

  • If yes → confirm the reads are off the hot path, and count the hops each request pays. Verify the hit rate beats the hop, not just the database query.
  • If no → split it. Local map for the hot reads, cluster-wide only for the few values whose staleness is a correctness bug.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. Instrument reads per node per second, then the tolerable staleness of each value.

Case study: Future and Promise composition

One compose step forgets to complete its promise, and the caller does not fail — it waits, holding a connection, until a timeout that may not exist.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: A Promise is the writable end, a Future the readable one. Compose, map, and recover chain steps without blocking a thread. The chain is one error channel: the first failure skips every downstream step until a recovery claims it — and a step that never fails its promise stops every step after it.

The Vert.x knowledge gap it signals

Composition moves the failure path into the shape of the chain, away from the code you read. Each link is a claim about who owns the error. Recover turns a failure into a value; otherwise supplies a fallback value; no handler means the error is dropped and nobody hears it. The gap question: for each link, who receives the failure — a named handler, or no one?

ImportantWhen the domain mandates it

Recovery composed exactly where the domain names it. A cache lookup fails and recover serves the database read, because the cache was always optional. A metrics call fails and otherwise completes with an empty result, because metrics are not load-bearing. The fallback is a decision written where it applies, not scattered.

WarningWhen it’s a guess dressed as engineering

The chain with a lost failure. A middle step calls an async API, subscribes with onSuccess only, and never completes its own promise on error. Upstream fails, downstream never starts, the promise stays pending, the request hangs. Nothing looks wrong: a handler exists, a chain exists, no exception is thrown. The error died inside the chain, and the symptom appears as latency.

TipThe faithfulness test

For each composed chain: who handles the failure path — named — or does the error die inside the future?

  • If yes → check each link completes or fails its promise on every branch, including the branches that throw.
  • If no → add a recovery at the boundary that owns the decision, and fail the promise in every terminal branch, not just the happy one.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. Count the futures that can stay pending, and the timeout that would end each one.

Case study: Non-blocking database clients versus the JDBC bridge

Every handler is non-blocking, the event loop never stalls, the dashboard is green — and the JDBC bridge pool is the wall the service hits.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: Two database clients wear the same API shape. The reactive client speaks the wire protocol itself and never blocks. The JDBC bridge wraps a blocking driver and runs each query on a worker thread from a pool. One occupies no thread per query; the other occupies one for the whole roundtrip.

The Vert.x knowledge gap it signals

The bridge is not a lie, it is a borrow. It says: this driver blocks, so lend me a thread from a pool you must size, and the loop stays safe. The claim it encodes is that the pool is the real concurrency limit for the database. The gap question: how many queries are in flight at peak, and how large is the worker pool under the bridge?

ImportantWhen the domain mandates it

The bridge where the driver forces it: a database with no reactive client, a vendor driver only JDBC exposes, a nightly batch far from the hot path. The bridge’s pool is sized from measured in-flight queries and kept separate from the general worker pool.

WarningWhen it’s a guess dressed as engineering

The reactive application whose data layer is the bridge. Twenty worker threads, five hundred concurrent requests, the rest waiting on a queue nobody sized. Latency climbs while CPU idles, and the trace blames a database that is healthy. It reads as reactive because the call returns a Future. It behaves as a thread pool with extra steps.

TipThe faithfulness test

Which database client is actually non-blocking — verified — and what pool sits under the bridge, sized how?

  • If yes → count in-flight queries at peak against the pool, and confirm the bridge pool is separate from the general worker pool.
  • If no → the loop is safe but the path is not non-blocking end to end. Measure the wait, then either adopt the reactive client or size the bridge deliberately.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. Measure concurrent queries at peak, then the time each one occupies its thread.

Case study: HTTP client connection pool sizing

Fifty concurrent calls, a default pool of five connections, and forty-five callers queueing on a limit nobody chose.

Writing a Vert.x handler? Ask “which claim does this design make about blocking — what may wait, and what may never wait?” If you can’t answer, you’ve found a knowledge gap: the event loop enforces a guess. If you can, the design is knowledge embodied — the code catching up to what the workload demands.

Mechanism: The Vert.x HTTP client keeps pooled connections per endpoint, and WebClient sits on it. Reuse is the point: a pooled socket beats a handshake. Max pool size caps the connections; requests beyond the cap wait in a queue. Idle and keep-alive timeouts decide when a socket is dropped. They must end before the server ends its own, or the pool hands out sockets the server is closing.

The Vert.x knowledge gap it signals

Pool size is a claim about measured concurrency, never about caution. Reuse assumes calls are frequent enough to beat a handshake. The queue assumes the wait costs less than the alternative. Neither is free, and both are decisions. The gap question: what is the peak concurrent call count per endpoint, at the peak hour?

ImportantWhen the domain mandates it

The pool is sized above the measured concurrent-call count and states a wait policy: bounded queue with a fast failure, or unbounded with a measured timeout. Timeouts are set together — connect, request, and idle below the server’s keep-alive.

WarningWhen it’s a guess dressed as engineering

The default small pool under real load. Nobody set the maximum, so it stays at five; the wait queue has no bound and no policy; the p99 belongs to the queue, not to the service. Then the idle timeout outlives the load balancer’s: the first call on a stale socket fails as a read timeout, and the retries read as flakiness. Somebody did set a timeout, so it looks tuned. Nothing was sized. Under HTTP/2 one connection multiplexes streams, which moves the bound from sockets to streams — not away from it.

TipThe faithfulness test

What is the measured concurrent-call count per client — and is the pool above it, with a stated wait policy?

  • If yes → check the idle timeout against the server’s, and that the queue bound fails fast instead of growing silently.
  • If no → the pool is the bottleneck by construction. Raise it to the measured count, or bound the queue and let the caller see the rejection.
  • If you can’t answer → unclear. You haven’t found the design wrong — you’ve found incomplete workload knowledge. Measure concurrent calls per endpoint at peak, then the wait each one records.
