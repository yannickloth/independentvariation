Substrate Facts as Knowledge-Gap Indicators

A series of short posts that read hardware, runtime, and platform constraints as knowledge-gap indicators.

Every structure below rests on a number. A ceiling, a rate, a timeout, a count, a majority. Each post states the bound, gives its value, and asks whether the structure follows from it.

The first list in this topic asks whether the domain mandates a coupling. This list asks a narrower question, and a harder one: what is the number?

Three things decide. The constraint must be named — a fact about the machine, the runtime, the network, or the bill, not a layer called “infrastructure”. The value must come from this system, at this load, on this release. And an obligation must exist that the value breaches: the fact measures, the obligation rules out.

A real number can still fail to bind. It is borrowed from another system, stale after a release, negotiable by a contract, or idle against the measured peak. Each post names the case where the bound does force the shape, and the case where it does not.

For the same reading of design patterns over domain knowledge, see the first list. For the bounds a data type imposes, see the encoding list.

Pick a post on the left. It opens on the right.

Capacity bounds answer one question: how much may one unit hold, or how much may all of them spend together? The answer is a number. It is either in the documentation, or it is absent.

Time bounds answer how long something takes, or how stale an answer may be. Physics sets a floor; settings set the rest.

Failure bounds answer how much may fail, for how long, and what must survive. Each is arithmetic on a count, a rate, or a majority.

Topology bounds answer how many units may exist and where they may sit. They decide what can be split, what must stay together, and what the client’s own stack allows.

Case study: Vertical scaling (the capacity ceiling)

Bound: A ceiling is a hard upper bound the substrate places on capacity: how large one unit may grow, how many units may exist, and what all of them may spend together.

The substrate knowledge gap it signals

The ceiling is knowledge only when someone can name it and trace it to its source — measured on this system, or documented by the vendor. “We cannot fit this in one node” is a claim about a value. The gap question is whether anyone knows the value, where it came from, and which release or licence sets it. A headroom figure read off a laptop measures a laptop. An unstated ceiling still binds; it is a constraint nobody can design against.

ImportantWhen the fact bounds the shape

The limit is named, traced to its source, and binding: every larger unit is exhausted or priced out. A licence that caps seats. A device with fixed flash. An engine whose maximum is documented. Then the system must fit inside the named unit and state its headroom. Which mechanism enforces that — bounded retention, a smaller working set, a reduced requirement — is a further choice the ceiling does not make.

WarningWhen the ceiling does not force it

A real value fails to force a structure in four ways, and they overlap. It is borrowed — measured on another system. It is stale — a release removed it. It is negotiable — a contract term cited as physics, which a different signature lifts. It is idle — the headroom is large against the measured peak. In each case the value is cited and prescribes nothing. The structure pays for a wall it may never reach.

TipThe faithfulness test

Can one person name the ceiling, say where the number came from, and state the price of the next size?

  • If yes → the value is known, and the structure is answerable to it. Check next whether the working set approaches it; a known ceiling that stays idle indicates nothing.
  • If no → the ceiling is inherited, stale, or negotiable. Name it, or stop paying for it.
  • If you can’t answer → unclear. Measure the ceiling, or read it from the documentation, before you size the node.

Case study: Horizontal scaling (shared-nothing partition)

Bound: Shared-nothing means no mutable state crosses an instance boundary: no shared memory, no shared transaction manager, no shared storage. A failure does not propagate through state — but the failed instance’s own slice goes dark.

The substrate knowledge gap it signals

No mutable state is shared between two instances, so any domain invariant that spans them has no substrate support: it must be paid for explicitly — a partition key, an idempotency key, a compensating step, or a distributed transaction with its own coordination cost. First question: is there state to split at all? A stateless tier needs no key. If there is state, the gap question is whether the partition key is one the domain can name, or one only the deployment can.

ImportantWhen the fact bounds the shape

An alignment holds when the coarse-grained failure domain contains the domain’s consistency unit: each ledger, tenant, or account lies wholly inside one failure domain. A failure then removes units whole instead of tearing one. Orders in different tenants may sit on two machines; orders on the same ledger may not. Alignment is contingent, and must be re-checked when the platform changes: failure domains nest.

WarningWhen the key does not force it

The key exists to fit the deployment: session stickiness, a hash of a user id, a round-robin. The domain has one consistency unit — a ledger, a seat map, an inventory count — and distribution moves that invariant into coordination code. Where that cost is not payable, the unit must stay on one node, and the split stops at the unit boundary. The load figure that justified the split may never have been measured on this system.

TipThe faithfulness test

Does the domain own a partition key that matches the platform’s failure domain — and was the load measured here?

  • If yes → the partition is admissible: splitting along it needs no coordination inside each unit. Whether to split is a separate question, answered by a measured load.
  • If no → the key was chosen to fit the deployment. Keep the consistency unit on one node, and stop the split at the unit boundary.
  • If you can’t answer → unclear. Name the key and count its cardinality before the split.

Case study: Connection ceiling (the pool is the allowance)

Bound: A connection pool is a local allowance. The engine’s maximum concurrent connections is a hard limit; a licence maximum is a contractual one. Both refuse the connection; only one can be lifted by a purchase.

The substrate knowledge gap it signals

The limit is documented, and the deployment often never consults it. Pool size often arrives by copy from an example. Threads per instance often outnumber connections. Timeouts stay unset, so a starved caller waits until a timeout nobody chose. The gap question is what the engine allows and which component may spend it. The engine’s maximum is a substrate bound; whether the domain names the pool count is a separate question. Instances × pool size is the first multiplication, and it costs one line. Reserved, administrative, and replication connections spend from the same allowance.

ImportantWhen the fact bounds the shape

The limit is documented, binding, and below peak demand. Then access to it must be arbitrated, and the arbitration is a choice: queue the surplus, shed it with a fast failure, or refuse admission upstream. The limit forces that a decision exists. It does not choose which.

WarningWhen the limit does not force it

The pool is an arbitrary knob that nobody traced to the engine. Or the limit is idle: a hundred allowed, five in use. That makes the pool non-binding today, not wrong — size it to the peak the system must survive, and name that peak. Or the pool is oversized and holds connections open that no caller uses; each still counts against the engine, so the component next door is denied capacity. An undersized pool is a different fault: callers queue for a connection the engine would have granted.

TipThe faithfulness test

Has anyone multiplied instances by pool size and compared it with the engine’s limit?

  • If yes → the product is known and compared. Above the limit, the defect is already live; below it, the pool still has to match measured concurrency.
  • If no → the pool asserts a bound nobody computed. Do the multiplication; the number is in the engine’s documentation.
  • If you can’t answer → unclear. Read the limit, then multiply. Both take a minute.

Case study: Latency budget (the p99 subtraction)

Bound: A latency budget is an allowance of time, stated end to end and divided among the hops that must fit inside it. The sum of per-hop p99s is the envelope the chain must fit inside — a conservative one, because the tails of different hops do not necessarily align.

The substrate knowledge gap it signals

The budget is a subtraction, not an average. Averages hide the tail, and the tail is what the unlucky caller experiences. Physics sets the floor: light travels at about 200,000 km/s in fibre, so a thousand kilometres of fibre path costs about five milliseconds one way, before any code runs. The gap question is who divided the budget, and what is left at the last hop. Hop speed alone does not answer it.

ImportantWhen the fact bounds the shape

An end-to-end obligation exists and is stated: a payment authorisation window, a control loop, the point where a person stops waiting. Per-hop p99s are measured on this system and their sum exceeds the budget. Then something must give: a hop is removed, batched, or made asynchronous. The arithmetic requires one of these. It does not choose, and the three cost differently — asynchrony shortens the chain and moves a synchronous obligation into the consistency contract.

WarningWhen the budget does not force it

The budget was invented by the team and never tied to an obligation. Averages stand in for tails. Each hop is fast enough on its own; the measured sum exceeds the budget. Or the per-hop figures were borrowed from a development machine with no network and no contention. The structure optimises a number that no obligation outside the team required — not a customer, not a contract, not a downstream service.

TipThe faithfulness test

Has anyone stated the end-to-end budget and summed the measured per-hop p99s?

  • If yes → the arithmetic holds with the margin stated, provided the tails do not amplify. Confirm it against the measured end-to-end p99, including the work after the last hop.
  • If no → the hops spend a budget nobody set. Name the obligation, or drop the claim.
  • If you can’t answer → unclear. State the deadline and subtract each measured p99 from it.

Case study: Availability arithmetic (the serial product)

Bound: Serial availability multiplies, and only when the failures are independent. A dependency that must succeed takes its own share of the remaining uptime.

The substrate knowledge gap it signals

The obligation is a contract number. The chain length is a design decision. The gap question is how many independent dependencies must succeed, and what their product is. Per-service reliability does not settle it. Five serial hops at 99.9% give 99.5%. To deliver 99.9% over five independent hops, each must clear 99.98%. The product is one line of arithmetic, and it is rarely done.

ImportantWhen the fact bounds the shape

A stated obligation exists — a contractual SLA, a safety function, a payment window — and the product across the synchronous chain falls below it. Then the chain is shortened, or part of it becomes independently available. The product is known, and the structure is answerable to it.

WarningWhen the product does not force it

A component’s figure is often quoted as if it were the system’s. Redundancy is counted without correlated failure: two nodes in one rack share a power feed and a switch; one region shares a control plane; one pipeline shares a defect. A shared cause can take both, so the pair’s availability is bounded by the shared resource, not by the product. They do not always fail together — price the pair against the shared resource, and keep the protection the second node still gives. Or the figure came from a vendor page and was never composed with the rest of the chain.

TipThe faithfulness test

Has anyone stated the obligation, multiplied the availability across the synchronous chain, and separated the correlated failures?

  • If yes → the chain is counted under independence, and the shared causes are priced. The next check is whether each figure was measured or merely quoted.
  • If no → the claim is unsupported. The product may fall below it, and a shared cause can put it further below.
  • If you can’t answer → unclear. Count the hops that must succeed, then multiply.

Case study: Durability contract (the domain and the substrate join)

Bound: A durability contract is the platform’s claim about what survives which failure — a process, a disk, a region — from the point the caller is told the write succeeded. The claim is a promise; what survives is measured. Retention is a separate promise.

The substrate knowledge gap it signals

Two knowledge sources meet here. The acceptable loss window is domain knowledge — a ledger, an audit obligation, a commanded action. The price of each step up is a substrate fact: fsync costs a write round trip; synchronous replication costs a network round trip, about a millisecond per hundred kilometres between the replicas; an append-only log costs storage growth. The gap question is whether anyone wrote the loss window down, and whether the contract covers the failures the domain faces. One source justifies half a structure.

ImportantWhen the fact bounds the shape

The domain states a loss window in seconds or events, and the platform’s claim is weaker for the failures that matter. Then the difference is paid for explicitly, and the design record names the price. A ledger that must lose no acknowledged write needs an acknowledgement after a durable write to replicas that cannot fail together, at a stated quorum. One replica does not cover a zone; no replication covers a bad migration.

WarningWhen the claim does not force it

The loss window was never stated, so the team bought the strongest contract everywhere and pays for it on data that could be rebuilt. Or the window is stated and the claim covers the failures the domain faces; only then is the extra mechanism ceremony. Or a recovery figure was quoted from a vendor page and never mapped to the domain’s own window. A contract must be read for the failures it excludes.

TipThe faithfulness test

Is the loss window written down, does the contract claim to cover the failures you face, and is the price stated?

  • If yes → the join is explicit on paper. The remaining step is to confirm the production configuration implements it, for each failure mode.
  • If no → one side of the join is missing. Write the window, or stop paying for the promise.
  • If you can’t answer → unclear. Write the loss window in seconds or events, then read the contract against it.

Case study: Ephemeral ports (the client’s own ceiling)

Bound: Every outbound connection takes a local port from an ephemeral range — the Linux default, 32768 to 60999, which is 28,232 ports. The port stays reserved for about a minute after the client closes the connection — the TCP TIME_WAIT hold, fixed by the kernel.

The substrate knowledge gap it signals

The client host carries its own bound: the ephemeral port range its stack draws from. It belongs to the client, so the server’s pool size does not raise it. The gap question is how many connections the client may hold to one destination address and port, and how fast it opens new ones. The arithmetic is the range divided by the hold time.

ImportantWhen the fact bounds the shape

The design opens a short-lived connection per request to one destination, and the rate approaches the bound. Then the port range is the binding constraint: 28,232 ports divided by a 60-second hold gives about 470 new connections a second. Connection reuse keeps the workload away from the bound; a larger pool does not.

WarningWhen the range does not force it

The client holds long-lived pooled connections, so the port count is never approached. Or the client opens connections to many distinct destinations, so the range applies separately to each, not once for the host. One load-balancer address on one port is one destination, so the range applies to it in full. Or the rate is far below the bound.

TipThe faithfulness test

Is the counted connection rate to one destination address and port inside the range divided by the hold time?

  • If yes → the rate is inside the bound; reuse is optional.
  • If no → the rate is at or above the bound. Reuse connections, or accept the ceiling.
  • If you can’t answer → unclear. Read /proc/sys/net/ipv4/ip_local_port_range and count the rate.

Case study: Retry amplification (the product across layers)

Bound: A retry policy multiplies. If each layer makes three attempts — one call plus two retries — the layers below see 3ⁿ attempts for one request, where n is the number of layers that retry.

The substrate knowledge gap it signals

The retry count is local; the amplification is global. The gap question is which layer owns the retry, and how many layers retry at all. Twenty-seven attempts is a product no single policy computes. The downstream capacity must absorb the product, and while the retries nest inside the caller’s deadline, that deadline divides by it.

ImportantWhen the fact bounds the shape

Every layer retries with its own three attempts, so the product reaches twenty-seven. A single downstream stall can produce a retry storm, and the retries spend the capacity the dependency needs to recover. One owner with a stated attempt budget closes it: the layers below fail fast, each layer’s deadline is shorter than its caller’s, and the capacity is sized to the product.

WarningWhen the product does not force it

The product is small — one layer retries, or none does, and the capacity absorbs the attempts. Then a retry budget is ceremony. Or one owner already bounds the attempts, so the multiplication adds no new constraint.

TipThe faithfulness test

Does the product of the retrying layers fit the downstream capacity?

  • If yes → one owner suffices, and the capacity is sized to the product.
  • If no → the attempts multiply past the capacity. Name the owner, and bound the product.
  • If you can’t answer → unclear. Count the retrying layers, then multiply.

Case study: Connection setup (the round trips before the payload)

Bound: A new connection pays for its setup before any request bytes move: one round trip — a message out and its reply back — for TCP, one more for a full TLS 1.3 handshake. At a round-trip time of 50 ms, that is 100 ms.

The substrate knowledge gap it signals

The setup cost is paid once per connection. It is paid per request exactly when the client opens a connection per request, which is why reuse, or a shorter round trip, is what removes it. The gap question is the round-trip time and the connections one request opens. DNS adds a round trip on the first lookup, and none after that if the answer is cached.

ImportantWhen the fact bounds the shape

The client opens a connection per request over a long link, and the round trips are a large share of the obligation. Then reuse, session resumption, or termination at the edge reduces the setup to one handshake, or to zero with 0-RTT. Reuse also keeps the client inside its port range, and it does not raise one connection’s throughput. The measurement is the round-trip time and the connection count.

WarningWhen the setup does not force it

Connections are already pooled, so setup happens once and the cost is amortised. Or the client and server sit in the same datacenter, where the round-trip time is under a millisecond and the setup is noise. Then keep-alive saves no latency. It still leaves an idle connection for a timeout to reap.

TipThe faithfulness test

Is the measured setup a large share of the end-to-end budget?

  • If yes → the setup is the dominant term. Reuse connections, resume the session, or terminate at the edge.
  • If no → the setup is noise, and keep-alive adds an idle connection for nothing.
  • If you can’t answer → unclear. Measure the round-trip time and count the connections per request.

Case study: Partition count (the ceiling on consumer parallelism)

Bound: A partition is the unit of both order and assignment. Within a consumer group, each partition is assigned to one consumer, so useful parallelism is bounded by the partition count.

The substrate knowledge gap it signals

The partition count is chosen when the topic — the named log — is created, and it can only rise. An increase remaps keys across partitions. The gap question is how much parallelism the throughput target needs, and whether the partition count supplies it. Twelve partitions cap a group at twelve working consumers; the thirteenth is idle, not faster. A skewed key can put the load on one partition while the group waits on it.

ImportantWhen the fact bounds the shape

The throughput target divides into a required consumer count above the partition count. Then the partitions must increase before the consumers do, and the key distribution must keep the load even. The order is fixed: derive the required consumer count, then compare it with the partition count.

WarningWhen the count does not force it

The partition count already exceeds the required parallelism, so extra consumers would idle. Or ordering requires one partition for the key space, so the ceiling is the price of the order. Then adding partitions buys idle consumers and costs a rebalance.

TipThe faithfulness test

Does the partition count cover the required consumer count?

  • If yes → the parallelism is covered. Check next that the key distribution keeps the load even.
  • If no → the consumers exceed the partitions. Raise the count, or accept the limit.
  • If you can’t answer → unclear. Compute the required consumers from the throughput target.

Case study: Restore time (the copy time is a floor)

Bound: Recovery time is at least the data size divided by the restore rate, and longer by every step after the copy. One hundred gigabytes at two hundred megabytes per second is five hundred seconds, about eight minutes.

The substrate knowledge gap it signals

The recovery target is an obligation in minutes. The restore rate is a measured property of the backup medium, the network, and the target. The gap question is the size, the rate, and the obligation. Eight minutes of copy is the floor; verification, replay, and the decision to restore add to it. A backup that has never been restored has an unknown rate.

ImportantWhen the fact bounds the shape

A recovery target exists and the division misses it. Then the design must change: a warm replica, a smaller restore unit, or continuous replication. The division sets the requirement; which mechanism meets it is a second decision.

WarningWhen the division does not force it

The restore has been timed and fits the target with margin. Then a warm replica pays for a risk the restore already covers. Or the recovery target is unknown, so no division can be compared with it.

TipThe faithfulness test

Is the measured end-to-end restore time inside the recovery target?

  • If yes → the division fits with margin. The copy is one step of the path; the backup stays the fallback until the whole path is timed.
  • If no → the division misses the target. Change the mechanism, or state the longer time.
  • If you can’t answer → unclear. Restore a copy and time it end to end.

Case study: Page write amplification (the engine’s page is the unit)

Bound: The storage engine reads and writes in pages — 4 KiB here, 8 KiB in PostgreSQL, 16 KiB in InnoDB. A random update to a few bytes still costs a whole page on write-back.

The substrate knowledge gap it signals

The page is the smallest unit the engine writes back. Below the page, the device has its own unit: a sector, and an erase block for flash. So the write path can multiply again. The gap question is the page size and the size of the update. Eight bytes into a four-kilobyte page is 512 times the changed bytes. The workload spends the device’s sustained write budget, not the application’s byte count.

ImportantWhen the fact bounds the shape

The workload is random small writes at a rate the device cannot absorb, and the amplification is measured. Then batching, an append-only layout, or a larger write unit follows. The arithmetic sets the requirement: changed bytes multiplied by the amplification.

WarningWhen the page does not force it

Writes are sequential or batched, so many updates share one page. Or the working set sits in memory and the page is written once. Or the device is far from its write budget, so the amplification is real and unbilled.

TipThe faithfulness test

Is the amplified write rate inside the device’s sustained write budget?

  • If yes → the amplified rate fits when measured. Record the headroom and treat the fit as a threshold to monitor.
  • If no → the workload spends more than the device allows. Batch the writes, or change the layout.
  • If you can’t answer → unclear. Divide the page size by the update size, then compare with the rate.

Case study: Receive window (the bandwidth-delay product)

Bound: A sender may have only the smaller of the congestion window and the receive window in flight. The receive window divided by the round-trip time is the ceiling this post prices: 64 KiB over 100 ms caps one connection at 5.24 Mbit/s.

The substrate knowledge gap it signals

One connection carries only what its window allows, whatever the link is rated at. The gap question is the window and the round trip. Without window scaling — the option that multiplies the 16-bit window field — the window is capped at about 64 KiB, so a long link is filled by many connections or not at all. The division is an upper bound: loss, and the congestion window (the sender’s estimate of what the network will accept), can hold the rate lower.

ImportantWhen the fact bounds the shape

The obligation needs more than one connection’s worth of throughput over a long round trip, and the window is not scaled. Then parallel connections, or a larger window, follow. Reuse removes the setup cost, and it cannot raise one connection’s throughput. The measurement is the achieved rate per connection against the window divided by the measured round trip.

WarningWhen the window does not force it

Window scaling is enabled, the receive buffer is large enough, and the window has grown to the product of bandwidth and delay, so one connection already fills the link. Or the round trip is short and the window never binds. Then adding connections adds overhead rather than throughput.

TipThe faithfulness test

Does the required rate per connection fit the window divided by the round-trip time?

  • If yes → one connection can carry it. Scale the window only if the rate must grow.
  • If no → one connection cannot carry it. Scale the window, or spread the load.
  • If you can’t answer → unclear. Read the window, measure the round trip, then divide.

Case study: Integer key width (the positive range of the type)

Bound: An identifier has a width. A signed 32-bit integer spans 4,294,967,296 values, and an identity column spends the positive half: 2,147,483,647 inserts, after which the next one fails.

The substrate knowledge gap it signals

The key width is chosen at schema time and is expensive to change later. The gap question is how many rows this table will ever hold, and whether the width covers it. The arithmetic is the usable range, 2³¹ − 1, not the current row count. A migration under load is one price of getting it wrong.

ImportantWhen the fact bounds the shape

The obligation implies a row count above the type’s positive range. Then use a wider key, a sequence with a larger type, or a generated identifier. The bound is the range, and the requirement is a count.

WarningWhen the range does not force it

The table is bounded by the domain — a fixed set of regions, currencies, or statuses — so the range is never approached. Or the projected count stays below the limit for the table’s life. Then widening the key buys nothing and can cost a rewrite of the table and its indexes.

TipThe faithfulness test

Does the projected row count stay below 2,147,483,647?

  • If yes → the range covers the obligation, and the schema stays.
  • If no → the projected count passes the limit. Widen the key before the migration becomes urgent.
  • If you can’t answer → unclear. Project the count, then compare it with 2,147,483,647.

Case study: Quorum (the majority is arithmetic)

Bound: A majority is ⌊n/2⌋ + 1. Five nodes need three; four need three; three need two. A membership view is each node’s current list of voting members; two nodes can disagree on it. Two disjoint groups cannot both hold a majority of the same member set.

The substrate knowledge gap it signals

The node count decides how many independent failures the system tolerates, and whether a network partition can split the write path. The gap question is the node count and the failure the deployment must survive. Two nodes lost to one hypervisor or one deploy are one failure, and 2f + 1 does not count it. A majority of four is also three, so the fourth node adds cost without adding tolerance.

ImportantWhen the fact bounds the shape

The obligation names a failure count. Tolerate f independent crash failures over a fixed voting set, and the cluster needs 2f + 1 voting members. Then the node count follows from the failure count, not from the budget.

WarningWhen the count does not force it

The count is even, so the extra node adds cost without adding tolerance. Or the deployment counts copies, not voting members, so two network partitions can each believe they are the writer — the count is cited and never applied. Or the write quorum is set below a majority, which permits two writers by design.

TipThe faithfulness test

Does the node count give a majority above the number of failures the system must survive at once?

  • If yes → the arithmetic holds for one membership view. Confirm that every member shares it, and that an old writer is fenced — cut off before the new one starts.
  • If no → the count does not cover the failure. Add voting members, or state the lower tolerance.
  • If you can’t answer → unclear. Start from the failure count, double it, and add one.

Case study: Thread stack (the concurrency model has a memory bill)

Bound: Each thread reserves a stack. Eight megabytes is the Linux default, read with ulimit -s. Ten thousand threads therefore reserve about eighty gigabytes of address space, whether or not they touch it.

The substrate knowledge gap it signals

The stack size is a setting, and the thread count is a design decision. Together they are a memory bill. The gap question is the stack size and the concurrency model. Reserved, committed, and resident are three measures of the same memory: the reservation spends address space (the virtual range, not RAM), the commit charge is what a cgroup limit counts, and only resident pages consume RAM.

ImportantWhen the fact bounds the shape

The address space or the memory budget is finite, and the product exceeds one of them. Then a smaller stack, a fixed thread pool, or an event loop follows. The arithmetic is a multiplication, and it is done before the first thread starts.

WarningWhen the reservation does not force it

The host is 64-bit with address space to spare, and the touched stack pages are the real cost. Then the multiplication overstates the address-space bill, and the thread count binds on scheduling and kernel memory instead. Or the pool is fixed and small, and the stack size never matters.

TipThe faithfulness test

Does the reserved stack memory fit the address space and the memory budget?

  • If yes → the product is known. Compare it with both budgets before you commit to the model.
  • If no → the reservation exceeds one budget. Shrink the stack, bound the pool, or change the model.
  • If you can’t answer → unclear. Multiply the stack size by the maximum thread count.

Case study: DNS TTL (the staleness bound)

Bound: A DNS answer carries a time to live. A caching resolver may serve the old answer until that time expires. A 300-second TTL therefore bounds a conforming resolver’s staleness at five minutes.

The substrate knowledge gap it signals

The TTL is a promise about how fast a change propagates. The gap question is the TTL and the failover time the system promises. The staleness window is the remaining lifetime on each cached copy, not the TTL on the record just changed. A client that caches past the TTL extends the window.

ImportantWhen the fact bounds the shape

The failover obligation is shorter than the TTL, and the clients re-resolve inside it. Then the TTL must fall, and a lower TTL costs more queries. The trade is arithmetic: propagation time against query volume.

WarningWhen the TTL does not force it

The TTL is short and the obligation is long, so the record’s life is not the bound. Or clients cache past the TTL, so the TTL is a hope rather than a limit. Then the propagation time is unknown, and the plan must not depend on DNS alone.

Is the TTL inside the time a change may take?

  • If yes → the TTL fits. Confirm the clients re-resolve inside it, and keep one path that does not depend on DNS.

Bound: A broker accepts messages up to a stated size. Amazon SQS accepts 1,048,576 bytes of encoded message, which is 1 MiB. Above that size the broker rejects the message; the application stores the payload and sends a reference.

Case study: File descriptors (the per-process limit)

Bound: Every open socket, file, and pipe consumes one descriptor, and so does every other handle the kernel returns. The soft limit caps how many a process may hold; the next open fails with EMFILE.

The substrate knowledge gap it signals

The soft limit is per process; the kernel’s file-max is per host, and it fails with ENFILE. Each is read from its own file. The gap question is the soft limit and the descriptors one unit of work holds. A connection-per-request design spends a descriptor for the life of each connection, and a leak spends it forever. ImportantWhen the fact bounds the shape

The product approaches the soft limit under load, and the limit is the binding constraint. Then pool, close the handles, or raise the limit. The pool is bounded and small, the files are few, and the product sits far below the limit. Then the descriptor count is not the bound, and raising the limit can hide a leak rather than fix it.

TipThe faithfulness test

Does the descriptor product fit the soft limit under peak load?

  • If yes → the product fits. Record the peak count and watch the gap to the limit.
  • If no → the product exceeds the limit. Bound the pool, close the handles, or raise the hard and soft limits.

Bound: An inode is the record the filesystem keeps for one file. A filesystem with fixed inodes allocates one per file, directory, and symbolic link; a hard link adds a name and no inode. When the table is full, creating a file fails with ENOSPC (no space left on device) even though bytes remain.

Case study: Heartbeat detection (the detection bound)

Bound: A cluster notices a dead member by missing its heartbeat. Detection takes up to one interval plus the death timeout (the wait after the last beat before the member is declared dead) — two intervals when the timeout is one interval. With k tolerated missed beats, the bound is k + 1 intervals.

The substrate knowledge gap it signals

The detection time is a design parameter, and it trades against false positives. The gap question is how long a dead node may hold its role, and how many beats fit in that time. A 30-second interval allows up to 60 seconds of a dead node, which may be longer than the lock it holds or the client timeout above it.

ImportantWhen the fact bounds the shape

The tolerance is shorter than the detection bound, so the interval must fall. Then the setting follows the tolerance: interval ≤ (tolerance − failover time) ÷ (k + 1). A shorter interval costs more traffic, and more false positives on a slow network.

WarningWhen the interval does not force it

Detection comes from the client’s connection failing, not from a heartbeat, so the interval does not bound the window. Or the tolerance is long, and the interval sits well inside it.

TipThe faithfulness test

Does one interval plus the death timeout fit inside the time a dead node may hold its role?

  • If yes → detection fits the tolerance. Failover adds election and promotion on top, so check those too.
  • If no → the interval is too long for the tolerance. Divide the interval by k + 1, or change how detection works.
  • If you can’t answer → unclear. Subtract the timeout and the promotion time, then divide what remains by k + 1.

Case study: Retransmission timeout (the floor under a lost tail)

Bound: When a segment is lost and nothing later recovers it, the sender waits for a retransmission timeout. The kernel clamps that timeout at a minimum — 200 ms on Linux. Fast retransmit — resending as soon as later packets reveal the gap — recovers many other losses in a round trip or two.

The substrate knowledge gap it signals

The timeout is not the round trip. The gap question is the measured loss rate and the tail budget (the latency allowed for the slowest requests). At one percent packet loss, a request of k packets meets a loss about 1 − 0.99^k of the time — 9.6% at ten packets. So the tail is set by the loss and by the packets per request.

ImportantWhen the fact bounds the shape

The path loses packets, and the tail budget is below the timeout. Then retransmission cost enters the budget, and the design must remove the loss or tolerate the timeout. Fewer round trips and fewer packets reduce the exposure.

WarningWhen the timeout does not force it

The path is clean and the loss rate is near zero, so the timeout is never paid. Or the protocol runs over a transport with its own recovery, and this floor does not apply. Then the floor is real and idle.

TipThe faithfulness test

Is the tail cost of one loss inside the tail budget?

  • If yes → the loss cost fits the budget. The floor is real and unused.
  • If no → the loss sets the tail. Remove the loss, or widen the budget.
  • If you can’t answer → unclear. Measure the loss rate and the packets per request, then compute 1 − (1 − p)^k and multiply by the timeout.

Case study: Little’s law (the concurrency product)

Bound: In a stable system, the average number of items in it equals the arrival rate times the average time each spends there. At 1,000 requests a second and 100 ms end to end, 1,000 × 0.1 = 100 requests are in flight on average — a mean, not a count you will read at any moment.

The substrate knowledge gap it signals

Two measurements multiply into the pool size: the arrival rate and the time in the system, taken together. The pool size, the queue depth, the connection count, and the thread count are all this one product, applied once per dependency. Below it the requests queue and latency grows; above it the workers idle. A pool chosen by feel is a guess at this product.

ImportantWhen the fact bounds the shape

The required concurrency exceeds the pool, and the pool is what queues. Then size the pool from the product, and sum it across the dependencies the request waits on in series; the peak hour, not the mean day, is the input.

WarningWhen the product does not force it

The time in the system is short, so the product is small and any sane pool covers it. Or nothing on this side holds the work — a fire-and-forget send, a response streamed without buffering — so there is no pool for the product to size.

TipThe faithfulness test

Does the concurrency limit cover the arrival rate times the time in the system, at the peak hour?

  • If yes → the product does not rule the pool out. Watch the time in the system, which moves with the load.
  • If no → the requests queue by construction. Raise the limit, or cut the time in the system.
  • If you can’t answer → unclear. Measure the peak arrival rate, then the end-to-end time at that rate.

Case study: Queue wait (the headroom is the latency)

Bound: For one server with random arrivals and a random service time — the M/M/1 model — the mean wait in the queue is the service time times ρ ÷ (1 − ρ), where ρ is utilisation. At 0.8 that is 4 service times, at 0.9 it is 9, and at 0.95 it is 19. A scheduled arrival, or a second server, changes the curve.

The substrate knowledge gap it signals

Utilisation and waiting time are not two independent numbers; one divides into the other. The curve is not linear; it is a division by the headroom. A design sized at 90 percent runs ten times slower than an idle one, and a capacity report calls that healthy.

ImportantWhen the fact bounds the shape

The latency obligation is tight and the design runs near saturation. The arithmetic sets the headroom; which remedy to take is a second decision.

WarningWhen the queue does not force it

The load sits far below saturation, so the wait is a small multiple of the service time. Or the arrivals are scheduled — a nightly batch — rather than random, so no queue forms by luck. Then the formula overstates the wait, and headroom is not the constraint.

TipThe faithfulness test

Does the utilisation the design runs at keep the mean wait inside the latency obligation?

  • If yes → the wait fits at that utilisation. Check the peak, which sits above the mean.

  • If you can’t answer → unclear. Measure the service time, then the utilisation at peak.

A response’s exposure is a packet count, and the count is decided by the payload’s size. The tail — the slowest responses, not the average — is set by that count, so a response four times larger is four times more exposed. Shrinking a response is a latency remedy, not only a bandwidth one.

ImportantWhen the fact bounds the shape

The response is large and the tail budget is tight on a lossy path. Then shrink the response, or split it into pages so one loss costs one page.

WarningWhen the count does not force it

The path is clean, so no packet is lost at any size. Or the loss is recovered well inside the budget, and something else sets the tail. Then the count never shows up.

TipThe faithfulness test

Does a response of this packet count, at the measured loss rate, keep its recovery inside the tail budget?

  • If yes → the count fits the budget at that loss rate. Recheck after the response grows.
  • If no → the response’s size sets the tail. Shrink it, or split it.
  • If you can’t answer → unclear. Measure the response size and the loss rate on the real path.

Case study: Clock skew (the ordering bound)

Bound: NTP holds hosts within a few milliseconds on a good network, and a quartz oscillator drifts up to about 100 parts per million — 8.64 seconds a day if nothing corrects it. The skew between two hosts is the sum of both errors, and it moves with the network.

The substrate knowledge gap it signals

An event stamped on one host and compared on another carries the skew between them, and the skew is measured, not assumed. It is not symmetric either: a stamp from the slower clock dates its event earlier than the event happened.

ImportantWhen the fact bounds the shape

The ordering obligation is finer than the measured skew. Then use a logical clock — a counter, not a time — a single writer, or a sequence from one store; the skew is then out of the argument.

WarningWhen the skew does not force it

The obligation is coarser than the skew, so a millisecond of disagreement does not matter. Or one host stamps every event, and nothing crosses clocks. Then no ordering decision depends on the skew.

TipThe faithfulness test

Is the ordering obligation coarser than the measured skew between the hosts that stamp the events?

  • If yes → the stamps order the events. Record the skew, and watch it under load.
  • If no → two events can be ordered backwards. Move the order to one clock.
  • If you can’t answer → unclear. Measure the offset between the hosts that stamp.

Case study: Time column width (the last instant it holds)

Bound: A 32-bit signed integer counts 2,147,483,647 seconds from 1 January 1970, which ends on 19 January 2038 at 03:14:07 UTC. A column of that width cannot hold a later instant: a database rejects the write, and a 32-bit counter in application code wraps, which sends the date backwards.

The substrate knowledge gap it signals

A column holds instants up to a computable last one, and the domain’s furthest date is a requirement, not a guess. An expiry, a schedule, or a lease dated past 2038 does not fit. The width is set in the first migration, and changing it later is a migration under load.

ImportantWhen the fact bounds the shape

The domain stores an instant past 2038. Then widen the column now, while the table is small and the migration is a background job.

WarningWhen the width does not force it

The column holds a duration rather than an instant, so it never approaches the range. Or the domain has no date past 2038 — a fixed historical archive. Then nothing in the table reaches the edge.

TipThe faithfulness test

Does the column’s width represent the latest instant the domain must store?

  • If yes → the column holds the range. Record the latest instant it must represent.
  • If no → the write fails, or wraps, at a date you can compute. Widen it.
  • If you can’t answer → unclear. Find the largest instant in the domain, then compare it with the type’s range.

Case study: Certificate lifetime (the renewal window)

Bound: Public certificate authorities may issue a TLS certificate valid for at most 200 days, and the ceiling falls to 100 in March 2027 and to 47 in March 2029. Many issue for 90 already. Renewal must complete before expiry, on a schedule no longer than the certificate’s life.

The substrate knowledge gap it signals

Two clocks run against each other: the certificate’s life, and the time a renewal takes from decision to deployment. That time includes an approval, a change window, and a rollback. A life of 90 days and a renewal that takes a quarter is an outage with a date on it.

ImportantWhen the fact bounds the shape

The renewal path includes a manual step and the life is 90 days. Then automate the renewal and exercise the automatic path — an unexercised automation is a manual process with extra steps.

WarningWhen the lifetime does not force it

Renewal is automated and has been exercised, so the life does not bound the schedule. Or the certificate is internal, with a life long enough to cover the process.

TipThe faithfulness test

Does the automated renewal complete before expiry, with margin for one failed attempt?

  • If yes → the schedule fits the life. Exercise the failure path as well as the happy one.
  • If no → an expiry is scheduled, not possible. Automate the renewal, or shorten the process.
  • If you can’t answer → unclear. Read the certificate’s dates, then time one renewal end to end.

Case study: Bit error rate (one error per 125 TB)

Bound: The unrecoverable bit error rate is the chance that a read cannot be recovered: the drive reports a failure rather than returning a wrong bit. At 10⁻¹⁵, one failure falls in 10¹⁵ bits, which is 125 TB. A 100 TB restore reads 8 × 10¹⁴ bits, and if the failures arrive independently it meets at least one 1 − e^−0.8 ≈ 55 percent of the time.

The substrate knowledge gap it signals

The volume read in one operation is what meets the rate; the rate alone says nothing. A restore reads the whole set at once, so the rate applies to all of it. The rated figure is the failure the drive detects and reports, so the byte is gone, not wrong: a checksum names the block that failed, and only a second copy read on its own returns the byte.

ImportantWhen the fact bounds the shape

The operation reads more than the rate allows, and the data carries no checksum. Then add end-to-end checksums, verify the stored data on a schedule, and keep a second copy that is read on its own; the operation’s volume is the quantity that decides the risk.

WarningWhen the rate does not force it

The volume read in one operation is small, so the chance of meeting a failure is small. Or a second copy is served on the failed read, so one failure costs a retry and not the restore.

TipThe faithfulness test

Does the volume read in one restore stay inside the bytes one error falls in?

  • If yes → the restore is unlikely to meet an error. Keep the checksums, which catch the rest.
  • If no → the restore expects an error. Verify with a checksum, and keep a second copy.
  • If you can’t answer → unclear. Read the drive’s rate, then the bytes one restore reads.

Case study: Queue depth (in flight divided by service time)

Bound: A device can serve many requests at once; a loop that waits for each serves one. A device with a queue depth of 32 and an unloaded service time of 200 microseconds completes at most 32 ÷ 0.0002 = 160,000 requests a second, and it keeps that rate only if the service time holds at that depth. At a depth of one it completes 5,000.

The substrate knowledge gap it signals

What the device offers is parallelism; what the code allows is a count of outstanding requests, and the two are set in different places. A loop that waits for each request caps the rate at one divided by the service time, whatever the hardware can do. The depth lives in the application, not on the drive.

ImportantWhen the fact bounds the shape

The obligation needs more than one request’s worth, and the code waits for each to finish. Then issue concurrently, up to the device’s depth, and measure the service time at that depth; an unloaded measurement flatters the device.

WarningWhen the depth does not force it

The device’s service time is long and its parallelism small — a spinning disk, where depth adds queueing and no throughput. Or the code already issues concurrently, so the depth is spent.

TipThe faithfulness test

Does the in-flight request count, divided by the service time, cover the rate the obligation needs?

  • If yes → the depth covers the rate. Measure the service time at that depth, not in isolation.
  • If no → the loop is the limit, not the device. Issue concurrently, up to the depth.
  • If you can’t answer → unclear. Count the outstanding requests in the code, then time one at the device.

Case study: Failure domains (nodes are not denominators)

Bound: Nodes that share a switch, a power feed, or a hypervisor share a failure: when that component goes, all of them go. A rack of 20 nodes on one top-of-rack switch presents one failure domain, and its availability is that switch’s, not twenty nodes’.

The substrate knowledge gap it signals

The unit that matters is the independent failure domain, and a node is not one. Counting nodes counts one switch failure twenty times, and a deploy that touches every node is a single failure with no arithmetic at all. That one appears in no availability model.

ImportantWhen the fact bounds the shape

The obligation names a failure count, and the deployment has fewer independent domains. Then spread the nodes across domains, or state the lower tolerance; the deploy’s blast radius belongs in the same count.

WarningWhen the domains do not force it

The nodes share nothing that can fail together — separate power, separate switches, staged deploys — so a failure takes one domain. Then the node count is the domain count, and the multiplication is honest.

TipThe faithfulness test

Does the number of independent failure domains cover the failure count the obligation names?

  • If yes → the domains cover the failure. Confirm that no deploy touches two domains at once.
  • If no → one event takes more than the obligation allows. Spread the nodes, or state it.
  • If you can’t answer → unclear. List what each node shares with its neighbours.

Case study: MTU (frame size, and the payload behind it)

Bound: The MTU is the largest packet one link carries: 1,500 bytes here. Take away the IP and TCP headers, 40 bytes, and one connection may send 1,460 bytes of payload — the maximum segment size. A tunnel adds its own header first, so VXLAN leaves 1,410 and IPsec about 1,400. A packet above the path’s MTU is dropped rather than split whenever fragmentation is disallowed — always on IPv6, and on TCP over IPv4.

The substrate knowledge gap it signals

The MTU that matters is the smallest one on the path, and it is measured at the far end, not at the host. When the router’s “fragmentation needed” message is filtered, the drop is silent, so the connection stalls rather than fails.

ImportantWhen the fact bounds the shape

The path’s MTU is below the sender’s and that message is filtered. Then set the MSS explicitly, clamp it at the tunnel, or keep messages under the smallest MTU; the tunnel’s header is the part you can size, and the path’s MTU is not.

WarningWhen the MTU does not force it

The path is uniform and the message arrives, so the sender learns the limit. Or every message is smaller than the smallest MTU on the path.

TipThe faithfulness test

Is the largest message the design sends below the smallest MTU on the path?

  • If yes → the messages fit every hop. Recheck when an overlay is added.
  • If no → a hop drops the packet and the message may not arrive. Clamp the MSS, or send less.
  • If you can’t answer → unclear. Probe the path’s MTU end to end, then read the overlay’s overhead.

Case study: Zone boundary (the cost of crossing it)

Bound: Round trips inside one availability zone — a separate datacenter with its own power and network — take about 0.25 ms. Across zones in one region they take one to two. A request making 20 sequential round trips spends 5 ms inside a zone and 30 ms across.

The substrate knowledge gap it signals

A deployment diagram shows where the services run, not where the data crosses. Each sequential call pays the boundary once; parallel calls pay it once for the batch. The crossing is a property of the data flow, not of the drawing.

ImportantWhen the fact bounds the shape

The request makes many sequential round trips and they cross a zone boundary. Then batch the calls, or co-locate the data with the work; the round-trip count is what batching changes.

WarningWhen the boundary does not force it

The calls are few, or they run in parallel, or the boundary is crossed once. Then the zone is a small share of the budget, and the service time is what to measure.

TipThe faithfulness test

Does the number of sequential round trips, times the boundary’s cost, fit the latency obligation?

  • If yes → the boundary fits. Count the round trips again after the next refactor.
  • If no → the topology, not the code, sets the latency. Co-locate, or batch.
  • If you can’t answer → unclear. Trace one request, count its sequential calls, note where each lands.

Case study: Route convergence (the failover it sets)

Bound: A routing change spreads as each router learns the new path and passes it to its neighbours; worldwide, the common case is 30 to 180 seconds and the tail runs to fifteen minutes or more. Anycast — one address announced from several sites — moves the flows with the route, so a moved flow loses its connection state.

The substrate knowledge gap it signals

The failover the obligation allows is compared against a propagation time that runs on routers, not on your schedule. The route is withdrawn only after a health check fails, so the health check adds to it. The client’s resolver and its connection reuse add again.

ImportantWhen the fact bounds the shape

The obligation is shorter than convergence. Then put the switch above routing: a load balancer, a health-checked endpoint, an application-level redirect — a layer that answers before the routers agree.

WarningWhen convergence does not force it

The failover is regional and the obligation is measured in minutes. Or the clients reconnect and the lost state is acceptable. Then routing is fast enough, and a second mechanism above it is cost without benefit.

TipThe faithfulness test

Does the routing convergence time, plus the health check, fit inside the failover time the obligation allows?

  • If yes → routing can carry the failover. Check the client’s reconnect time on top.
  • If no → the route is slower than the promise. Move the switch above routing.
  • If you can’t answer → unclear. Time a route withdrawal, then add the health check.

Case study: Socket distance (the share that crosses)

Bound: A core reaches memory attached to its own CPU socket in about 80 nanoseconds, and memory on the other socket in about 130 to 140. A working set spread across both pays the remote price on the accesses that cross.

The substrate knowledge gap it signals

The cost is decided by the share of accesses that cross, not by the average latency of memory. The share is a property of the allocator and the thread placement, so it is measured, not assumed. Binding a thread does nothing for memory the thread does not own.

ImportantWhen the fact bounds the shape

The workload is latency-bound and its working set spans sockets. Then shard by socket, allocate on the socket that reads, and bind the threads; the share of crossing accesses is the number the change moves.

WarningWhen the distance does not force it

The workload is throughput-bound and memory bandwidth is the limit, so using both sockets helps. Or the allocator already keeps each thread’s data local, so few accesses cross.

TipThe faithfulness test

Does the share of accesses that cross a socket, times the difference between the remote and the local latency, fit the per-access budget?

  • If yes → the placement fits. Measure the share again after the data grows.
  • If no → the topology of the memory sets the latency. Shard by socket, or bind.
  • If you can’t answer → unclear. Measure the remote share, then the local and remote latencies.

Case study: Timestamp resolution (the events per tick)

Bound: A timestamp resolves to one tick. At a peak of 10,000 events a second and a millisecond column, 10 events land on each value on average, and the busier milliseconds hold more — so the column cannot order them and cannot break the tie.

The substrate knowledge gap it signals

Ordering needs a resolution finer than the event rate, and the column has one tick to give. Resolution is a property of the type, and the event rate is a measurement. A sort on the timestamp leaves the tie in storage order, which is not the order they happened.

ImportantWhen the fact bounds the shape

The obligation needs a total order and the events per tick exceed one. Then add a sequence number, widen the resolution, or take the order from the source; the tie is decided in storage, so the fix belongs there.

WarningWhen the resolution does not force it

The event rate is far below one per tick, so ties are rare and any tie is harmless. Or the order comes from a sequence the store assigns, and the timestamp is metadata.

TipThe faithfulness test

Do fewer than one event per tick arrive at the peak event rate?

  • If yes → the timestamp orders them. Confirm the peak, not the mean.
  • If no → ties are certain at peak. Add a sequence, or widen the resolution.
  • If you can’t answer → unclear. Measure the peak event rate, then read the column’s precision.
