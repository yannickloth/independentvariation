Architecture Problems as Knowledge-Gap Indicators

A series of short posts that read architecture questions — boundaries, communication, failure, scale, and data — as knowledge-gap indicators.

An architecture question usually arrives with a safe generic answer: microservices scale, queues decouple, a cache makes it fast. Each post below takes one such question, states the generic answer, and asks which fact of this system decides it.

Pick a post on the left. It opens on the right.

A boundary records what the domain decided belongs together; packaging records what deploys apart. Each post keeps the two questions apart, because different facts answer them.

A distributed call makes a promise about time: when the answer exists, whether a step may happen twice, what may arrive out of order. Each post asks which promise the domain already made.

Every dependency can fail, and every failure has a detection cost. Each post asks what must survive, how fast the failure must be seen, and what a stale answer is worth.

A scaling move is a prediction about load. Each post asks which measured curve justifies it, and what consistency the move spends.

The store and the schema encode what must stay true. Each post asks which invariant the domain owns, and which one the mechanism only appears to guarantee.

Monolith, Modular Monolith, or Microservices

Question: “How do you decide between a monolith, a modular monolith, and microservices for a new system?”

The question hides two independent decisions.

  1. Where the boundaries go — what belongs together.
  2. Whether the pieces deploy independently — monolith versus microservices.

A modular monolith and a microservices system can have identical boundaries. They differ only in redeployment: “microservices” answers the deployment question, not the boundary question.

The architecture knowledge gap it signals

Decision 1: the boundaries — three principles, not three answers

Three principles can govern where boundaries go: - IVP: group elements that change together; separate those that change apart. - Cohesion: group elements that are functionally related. - Coupling: place boundaries to minimise dependencies across them.

They are not independent. When cost is dominated by maintenance — the common case — all three converge on nearly the same partition: keep together what changes together, separate what changes apart. Three vocabularies, one structure; that is why the boundary question feels like a single question.

They diverge only when another cost dominates: performance, distribution, security. Then coupling and cohesion stop meaning change locality, and the principles disagree — marking where a non-maintenance cost governs the design.

Decision 2: redeployment independence — the domain also decides Deployment separation buys three things: independent release cadence, independent scaling, independent failure isolation. Each is a domain fact, not a default. Two modules need separate deployment only when the domain makes one of them true: - Cadence: they change at different rates and must ship separately. - Scaling: one faces different load and must grow on its own. - Isolation: one must survive, or be contained, when the other fails.

If the domain requires none of these, microservices buys an independence nobody asked for — and pays a network, a consistency window, and a failure mode for it.

ImportantThe domain mandates it

Boundaries follow the change structure; the three principles agree. Deployment is split only where cadence, scaling, or isolation differ.

WarningThe domain doesn’t

Boundaries cut across things that change together — or services are split for “scale” while the domain forces lockstep releases. The topology asserts an independence the domain never granted.

TipThe faithfulness test

Two questions, kept apart:

  • What belongs together? → the domain’s change structure answers it; name the document that records it.

  • Must these deploy apart? → cadence, scaling, and isolation answer it; name the rate, the load figure, or the failure requirement that forces it.

  • If no document answers the first → stop: the boundary is unwritten, and the diagram is choosing it. If no number or requirement answers the second → stop: the independence is unrequested, and the topology is choosing it.

Start with the domain, then choose the packaging. The architecture is underneath; the topology is downstream.

Shared Database or API

Question: “Should these two services share a database, or integrate through an API?”

The claim is who owns a row’s meaning. A shared table has no contract: changing what a field means needs no DDL, so nothing announces it. An API publishes a named contract; one side answers for it.

Both are defensible. Whether the meanings can diverge is a domain fact; who answers is a choice.

The architecture knowledge gap it signals

A shared table enforces shape and declared constraints, not each side’s private reading. Redefine a field’s meaning and the other side’s reading is wrong until it follows. An API names the meaning, at a price: a round trip, a failure mode, versioning.

The gap question, on a redefinition not an addition: must both sides change together, or can one change alone? Disjoint schemas are not table-sharing; the test is about rows.

“It is only a read” does not avoid the claim. A reader still depends on the fields it reads. A named contract makes the telling someone’s job; a table leaves it to whoever notices.

ImportantWhen the domain mandates it

One transaction boundary: one invariant spans two capabilities, stock on hand and the stock ledger agreeing at every commit. Two writers on one table still commit twice; both writes must land in one serialisable transaction, or the second aborts and retries. Across two databases only two-phase commit, or one store under one owner, keeps that; a saga trades it for compensation.

API: no invariant binds the two at every commit. Billing issues an invoice; a report reads it a day later. The lag is the domain’s call; the contract still needs versioning.

WarningWhen it’s a guess dressed as engineering

One guess: a shared table chosen for a faster join. A join is a performance fact; a cross-table constraint is an invariant, and belongs above. If performance is the reason, name the query, measure it, materialise or cache it, then read it through a published view: no writes back, a contract to version, a lag. A view inherits redefinitions too; publishing announces, never protects.

An API spans two halves of one invariant, because services must not share databases. The invariant becomes a saga, a failure mode nobody asked for, unless the domain accepts drift.

TipThe faithfulness test

❓ Can the two readings differ on one row? Must both change together, or can one alone?

  • If both must change together → one meaning owner and a coordinated release; add one transaction boundary only where the row must also agree at every commit.
  • If one can change alone → a published contract: an API if the other side writes, a view if it only reads and can absorb a rename.
  • If one ships and the other is silently wrong in meaning → the boundary is worse than useless; stop and produce the shared-meaning record before either side ships.
  • If you can’t answer → stop. The artifact to produce is the row-meaning record: which side owns the meaning of each column, and who signs when it changes. Until it is on file, nobody wrote the meaning down, and the boundary between the two is the code’s guess.

Principle of Least Surprises

Question: “How do you apply the Principle of Least Surprises when designing components?”

Least surprise is usually taught as consistency: don’t be clever, don’t hide side effects. The domain-knowledge reading is stronger. Surprise is what the caller could not predict because the component answered a domain question the caller did not know was being answered.

The architecture knowledge gap it signals

A component surprises when its behavior encodes domain knowledge the caller cannot see — a default, an ordering, a rounding, an implicit rule. Every default is a silent claim: “this is the normal case.” Every surprising side effect is a domain decision the interface failed to name.

Least surprise is therefore not a style preference. It is a completeness check on whether the domain knowledge is visible where it is used.

ImportantThe domain mandates clarity

The domain rule exists and the interface names it. The caller can predict the outcome because the rule is in the vocabulary. A payment method that rejects amounts below one cent is not surprising — the minimum is a stated business rule.

WarningThe domain doesn’t

The rule hides in an implementation default: the “sensible” timezone, the “usual” tax rate, the “standard” retry. The caller is surprised because an unstated domain decision fired. The fix is not less surprise in the code; it is naming the domain fact the code already assumes.

TipThe faithfulness test

Can a caller who knows the domain, but not this implementation, predict the behavior?

  • If the default, the ordering, and the rounding each cite a written rule → the knowledge is visible, and the caller can predict the outcome.
  • If a default exists with no rule behind it → a domain decision is buried; surface it, then cite the rule.
  • If you can’t answer → stop. The artifact to produce is the list of defaults this component applies, each with the written rule that sets it. A default with no rule behind it is the surprise.

Accidental Complexity at Scale

Question: “How do you avoid accidental complexity when scaling a system?”

The usual answer is a checklist: cache, shard, queue, replicate, split. That checklist is where accidental complexity is born. The domain-knowledge lens separates the complexity the problem forces from the complexity a technology choice adds.

The architecture knowledge gap it signals

Scale itself is not a requirement until the domain names it. “Handle more traffic” is not a domain fact; “the month-end close must finish before the regulator’s deadline” is. Distribution, caching, and sharding each add a coupling — consistency windows, failure modes, partition keys. Those couplings are justified only when a domain property requires them.

Complexity added ahead of the domain reason is accidental by definition.

ImportantThe domain mandates it

A real forcing condition exists: data must survive an availability zone, a workload must finish inside a legal window, two regions must stay live for latency the customers contracted for. Then the added machinery encodes a known requirement, and you can name the domain fact each piece serves.

WarningThe domain doesn’t

You cannot name the domain fact any component serves; the architecture exists “to be scalable” for load nobody measured or promised. Now every added piece is a coupling with no mandate — the accidental complexity the question warned about, introduced by the very attempt to avoid it.

TipThe faithfulness test

For each scaling mechanism, name the requirement it serves and the document, contract, or measurement that states it.

  • If every component maps to a stated requirement → the complexity is essential and justified.
  • If a component maps to none → remove it; you added the accident.
  • If you can’t answer → stop. The artifact to produce is the capacity figure or the service-level obligation, with its owner named. A mechanism that serves no written requirement is accidental complexity by definition.

Synchronous or Asynchronous

Question: “How do you choose between synchronous and asynchronous communication?”

The decision is usually framed as a performance and resilience trade-off. The domain-knowledge lens reframes it: sync versus async is a statement about time — and a measured limit can revise that statement.

The architecture knowledge gap it signals

Synchronous says: the caller needs the answer now, as part of this activity. Asynchronous says: the caller can continue before the answer exists, and the answer will be handled later. Both are claims about what the business expects — whether a step is part of the current act or a separate future act. The transport (HTTP, message, stream) merely encodes that expectation.

ImportantThe domain mandates it
  • Synchronous: the customer is waiting to see the seat confirmed before payment; the answer must exist before the activity can continue.
  • Asynchronous: a shipment is arranged after the order is accepted. The order does not need the courier’s answer to be an order. The domain treats the step as a later act with its own life.

A second source: processing time

Sometimes the caller wants the answer now, but the computation cannot finish inside any tolerable window. Processing time rules out the synchronous form. A test reveals this. Once measured, the limit revises the temporal expectation itself: the step is now known to be a later act. The domain knowledge switches to async in intent — it is no longer a sync step the machine fails to serve. The revision is scoped to the tested platform, hardware, OS, and configuration; change the environment, and the fact must be re-established.

WarningThe domain doesn’t

Choosing async for throughput, or sync for “simplicity,” while the domain expects the opposite. A customer told “order placed” over an async pipeline that later fails has been promised something the flow could not deliver. A synchronous chain for a step the business treats as separate couples the two activities and makes a failure in one look like a failure in both.

TipThe faithfulness test

Two questions:

  • Does the current activity need the answer, or is the answer a separate later act?
  • If it needs the answer, can the machine deliver it inside the tolerable window?

Answer the first from the process document that states which steps are inseparable. Answer the second from a measured latency for that call path, recorded with its platform and configuration. If either answer is missing → stop: write the expectation down before the interaction type is chosen, because until then the technology default is deciding. If the measurement rules out the synchronous form, the intent becomes async — record the figure that forced it.

Idempotent Operations

Question: “How do you design idempotent operations for systems with retries?”

The standard answer is a dedup key and a seen-set. The domain-knowledge lens shows that the hard part is not the mechanism. It is deciding what “the same operation” means — and only the domain can.

The architecture knowledge gap it signals

Retries are a transport concern. Duplicates are a domain possibility with domain meaning. Idempotency is the rule “doing this again with the same identity is a no-op.” The identity is the domain’s: the order number, the trade reference, the invoice id.

If the dedup key is a message UUID, the system catches transport retries but misses the real duplicate: the customer who clicked twice, the two batches carrying the same instruction.

ImportantThe domain mandates it

The domain already defines when two things are the same act, and repeating it changes nothing: paying invoice 7 twice pays it once. The idempotency key is that identity, and the handler enforces the domain’s own rule. This removes the dependence on at-most-once delivery the domain never should have trusted.

WarningThe domain doesn’t

The key is technical and the domain identity is absent. Duplicate orders, double bookings, and double charges slip through under different message ids. The system is idempotent for the infrastructure’s duplicates, not the domain’s.

TipThe faithfulness test

Would the domain use this key to decide “this was already done”?

  • If the key appears in a written rule or record that names the act → idempotent at the right level.
  • If the key is generated by the transport and names no act → you deduplicate the transport and miss the domain duplicate.
  • If you can’t answer → stop. The artifact to produce is the identity rule, naming which field makes two requests one act. Until that rule is on file, the key is a message id.

Race Conditions

Question: “How would you prevent race conditions in a high-throughput workflow?”

The reflex is locks, transactions, and actors. The domain-knowledge lens asks first: is the contention a fact about the world, or an artifact of how we built it?

The architecture knowledge gap it signals

A race condition matters only when two conflicting operations touch something the domain says cannot be shared inconsistently. Sometimes that is real: one seat, one parking spot, ten license seats, one account balance. The constraint — “only N at once,” “only one owner” — is domain knowledge. Other times the “contention” is an implementation accident: two workers updating the same cache row or the same counter that exists only for bookkeeping.

ImportantThe domain mandates protection

The domain names the scarce resource and its rule: “a seat belongs to one booking.” Then the lock or the atomic transition encodes a real invariant, and the throughput question becomes “how do we respect the constraint quickly,” not “how do we avoid locks.”

WarningThe domain doesn’t

The contended object has no domain meaning — it is a technical counter, a shared cache, a statistics row. Locking it serializes the whole workflow to protect a fact nobody in the business needs protected. The throughput loss is real; the invariant it defends is not.

TipThe faithfulness test

Is the contended thing a domain-scarce resource with a stated rule?

  • If a written rule names the resource and its limit — one seat, one owner, ten licences → protect the invariant.
  • If the contended object appears in no domain document → remove the shared state or confine it; you are racing to protect a fiction.
  • If you can’t answer → stop. The artifact to produce is the scarcity rule with its owner named. A lock that defends no such rule serialises the workflow for nothing.

#RaceConditions #Concurrency #Locks #DomainKnowledge #SoftwareArchitecture #HighThroughput

Queues, Streams, or Direct Calls

Question: “How do you decide when to use queues, streams, or direct calls?”

The comparison usually weighs latency, durability, and ordering. The domain-knowledge lens reduces it to one question: does the domain treat this as one activity, or as a fact others will care about?

The architecture knowledge gap it signals

  • A direct call says: this is part of one activity; I need the answer to continue.
  • A queue says: do this later, once; the work is addressed to a consumer.
  • A stream says: this happened; anyone who cares may observe it, possibly many times, possibly replaying.

Choosing the mechanism encodes a claim about who cares, how many, and when — all domain facts.

ImportantThe domain mandates it

A direct call when the step is inseparable from the caller’s activity. A queue when the domain has a piece of deferred work with one owner (“send this statement”). A stream when the domain has events others legitimately need and history matters (“a payment cleared,” seen by billing, fraud, and reporting).

WarningThe domain doesn’t

A queue for something with many real consumers, losing the later ones. A stream for what is really a command one consumer must execute. A direct call for a step the domain treats as a separate later act, coupling both lives. The mechanism asserts semantics the domain never assigned.

TipThe faithfulness test

Who cares that the fact happened, how many, and may they replay?

The answer sorts the three, and it has a home. Name the document or the owner that settles who subscribes, how many times each subscriber performs the work, and whether a subscriber may replay history. If no such document exists → stop: write the domain’s event and command structure, with its owner named, before choosing between the queue, the stream, and the call. Until that document is on file, the tool decides.

Sagas for Long-Running Workflows

Question: “What’s the role of sagas in long-running workflows?”

A saga sequences local steps and, on failure, compensates the completed ones. The domain-knowledge lens: a saga is legitimate only when the domain itself knows how to undo each step.

The architecture knowledge gap it signals

Compensation is not a technical rollback. It is a domain act — cancel a booking, refund a charge, restock a shipment. The domain must already perform these reversals in the real world. If it does, the saga is the domain’s own “how we undo this” rules made executable, and it correctly refuses to pretend a cross-boundary process is atomic.

ImportantThe domain mandates it

The process spans boundaries that cannot be one transaction, and each completed step has a real, named reversal. Then a saga is the code catching up to knowledge the business already holds. This is the pattern’s whole justification: the domain knows how to reverse each act.

WarningThe domain doesn’t

The “compensation” is a data cleanup only engineers understand, or the steps are atomic within one boundary. The saga then invents undo actions the business never named. It asserts per-step reversibility nobody decided.

TipThe faithfulness test

Does the domain perform these reversals — a cancellation, a refund, a restock — or would the “compensation” be a cleanup only engineers understand?

  • If a written procedure names each reversal and its owner → applicable; compensations are the domain’s own reverse acts.
  • If no procedure names them → inapplicable; name the reversals before the saga, or keep one transaction.
  • If you can’t answer → stop. The artifact to produce is the reversal table: each step, the act that undoes it, and the owner of that act. Until it is on file, the saga invents undo actions the business never named.

Exactly-Once Processing

Question: “How do you design for exactly-once or effectively-once processing guarantees?”

Exactly-once delivery across a network is a myth. Effectively-once is achievable — but only if the domain defines “once.” The domain-knowledge lens: the guarantee lives in the domain identity, not the transport.

The architecture knowledge gap it signals

“Exactly-once” means: the effect happens once even if the message arrives many times. To know it happened once, you must know what “it” is — a domain identity. Effectively-once is idempotent handling keyed by that identity, plus durable state. Without the domain identity, you can suppress transport duplicates but not semantic ones.

ImportantThe domain mandates it

The domain defines the operative identity and treats repeats as the same act (“invoice 7 may be paid once”). Then exactly-once is a domain rule enforced by an identity and a recorded outcome. The guarantee is real because the identity is real.

WarningThe domain doesn’t

The key is a transport id, and two genuine domain duplicates carry different ids. The system claims exactly-once while double-processing the very cases the business fears.

TipThe faithfulness test

Does the domain say when two messages describe one act?

  • If a written identity rule names the operative field → effectively-once is achievable on that identity.
  • If the key is the message id and no rule names the act → you have exactly-once for retries and none for reality.
  • If you can’t answer → stop. The artifact to produce is the operative-identity rule, naming the field two genuine duplicates share. Until it is on file, the guarantee covers the transport only.

#ExactlyOnce #Idempotency #Messaging #DomainKnowledge #DistributedSystems #SoftwareArchitecture #EIP

Partial Failures

Question: “How do you handle partial failures in distributed systems?”

Retries, timeouts, compensations, let-it-fail — the menu is technical. But “what should happen when this step fails midway?” is a business question: legal deadlines, SLA promises, manual fallbacks, who gets notified.

The architecture knowledge gap it signals

A partial failure is not just a technical state. It is often a domain state with a name: “order accepted but not confirmed,” “payment captured but not settled.” The domain decides whether that intermediate state is allowed, how long it may persist, and who resolves it. The failure-handling strategy should encode those decisions.

ImportantThe domain mandates it

The domain names the partial state and its remedy: escalate to a human after N hours, refund automatically, hold the order for a promised window. Then retries, timeouts, and compensations carry real meaning — each is a domain rule for a named intermediate state.

WarningThe domain doesn’t

The failure handling is generic: infinite retry, silent drop, a log line. No one asked what the business wants to happen when step three of five fails. The technical default decides the outcome, and the domain consequence surfaces as a customer complaint.

TipThe faithfulness test

Does the domain name the intermediate state after a partial failure, and what must happen in it?

  • If a written rule names the state and its remedy → the strategy encodes knowledge.
  • If no rule names the state → you have left a business outcome to a retry policy.
  • If you can’t answer → stop. The artifact to produce is the state list with its remedies: for each step that can fail midway, the named state, its deadline, and who resolves it. Until it is on file, the technical default decides.

#PartialFailure #Resilience #DistributedSystems #DomainKnowledge #ErrorHandling #SoftwareArchitecture #SLA

Consistency Across Services

Question: “What patterns help maintain consistency across multiple services?”

Eventual consistency, sagas, outbox, two-phase commit — the patterns are tools. The domain-knowledge lens: consistency is not a global setting. It is a per-fact claim about which things must agree at once, and the domain owns that claim.

The architecture knowledge gap it signals

“Consistent” is meaningless without the unit. The domain decides what counts as one indivisible fact: an order and its line items must agree always; an order and its analytics record may lag. Cross-service consistency is a set of domain-drawn transaction boundaries, expressed across process seams. The pattern should follow the boundary, never define it.

ImportantThe domain mandates it

Two facts are one unit in the domain and must change together: money debits and credits, a booking and its seat. Then the pattern — a saga, a single transaction, an outbox — preserves a real invariant.

WarningThe domain doesn’t

Two facts are independent in the domain but bolted together by a pattern “for safety,” or two parts of one unit are split and reconciled “for scale.” The first adds coordination the domain never needed; the second risks violating an invariant the domain always had.

TipThe faithfulness test

Which facts must agree at the same instant, in the domain’s own terms?

That defines the boundary. Pick the pattern to honor it, and cite the invariant that states it. If no written invariant says which facts agree → stop: the unit of consistency is unwritten, and the framework is deciding. Until that invariant is on file, the boundary is the framework’s.

Resilience to Dependency Failure

Question: “How do you design a resilient system that survives external dependency failures?”

Circuits, bulkheads, retries — but resilience is not a property you bolt on. It is a set of decisions about what to do when a dependency dies, and those decisions are domain ones.

The architecture knowledge gap it signals

When an external system fails, the domain must say what is acceptable: keep serving from a cached or alternate source, degrade a feature, queue and reconcile later, or fail loudly. Each is a business stance. A circuit breaker is only the mechanism; the fallback is the knowledge.

ImportantThe domain mandates it

The domain names the fallback: use the secondary supplier, take payments offline and key them in later, show the last-known price. Then the resilience pattern encodes a real business rule, and the failure has a designed, lawful outcome.

WarningThe domain doesn’t

The fallback is an engineering guess — serve stale data, return a default, silently drop. No one asked whether the business permits it. The system “survives” the outage by doing something the domain never sanctioned.

TipThe faithfulness test

Does the domain name what must happen when this dependency fails?

  • If a written fallback rule covers this dependency → the mechanism encodes knowledge.
  • If no rule covers it → resilience is cosmetic; the outage still decides the outcome.
  • If you can’t answer → stop. The artifact to produce is the fallback rule with its owner named: what is served, what is degraded, and what is refused. Until it is on file, the engineering guess is the fallback.

Detecting and Isolating Slow Services

Question: “What’s your approach to detecting and isolating slow services?”

Dashboards, timeouts, bulkheads. But “slow” is relative to a promise. The domain-knowledge lens: a service is slow only against a deadline the domain cares about, and isolation serves that deadline.

The architecture knowledge gap it signals

Latency is not a domain fact by itself; a promised response time is. “Checkout must answer in 2 seconds” or “the nightly settlement must finish by 6 a.m.” is domain knowledge. Timeouts and bulkheads should encode those promises, not arbitrary constants.

ImportantThe domain mandates it

A stated deadline exists — an SLA, a legal window, a customer expectation. Then the timeout is that promise, and isolating the slow dependency protects the paths that carry promises. The threshold is defended by a named commitment.

WarningThe domain doesn’t

The timeout is a round number pulled from a template; nothing breaks differently at 1s versus 3s in domain terms. Then calls are cut off arbitrarily, and “isolation” protects no promise — it protects a guess.

TipThe faithfulness test

Which domain promise does this timeout defend?

  • If a written obligation states the deadline → the threshold encodes knowledge.
  • If no obligation states it → you have invented a deadline.
  • If you can’t answer → stop. The artifact to produce is the service-level obligation, or the legal or contractual deadline, with its value and owner. Until it is on file, the number is a guess that cuts calls off.

#Latency #Timeouts #Bulkhead #SLA #DomainKnowledge #SoftwareArchitecture #Observability

Caching Layers

Question: “How do you design caching layers (L1/L2) to avoid stale data and thundering herds?”

TTLs, jitter, single-flight — but the first question is not “how long” in technical terms. It is “how stale may this answer be?” — and that is a domain freshness tolerance.

The architecture knowledge gap it signals

A cache is a bet that a slightly old answer is acceptable. The size of “slightly” is domain knowledge: account balances may be seconds fresh; a product description may be hours stale; a tax rate changes once a year and is not stale for months. L1 versus L2, TTL, and invalidation all encode that tolerance. Thundering herds are technical, but they exist because the tolerance was set and the refresh synchronized.

ImportantThe domain mandates it

The domain states a freshness tolerance per fact. Then each layer’s TTL is that tolerance, and invalidation is triggered by the domain event that makes the value wrong.

WarningThe domain doesn’t

A uniform TTL from a default, unrelated to what any fact tolerates. Some data serves stale and violates a promise; other data is refreshed needlessly, wasting capacity. The cache asserts a freshness policy the domain never set.

TipThe faithfulness test

What staleness does the domain permit for this value, and which event invalidates it?

  • If a written tolerance and a named invalidation event cover this value → the TTL encodes knowledge.
  • If neither exists → the number is a guess.
  • If you can’t answer → stop. The artifact to produce is the freshness tolerance with its owner: for this value, the permitted age and the event that makes it wrong. Until it is on file, the cache asserts a policy the domain never set.

#Caching #CacheInvalidation #ThunderingHerd #DomainKnowledge #SoftwareArchitecture #Performance

Vertical or Horizontal Scaling

Question: “What are the signals that a system needs vertical scaling vs horizontal scaling?”

CPU graphs and cost curves are the usual signals. The domain-knowledge lens: the real signal is whether the domain allows the workload to be split, and whether growth is in a shared resource or independent ones.

The architecture knowledge gap it signals

Horizontal scaling assumes the work can be partitioned and the state replicated without breaking a domain invariant. Vertical scaling assumes it cannot — one big node is the honest shape. Which is true depends on the domain: can two orders be handled by two machines with no shared invariant? Can one ledger be?

ImportantThe domain mandates it

If the domain’s units of work and state partition cleanly, horizontal scaling matches reality. If the domain has a genuinely single, centralized thing — one account sequence, one authoritative counter — vertical scaling respects that.

WarningThe domain doesn’t

Horizontal “scaling” applied to something with a global invariant, forcing distributed coordination to preserve what one machine held naturally. Or vertical scaling of something trivially partitionable, paying ever-larger machine prices for no domain reason.

TipThe faithfulness test

Can the domain’s work and state be split without breaking an invariant?

  • If the partitioning rule is on file and no invariant crosses the split → horizontal.
  • If a written invariant must stay whole → vertical, or re-architect the invariant.
  • If you can’t answer → stop. The artifact to produce is the domain’s decomposition: which units partition cleanly and which invariant forbids it. Until it is on file, the topology is a machine-price guess.

Read-Heavy Workloads

Question: “How do you design read-heavy workloads for maximum throughput?”

Replicas, caches, denormalization, CQRS. But “maximum throughput” is the trap. Throughput is bounded by what the readers are allowed to see. Freshness tolerance, not horsepower, sets the ceiling.

The architecture knowledge gap it signals

Reads are cheap to scale only if they may be served from a copy. Whether they may — and how stale the copy may be — is domain knowledge. A price shown to browsing users may lag; a price shown at checkout may not. CQRS and read replicas are domain claims that reads are separable from writes and tolerate a delay.

ImportantThe domain mandates it

The domain distinguishes reads that tolerate staleness from reads that do not. Then replicas and read models serve the tolerant ones, and the strict ones read the source of truth. Throughput rises along the line the domain drew.

WarningThe domain doesn’t

Every read is pushed behind a replica or cache “for throughput,” including the ones that must be current. The system is fast and wrong at the moment it matters — the final stock check, the balance at withdrawal.

TipThe faithfulness test

Which reads must reflect the latest write, and which may lag?

  • If a written tolerance says which reads may lag → scale those, and cite it.
  • If no tolerance covers the split → you are trading correctness for speed blindly.
  • If you can’t answer → stop. The artifact to produce is the per-read freshness tolerance, with its owner. Until it is on file, every read is pushed behind a copy on the same guess.

Database Load Without Losing Consistency

Question: “What patterns help reduce database load without harming consistency?”

The question already concedes the constraint — consistency — but which consistency? The domain-knowledge lens: “harm” is domain-specific, and the patterns only work once you know which invariant is load-bearing.

The architecture knowledge gap it signals

Denormalization, caching, materialized views, and read models all reduce load by keeping a second copy. They are safe exactly when the copy may lag for the domain’s purposes. The load reduction is real; whether it “harms consistency” depends on whether the lagged fact is one the domain requires to be current.

ImportantThe domain mandates it

A fact is read-tolerant in the domain — reporting, browsing, search — even though it is written strictly. Then a read model or cache absorbs the load without touching any invariant.

WarningThe domain doesn’t

A lookup that participates in an invariant is served from a lagging copy: the overdraft check reads a five-second-old balance. Load fell; the invariant silently broke. Nobody asked which reads were allowed to lag.

TipThe faithfulness test

For each offloaded read, does the domain require the value to be current when read?

  • If a written tolerance covers the read → offload it.
  • If an invariant consumes the value → keep it on the source.
  • If you can’t answer → stop. The artifact to produce is the read-to-invariant map: which reads feed an invariant, and which tolerate lag. An unmapped read is still on the guess.

Hot Partitions

Question: “How do you approach hot partition problems?”

The obvious move is to salt the key or spread the load. The domain-knowledge lens: a hot partition usually means the domain funnels many operations through one entity — and that entity often exists for a reason.

The architecture knowledge gap it signals

A partition key is an identity choice: what makes a thing the same thing. A hot key says “most activity touches this one identity” — the current account, the flagship customer, the singleton counter, the day’s date. The heat is a domain fact before it is a scaling problem. Salt it and you may break the very grouping the domain needs.

ImportantThe domain mandates spreading

The heat is accidental — a skewed key format or a monotonically increasing id. Then re-keying to a domain-meaningful distribution removes the hotspot without touching meaning.

WarningThe domain doesn’t

The hot key is a real, single domain entity — one ledger, one tenant, one sequence. Salting splits it and forces coordination to restore the invariant. The scale technique fights the domain.

TipThe faithfulness test

Is the hot key a real, singular domain entity or an implementation artifact?

  • If the key names an entity in the domain documents → redesign the invariant, or accept the scaling limit honestly.
  • If no document names it → re-key; the heat is accidental.
  • If you can’t answer → stop. The artifact to produce is the key-to-entity record: what the partition key names, and whether the business has that thing. Until it is on record, salting may break the grouping the domain needs.

High-Volume Writes

Question: “How do you handle high-volume write workloads?”

Batching, async writes, log-structured storage, sharding. The domain-knowledge lens: write volume is manageable only after you know whether the domain needs the history, the current state, or both.

The architecture knowledge gap it signals

High-volume writes stress the current-state store. If the domain is event-shaped — it needs to know what happened and when — an append-only log is the honest fit and absorbs volume naturally. If the domain cares only about the present value, in-place updates suffice. Choosing between them is a domain claim about history.

ImportantThe domain mandates it

The domain needs the sequence of facts: audit, replay, temporal queries, dispute resolution. Then event-sourced or append-only storage serves a real requirement while scaling writes.

WarningThe domain doesn’t

The domain only ever asks for the latest value, yet a log is piled on “for safety.” Storage grows without a consumer of the history; the machinery serves no domain question.

TipThe faithfulness test

Does the domain ever need to ask what happened, not just what is?

  • If a written requirement names a question about history → append the facts.
  • If no requirement names one → keep current state and scale it.
  • If you can’t answer → stop. The artifact to produce is the history requirement: the questions the business must be able to answer about past events, and for how long. Until it is on file, the log serves no one.

Relational or Document Store

Question: “How do you pick between relational vs document database?”

The comparison lists schema flexibility versus joins. The domain-knowledge lens: both really ask “is this one fact or several?” — and that is an aggregate boundary question.

The architecture knowledge gap it signals

A document database suits data the domain treats as one thing, fetched and changed together — an order with its lines. A relational database suits data whose parts are independent facts that must be queried across — customers, orders, products. The storage model should mirror the domain’s own unit of consistency and retrieval.

ImportantThe domain mandates it

The domain has self-contained aggregates read as a whole and rarely joined. Then documents fit: one read, one write, one invariant. The domain has independent entities joined in many ways. Then relations fit.

WarningThe domain doesn’t

Documents chosen for “flexibility” over data the domain requires to be consistent across kinds. Or tables over data the domain always handles as one unit, forcing artificial joins to reassemble a fact the domain never split.

TipThe faithfulness test

Is the data one fact the domain reads together, or several the domain joins?

Match the store to that, and cite the rule that fixes the aggregate boundary. If no written rule fixes it → stop: the aggregate boundary is undecided, and the database is choosing it.

Distributed Transactions or Eventual Consistency

Question: “When would you use distributed transactions vs eventual consistency?”

This is the cleanest domain question in the list. Both patterns answer “what must be true at the same time?” — and only the domain knows.

The architecture knowledge gap it signals

A distributed transaction asserts: these changes are one indivisible fact across systems. Eventual consistency asserts: these changes are separate facts that will converge. The choice is a domain claim about whether the parts are one unit.

ImportantThe domain mandates one unit

The domain treats the changes as inseparable: a debit and its credit, a stock decrement and its reservation. Then a transaction — or a saga with real reversals — preserves the invariant. Eventual consistency would admit a state the domain forbids.

WarningThe domain doesn’t

The changes are genuinely separate: an order and its search index, a profile and its recommendations. Then eventual consistency is honest — and forcing a distributed transaction buys coordination for two facts the domain never tied together. The coordination cost is the fee for a boundary that does not exist.

TipThe faithfulness test

Are these changes one fact or several, in the domain’s own terms?

  • If a written invariant ties them into one fact → atomicity is required.
  • If the documents name them as separate facts → converge.
  • If you can’t answer → stop. The artifact to produce is the invariant that states which changes are one unit. Until it is on file, the unit of consistency is unwritten, and that is the gap, not the choice.

Audit-Friendly Systems

Question: “How do you design an audit-friendly system without killing performance?”

Audit is usually framed as overhead. The domain-knowledge lens: who must be able to answer who-changed-what is a domain — often legal — fact, and what it requires dictates both design and cost.

The architecture knowledge gap it signals

“We must be able to prove who changed what” is regulatory, contractual, or safety knowledge. It decides whether you keep an immutable log, for how long, whether history is queryable, and whether current state may be derived from it. The performance tension appears only once those requirements are known — and sometimes disappears, because the audit store is what makes the system fast.

ImportantThe domain mandates it

A real obligation exists — a regulator, a contract, a safety case. Then an append-only history is not overhead but a requirement, and event sourcing may serve both audit and performance at once.

WarningThe domain doesn’t

“Audit” is copied in as a generic nicety, with no rule about what must be reconstructable and for how long. The system pays for history nobody is obliged to consult, or logs too little for a rule that does exist.

TipThe faithfulness test

Is there a named obligation to reconstruct who changed what, and for how long?

  • If a regulation, contract, or safety case states it → the requirement defines the design.
  • If no obligation names it → trim it.
  • If you can’t answer → stop. The artifact to produce is the retention obligation with its duration and its source. Until it is on file, the system pays for history nobody is obliged to consult.

Schema Evolution Without Downtime

Question: “What’s your strategy for schema evolution without downtime?”

Expand-contract, dual writes, versioned APIs. The domain-knowledge lens: backward compatibility is about your consumers, and who they are — and how fast they can move — is domain knowledge.

The architecture knowledge gap it signals

A schema is a shared vocabulary. Changing it disrupts whoever reads and writes it. Whether that disruption is acceptable depends on the domain: who the consumers are (other teams, old app versions, external partners), whether old and new must coexist, and for how long. Expand-contract is only the mechanical shape; the policy is the domain’s release reality.

ImportantThe domain mandates it

The domain identifies slow-moving or external consumers and a period during which both old and new must work. Then expand-contract, versioning, and dual reads encode a real compatibility window.

WarningThe domain doesn’t

An “evolving schema” with consumers unknown or ignored. A migration runs in one step, and a consumer that could not move in time breaks. The absence of policy was itself a decision, made by not deciding.

TipThe faithfulness test

Who must keep working during the change, and for how long?

  • If a consumer list and a compatibility window are on file → the migration encodes it.
  • If no list and no window exist → you have assumed consumer agility you never verified.
  • If you can’t answer → stop. The artifact to produce is the consumer inventory with each consumer’s migration window. Until it is on file, the one-step migration risks a consumer that could not move in time.
