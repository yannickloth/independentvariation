Encoding Limits as Knowledge-Gap Indicators

A series of short posts that read data representation — widths, units, and byte encodings — as knowledge-gap indicators.

Every structure below rests on a width. A bit count, a unit, a scale, a factor. Each post states the limit, gives its value, and asks whether the structure follows from it.

The substrate list asks what the machine allows. This list asks a narrower question, and a more permanent one: what does the type hold? A width is chosen once, with the schema, and it outlives the hardware it was chosen on.

Three things decide. The width must be named — a field in the protocol, a column in the schema, a factor in the codec. The value must be the one this system stores, not the one the documentation suggests. And an obligation must exist that the value breaches: the type measures, the obligation rules out.

A width can still fail to bind. It is borrowed from another system, idle against the values actually stored, or enforced by a constraint that already holds it. Each post names the case where the limit does force the shape, and the case where it does not.

For the same reading of design patterns over domain knowledge, see the Software Patterns list. For the bounds the machine imposes, see the substrate list.

Pick a post on the left. It opens on the right.

Numeric bounds answer how much a type can hold, and how exactly it holds it. The width is chosen with the schema; the values arrive later.

Text bounds answer how many bytes one character takes, and which characters are the same character. The encoding is a fact about the format, not about the language.

Identifier bounds answer how many things a field can name. Each is a field width, and the width sits in the protocol, not in the application.

Wire bounds answer how many bytes the encoding adds before the payload is read. The overhead is paid on every message, and it is counted on the encoded form.

Case study: Double precision (the significand is 53 bits)

A double cannot represent 0.10 at all, so money held as a fraction drifts from the first operation. Held as integer cents it is exact — until 2⁵³, which is 90 trillion dollars of them.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: An IEEE 754 double carries a 53-bit significand — about 15 to 17 decimal digits — and it stores binary fractions. One tenth has no exact binary form, so 0.1 + 0.2 differs from 0.3, and past 2⁵³ consecutive integers are no longer all representable.

The encoding knowledge gap it signals

The precision the domain needs and the range of its values are two questions, and one type answers both badly. The first failure is representational and immediate: a value written with a tenth in it has no exact binary form, so it is already wrong at the moment it is stored. The second is arithmetical and far off: integer cents stay exact until the count passes 2⁵³, which is 90 trillion dollars of them.

ImportantWhen the precision bounds the shape

The domain compares or sums money, and the representation is binary floating point. Then store integer cents, or use a decimal type that carries its own scale — the comparison is then exact by construction.

WarningWhen the precision does not force it

The values are measurements, and 15 digits far exceed what the instrument resolves. Rounding at the display is then honest, and the representation costs nothing.

TipThe faithfulness test

Does the representation hold every value the domain must compare exactly?

  • If yes → the arithmetic is exact. Record the range, and recheck it.
  • If no → two values that differ compare equal, or a sum drifts. Move to integer cents.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Take the largest value and the smallest step, then test both.

Case study: Float32 precision (24 bits, about 7 digits)

A 32-bit float holds 24 bits of significand. Add 1.0 to 16,777,216 and you get 16,777,216 back. The addition is not lost to a bug; the type has no room for it.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A single-precision float carries a 24-bit significand, which is about 7 decimal digits. Between 2²³ and 2²⁴ the neighbours sit 1 apart, so every integer in that range is exact. From 2²⁴ up they sit 2 apart, so 1.0 added to 16,777,216 leaves it where it was, and the next value above it is 16,777,218.

The encoding knowledge gap it signals

What the domain must resolve is a step, and one step is all the type gives at the top of its range. Start a counter at 16,777,216 and add one a million times: it never moves, and the total is short by a million. The loss is silent, and the result still looks like a number.

ImportantWhen the precision bounds the shape

The domain sums many small values into a large total, and the type is single precision. Then accumulate in a wider type, or keep the parts and sum them at the end — the order of addition changes the answer.

WarningWhen the precision does not force it

The values are measurements whose own precision is coarser than 7 digits, so the type is finer than the instrument. Or the totals stay far below 2²⁴.

TipThe faithfulness test

Is the smallest step the domain resolves representable at the largest value it reaches?

  • If yes → the type resolves the domain. Test the largest value, not a small one.
  • If no → small additions vanish in the total. Widen the accumulator.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Take the largest total and the smallest increment, then add one.

Case study: Counter width (the time to the top of the range)

A signed 32-bit counter incremented a thousand times a second reaches the top of its range in 24.9 days. The column is a counter, the traffic is steady, and nothing in the schema says so.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A signed 32-bit integer reaches 2,147,483,647. At 1,000 increments a second, that is 2,147,483,647 ÷ 1,000 ÷ 86,400 = 24.9 days. What happens at the top depends on the engine: PostgreSQL and strict-mode MySQL reject the write, permissive MySQL clamps at the maximum, and a 32-bit counter in application code wraps to a negative value. Only the clamp and the wrap are silent.

The encoding knowledge gap it signals

The increments per second and the width are set in different places and at different times. The width is fixed in a migration; the rate is whatever production turns out to send. A counter that wraps or clamps corrupts a total, a balance, or a sequence, and it does so on a date you can compute in advance.

ImportantWhen the width bounds the shape

The rate and the lifetime together exceed the range. Then widen the column now, or reset the counter on a documented period — and record the date the current width buys.

WarningWhen the width does not force it

The counter is bounded by the domain — a fixed set of retries, a page index — so it never approaches the range. Or the rate is far below one a second, and the range is centuries away.

TipThe faithfulness test

Does the increment rate times the counter’s lifetime stay below the type’s range?

  • If yes → the counter holds its life. Recheck when the rate grows.
  • If no → the counter stops or wraps on a computable date. Widen it, or reset it.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Measure the increments per second, then state the lifetime.

Case study: Decimal scale (digits before the point)

DECIMAL(10,2) holds eight digits before the point. A price column declared that way overflows above 99,999,999.99, and the declaration looks generous.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A DECIMAL(p,s) type holds p total digits, s of them after the point. DECIMAL(10,2) therefore holds 8 before it, and its largest value is 99,999,999.99. The scale is not decoration; it spends range.

The encoding knowledge gap it signals

The value the domain stores has a ceiling, and the type sets it before the first row exists. A currency with a large unit, a total accumulated across records, or an inflation-adjusted figure moves that ceiling. Widening it later rewrites the table.

ImportantWhen the scale bounds the shape

The largest value approaches the digits before the point. Then widen the precision and keep the scale the currency needs; the room you have is p − s, not p.

WarningWhen the scale does not force it

The domain bounds the value — a rating, a percentage, a tax rate — so the ceiling is never approached. Or the type is already wider than the currency’s largest unit.

TipThe faithfulness test

Does the largest value the domain stores fit the digits the type leaves before the point?

  • If yes → the column holds the range. Recheck when a total is added to it.
  • If no → the write fails, or rounds. Widen the precision.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Take the largest value, then subtract 2 from the precision.

Case study: UTF-16 units (one glyph, two units)

A limit of 255 characters holds 255 emoji in one store and 127 in a runtime that counts UTF-16 units. The unit is not the character.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: UTF-16 encodes a code point above U+FFFF as two 16-bit units, a surrogate pair. A length function that counts units reports 2 for one emoji, so a limit of 255 units holds 127 of them.

The encoding knowledge gap it signals

A limit counts a unit, and the domain stores characters; above U+FFFF, the top of the basic plane, the two stop agreeing. A limit inherited from a column may count bytes, units, or code points, and all three give different answers there. The validation passes, and the index or the column fails downstream.

ImportantWhen the encoding bounds the shape

The limit counts UTF-16 units and the data holds characters above the basic plane. Then count code points, or size the limit at two units per character — 255 units hold 127.

WarningWhen the unit does not force it

The data is confined to the basic plane by a constraint, so one unit is one character. Then the limit is exact, and the constraint is what holds it.

TipThe faithfulness test

Does the limit count the same unit the domain’s data is measured in?

  • If yes → the limit matches the data. Confirm the constraint holds it.
  • If no → the count and the limit disagree above the basic plane. Convert to code points.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Find the widest character the domain stores, then read the limit’s unit.

Case study: Encoding width (3 bytes against 4)

A four-byte character does not fit a three-byte encoding. In MySQL, utf8 stores three bytes and utf8mb4 stores four — and a 767-byte index key, the older row format’s ceiling, divides by 4 to 191 characters.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A character set fixes the most bytes one character may take. MySQL’s utf8 stops at 3, which covers only the first 65,536 characters; utf8mb4 takes 4. The index key has a byte ceiling too: 767 bytes under the older row format, so 767 ÷ 4 = 191 characters once the column is utf8mb4. The newer row format allows 3,072 bytes, which is 768.

The encoding knowledge gap it signals

A column has a byte ceiling from its encoding and a second from its index, and neither is measured in characters. An emoji is four bytes, so a utf8 column rejects it or truncates it. The index ceiling is the second bound, in bytes, on the same column.

ImportantWhen the encoding bounds the shape

The data holds characters outside the first 65,536 and the column is a 3-byte set. Then convert the column and its indexes to the 4-byte set, and size the index prefix to the row format’s key ceiling, which is a separate ceiling from the character set.

WarningWhen the encoding does not force it

The data is basic-plane by constraint, so 3 bytes cover every character. Or the index carries a prefix that already fits the key ceiling.

TipThe faithfulness test

Does the widest character the domain stores fit the bytes the column’s encoding allows?

  • If yes → the column holds the data. Check the index key limit, which is separate.
  • If no → the write fails or truncates. Widen the encoding, then the index prefix.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Find the widest stored character, then read the column’s set.

Case study: Escaping (one byte becomes two)

Half a million quotation marks become a megabyte of JSON. The payload doubled, and nothing in the source data changed.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A JSON string escapes the quote and the backslash with a backslash, and control characters as a six-byte sequence. A field of 500,000 quotation marks therefore encodes to 1,000,000 bytes before any structure is added.

The encoding knowledge gap it signals

What the ceiling counts is the parsed message, and what the domain holds is not that. The escaping factor is not fixed either: 2 for a quote, 6 for a control character written as \u0000. The worst case is six times the raw size, and the common case is two.

ImportantWhen the escaping bounds the shape

The payload holds text that escapes, and the ceiling counts encoded bytes. Then measure the encoded size, or move the text out of the message; the factor applies to the field that escapes, not to the payload’s average byte.

WarningWhen the escaping does not force it

The payload is text with no character that escapes, so the factor is one. Or the ceiling has headroom a factor of 6 does not spend.

TipThe faithfulness test

Does the encoded size of the largest payload fit the ceiling?

  • If yes → the payload fits. Measure it encoded, not raw.
  • If no → the escaping spends the ceiling. Move the text out, or send it in a form that does not escape it.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Encode the largest payload, then compare it with the ceiling.

Case study: Normalisation form (the same text, two encodings)

“café” is five bytes composed and six bytes decomposed. Under a binary collation that is two values in one unique index; under an accent-insensitive one it is two different words merged.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A character with an accent has a composed form, one code point, and a decomposed form, a base letter plus a combining mark. The two render alike. Under a binary collation they are unequal byte strings, so a unique index takes both; under an accent-insensitive Unicode collation they compare equal, so the index merges them — and merges any two words that differ only in accent. The collation decides, not the text.

The encoding knowledge gap it signals

Equality here is decided in two layers: the form the text is stored in, and the collation it is compared under. A value typed on one system and pasted into another may arrive in either form. Equality, uniqueness, and search all inherit both choices.

ImportantWhen the form bounds the shape

The domain compares text for equality or uniqueness and accepts input from several sources. Then normalise on write to one form, and normalise the input of every lookup the same way — five bytes and six bytes are then the same word.

WarningWhen the form does not force it

The text is ASCII by constraint, where the two forms coincide. Or comparison is by an identifier the domain assigns, not by the text.

TipThe faithfulness test

Does the domain store text in one normalisation form, and does every writer and every lookup read the same rule?

  • If the stored form and the collation are both on file, and each writer and lookup cites them → equality means what it appears to mean. The equality is the domain’s.
  • If the form and collation are on file, but two writers disagree on which applies to a comparison → the meaning is not settled. Nobody has decided which reading binds in this system. A written form records that decision; it does not make it.
  • If no rule is on file → two identical-looking values are two rows. Normalise on write and on lookup.
  • If you can’t answer → stop. The artifact to produce is the normalisation and collation rule with its owner. Until it is on file, “the same word” has no agreed test.

Passing: Kraków → source: schema note, form NFC, collation pl-PL-x-icu, owner: data platform. Failing: “text is text” → source: none; the default collation compared them and nobody checked.

Case study: Identifier width (the birthday bound)

A random UUID carries 122 bits. At a billion ids the chance of one collision is 10⁻¹⁹; at 63 bits it is 5 percent. Same generation loop, different field width.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A random identifier of b bits collides with probability near n² ÷ 2^(b+1) after n values. A version-4 UUID spends 122 bits on randomness, so a billion ids give 10¹⁸ ÷ 2¹²³ ≈ 10⁻¹⁹. A 63-bit id at the same count gives 5 percent.

The encoding knowledge gap it signals

Two numbers decide the risk — the ids the domain will ever generate, and the bits that are random — and the first is a projection, not a measurement. The square in the formula is what hurts: ten times the ids is a hundred times the risk. Bits spent on a timestamp, a node, or a version do not count toward the randomness.

ImportantWhen the width bounds the shape

The projected id count and the random bits give a collision chance above the obligation. Then add bits, or take the uniqueness from a single writer; every extra bit buys √2 more ids at the same risk.

WarningWhen the width does not force it

The ids stay far below the count where a collision becomes likely, so a 122-bit id is not the constraint. Or a single sequence assigns them, and randomness is not the source of uniqueness.

TipThe faithfulness test

Does the projected id count, squared, stay far below two to the random bits plus one?

  • If yes → collisions do not rule the scheme out. Record the count the estimate assumes.
  • If no → a collision is expected within the obligation. Add bits, or use a sequence.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Count the random bits in the format, then project the ids.

Case study: Port field (16 bits in the protocol)

A TCP port is 16 bits. A design that gives each tenant a port serves about 64,500 of them on one address, and the first 1,024 are taken.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: The TCP and UDP port field is 16 bits, so 65,536 values exist and 65,535 are usable. Ports below 1,024 are privileged on Unix, so a scheme that allocates one port per tenant has 64,511 to give.

The encoding knowledge gap it signals

A port is a 16-bit key, and one tenant per port makes it a scarce resource. The key sits in the protocol, not in the application, so the tenant count and the port count are the same number. A bigger machine does not help; a second address does, because the space is per address, not per host.

ImportantWhen the field bounds the shape

The tenant count approaches the field. Then route by name instead: a header, a path, or the TLS server name, all of which ride one port, so the tenant count leaves the port space entirely.

WarningWhen the field does not force it

The tenant count is small and bounded, or ports are reused across distinct addresses. Either way the port field never fills.

TipThe faithfulness test

Does the tenant count fit the ports the scheme can allocate?

  • If yes → the scheme scales to that count. Recheck at ten times the tenants.
  • If no → the protocol field is the ceiling. Route by name, not by port.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Count the tenants, then subtract the privileged range.

Case study: Address space (32 bits, exhausted)

Four point three billion IPv4 addresses exist, and the registries ran out between 2011 and 2020. A design that needs one per device is a design on top of translation.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: IPv4 has a 32-bit address field: 4,294,967,296 values, less the reserved and multicast blocks. The free pool is gone — the last blocks went between 2011 and 2020 — so a new public address is a purchase or a translation.

The encoding knowledge gap it signals

Addresses are a budget with two columns — what the design needs and what it can obtain — and the second is no longer a technical quantity. Translation adds a table with its own bound and its own failure. Private space is large but not public, and it ends at the network’s edge.

ImportantWhen the field bounds the shape

The design needs a routable address per unit and cannot obtain one. Then use a protocol with a larger field, or a translation layer whose table is sized and monitored — the table becomes the bound to watch.

WarningWhen the field does not force it

The design lives inside one network, where a private block holds 16.7 million addresses. Or the units are far fewer than a block, and nothing runs out.

TipThe faithfulness test

Does the address count the design needs fit the addresses that can be obtained?

  • If yes → the design fits the space. Count the translation entries it also needs.
  • If no → the space, not the code, is the limit. Widen the field, or translate.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Count the units that need a routable address.

Case study: MAC address (24 bits of vendor space)

A MAC address is 48 bits, and half of a globally assigned one names the vendor. One vendor’s block holds 16,777,216 device addresses, and that block is the vendor’s to allocate, not yours.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A MAC address is 48 bits. The first 24 are the vendor’s block, assigned by the standards body, and the last 24 identify the device, so one vendor has 2²⁴ = 16,777,216 addresses and the whole space holds 2⁴⁸. One bit can mark an address as locally assigned instead, belonging to no vendor.

The encoding knowledge gap it signals

An identifier drawn from the hardware inherits someone else’s allocation. A design that derives one from the MAC address inherits the vendor’s 24 bits, and the block is not the design’s to grow. Virtual machines and containers make the count independent of the hardware.

ImportantWhen the field bounds the shape

The device count in one vendor’s block approaches 16.7 million, or the design assumes a fixed hardware address per unit. Then assign the identifier in software, where the width is yours.

WarningWhen the field does not force it

The devices are far fewer than the block, and the hardware address is only a local label. Then the block never fills.

TipThe faithfulness test

Does the device count fit the identifier space the design controls?

  • If yes → the identifiers fit. Confirm the control is in software, not in the hardware.
  • If no → the field is the ceiling. Assign the identifier yourself.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Count the devices, then find who allocates their addresses.

Case study: Base64 (four characters per three bytes)

Base64 turns three bytes into four characters. A 1 MiB ceiling therefore accepts 786,432 bytes of binary, and a 900,000-byte file does not fit.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: Base64 encodes every three bytes as four ASCII characters, so the encoded payload is four thirds of the raw one. A ceiling of 1,048,576 bytes, counted on the encoded message, leaves 786,432 raw bytes.

The encoding knowledge gap it signals

A binary payload and a text ceiling are two different sizes, and the gap between them is one byte in three. The ceiling counts what the transport carries, which is the encoded form; the design usually reasons about the file it stored. The difference is not a rounding.

ImportantWhen the encoding bounds the shape

The payload is binary and the ceiling counts encoded bytes. Then store the object and send a reference, or compress before encoding — the encoding is a transport cost, not a storage plan.

WarningWhen the encoding does not force it

The transport is binary — a protocol that carries bytes without an alphabet — or the ceiling counts raw bytes. Then the factor is one, and the raw size is the right input.

TipThe faithfulness test

Does the raw payload, times four thirds, fit the ceiling the transport counts?

  • If yes → the encoded form fits. Measure the file, not the string.
  • If no → the encoding spends a third of the ceiling. Store the object, or send a reference.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Encode the largest file, then compare the result with the ceiling.

Case study: Compression ratio (the limit is on the output)

A kilobyte of compressed input expands to a megabyte. At a thousand to one, a 10 MB request becomes 10 GB of memory, and the size limit was checked on the way in.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A compression format expands by a ratio it chooses, not one you choose. Deflate tops out near 1,032 to 1 — roughly a kilobyte to a megabyte — and it reaches that ceiling on a long run of one repeated byte. At 1,000 to 1, a 1 MB payload expands to 1 GB and a 10 MB payload to 10 GB.

The encoding knowledge gap it signals

What the design checks and what it spends are two different sizes: the bytes received and the bytes produced. The request limit applies to the first, and the memory is spent on the second. The output is where the memory is spent, and the ratio is not under the design’s control.

ImportantWhen the ratio bounds the shape

The design accepts compressed input from a source it does not control. Then bound the output as it is produced, and stop at the limit — the input’s size says nothing about the memory it will cost.

WarningWhen the ratio does not force it

The payload is uncompressed, so the received size is the produced size. Or the decompressed output is already capped by a bound the design enforces at the source’s stated ratio.

TipThe faithfulness test

Is the decompressed size bounded as it is produced, at a limit the design states?

  • If yes → the expansion stops at the limit. State the limit with the endpoint.
  • If no → a small request spends memory sized by the ratio, not by the request. Bound the output, not the input.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Decompress the worst payload you accept and measure the output.

Case study: Header overhead (metadata has a rate too)

Eight kilobytes of headers on every request, ten thousand requests a second, is 80 MB a second of names and cookies. That is 640 Mbit/s before the first byte of payload.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A request carries its method, its path, its cookies, and its tracing headers. At 8 KB of headers and 10,000 requests a second, the metadata alone moves 8,000 × 10,000 = 80,000,000 bytes a second, which is 640 Mbit/s. That is what HTTP/1.1 pays. Newer HTTP versions compress repeated header names, which shrinks a steady stream sharply — but a first request, or a cookie that keeps changing, still pays nearly in full.

The encoding knowledge gap it signals

Metadata has a rate too, and nobody measures it. A cookie that grows, a tracing header, and an authorization token all add to the same figure, and they apply to every request, including the ones that return nothing.

ImportantWhen the overhead bounds the shape

The headers are large and the rate is high, so the metadata is a share of the link and of the parse time. Then shrink the cookie, let header compression carry the repeated names, or cache the response so the request never repeats.

WarningWhen the overhead does not force it

The headers are small, the rate is modest, or the responses are large enough that the payload dominates. Then the metadata is noise.

TipThe faithfulness test

Does the header size times the request rate fit the share of the link and the CPU the obligation allows?

  • If yes → the metadata fits. Recheck when a cookie or a token grows.
  • If no → the names cost more than the payload. Cut the headers, or cache the response.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Measure one request’s headers, then count the requests per second.

Case study: Checksum width (the false-negative rate)

A 32-bit checksum misses one random corruption in 4.3 billion. At a million messages a day, an undetected one is expected about every twelve years — and over twelve years the chance of at least one is 63 percent.

Choosing a structure? Ask “what measured fact constrains this structure, and what is its value?” If you can’t answer, you’ve found a knowledge gap. If you can, you hold the number. The number rules out a design only where the design breaches an obligation: the fact measures, the obligation rules out. Which of the remaining designs you take is a second decision.

Bound: A b-bit checksum passes a random, independent corruption with probability near 1 ÷ 2^b. Real checksums do better on the damage that actually happens — a short run of flipped bits is caught outright — so treat that figure as the worst case. For a 32-bit checksum it is one in 4,294,967,296, so the width covers that many messages before one miss is expected. At a million messages a day, 4.3 billion messages take 4,300 days, about 11.8 years. A mean of one miss in that span is a 63 percent chance of at least one.

The encoding knowledge gap it signals

The messages the design will check and the probability the obligation allows are two numbers, and only one of them is measured. The width is fixed by the format. The rate is per message, so it scales with traffic, and a wider checksum costs bytes on every one.

ImportantWhen the width bounds the shape

The message count over the system’s life makes the expected false negative exceed the obligation. Then use a wider checksum, or a cryptographic hash — the width is a format choice, so changing it later changes every message.

WarningWhen the width does not force it

The count is far below the width’s reach, so a false negative is not expected within the system’s life. Or the transport already detects corruption, and the checksum guards something else.

TipThe faithfulness test

Does the message count times two to the minus the checksum width stay inside the obligation?

  • If yes → the width covers the count. Record the count the estimate assumes.
  • If no → a false negative is expected. Widen the checksum.
  • If you can’t answer → stop. Take the measurement and cite it with its source. Read the checksum width, then count the messages per year.
