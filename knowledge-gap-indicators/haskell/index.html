Laziness, purity, and GHC as knowledge machinery.

Laziness is an evaluation-order claim; a type class is a law over a family of types. Each post reads the claim and what GHC makes of it.

Pick a post on the left. It opens on the right.

Writing Haskell? Ask “what does this type carry — purity, strictness, totality — and what does GHC do with it?” If you can’t answer, you’ve found a knowledge gap: the type stands in for a fact nobody stated. If you can, the type is knowledge embodied — the program catching up to what the domain decided.

Case study: Laziness (the default evaluation claim)

A million-element fold returns the right number and holds 30 MB of unevaluated additions — one apostrophe (foldl') would have freed them.

Writing a Haskell definition? Ask “which fact does the type system carry — purity, totality, strictness — and what does GHC actually do with it?” If you can’t answer, you’ve found a knowledge gap: the types enforce a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: By default a binding is not a value but a recipe: GHC emits a thunk and runs it only when something demands the result, and only to weak head normal form (one constructor deep). That buys infinite structures and short-circuiting, and costs a heap profile set by demand sites the type never names.

The Haskell knowledge gap it signals

foldl and foldl' share one type: (b -> a -> b) -> b -> [a] -> b. Nothing in that signature separates the version that forces each step from the version that stacks a million thunks: strictness is not carried in a Haskell type. It sits in a bang pattern, a $!, StrictData, or whatever GHC’s strictness analyser inferred. The developer must know, accumulator by accumulator, which chains are forced on purpose and which by luck.

The gap question: which accumulators are forced on purpose, and which by the optimiser?

ImportantWhen the types encode reality

Demand is incremental: take 10 . filter p over an infinite enumeration, zipWith of two generated sequences, the first hit from find. The producer never runs ahead of the consumer, and GHC’s foldr/build fusion can rewrite the pipeline into one loop with no intermediate lists.

WarningWhen it’s a guess dressed as engineering

foldl (+) 0 over a million-element list. Each step allocates ((0+1)+2)+3 …; nothing forces the accumulator until the last demand, so the sum arrives as a million thunks and tens of megabytes for one number. foldl' was one apostrophe away. -Wall stays silent, and -O2 can rescue this exact shape — so the leak shows in the test run, not the benchmark. It type-checks, terminates, and is correct: the cost is absent from every artifact except the heap.

TipThe faithfulness test

Which accumulators in this program are forced — measured in a GC profile — or is every fold a thunk chain waiting to happen?

  • If yes → the demand sites are the ones you can name. Keep the profile in CI so a refactor cannot move them silently.
  • If no → the fold is a thunk chain priced by the optimiser. Use foldl', or force with $!.
  • If you can’t answer → stop. Read peak live heap (maximum residency) under +RTS -s. The choice waits until that is on file.

Case study: Purity and the IO boundary

The signature says the function cannot print. Its return value came from a cache populated at a moment nobody chose.

Writing a Haskell definition? Ask “which fact does the type system carry — purity, totality, strictness — and what does GHC actually do with it?” If you can’t answer, you’ve found a knowledge gap: the types enforce a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: An IO in the type marks a computation that may touch the world; an arrow without it promises referential transparency, so GHC may reorder the call, share one result, or delete it. The trade is the plumbing: every effect shows at every call site, and every caller carries IO up to main.

The Haskell knowledge gap it signals

The type tracks effects, not totality. f :: Int -> Int may still loop forever or crash on error — divergence and pure-code exceptions are not in the signature. The arrow therefore promises interchangeable calls, not a delivered result. The developer must know which claim the module makes, and where its effects may sit.

The gap question: which module may decide when an effect happens?

ImportantWhen the types encode reality

The domain draws the boundary where the signature does. Parsing, validation, and the state transition are pure functions from data to data; main reads the file, calls them, writes the answer. The core is property-testable without mocks, safe on many threads — and GHC may inline and merge duplicate expressions there precisely because nothing can be observed.

WarningWhen it’s a guess dressed as engineering

{-# NOINLINE cache #-} around unsafePerformIO (newIORef Map.empty), memoising a lookup the signature calls pure. The effect fires once per thunk, on whichever demand arrives first, and a value read from the environment at first use is that environment forever. The purity claim survives in the type and dies in the runtime. unsafePerformIO asserts the effect is order-independent — the same answer whenever it runs — and nothing checks the assertion — not the type checker, not the tests that keep passing.

TipThe faithfulness test

Which functions in this system can affect the world — exactly those with IO in the type, or are there smugglers?

  • If yes → the boundary belongs to the type. Check that main reads in one screen, and that error counts as an effect.
  • If no → the signature is a claim the runtime does not honour. Move the effect into IO, or into ST when it is local mutation (pure once runST closes the scope).
  • If you can’t answer → stop. Grep unsafePerformIO and every error. The choice waits until that is on file.

Case study: Type classes (instances as global facts)

The same nub (removes repeats by ==) returns a different list in two builds; no source line changed, only a dependency.

Writing a Haskell definition? Ask “which fact does the type system carry — purity, totality, strictness — and what does GHC actually do with it?” If you can’t answer, you’ve found a knowledge gap: the types enforce a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: A type class is a record of functions GHC passes implicitly: Eq a becomes a dictionary argument, resolved once per type, at compile time. That buys composition across packages — every consumer of Eq User gets one equality — and costs the freedom to declare instances anywhere.

The Haskell knowledge gap it signals

The compiler checks that an instance exists and its methods type-check. It does not check that == is an equivalence or compare a total order; Data.Map and sort assume those laws and go quietly wrong. The developer must know who owns each instance, and which law it satisfies.

The gap question: for this type, is there one defensible meaning of equality?

ImportantWhen the types encode reality

Instances sit beside the type or the class. Coherence holds by construction: one candidate exists, every package sees it, and a dependency cannot change a result. A second legitimate meaning gets a newtype — newtype ByName = ByName User — so the choice is written at the call site, not inferred from imports. -Worphans in CI, failing the build, keeps it that way.

WarningWhen it’s a guess dressed as engineering

Two orphan instances for one pair: Eq User by id in the service package, Eq User by every field in reporting. Each package compiles; its tests pass. A program whose closure reaches only one compiles and uses it; the second arrives as a duplicate-instance error when a dependency adds it. Same expression, different result, chosen by a build file. Orphans seduce because they are local: the instance sits where you needed it, and the bill goes to every program that later combines yours with another.

TipThe faithfulness test

For each instance: who owns it — and could two packages disagree about the same instance in one program?

  • If yes → ownership is structural and the meaning cannot move. Check the laws as tests; the compiler checked signatures only.
  • If no → a global fact has a local owner. Move it beside the type or the class, or wrap the type in a newtype.
  • If you can’t answer → stop. Run -Worphans on the tree. The choice waits until that is on file.

Case study: Strictness annotations and forcing

A record with eight lazy fields allocates eight thunks, and the bill lands in whichever function reads them first — rarely the one that built them.

Writing a Haskell definition? Ask “which fact does the type system carry — purity, totality, strictness — and what does GHC actually do with it?” If you can’t answer, you’ve found a knowledge gap: the types enforce a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: A field without ! holds a thunk: the expression stays unevaluated until something demands it. A ! forces it to weak head normal form (one constructor deep) when the record is constructed, and -XStrictData makes that the module default. The trade is placement and amount: a lazy field can skip work nobody needs and can also pile up deferred computation; a strict field pays at every construction, including those whose record nobody reads.

The Haskell knowledge gap it signals

Whether a field is always consumed is a fact about your program, not the record type. You must know which parts of the value a consumer touches, and when. A field left lazy because “it might be expensive” is a guess about a consumer you have not listed; a bang added because “laziness is slow” is the same guess in reverse.

The gap question: which fields are forced at construction, and who forces the rest?

ImportantWhen the types encode reality

Strict fields on records whose components are always consumed: a config read in full at startup, a metrics record whose every counter is summed. No thunk is built that nobody forces, and no field is forced that costs more than it saves.

WarningWhen it’s a guess dressed as engineering

The record crossing an API boundary with every field lazy. The library builds it cheaply, the boundary benchmarks beautifully, and the caller pays the forcing — one thunk at a time, inside whatever loop touches the fields, with the cost attributed to the caller. Deferred work is not free work. It is work with an unstated owner.

TipThe faithfulness test

For each record: is the forcing site named — or is it somebody else’s problem?

  • If yes → the strictness is a contract the writer states and the reader can check. Verify the forcing is not repeated per access, and that no thunk retains a large structure.
  • If no → you have a thunk with no owner. Name each field’s consumer, then force at the last point that still has the information.
  • If you can’t answer → stop. Trace each field to its reader, or profile for retention. The choice waits until that is on file.

Case study: SPECIALIZE and cross-module inlining

The pragma sits at the top of the module, the dictionary (class-method record) calls sit in the inner loop, and only the dumped core (GHC’s intermediate form) tells you which one shipped.

Writing a Haskell definition? Ask “which fact does the type system carry — purity, totality, strictness — and what does GHC actually do with it?” If you can’t answer, you’ve found a knowledge gap: the types enforce a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: In an optimised build, {-# SPECIALIZE f :: Int -> Int #-} asks GHC to build a monomorphic copy (one fixed at Int) and rewrite matching calls to it. The copy is a rewrite rule (a compile-time substitution), and a rule fires only where the compiler can see the call’s types. Across a module boundary, the rule needs the function’s unfolding (its body, kept in the interface file), which INLINABLE exposes. Without it, the callee compiles, the caller compiles, and no specialization exists.

The Haskell knowledge gap it signals

You must know which call sites are hot, at which types, and in which module. That is a fact about execution, not syntax. A pragma says “specialize this”; it never says “this is called a million times at Int from a module that cannot see me.” The cost of polymorphism is the dictionary: a record of methods, called through at every un-specialised site.

The gap question: which call sites did you measure, and at which types?

ImportantWhen the types encode reality

The hot polymorphic function marked INLINABLE, with SPECIALIZE for exactly the two types the profile shows, checked in the generated core: the specialized name present, the dictionary arguments gone, the loop monomorphic. The cost is paid where it was measured.

WarningWhen it’s a guess dressed as engineering

The numeric inner loop behind a module boundary. The function was compiled without INLINABLE, so no unfolding left the module; every iteration takes a Num dictionary and calls + through it. Nothing in the source mentions a dictionary. The benchmark is read as “GHC is slow at abstraction”, when the abstraction was never resolved. The mirror trap: INLINABLE sprayed everywhere, inflating code size and compile time to specialize functions called twice.

TipThe faithfulness test

Was the specialization verified in the generated core — or assumed from the pragma?

  • If yes → the specialization is a fact here. Re-check after a refactor changes its types.
  • If no → you have a wish, not a specialization. Dump the core, grep for the specialized name and dictionary parameters.
  • If you can’t answer → stop. Profile first, then read the core of the hot path. The choice waits until that is on file.

Case study: Making illegal states unrepresentable

The smart constructor validates on the way in, and the module exports Email(..) — so the next module writes the illegal value by hand.

Writing a Haskell definition? Ask “which fact does the type system carry — purity, totality, strictness — and what does GHC actually do with it?” If you can’t answer, you’ve found a knowledge gap: the types enforce a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: Three mechanisms: a newtype that gives a validation its own type, a sum type (one constructor per case) that gives the impossible state no constructor, a phantom parameter that pins the phase. Each moves an invariant from a comment into the type checker. The trade: an escape hatch — an exported raw constructor, an unsafeCoerce — puts the invariant back into the programmer’s head, silently, with nothing to catch a breach.

The Haskell knowledge gap it signals

You must know the invariant, who may break it, and which module boundary enforces it. “Non-empty” is a claim about the values the program can produce, not a property of the list type. If the only rule is a mkNonEmpty that calls error on [], the invariant is a crash, not a type.

The gap question: at which boundary can the illegal value still be constructed — and is that boundary named?

ImportantWhen the types encode reality

Data.List.NonEmpty where the domain guarantees at least one element, so head is total. A sum type whose constructors are exactly the states the protocol has. A phantom parameter so open and closed connections do not type-check interchangeably.

WarningWhen it’s a guess dressed as engineering

The smart constructor whose raw constructor is exported — Email(..) beside mkEmail — “for tests”. Or unsafeMkEmail in the same module. The invariant is documented, the check runs on some paths, and one module constructs the illegal value with a clean type. The types still read as proof, and reviewers trust a type that no longer means what it says.

TipThe faithfulness test

For each invariant: does the type make it unrepresentable — or is the check sitting next to a raw constructor?

  • If yes → the compiler is the enforcement, and a bypass is a compile error. Read the export list; the invariant lives there.
  • If no → the check is a convention. Close the constructor, or admit the invariant is unchecked and test it at every producer.
  • If you can’t answer → stop. List the invariants, then the constructors that can build each type. The choice waits until that is on file.

Case study: Partial functions (head, tail, !!, fromJust)

head on the list that is empty “never” — until a refactor lets it be empty, at 3 a.m., in production.

Writing a Haskell definition? Ask “which fact does the type system carry — purity, totality, strictness — and what does GHC actually do with it?” If you can’t answer, you’ve found a knowledge gap: the types enforce a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: head :: [a] -> a is total in its type and partial in its value: the signature promises an a for every list, and the empty list has none. !! promises an element for every index, fromJust promises a Just. -Wall reports -Wincomplete-patterns for a case expression you wrote, and says nothing about a head you called: the partiality is in the library. The trade is convenience against a claim that appears in no type.

The Haskell knowledge gap it signals

“This list is non-empty” and “this key exists” are facts about the program’s states. They live in the programmer’s head, and the signature does not repeat them. Every call to head is an unverified assertion, and the compiler cannot count the assertions it was never told about.

The gap question: which functions here can fail at runtime without their type saying so?

ImportantWhen the types encode reality

Total functions whose signatures state every outcome: an exhaustive match over a sum type, NonEmpty a where the domain guarantees an element, Maybe where absence is a real outcome. The caller is forced to handle each case, and the empty list is impossible or handled.

WarningWhen it’s a guess dressed as engineering

A filter, a takeWhile, or a new caller produces [] where the author assumed otherwise. Then fromJust on the Maybe the author did not want to match: the absence was known, felt as noise, and deleted with a function that throws. Each one is a Maybe-shaped fact turned back into an exception, and the type stops reporting it.

TipThe faithfulness test

Does every function here state its failure in its type — or is a partiality hiding behind a total-looking signature?

  • If yes → the signature is the contract. Check that -Wincomplete-patterns is on and clean.
  • If no → each partial call is an assertion with no witness. Replace head and tail with a match or NonEmpty, fromJust with a case.
  • If you can’t answer → stop. List every head, tail, !!, fromJust, and ask who guaranteed the precondition. The choice waits until that is on file.

Case study: Numeric defaulting and fromIntegral

fromIntegral narrows an Int64 to an Int32 with no line that says so, and the defaulting rule quietly picks Double for money.

Writing a Haskell definition? Ask “which fact does the type system carry — purity, totality, strictness — and what does GHC actually do with it?” If you can’t answer, you’ve found a knowledge gap: the types enforce a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: An ambiguous Num constraint is resolved by a defaulting rule you never wrote: Integer if it satisfies every constraint, else Double. let n = 1000000 is Integer; 1/2 is Double; a module-level default (Int, Double) changes the first, not the second. fromIntegral :: (Integral a, Num b) => a -> b wraps or truncates when the target is narrower. The trade: one conversion site against a type that no longer says what was converted.

The Haskell knowledge gap it signals

You must know the width of every numeric value at every boundary, and which conversions run there. The compiler knows the types it inferred; it does not know the identifier is 18 digits, or that money needs exactness. A defaulted type is a decision made by a rule, attributed to no one.

The gap question: which numeric type did the compiler choose here, and did you choose it?

ImportantWhen the types encode reality

Numeric types pinned by signatures where the width matters: Int64 for identifiers, Natural for counts, a decimal type for money, Word32 for a hash. Explicit fromIntegral at the boundary, with a range check beside it, so the narrowing is a site a reader can find and a test can hit.

WarningWhen it’s a guess dressed as engineering

The Int64 identifier narrowed by fromIntegral into an Int32 at the serialization boundary: no line mentions narrowing, values past the bound go negative or wrap, and the failure surfaces as a wrong lookup rather than an exception. Defaulting that silently chose Double for a money field, because the literal 0.1 needed a Fractional type and nobody wrote one.

TipThe faithfulness test

For each numeric boundary: which conversion runs — written down — and could it truncate or lose precision?

  • If yes → the conversion is a decision with a visible site. Check the range assumption against real data, not test data.
  • If no → the compiler chose. Pin the type in a signature and make the narrowing explicit.
  • If you can’t answer → stop. Turn on -Wtype-defaults and annotate every boundary it reports. The choice waits until that is on file.
