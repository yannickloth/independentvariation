Micronaut Compile-Time DI

Compile-time versus runtime dependency injection in Micronaut.

The framework learns about the application at build time. Each post asks what it learned, and from whose knowledge.

Pick a post on the left. It opens on the right.

Adopting compile-time wiring? Ask “what did the framework learn about this application at build time, and from whose knowledge?” If you can’t answer, you’ve found a knowledge gap: the compile-time metadata stands in for facts about the runtime. If you can, the wiring is knowledge embodied — the build catching up to what the application decided.

Case study: Compile-time dependency injection

Two services hold the same beans: one boots in 40 ms, the other in 3 seconds. One framework read the graph at build time; the other reads it at every start.

Accepting a Micronaut default? Ask “what did the framework learn about my application at build time, and which fact did that bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: Micronaut’s annotation processor emits a definition per bean, so the container builds graphs from generated classes instead of scanning a classpath reflectively. Startup is a bounded sequence of constructor calls, and a native image has no reflection metadata to guess at. The trade: the candidate set is fixed at compile time, so a bean that only appears at run time — registered, scanned, or loaded later — has no definition at all.

The Micronaut knowledge gap it signals

The framework learned which beans exist, what each constructor needs, and the order they must be built in — from your source code. That is a claim: every bean is knowable statically; any bean the source cannot see breaks it, and none appears in the artifact.

The gap question: is the bean graph a build-time fact or a runtime surprise?

ImportantWhen the domain mandates it

Cold starts on serverless and container platforms, where boot time is billed and a fixed graph is what makes the number small. Measure the start on the target runtime with the production bean count.

WarningWhen it’s a guess dressed as engineering

Runtime-DI habits carried across unchanged: a factory scanning a directory for handlers, a registry filled from ServiceLoader at first use. It compiles, tests pass, and the container wires exactly what the generated definitions describe — the late registrations riding alongside, invisible to the compiler and absent from the native binary.

TipThe faithfulness test

Which beans are decided at runtime, by condition — can you list them — or is the graph fully known at build?

  • If yes → the graph is a build-time fact and the startup number is its consequence. Check that nothing registers after startup.
  • If no → name the conditions, then move each to a compile-time requirement or accept that this part sits outside the framework’s knowledge.
  • If you can’t answer → stop. Compare the bean count at startup with the count of generated definitions. The choice waits until that is on file.

Case study: AOP without proxies

Three interceptors wrap one method — retry, trace, transaction — a patch bump reorders them with no annotation changed, and the first symptom is a duplicate charge.

Accepting a Micronaut default? Ask “what did the framework learn about my application at build time, and which fact did that bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: Micronaut resolves interception at compile time: an advised bean gets a generated subclass whose interceptors run in an order the processor fixed, with no runtime proxy and no reflection. That class is ordinary Java in your build output. The trade: cross-cutting behavior costs nothing at startup and survives native image, but the composed behavior of stacked advice lives in that file, not in the annotations.

The Micronaut knowledge gap it signals

Annotation order is not call order: the processor learned each method’s interceptors and emitted one order, and whether that suits the domain is a fact about your workload. A retry outside a transaction re-runs the whole transaction, commit included; inside, it re-runs one statement. A span outside the retry records one per attempt; inside, one total.

The gap question: what fixes this interceptor order, and has anyone read the answer? For this bean the answer is the generated chain, stated nowhere else.

ImportantWhen the domain mandates it

Retry and tracing advice on an outbound client, with the generated order read once, noted in the design notes, and asserted by a test. An upgrade that reorders the chain fails loudly.

WarningWhen it’s a guess dressed as engineering

Advice stacked three deep from three libraries, assuming annotations imply sequence. Nobody opens the generated subclass. The behavior is real, ordered, and determined, in a file no reviewer reads — so a patch bump that reorders one library changes the system silently, and the first symptom is a duplicate charge.

TipThe faithfulness test

What is the final call order for this bean — read from the generated source, or assumed from the annotations?

  • If yes → the chain is known and reviewable. Record and assert it, so the next upgrade cannot move it quietly.
  • If no → you are running an order you never chose. Read the generated class for one advised bean and write the order down.
  • If you can’t answer → stop. Open the generated source for the most-advised bean and diff the order after each upgrade. The choice waits until that is on file.

Case study: Bean introspection

The same serializer returns a complete object on the JVM and an empty one in the native binary — same classes, same annotations, different runtime.

Accepting a Micronaut default? Ask “what did the framework learn about my application at build time, and which fact did that bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: Annotate a class with @Introspected and the processor generates BeanIntrospection metadata at build time, so a serializer using it reads properties without reflection. The trade is coverage: a class with metadata serializes anywhere, native image included; a class without it falls back to reflection, which works until reflection is gone.

The Micronaut knowledge gap it signals

The framework learned which properties each class exposes, for the classes it was told of. That is a claim: the serialized types are enumerable from the source, and the claim covers your annotated types, not your controllers. Error payloads, cache entries, message bodies, types nested in your own DTOs — each crosses a serialization edge, and each is a fact the build learned or did not.

The gap question: is the bean graph a build-time fact or a runtime surprise? For serialization the set is the types with generated metadata; the gap is all the rest.

ImportantWhen the domain mandates it

A boundary that must run native: JSON routed through introspections, every payload type round-tripped in the binary’s test run.

WarningWhen it’s a guess dressed as engineering

A library deserializes by reflection on classes with no introspection — a third-party type, a DTO from a module built without the processor. On the JVM nothing looks wrong: tests pass, staging is green, the fallback returns the right object. Under native image the same call returns an empty payload, and the trace points at the library, not the annotation missing three modules away. Silent by design.

TipThe faithfulness test

Which classes are serialized — and is their metadata generated, verified for the native build?

  • If yes → the boundary is a build-time fact. Check that no nested type was forgotten: an outer introspection does not imply the inner.
  • If no → the fallback is doing the work. Annotate the type, or use a serializer path that refuses what it cannot generate.
  • If you can’t answer → stop. Round-trip every payload type in a native build and list those that came back empty. The choice waits until that is on file.

Case study: @Executable and introspection boundaries

The endpoint passes every test, every JVM build, every staging deploy — and returns 404 in the native binary that ships.

Accepting a Micronaut default? Ask “what did the framework learn about my application at build time, and which fact did that bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: @Executable marks a class so the ExecutableMethodProcessor registers its methods where bean conventions would not; @Introspected does the same for serialization metadata. Both are opt-in declarations telling the processor to emit code. Opt-in is a boundary with no middle where conventions are silent: what is declared is generated, what is missed is not, and the miss is silent on the JVM.

The Micronaut knowledge gap it signals

The gap is not in what the processor emitted but in what nobody asked it for. The question is whether the annotated set equals the set your runtime needs. A bean in a library module built without the processor, a class the build never treated as a bean, a nested payload without introspection — each is an omission with no local symptom.

The gap question: is the route set a build-time fact or a runtime surprise? The omission is the surprise, and the JVM hides it.

ImportantWhen the domain mandates it

A build output enumerating every generated definition and every registered method, read in review and diffed per release. A route without a generated entry then fails the review, not the deploy.

WarningWhen it’s a guess dressed as engineering

A controller in a library module compiled without the processor: the JVM falls back to a reflective definition, the native image has no reflection, and the route 404s only in the binary that ships. Every JVM test says the route exists. The seduction is the evidence — green tests, a working local build, a production report that reads like a routing bug in a component nobody touched.

TipThe faithfulness test

Does the build report list every route — checked — or is the gap found by a user?

  • If yes → the route set is a build-time fact. Check the diff, not the list: an omission shows up as an unintended deletion.
  • If no → the artifact asserts routes the build never generated. Compare the list with the API contract.
  • If you can’t answer → stop. Enumerate the generated definitions, then call every documented route in a native build. The choice waits until that is on file.

Case study: Declarative client (@Client interface)

One annotated interface becomes an HTTP client — and one hand-rolled call for an awkward endpoint splits the contract in two.

Accepting a Micronaut default? Ask “what did the framework learn about my application at build time, and which fact did that bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: An @Client interface declares one method per remote endpoint. Micronaut generates the implementation at compile time and binds the base URL from micronaut.http.services.<id>.url. Timeouts and a @Fallback sit beside the declaration. The trade: one contract that the compiler checks and every caller reuses, against a hand-rolled client whose paths, headers, and error handling drift from the provider’s.

The Micronaut knowledge gap it signals

A declared client asserts that the remote service has a stable contract, that callers share it, and that the address is configuration rather than code. Each is a claim about a service you do not own that can be false. The gap question: for each remote service, is there exactly one declared contract — single-sourced — and where does its URL come from?

ImportantWhen the domain mandates it

One service, many callers, one provider contract: checkout calling payments, a gateway calling identity. Then declare a single client per service, put timeouts and fallback beside the declaration, and let every caller inject the same interface. A provider change becomes one edit in one file.

WarningWhen it’s a guess dressed as engineering

“Simpler to write it by hand.” One awkward call gets a second client on RestClient or raw HTTP, because the interface felt heavy for one endpoint. The contract now lives in two places, only one is reviewed, and they disagree the day the provider answers 429 — the declared client had a fallback, the hand-rolled one had none, and the busiest caller was the one without it.

TipThe faithfulness test

For each remote service: is there exactly one declared contract — single-sourced — and where does its URL come from?

  • If yes → the client is the contract. Check that timeouts and the fallback sit beside the declaration, not in a caller.
  • If no → the contract is duplicated, and the duplicate is already wrong. Fold the hand-rolled call in.
  • If you can’t answer → stop. List every outbound call per service, then the file each contract lives in. The choice waits until that is on file.

Case study: Validated configuration (@ConfigurationProperties)

Every key was marked optional, and the one feature that needs a real value finds out in production.

Accepting a Micronaut default? Ask “what did the framework learn about my application at build time, and which fact did that bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: A @ConfigurationProperties bean binds a key group to typed fields, and the annotation processor generates that binding at build time. With @Validated, @NotNull, and @Context scope, a missing key fails startup — the context-scoped bean is created at startup, and startup fails if a required property is missing. The trade: required keys declared and enforced before the application serves a request, against an optional-everything configuration where every key’s presence is discovered at runtime.

The Micronaut knowledge gap it signals

Marking a key required is a claim that the feature cannot function without it — not that it is usually set. Only the team that owns the feature can supply that claim. The gap question: which config keys are required for this feature to work — enforced at startup — or discovered when it first runs?

ImportantWhen the domain mandates it

A key without which the feature is meaningless: a signing secret, a database URL, a tenant identifier. Then bind it as a required field with a constraint, and let a bad deployment die at startup, not at 3 a.m. in the one path that reads it. Bind the type too: a duration as a duration.

WarningWhen it’s a guess dressed as engineering

“Keep it optional for flexibility” — a @Nullable field or an empty default, applied to every key because one is genuinely optional. The group now boots in any state. The missing key surfaces when the rarely-used feature runs: the nightly export, the regional failover, the admin path nobody exercises — in production, on the day it matters. Optionality spread over a group hides which single key was ever the exception.

TipThe faithfulness test

Which config keys are required for this feature to work — enforced at startup — or discovered when it first runs?

  • If yes → the group encodes what the feature needs. Check each key has a type, not just a presence rule.
  • If no → the group encodes nothing, and startup proves only that the process can boot. Make the true requirements fail fast.
  • If you can’t answer → stop. Remove each key in a test profile and record which feature breaks. The choice waits until that is on file.

Case study: Netty server (thread selection and event loops)

A handler that returns a reactive type is assumed non-blocking — put JDBC inside it and every request on that event loop queues behind the database.

Accepting a Micronaut default? Ask “what did the framework learn about my application at build time, and which fact did that bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: Micronaut serves HTTP on Netty, with a small set of event loops derived from the processors the JVM sees and a blocking pool behind them. Thread selection AUTO reads the handler’s return type: a reactive type stays on the loop, a plain object moves to the blocking pool. The trade: thread economy on the loop against blocking handlers moved to a bounded pool.

The Micronaut knowledge gap it signals

Deciding where a handler runs requires knowing what its body does — wait on a socket, wait on a database, or compute. That is a property of your code, invisible to the framework, which is exactly why AUTO guesses from a type. The gap question: which endpoints run blocking code — listed — and on which pool, sized from what measurement?

ImportantWhen the domain mandates it

Blocking endpoints that are known and counted: JDBC, a filesystem read, a legacy client without async support. Then mark them with @ExecuteOn(TaskExecutors.BLOCKING), size that pool from the concurrency the dependency tolerates, and verify the loop count against the container’s CPU quota — the count follows the processors the JVM sees, which in a container may be the host’s, not the quota’s.

WarningWhen it’s a guess dressed as engineering

A handler declared reactive, returning a Mono, while its body runs a blocking JDBC query — often wrapped to look asynchronous. AUTO trusts the return type, keeps it on the loop, and one slow query stalls every connection that loop owns. Under default configuration the symptom is polite: throughput can halve as load rises, latency climbs, and no thread dump shows a blocked pool.

TipThe faithfulness test

Which endpoints run blocking code — listed — and on which pool, sized from what measurement?

  • If yes → the placement is a fact. Confirm the pool each blocking handler runs on — not the loop count.
  • If no → some loop is running a database call. Mark the handler, and size the pool it moves to.
  • If you can’t answer → stop. Time each endpoint’s body, then read loop count and pool saturation under load. The choice waits until that is on file.

Case study: Bean conditions (@Requires)

A bean exists in production and not in the test suite, and no test ever fails — the wiring is simply absent on one side.

Accepting a Micronaut default? Ask “what did the framework learn about my application at build time, and which fact did that bake in?” If you can’t answer, you’ve found a knowledge gap: the framework decided on your behalf. If you can, the default is knowledge embodied — the build catching up to what the workload demands.

Mechanism: @Requires makes a bean definition conditional — on a class, a property, an environment, another bean’s presence or absence. The processor bakes the definitions into the build, and the context resolves the conditions at startup, against the classpath and configuration it actually has. The trade: wiring declared per environment and fixed at startup, against a container that decides at runtime.

The Micronaut knowledge gap it signals

A condition is a claim about which environments and classpaths this application runs in, and those combinations are the team’s to enumerate, not the framework’s. The build answers only the question it was asked. The gap question: under which conditions does each conditional bean exist — enumerated — and do the tests cover the production combination?

ImportantWhen the domain mandates it

Genuinely different environments: an in-memory queue, a broker client where the client library is on the classpath, a stub for an external provider in the test profile. Then write the conditions down per bean, and let the test profile differ only where production differs, so the coverage gap stays visible.

WarningWhen it’s a guess dressed as engineering

A bean gated on @Requires(classes = SomeClient.class) where the test profile, lean on dependencies, lacks that library. The bean is absent in CI, the endpoint that injects it is absent too, and the build succeeds because nothing ever asked for it. The path ships unexercised, exists in production, and is first run there — a startup decision made against a test classpath that never matched the deployment.

TipThe faithfulness test

Under which conditions does each conditional bean exist — enumerated — and do the tests cover the production combination?

  • If yes → the conditions are documented facts. Check the test profile’s differences are the intended ones, not missing dependencies.
  • If no → some path is greened by absence. Add the dependency to the test classpath, or delete the condition.
  • If you can’t answer → stop. List conditions, then diff the production classpath against the test one. The choice waits until that is on file.
