Rust: The Compiler as Knowledge Enforcer

The Rust compiler as a knowledge enforcer, and its targets.

The compiler checks a fact — what owns this, what may alias, what may wait — and the check costs something. Each post names the fact checked and the price paid.

Pick a post on the left. It opens on the right.

Writing Rust? If you can, the annotation is knowledge embodied — the compiler catching up to what the domain decided.

Case study: The borrow checker

Two threads borrow the same vector mutably and the build stops — the compiler ruled the pairing out before the binary existed.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: Rust allows many immutable borrows or exactly one mutable borrow, checked on every path. Aliasing plus mutation is the pair it forbids, and a data race needs exactly that pair — so safe code cannot race. The guarantee follows from the typing rule, not from a convention the team promises to honor.

The Rust knowledge gap it signals

The checker asks one question: right now, how many readers, and is anyone writing? A design that answers this has one shape. One that cannot has two owners, or a cache behind a lock, or a callback outliving its caller — and the compiler forces the developer to name which, at the line where the ambiguity sits.

The gap question: which sharing pattern is this program’s real shape — and did the types encode it, or was the checker defeated?

ImportantWhen the types encode reality

A widget tree with one owning parent and borrowed children. A handler taking &Request and returning owned data. A batch pass reading a large buffer immutably while writing results elsewhere. The rule costs nothing, because the sharing really is many readers or one writer.

WarningWhen it’s a guess dressed as engineering

Rc<RefCell<T>> on every field. The borrow rules rejected the graph, so shared mutable state came back wrapped and the check moved to runtime: RefCell panics on a conflicting live borrow, deep inside a request, far from the line that caused it. The signature now reads “anyone may mutate at any time” — the claim the compiler declined to verify. It compiles.

TipThe faithfulness test

Which sharing pattern is this program’s real shape — and did the types encode it, or was the checker defeated?

  • If yes → the types are the design record. Check that the owning side is the one the domain names.
  • If no → name the aliasing the program actually has, then choose: restructure to one owner, or admit shared mutation and pay for it explicitly.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Draw the ownership graph of the live values and compare it with the signatures.

Case study: Ownership and moves

A function hands back a 10 MB buffer and no byte of the buffer is copied, no allocator runs, no collector wakes — the signature alone decided where the memory went.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: A value has one owner. Passing a non-Copy value moves it, and the old binding is dead; when the owner leaves scope the value drops, in an order the compiler fixes. No tracing collector runs, so no pause interrupts the program. The trade is ergonomics: a signature that moves its argument ends the caller’s use of it.

The Rust knowledge gap it signals

Ownership is a claim about handoffs. Either the caller still needs the value or it does not. A move says its work in that scope is finished and its future belongs to the callee; a borrow says the caller keeps it and the callee only looks. The compiler accepts the move and rejects the later use — then accepts a clone and rejects nothing.

The gap question: which clones are real copies the domain needs — counted — and which are compiler-appeasement?

ImportantWhen the types encode reality

A builder consuming self and yielding the finished value, because the caller has no use for the half-built thing. A message sent through a channel, where the sender’s value is dead by definition. Accessors taking &self and returning borrowed fields.

WarningWhen it’s a guess dressed as engineering

.clone() scattered until it compiles. The borrow rules refused a second use, so the value was duplicated instead of the design corrected. Each clone duplicates a whole value the rules never required, and it asserts a fact nobody stated: that two copies of this value may diverge. It hides the real lifetime structure, so the next reader cannot tell an intentional snapshot from a truce with the compiler.

TipThe faithfulness test

Which clones are real copies the domain needs — counted — and which are compiler-appeasement?

  • If yes → count them, and say why each copy exists in the domain, not in the borrow checker.
  • If no → give the callee a reference, or move once at the real handoff, and let the original die there.
  • If you can’t answer → unclear. You haven’t found ownership wrong — you’ve found incomplete knowledge of your own program. Trace each clone back to the call that demanded it, and ask what the caller did next.

Case study: Lifetimes

The signature says the returned reference lives as long as the input, and the checker enforces it — so a cache cannot outlive the store it reads.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: A lifetime is a named scope, and a reference may not outlive the data it points at. The compiler infers most; where a function without a self parameter returns borrowed data from several inputs, the developer writes the relation down and every call site is checked against it. The trade is annotation overhead exactly where the data flow is complex.

The Rust knowledge gap it signals

An annotation states how long a value stays alive relative to another. It forces the developer to say which object owns the memory, which merely looks at it, and for how long that stays legal. That is a domain fact, not syntax. Elision hides it only while the shape is simple.

The gap question: for each reference, what is its real scope — and does the signature say so, or was ’static a shortcut?

ImportantWhen the types encode reality

A cache holding &’store Entry values into a longer-lived store: the annotation states the store outlives the cache, true by construction and worth stating. A parser returning a slice of its input.

WarningWhen it’s a guess dressed as engineering

’static added until the errors stop. It compiles, so the reference now claims to live for the whole program — true by construction, false as a design statement. The real relationship was never modeled and the structure bent around the annotation: the borrow became an owned copy, or a leak, or an Arc with no sharing. The signature says “forever” because nobody could say “as long as the store”.

TipThe faithfulness test

For each reference, what is its real scope — and does the signature say so, or was ’static a shortcut?

  • If yes → the scope is a domain fact and the signature repeats it. Check that the owner outlives every borrower on every path.
  • If no → name the real scope, write the lifetime that carries it, or move the data so no reference crosses.
  • If you can’t answer → unclear. You haven’t found lifetimes wrong — you’ve found incomplete knowledge of your own program. List each reference, its owner, and the longest path on which it is used.

Case study: Send and Sync

A type that was never thread-safe fails to compile the moment it enters a channel — the compiler rejects a bug with no runtime symptom before anyone writes it.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: Send marks a type that may move to another thread; Sync marks one whose shared references may be used from several threads. Both are auto traits derived by the compiler from the fields; unsafe impl overrides that. A thread spawn or a channel send requires Send, so the crossing is checked at compile time. The trade is the wrapper maze wherever the requirement bites.

The Rust knowledge gap it signals

Thread safety here is a type property: the developer must know which values genuinely cross a thread and which never leave theirs — a fact about the program’s execution structure. The compiler checks the types it is given; it cannot check whether the crossing was real.

The gap question: which values genuinely cross a thread boundary — and does the type structure say exactly that, no more?

ImportantWhen the types encode reality

A channel carrying only Send types, its receiver on another thread. A job struct owning its inputs and taking no references, because it must outlive the scope that built it. A shared counter behind Arc<AtomicUsize>, where many threads really read and write.

WarningWhen it’s a guess dressed as engineering

Mutex<T> around values that never cross a thread. The lock asserts concurrent access and no second thread exists to contend for it. The cost is real: a lock on every read, a poison path nobody designed, guards in the API — a compile-time claim about contention that no measurement supports. Worse, unsafe impl Send on interior-mutable state silences a correct check.

TipThe faithfulness test

Which values genuinely cross a thread boundary — and does the type structure say exactly that, no more?

  • If yes → the wrappers mark real crossings. Check what happens on the panic path, when a lock poisons.
  • If no → drop the wrapper, keep the value on its thread, and let the type say so.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Draw the threads, then the values passing between them.

Case study: Monomorphisation versus dyn Trait

One generic function called with twelve types compiles twelve times, and the release binary grows tens of kilobytes for code that runs on two.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: A generic function is stamped out once per concrete type: fn area<T: Shape>(s: T) becomes one function per T, each specialised and inlinable. A dyn Trait call goes through a vtable, so one function serves every type at a pointer hop. Static dispatch buys inlining and a known callee; dynamic dispatch buys one code path and a binary that does not grow with call sites.

The Rust knowledge gap it signals

Monomorphisation is a claim that this call site is hot enough to pay per-type code — in compile time, binary size, and instruction cache. The developer must know which paths are measured hot, and which boundaries want one code path for an open set of types. The gap question: which call sites are hot enough to pay per-type code — measured — and which boundaries want exactly one code path?

ImportantWhen the types encode reality

A numeric kernel over f32 and f64 on a measured hot path, where inlining removes the call and lets the vectoriser see the loop. Two instantiations, both benchmarked faster than the dyn version by a measured margin. And at the plugin boundary, dyn: the type set is open, the call happens once per item, and one code path is the requirement rather than a compromise.

WarningWhen it’s a guess dressed as engineering

Generics over everything, because generics are faster. The binary bloats, compile time triples, and the extra instantiation shows no gain in any benchmark. The mirror trap: dyn in an inner loop, because dyn keeps the binary small — the indirection blocks inlining on the one path the profiler flags.

TipThe faithfulness test

Which call sites are hot enough to pay per-type code — measured — and which boundaries want exactly one code path?

  • If yes → the dispatch matches the profile. Re-check every release; hot paths move.
  • If no → you chose dispatch by slogan. Profile the path; instantiate where it is hot, box where the type set is open.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Time both builds, compare size, and read the profile.

Case study: Zero-cost abstractions

An iterator chain of map, filter and sum compiles to the loop you would have written — until one closure fails to inline, and it compiles to a chain of direct calls.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: “Zero cost” is a claim about one compilation, not a property of the language: the abstraction costs nothing when the optimiser erases it into the code you would have written. An iterator chain, a trait bound, a closure — each disappears in release when inlining succeeds, and each survives as real work when it does not.

The Rust knowledge gap it signals

A zero-cost claim is narrow: this chain, this profile, these settings. The developer must know whether the machine code was compared, or the benchmark timed, on that path — and which constructs defeat inlining: dyn dispatch, a boxed closure, bounds checks the optimiser cannot hoist. The gap question: was zero cost measured on THIS path — assembly or benchmark — or assumed from the slogan?

ImportantWhen the types encode reality

A filter-map-sum over a Vec<u64> in release, checked against the manual loop: identical instructions, timings within noise, no calls and no bounds checks in the disassembly. The abstraction is verified — the compiler wrote the loop, and the source stays composable. A trait bound on a numeric function, inlined at both call sites, shows the same.

WarningWhen it’s a guess dressed as engineering

“Zero cost” as folklore. The closure boxed as Box<dyn Fn>, so the call is indirect and the chain never flattens. The release profile with LTO off and sixteen codegen units — code split before inlining, so nothing crosses a boundary. The abstraction that failed to inline, found only because someone finally looked at the assembly.

TipThe faithfulness test

Was zero cost measured on THIS path — assembly or benchmark — or assumed from the slogan?

  • If yes → the abstraction earned its name here. Re-measure after every toolchain upgrade; inlining moves between releases.
  • If no → you hold a hope, not a fact. Compare the disassembly with the hand-written loop, or time both, before the claim ships.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Compile with debug symbols, read the disassembly, and count the calls.

Case study: Rc, Arc, and interior mutability

A forum’s comment graph builds, passes its tests, and its memory climbs for 6 days straight — nothing is wrong except that no reference count ever reaches zero.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: Rc counts owners on one thread, Arc counts them across threads, and RefCell, Mutex and RwLock let a shared handle mutate. The count is a claim: several owners, no single one responsible for the end. A cycle makes the count never fall to zero — and Weak is the only edge that does not count.

The Rust knowledge gap it signals

Sharing is a structural fact about the program: which nodes genuinely have more than one owner, and which edges are back-references that must not own. The developer must also know which lock is contended, and for how long, measured. The gap question: which nodes genuinely have multiple owners — stated — and are the cycles broken with Weak, checked?

ImportantWhen the types encode reality

A tree or graph with parent links: Arc on the nodes several readers hold, Weak on each parent back-edge, so the child never keeps the parent alive. The sharing is visible in the signature, the cycle is broken by construction, and a test drops the root and asserts the nodes are freed.

WarningWhen it’s a guess dressed as engineering

Arc<Mutex<T>> as a default shared state — the lock nobody measured, the contention nobody profiled, and every read serialised behind a write-capable handle. Cloning an Rc purely to silence a borrow error, which invents a second owner to satisfy the checker. And the parent-owns-child, child-owns-parent cycle that leaks until the process dies, invisible to every test.

TipThe faithfulness test

Which nodes genuinely have multiple owners — stated — and are the cycles broken with Weak, checked?

  • If yes → the count states the structure. Confirm every cycle has one Weak edge, and that the lock’s wait was measured at load.
  • If no → the count is hiding the shape. Draw the ownership graph, name the owners, and break each cycle with a Weak edge.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Watch the memory over hours, not minutes, and graph who owns what.

Case study: unsafe

An unsafe block added to skip a bounds check in 2025 still runs in 2027, and the invariant it assumed was broken by a refactor in 2026 — the compiler checked neither claim.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: unsafe moves to the human a check the compiler cannot perform: an FFI call, a SIMD intrinsic, a self-referential structure, a hand-rolled arena. Inside the block a specific set of safety checks is lifted — the block is a promise that the invariant holds, and a promise is not evidence.

The Rust knowledge gap it signals

Each block names an invariant the type system cannot state: this pointer is valid and aligned, this memory is initialised, nothing else aliases it, this thread has exclusive access, this layout matches the C struct. The developer must know which invariant, and where it is written. The gap question: which invariant does each unsafe block uphold that the compiler cannot check — written where?

ImportantWhen the types encode reality

Blocks kept minimal, each with a SAFETY comment naming the upheld invariant and the surrounding code that establishes it. A test exercises the unsafe block. Miri (the interpreter that checks undefined behaviour) checks its Rust-only paths. The module that reads uninitialised buffers is fuzzed, the FFI wrapper is called against the real library, and a debug assertion states what the optimiser now assumes.

WarningWhen it’s a guess dressed as engineering

unsafe for speed — get_unchecked in the loop, the invariant documented nowhere. Variants of the same mistake: one unsafe fn wrapping a whole module, so the boundary is invisible and every caller inherits the burden. A transmute reinterprets bits the type system wanted to check. An unsafe impl Send rests on a comment no test can reach.

TipThe faithfulness test

Which invariant does each unsafe block uphold that the compiler cannot check — written where?

  • If yes → the promise is auditable. Re-read each comment against the code whenever the block or its callers change.
  • If no → the burden moved to everyone who reads the file later, and they were not told. Write the invariant, or drop the block and pay for the check.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Run Miri on the module, grep every unsafe, and write the missing comment.

Case study: Rayon (the work-stealing pool)

Sixteen cores, a build step at 40 seconds on one core and 41 on sixteen — the loop was parallel, the work was not.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: par_iter splits a range across a thread pool, steals from busy threads, and collects results in order. The split pays only when the chunks are equal, independent, and CPU-bound; a lock or a shared counter inside the closure re-serializes them without a word. The trade is a scheduling cost per split against parallelism that exists only if the work divides.

The Rust knowledge gap it signals

Speedup is a fact about the work. The developer must know three things: how much of the runtime is CPU, how evenly it divides, and what each closure touches. Rayon checks the closure is Send and Sync. It does not check that the work is CPU-bound or the chunks balanced.

The gap question: is the work CPU-bound and independent — measured — and does any closure share state that serializes it secretly?

ImportantWhen the types encode reality

Per-pixel work on an image, a numeric grid reduced to one scalar, a batch of documents tokenized. Each chunk costs the same, touches nothing shared, holds the CPU throughout. Speedup tracks the cores up to memory bandwidth.

WarningWhen it’s a guess dressed as engineering

par_iter over a loop that makes a blocking call per item behind a single connection or disk. Sixteen threads park on it, the pool saturates, wall time lands where the sequential version was — the parallelism lived in the API. Or one Arc<Mutex<Vec>> collecting results: it compiles, and every chunk queues on one lock while the cores idle. The benchmark ran once and never repeated.

TipThe faithfulness test

Is the work CPU-bound and independent — measured — and does any closure share state that serializes it secretly?

  • If yes → the pool matches the work. Check that chunks stay coarse enough to amortize the split.
  • If no → the parallelism is nominal. Keep the loop sequential, or move the waiting out of it first.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Time one core’s CPU, then list every shared value a closure touches.

Case study: async/await (the compiled state machine)

A request is cancelled mid-flight, the handler returns, and the database transaction is still open — nothing failed, the future was simply dropped.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: An async fn compiles to a state machine: one variant per await point holding the locals live there, driven by poll. Sized and non-recursive, the future sits inline in the caller’s frame, no allocation per call; recursion or dyn forces Box::pin. The trade is allocation-free futures against cancellation that can land only at an await, and a Drop that cannot await.

The Rust knowledge gap it signals

The developer must know where this future may be dropped, which state is live at that line, and which of it needs an await to undo. The compiler checks, where a spawn demands it, that the future is Send across its awaits and that locals live long enough. It does not check that a dropped future leaves the system consistent.

The gap question: where may this future be dropped — and what cleanup must survive that point?

ImportantWhen the types encode reality

A hot path of nested async fns, no Box::pin: futures inline. A timeout or select! around a future owning nothing that needs rollback — an idempotent read, a reference-counted buffer. Cancellation drops it, the state machine goes, nothing was half-done.

WarningWhen it’s a guess dressed as engineering

A transaction held across an await, with rollback in Drop. Cancel at the wrong await — a select! arm, a client disconnect — and Drop runs, which cannot await, so the ROLLBACK never reaches the server. The connection returns to the pool still inside a transaction, and the next request inherits it: a write that fails for reasons no one traces to a cancellation three layers up. It compiles, is idiomatic, untested on the cancel path.

TipThe faithfulness test

Where may this future be dropped — and what cleanup must survive that point?

  • If yes → the awaits are the cancellation map. Check what Drop does at each of them.
  • If no → the cleanup sits after a suspension, not before it. Move it, or own the work in a task that no caller can drop.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. List the await points, then name what each one leaves half-done.

Case study: no_std (the target without an OS)

The firmware tests pass on the laptop, and the first cross-compile for the microcontroller fails four dependencies down.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: #![no_std] removes the std crate, leaving core and, if you opt in, alloc: no threads, no files, no clock, and no allocator unless you supply one. Every crate in the tree must make the same choice, and Cargo features are additive and unified, so one dependency enabling its std feature turns std on for the build. The trade is a small binary with no OS assumptions against an ecosystem split along that exact seam.

The Rust knowledge gap it signals

The developer must know which crates in the tree need an allocator, a heap, or an OS, and which of those the target ships. core is portable; alloc needs a global allocator you supply; std needs a system. The compiler checks the tree builds for the target — but only when someone builds for the target.

The gap question: does every dependency support no_std for this target — checked at which feature set?

ImportantWhen the types encode reality

A core-only tree: fixed buffers, embedded-hal traits (portable hardware interfaces), defmt logging, a parser with no allocation. Built for thumbv7em-none-eabi in CI, then flashed and exercised on the board. Every dependency is pinned to the feature set that keeps it allocation-free.

WarningWhen it’s a guess dressed as engineering

The crate is no_std and a dependency’s default features pull std in. On the host the tests pass because std exists; on the target the break surfaces at the layer that never touched the hardware. Or a Vec appears, someone bolts on an allocator, and the firmware links — until the first large allocation exhausts a heap nobody measured, at runtime, on a device with no console.

TipThe faithfulness test

Does every dependency support no_std for this target — checked at which feature set?

  • If yes → the tree is this target’s tree, not the host’s. Check next the allocator budget and the panic strategy.
  • If no → the no_std claim covers your crate, not your program. Cut the dependency, or gate it, then prove it stays off on the target.
  • If you can’t answer → unclear. You haven’t found the construct wrong — you’ve found incomplete knowledge of your own program. Build for the target triple, then read the resolved feature set per crate.

Case study: wasm32-unknown-unknown (the browser build)

The same crate compiles for the browser and the server, and only one target honors a thread by default.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: The target compiles a crate to a WebAssembly module the browser loads; wasm-bindgen marshals values across the JS boundary. Ownership and lifetimes are checked as natively; platform capability is not. std::thread::spawn compiles, then fails at the first call: this target has no threads without atomics and shared memory, and both need the page cross-origin isolated (the COOP/COEP headers). Blocking work compiles and blocks the main thread. The trade is one codebase against bundle size, a thread model the target lacks, and a boundary that copies.

The Rust knowledge gap it signals

The target states what the platform provides: a heap, no file system, no threads by default, no clock to borrow. The program states what it needs: a pool, a blocking read, a buffer copied per call. Nothing compares the two lists. The gap question: does this program block, spawn, or sleep on the main thread — and does the artifact pay for the feature it carries?

ImportantWhen the types encode reality

Core logic shared to wasm with the boundary drawn thin: pure functions over owned buffers, a measured bundle against a stated budget. It pays because it is the same logic — same tests, same fixes — and every platform difference sits outside it.

WarningWhen it’s a guess dressed as engineering

The whole crate shipped because it compiled: megabytes where two hundred lines of JavaScript would serve, a framework pulled in to avoid writing a fetch. Then the ported worker pool that panicked in production — the build was green throughout.

Is the bundle size measured — and does the program stay clear of spawning, blocking, or sleeping on the main thread?

Case study: Cargo feature flags (the compile-time switch)

Two features that each pass CI meet in a combination never compiled, and the failure appears in the customer’s build.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: A feature is a named set of optional dependencies, code, and features. The resolver unifies them once per build across the whole graph: enabling one anywhere enables it everywhere, except through the build-dependency seam, so “optional” is a claim about the artifact, not the caller. The trade is optional functionality compiled in or out against combinatorics — n features give 2^n builds, and CI runs n+2.

The Rust knowledge gap it signals

The domain decides which optionality is real: a deployment choice, one binary per customer; a platform choice, one build per target; a debugging aid. Cargo cannot tell those apart. Additive-only is a convention the build does not enforce. The resolver will turn a feature back on through a crate three levels down — which is how a no_std tree grows a hidden std dependency the host never misses. The gap question: are the shipped combinations written down, and does anything reject a build outside them?

ImportantWhen the types encode reality

Features additive-only, the shipped combinations the tested ones: CI builds --no-default-features, each feature alone, all features; mutually exclusive backends guarded by compile_error! so the bad pair fails at the first crate.

WarningWhen it’s a guess dressed as engineering

Mutually exclusive features accepted by the build. Both backends compile, a cfg! selector picks one silently, and the broken pair waits for the profile nobody runs locally — release, with a customer’s feature set. Also: an “optional” dependency the team believes is off, switched on by a crate nobody read.

TipThe faithfulness test

Which feature combinations actually ship — tested — and is “additive-only” enforced by the build or assumed by the team?

  • If yes → features are a supported interface. Keep them additive, and let CI own the matrix: a new feature arrives with its combinations.
  • If no → every combination you did not build is a configuration you did not design. Shrink the matrix, or reject pairs that must not meet.
  • If you can’t answer → unclear. You haven’t found the flags wrong — you’ve found incomplete knowledge of your own build. List the artifacts you ship, then the features each sets.

Case study: Monomorphisation (speed bought at compile time)

A 40-minute build is a design decision that never appeared in a review.

Writing a Rust construct or choosing a target? Ask “which fact did the compiler check for me — what owns this, what may alias, what may wait — and what did it cost?” If you can’t answer, you’ve found a knowledge gap: the borrow checker enforces a guess. If you can, the code is knowledge embodied — the types catching up to what the program means.

Mechanism: Rust compiles a generic function into one machine-code copy per concrete type it is called with. Those copies cost nothing at run time and everything at build time: compile minutes scale with the number of instantiations, and macro-heavy code adds expansion on top. cargo build --timings shows which crate pays. The trade is runtime speed bought with compile minutes against crate boundaries that keep iteration fast.

The Rust knowledge gap it signals

The fact here is the shape of the work: how often one edit is compiled, how long CI may take, how many people wait on it. Code does not carry that; the workspace does. A crate boundary is a build boundary — an edit recompiles its own side, not the other, and costs inlining for code that is neither generic nor marked #[inline]. The gap question: which dependency edge, named, costs the most build time, and what budget must it fit?

ImportantWhen the types encode reality

Crate boundaries drawn so CI builds stay under a stated budget: a clean build of 6 minutes, an incremental edit of 20 seconds, both measured with cargo build --timings and tracked as numbers, not feelings.

WarningWhen it’s a guess dressed as engineering

One giant crate with generics everywhere — 40-minute builds, and the velocity tax nobody put on any budget, because compile time is not a line item anyone owns. “Zero-cost abstraction” is true of the running program and false of the day: the cost moved from the user’s CPU to every developer’s edit. Add a proc-macro derive on every type and watch the tax compound.

TipThe faithfulness test

What is the measured CI build time — and which dependency edge drives it, named?

  • If yes → the generics are inside their budget. Watch the edge that grew this month, and keep the incremental path short.
  • If no → the abstraction is not free. Split the workspace at the boundary the work actually crosses, or cut an instantiation.
  • If you can’t answer → unclear. You haven’t found the generics wrong — you’ve found incomplete knowledge of your own build. Time the edges, not the total.
