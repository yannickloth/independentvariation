.NET Knobs and Practices

.NET runtime knobs and practices as knowledge-gap indicators.

Every knob or practice below moves two numbers: the one it aims at, and one it did not. Each post names the knob, states the trade, and asks which measured fact of this workload answers it.

Case study: Server GC versus Workstation GC

Same build, same load: server GC returns 44,000 requests a second holding 690 MB, workstation 31,000 holding 380 MB — each team calls its number correct.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: Server GC gives the process one heap per core, each with its own allocation budget and collection thread; workstation GC gives it one heap, collected by the triggering thread. The trade is parallel collection against footprint and pause shape: per-core heaps and helper threads are memory the process must be granted. In a container, server GC sizes its heap count from the CPU limit, not the host’s core count — unless GCHeapCount pins it.

The .NET knowledge gap it signals

The team must know how many cores it gets, and whether a human waits: throughput on a batch job is invisible to users, pause on an editor is visible on every keystroke. The gap question: which of throughput and pause does this workload sell, and how many cores does the scheduler really give the process?

ImportantWhen the domain mandates it

A request service on 16 cores, same allocation profile: workstation 31,000 requests a second at 380 MB peak RSS (resident set size), server 44,000 at 690 MB with p99 pause flat. Nobody watched the process and memory was free, so the mode was chosen by the number the customer pays for. An editor takes the opposite side: one heap, a smaller resident set.

WarningWhen it’s a guess dressed as engineering

Server GC copied into a small container because “web APIs use server GC”. The pod gets 1.5 CPU and 512 MB; the host has 64 cores. The limit should size two heaps; a teammate pinned GCHeapCount to 64, copied from the host’s spec. Sixty-four heaps and their helper threads divide a core and a half, each keeps its own gen0 budget, and the pod is OOM-killed while reporting low CPU.

TipThe faithfulness test

What do the measured throughput and pause profile need — and how many cores does this process really get?

  • If yes → it answers a stated requirement. Re-measure when the CPU limit or traffic shape changes.
  • If no → a default inherited from another machine. Let the CPU limit, not a config value, decide the heap count.
  • If you can’t answer → stop. Measure requests a second and p99 pause per mode at the real CPU limit, with peak RSS. The choice waits until that is on file.

Case study: DATAS (Dynamic Adaptation To Application Sizes)

The pod’s memory bill halved and its collection count rose 2.4× — memory was the scarce resource, and the four percent of throughput was the number nobody wrote down.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: DATAS — server GC only, opt-in on .NET 8, default on .NET 9 and later — derives heap count from the live data instead of the core count, shrinking the gen0 budget when that live set is small. The trade is footprint against collection frequency: a smaller budget fills sooner, so collections arrive more often and each does less work.

The .NET knowledge gap it signals

The team must know which resource is scarce here: a memory limit is a number in a manifest, throughput a number in an SLA, and the runtime reads neither. A mode that shrinks the heap where memory is free and cores are busy turns a non-constraint into a cost. The gap question: is the binding constraint memory or throughput — measured, and for which SLA?

ImportantWhen the domain mandates it

A queue worker in a 900 MB container, live set 210 MB, over a week. DATAS off: peak RSS 940 MB, three OOM kills. On: peak RSS 480 MB, collection count up 2.4×, throughput 18,400 to 17,600 messages a minute. A four percent loss against a ceiling the pod was breaching is a trade one sentence defends.

WarningWhen it’s a guess dressed as engineering

DATAS left on for a throughput-bound server GC batch job on a 32-core host with memory to spare. The live set is small — millions of objects a second, most dead within a pass — so the budget shrinks and the collector runs several times as often. Throughput drops nine percent, the memory saving is invisible because nothing there counts memory, and a default charged the number the SLA names.

TipThe faithfulness test

Is the binding constraint memory or throughput — measured, and for which SLA?

  • If yes → it is aimed at the constraint. Watch collection count beside RSS.
  • If no → a default doing an unrequested favour. Disable it, or write down the memory it protects.
  • If you can’t answer → stop. Measure peak RSS and collection rate on and off, at the limit that would kill the pod. The choice waits until that is on file.

Case study: Span<T> and Memory<T>

A parser’s allocations fell from 1.2 GB per 10,000 requests to 40 MB — then the same span types made an async method uncompilable.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: Span<T> is a ref struct — a pointer and a length over existing memory — so a slice costs two integers, where string.Substring copies. The trade is allocation-free slicing against a lifetime the compiler enforces: no boxing, no class field, no lambda capture, no crossing an await. Memory<T> is the heap-safe sibling for slices that outlive their method.

The .NET knowledge gap it signals

The team must know whether this path’s cost is allocation, and where each slice must live. A slice is free only while its buffer lives; once it outlives the method, Memory<T> or a copy comes back — the old allocation in new syntax. The gap question: is this path measured as allocation-bound, and can every slice die inside its own method?

ImportantWhen the domain mandates it

A log and CSV parsing path over 10,000 fixed requests: 1.2 GB allocated, 210 gen0 collections, 11 percent of wall time in GC. Parsed over ReadOnlySpan<char> from the request buffer instead: 40 MB allocated, 12 gen0 collections, 1 percent in GC, throughput up 11 percent. No slice escaped the parse method.

WarningWhen it’s a guess dressed as engineering

Span spread through a codebase because spans are faster. A 200-byte model is built with stackalloc, the stack frame grows, and a method that must await a database call cannot hold the buffer — so the code grows a synchronous twin and a defensive copy. The path allocated once per request, a number nobody had taken. On .NET 9 and later a ref struct local may live in an async method that crosses no await — removing the compile error, not the reason for it.

TipThe faithfulness test

Is this path measured as allocation-bound — or is Span fashion?

  • If yes → the slices encode a real lifetime fact. Keep the measurement, so a later return to Substring shows its price.
  • If no → a constraint bought for an unmeasured number. Keep Substring; revisit when the profiler names this path.
  • If you can’t answer → stop. Measure allocated bytes per request and GC time share. The choice waits until that is on file.

Case study: Sync-over-async (.Result, .Wait())

One .Result in a shared library passed every unit test, then deadlocked the first request from a UI handler.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: .Result and .Wait() block the calling thread until the task completes. Where a synchronization context exists — WinForms, WPF, MAUI, legacy ASP.NET — the awaited continuation is posted back to it, and the thread it needs is the one blocked on .Result. Without a context, as in ASP.NET Core, the deadlock becomes starvation: every blocked pool thread must be replaced by injection, the pool adding a thread on demand.

The .NET knowledge gap it signals

The team must know two facts about every call site: whether a synchronization context is ever present on the calling thread, and how many callers reach it at peak. Both belong to the host, not the method: the same line is safe in a console job, fatal in a UI handler. The gap question: is this path ever called with a synchronization context, or at production concurrency?

ImportantWhen the domain mandates it

Genuinely synchronous code kept synchronous. A CLI import tool reads, transforms and writes a file on its own thread, with no context and one caller, calling a library it cannot change. It blocks with GetAwaiter().GetResult(), which keeps the original exception: 4,000 files a minute.

WarningWhen it’s a guess dressed as engineering

One .Result inside a library method, “just here”, since the caller was synchronous. The tests pass: the console harness has no context, and the runner’s is not the UI’s. Then a WPF screen calls it and the window stops responding on the first click, the stack trace showing an incomplete task whose continuation never ran. In ASP.NET Core the same line starves: 200 blocked pool threads, p99 from 40 ms to 12 seconds at 15 percent CPU.

TipThe faithfulness test

Is this path ever called with a synchronization context or under load — measured?

  • If yes → it is a defect with a schedule. Await to the top of the stack, or make the entry point synchronous end to end, priced against every signature it changes.
  • If no → blocking describes the work, and claims something about the host. Keep the call behind a context-free boundary.
  • If you can’t answer → stop. Grep for .Result and .Wait(), then measure queue length at peak. The choice waits until that is on file.

Case study: ConfigureAwait(false)

ConfigureAwait(false) skipped the post-back on every continuation after it — and a control that needed its UI thread was touched from the pool, four frames below.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: An await captures the current SynchronizationContext and TaskScheduler, then posts the continuation back to them. ConfigureAwait(false) skips the capture, so the continuation resumes on any thread pool thread. It buys the post-back and spends the assumption that the continuation lands on the synchronization context’s thread — the UI thread that must touch a control.

The .NET knowledge gap it signals

The knob answers a question about your callers, not your code: which re-enter on a specific thread, and which read ambient state after the await. A library that touches no UI and reads no ambient state can suppress the capture. The gap question: who is downstream of this await, and what does each one need from the context?

ImportantWhen the domain mandates it

A library exercised under a UI dispatcher, where each captured post-back costs a hop nothing below it uses. Ten thousand awaits hold ten thousand post-backs; false removes all ten thousand. Default the library to false, and let the app layer keep the context deliberately, because the app is the layer that owns it.

WarningWhen it’s a guess dressed as engineering

False copied across application code because a style guide said so. A WPF handler awaits a call, and its continuation touches a control from a pool thread — no exception at the await, only a cross-thread failure four frames down, in a path no test covered. The win is a hop nobody measured; the loss is a crash the console harness never produced.

TipThe faithfulness test

Does anything downstream need the context — can you name it — or was false copied from a style guide?

  • If yes → keep the capture here, and suppress it inside the library.
  • If no → the suppression is free, and the hop was never doing work for anyone.
  • If you can’t answer → stop. Measure which continuations resume on a specific thread, then list every ambient read after each await. The choice waits until that is on file.

Case study: ValueTask

ValueTask removed the allocation from a cache lookup that usually hits — and then two consumers awaited the same instance, which the type forbids.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: A Task is a heap object, so a synchronous completion still allocates one unless the runtime hands back a cached instance. ValueTask is a struct wrapping a result, a Task, or an IValueTaskSource, so the synchronous case allocates nothing. It buys the allocation and spends a discipline: one consumption, one await, never stored, never awaited twice. Break it and the behavior is undefined, not merely slow.

The .NET knowledge gap it signals

The knob presumes two facts about your path: that it completes synchronously most of the time, and that exactly one consumer touches the result. The first is measurable; the second is structural. A hot cache lookup satisfies both. A method whose result gets logged, branched on, and returned satisfies neither. The gap question: is single consumption guaranteed by the shape of this code, or by hope?

ImportantWhen the domain mandates it

A measured hot path that usually returns without awaiting — a memory cache hit, a buffer already filled. Ten million calls, and each cache hit still allocates a Task where the ValueTask path allocates nothing; the count on that path goes to zero. The discipline holds because one caller awaits it once.

WarningWhen it’s a guess dressed as engineering

“Less allocation” adopted everywhere. A method returns ValueTask, and an interceptor awaits it, then the caller awaits it again: a second await is undefined behavior when the source is an IValueTaskSource — it throws, or it corrupts. Or the value gets handed to two consumers that both start it. The allocation win was nanoseconds; the failure is a corrupted result in production.

TipThe faithfulness test

Does the measured path usually complete synchronously — and is single-consumption guaranteed by structure, or by hope?

  • If yes → ValueTask is the honest type here. Verify no call site awaits twice or stores it.
  • If no → use Task. The allocation is the price of a contract your code actually uses.
  • If you can’t answer → stop. Measure the synchronous completion rate, then count the consumers per result. The choice waits until that is on file.

Case study: IAsyncEnumerable

IAsyncEnumerable streamed a four-million-row report at constant memory — and the caller called ToListAsync, and the memory came back all at once.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: The consumer awaits MoveNextAsync and processes each item before the next arrives. It buys constant memory and a first result before the query ends. It spends the total count, unknown until the stream finishes, and the simpler code that took a materialized list.

The .NET knowledge gap it signals

Streaming presumes two facts: the result set is large enough that materializing hurts, and the consumer acts on each item as it arrives. Both are measurable. A consumer that buffers, sorts, or shows a page count has already given up the win, whatever the type promises. The gap question: what is the measured result size — and does the consumer process incrementally, or buffer anyway?

ImportantWhen the domain mandates it

A measured large result set: four million rows at 200 bytes is 800 MB materialized, against a stream that holds one row plus its buffer. The consumer writes each row to a file or a response before the next arrives, so first byte leaves earlier and memory flatlines. The async enumeration per row now buys something: the producer is I/O-bound, and the consumer keeps pace.

WarningWhen it’s a guess dressed as engineering

IAsyncEnumerable over a twelve-row lookup table. Twelve rows fit in one page, yet the streaming machinery adds an async state machine, an await per row, and a caller that must step it — and the caller buffers it straight into a list to get the count. Paid for, never collected.

TipThe faithfulness test

What is the measured result size — and does the consumer actually process it incrementally, or buffer it anyway?

  • If yes → streaming is the honest shape. Check that nothing downstream sorts, counts, or materializes before use.
  • If no → materialize. A list is simpler, and the total count is knowledge you get for free.
  • If you can’t answer → stop. Measure the rows and the bytes per row, then trace whether the consumer holds them all. The choice waits until that is on file.

Case study: NativeAOT, ReadyToRun, plain JIT

NativeAOT took a CLI’s startup from about 80 ms to about 10 ms — and then the JSON serializer threw at runtime on a type the compiler never saw.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: JIT compiles IL on first call and re-optimizes hot paths from real profiles, so steady state wins and startup pays. ReadyToRun precompiles IL to native while keeping the JIT available: startup improves, the binary grows. NativeAOT compiles the whole closed world ahead of time, so startup and footprint drop and reflection stops being free.

The .NET knowledge gap it signals

The knob presumes startup dominates and every dependency survives a closed world. Startup-dominated is measurable; AOT-safe is knowable only by trying. Tiered compilation with dynamic PGO, on by default since .NET 8, means the JIT’s peak is the number you give up. The gap question: does startup or steady state dominate, measured — and is the dependency tree known to be AOT-safe?

ImportantWhen the domain mandates it

A measured startup-dominated workload: a CLI at about 80 ms to first output, mostly compiling methods it never runs, against about 10 ms under AOT.

WarningWhen it’s a guess dressed as engineering

NativeAOT on a long-running, reflection-heavy API. Startup was never the bottleneck — the process lives for days — so the win is invisible and the cost permanent. Plugins loaded by assembly name, a serializer mapping by reflection, proxies built at runtime: each becomes a runtime failure the compiler never saw, at the first request that touches it.

TipThe faithfulness test

Does startup or steady state dominate, measured — and is the dependency tree known to be AOT-safe?

  • If yes → AOT or ReadyToRun is knowledge, not fashion. Check the trim and AOT analyzer warnings, and test every reflection path.
  • If no → stay on the JIT. Keep the throughput: startup is paid once, throughput every day.
  • If you can’t answer → stop. Measure time to first useful output against throughput at sustained load, then list every reflection call in the tree. The choice waits until that is on file.

Case study: IL trimming

The publish folder dropped fifty-four percent, and the first request with an unregistered subtype died on missing metadata.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: The linker walks the call graph from entry points and deletes the IL nothing calls. Reflection is not a call edge: a type named in a serializer attribute or emitted by an ORM proxy is reachable only at run time, so the linker trims it unless an annotation roots it, and the app fails at first use. The trade is size and cold start against every path only reflection knows; .NET 8’s annotations narrow that surface, not the trade.

The .NET knowledge gap it signals

The team must know its own reflection surface: which types the runtime resolves by name, and which the tests exercise. The library’s annotations describe the library, not your use of it. The gap question: which types are reached only via reflection — enumerated how — and is that list tested after trimming?

ImportantWhen the domain mandates it

A self-contained or AOT deploy where size and cold start are constraints: enumerate the reflection surface in a descriptor (files that list reflection-reached types) or a source-generated context, and run the integration suite on a trimmed publish. Measured: publish 210 MB to 96 MB, cold start 2.4 s to 0.9 s, eleven metadata exceptions caught in that first trimmed run.

WarningWhen it’s a guess dressed as engineering

Trimming a service dense with runtime polymorphism — dynamic JSON, assembly scanning, lazy proxies — because the folder looked big. It publishes, it starts, the unit tests pass because they never touch the artifact. Weeks later an unforeseen subtype throws a metadata exception naming a type the source contains. Suppressing the warnings to get green makes the guess permanent.

TipThe faithfulness test

Which types are reached only via reflection — enumerated how — and is that list tested after trimming?

  • If yes → the trim states a checkable reachability claim. Re-check it per library upgrade, not the build.
  • If no → the trim was a size decision that deleted reachable code. Enumerate the surface first, or leave the reflection-heavy assemblies untrimmed.
  • If you can’t answer → stop. Run a trimmed publish under the integration suite and log every metadata failure. The choice waits until that is on file.

Case study: Nullable reference types

Nullable went on across the solution, the build went green in a day, and nobody can say which parameters may now be null.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: The compiler tracks flow for reference types and warns when null can reach a dereference. It checks nothing at run time — the annotation is a claim, not a guard. The gain is a compile-checked nullability claim; the price is the annotation discipline legacy code owes, since every signature becomes a statement somebody must defend. Since .NET 6 templates enable it project-wide, an enable is a commitment, not a sprinkle.

The .NET knowledge gap it signals

Nullability is a domain fact at each boundary: which inputs may be absent, which invariants hold after construction. The compiler proves a local flow; it cannot know whether absent means “not yet set” or “caller broken”. The gap question: is every nullable annotation backed by a stated invariant — or silenced to make the build pass?

ImportantWhen the domain mandates it

Enabled per project, warnings as errors, each resolved into a real decision: handle the null, or non-null the parameter and make callers prove it. Measured on a forty-project solution done this way: 1,900 warnings, 61 that a reviewer traced to a real null path — 61 latent bugs in code declared fine.

WarningWhen it’s a guess dressed as engineering

Enabled wholesale with <NoWarn>CS8600;CS8602;CS8618</NoWarn>, or a nullable-disable atop the files that complained. The build is green: every warning silenced, and a string? with no invariant behind it reads as a contract. The seduction is real: the property is on, the dashboard says “adopted”, and every consumer trusts a contract nobody checked.

TipThe faithfulness test

Is every nullable annotation backed by a stated invariant — or silenced to make the build pass?

  • If yes → the annotation is knowledge the compiler enforces. Check the ! suppressions next; each is a hand-written exception to it.
  • If no → at least one annotation is decorative. Fix those, or revert the enable.
  • If you can’t answer → stop. Count the suppressed warnings, then trace what each flagged. The choice waits until that is on file.

Case study: C# records

An order in a HashSet has its status flipped to Shipped, and the lookup misses — its hash moved to another bucket, and the set never rehashed it.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: A record gets compiler-written equality over its fields, a matching hash code, and with expressions that copy and modify in one line. The trade is value semantics — equal by data, replaced by convention rather than enforced — against identity semantics, equal by reference or id, which an entity needs to stay itself while its data changes. record struct adds struct rules — copies on assign, no inheritance; with copies shallowly, so nested mutable state stays shared.

The .NET knowledge gap it signals

The team must know, per type, whether the domain identifies it by its data or by a persisted id. Money, a date range, a DTO — data is the identity. An order, a user, a document — the id is the identity, and two versions with different data are one thing. The gap question: is this thing a value (equal by data) or an entity (equal by identity) — decided, not defaulted?

ImportantWhen the domain mandates it

DTOs, messages, and domain values as records, so copy-and-modify collapses into order with { Status = Shipped } — no builder, no forgotten field. Measured on a mapping layer converted this way: 1,400 lines of copy code became 260, and three bugs where a copy kept a stale field left with them.

WarningWhen it’s a guess dressed as engineering

Records for entities. The instance goes into a set, someone sets a property, and the entity can no longer be found under the key it was added with — no exception, no trace. Then mutable properties undercut the claim: init becomes set, and equality changes while the object is in use.

TipThe faithfulness test

Is this thing a value (equal by data) or an entity (equal by identity) — decided, not defaulted?

  • If yes → equality by fields is the domain’s rule. Check the record is immutable, so the hash cannot move under its container.
  • If no → it is an entity. Give it reference or id-based equality, and never key a set on mutable fields.
  • If you can’t answer → stop. Ask what the domain calls the same thing twice. The choice waits until that is on file.

Case study: Structs versus classes

A 200-byte struct crosses four methods per call, and the profiler puts 11 percent of sampled time in the copy.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: A struct is a value: it lives inline in its container, allocates nothing, and sits close to the data beside it. Every by-value assignment copies the whole thing: a by-value parameter, a return, a field store, each a memcpy. The trade is allocation and locality against copy cost, and the cost scales with a size nobody wrote down. readonly struct with in parameters — pass by reference, no copy — is the lever; a non-readonly member on a readonly field still copies.

The .NET knowledge gap it signals

The team must know two numbers about its own workload: the struct’s byte size, and how often it travels. A sixteen-byte value passed once per request is free; the same value in a four-million-element array walked twice is the hot path, where locality wins. The gap question: what is the measured size of this struct — and is it immutable, so copies are safe?

ImportantWhen the domain mandates it

Small immutable value types on a measured hot path: an identifier wrapper, a coordinate, a key. Measured on a parsing loop over four million price points: the class version spent 38 percent of its time in garbage collection, the readonly struct with in parameters spent 6 percent, and the pass went from 210 ms to 95 ms — allocation removed and locality gained, not a cleverer algorithm.

WarningWhen it’s a guess dressed as engineering

A 200-byte struct passed everywhere because structs are “faster”, and the copies add up. Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. Mechanism: ArrayPool<T>.Shared lends an array and takes it back on Return, so each rent reuses a pooled array instead of a fresh allocation. Above 85,000 bytes that is the difference between an LOH segment and none, and LOH objects are reached only in Gen2 — the pause you are reading. The trade is a lifetime obligation: every rent needs a return on every path, and the buffer comes back dirty.

The .NET knowledge gap it signals

The team must know its allocation profile: which buffers cross 85,000 bytes, how often, and whether Gen0 already absorbs them. Reuse pays where the churn measures as LOH pressure; where it is Gen0 churn, the pool buys nothing and adds a return path. The gap question: is this churn LOH-heavy by measurement, and does every path return what it rents, exceptions included?

ImportantWhen the domain mandates it

A gateway copying bodies into 128 KiB buffers at 2,000 requests a second puts about 250 MiB/s on the LOH. Pooling a bounded set takes LOH allocation to near zero and Gen2 from about 30 a minute to 2 — the unexplained Gen2 pause gone — with the pool size now setting the ceiling.

WarningWhen it’s a guess dressed as engineering

Pooling 64-byte arrays in a hot loop because “allocation is expensive.” Gen0 allocation is a pointer bump and Gen0 collection is cheap; the pool adds a return obligation on every branch, a dirty-data bug on the first path that forgets to clear, and a stale byte from another request in a response.

TipThe faithfulness test

Is the churn measured as LOH-heavy — and does every code path return what it rents, even on exception?

  • If yes → the pool answers a measured fact. Check it is bounded, that buffers carrying request data are cleared, and that used length is tracked apart from array length.
  • If no → no on the churn means nothing pays for the pool — measure first; no on a path means a missing return — fix it. Gen0 churn takes a plain allocation.
  • If you can’t answer → stop. Measure bytes allocated per second by size bucket, then Gen2 pause time and cause. The choice waits until that is on file.

Mechanism: A registration declares how long an instance lives: transient one per resolution, scoped one per scope — per request in a web host — singleton one for the life of the container. ImportantWhen the domain mandates it

An order API scopes its DbContext to the request — the request is the transaction boundary — and keeps the configuration reader singleton, since the process owns it. WarningWhen it’s a guess dressed as engineering

A singleton holding a scoped DbContext, because “the context is expensive to construct and we wanted one.” The first request’s context is captured and served to every later request — last week’s prices — and under overlap it corrupts across threads: a DbContext is not thread-safe, so callers interleave on one change tracker (its per-request entity set) — “A second operation was started on this context instance” at load, or request A’s entities saved by request B.

For each dependency, whose lifetime does it share — stated, or discovered at runtime?

  • If you can’t answer → stop. Read every constructor argument’s registration, then the concurrency it implies. The choice waits until that is on file.

Mechanism: A hosted service is started by the host, receives a stopping token, and must stop before the process exits: services start in registration order, stop in reverse, and the host waits up to its shutdown timeout — 30 seconds by default — to drain them all. The team must know what the work does when interrupted: which writes are idempotent, and how long a batch takes. The gap question: what happens to in-flight work when the process stops — stated, and does the shutdown path honor it?

ImportantWhen the domain mandates it

A worker consuming 400 messages a second: on deploy it stops accepting, finishes the batch in flight, and exits in 1.8 seconds, queue depth zero. Across 50 deploys: zero truncated batches against a handful before, and no longer deploy time, since the drain finished inside the timeout.

WarningWhen it’s a guess dressed as engineering

A Task.Run fired from startup “for the background job.” The host does not await it, so shutdown has nothing to drain. The next deploy ends the process mid-write: no commit of the pending write, no retry, no error. It worked locally, because no debug session raced a deploy. The work looks asynchronous and is unowned.

What happens to this work when the process stops — stated — and does the shutdown path honor it?

Case study: Task.Run wrapping (the false offload)

A controller awaits Task.Run around an HTTP call, the throughput halves at 800 requests a second, and the work was never CPU-bound.

Changing a .NET knob or adopting a practice? Ask “which measured fact of this workload does it answer, and what does it trade away?” Every knob moves two numbers — the one you aim at, and one you did not. If you can’t name both, you’ve found a knowledge gap: the knob is a superstition. If you can, it’s knowledge embodied — the runtime catching up to what the workload demands.

Mechanism: Task.Run queues a delegate to the pool and returns a task. The trade is a thread hop to shed the caller’s context: the delegate’s synchronous part runs on a pool thread, and the caller’s continuation needs one again, so a wrapped call pays two pool work items where one would do. On ASP.NET Core there is no synchronization context to escape, so the hop buys nothing.

The .NET knowledge gap it signals

The team must know the shape of the work: CPU-bound or waiting on IO, and which thread pool the caller already occupies. Wrapping wait-bound work relabels it; wrapping CPU-bound work moves it to a pool thread the pool must still supply, and the demand is unchanged. The gap question: is the wrapped work CPU-bound by measurement, and does the caller sit on the pool it starves?

ImportantWhen the domain mandates it

A desktop application recomputing a 400 ms report on the dispatcher thread at every filter change leaves the window at about 2.5 frames a second. Moving the compute behind Task.Run with a cancellation token holds the UI at 60 frames, and the calculation still takes 400 ms — one pool thread against a responsive window.

WarningWhen it’s a guess dressed as engineering

Task.Run around an awaitable inside a server request, “so it does not block the request thread.” Nothing was blocking: async IO frees the thread at the first await. Under load the pool queue grows, the pool injects a thread about once a second, and p99 triples while the CPU sits idle. Wrapping a synchronous call is worse: one pool thread parks while another works.

TipThe faithfulness test

Is the wrapped work actually CPU-bound — and does the caller sit on the same pool it starves?

  • If yes → the offload is real. Pass a cancellation token, keep the delegate short, and check the thread pool has threads at peak.
  • If no → no on CPU-bound means IO in disguise: await it directly, remove the wrap. No on the pool means the offload stands.
  • If you can’t answer → stop. Measure CPU time against wall time for the call, then pool queue length at peak. The choice waits until that is on file.
