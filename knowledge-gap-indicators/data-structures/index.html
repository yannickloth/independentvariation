Data Structures as Knowledge-Gap Indicators

A series of short posts that read each data structure as a contract on order, cost, and the operations it refuses.

Where the algorithm list reads the order of operations, this list reads what holds the data: the order it keeps, the cost it promises, the operations it refuses. Each post names the structure, states the contract, and asks whether the domain supplied it.

Pick a post on the left. It opens on the right.

Choosing an algorithm or a data structure? Ask “which facts does this choice encode — the operation mix, the scale, the ordering, the exactness the domain demands, among others?” If you can’t answer, you’ve found a knowledge gap: the structure pays for a prediction nobody wrote down. If you can name those facts, the structure is the knowledge embodied — the code catching up to what the domain decided.

Case study: Dynamic array (the doubling vector)

Construct: One contiguous block, a count, a capacity. Append is O(1) amortized: a resize copies n elements, and doubling spreads that copy over the next n appends. Positional access is O(1). Insert in the middle is O(n). The predictions: appends dominate writes, positional access dominates reads, an occasional pause is acceptable, insertion order is the order the domain means.

The data-structure knowledge gap it signals

The array bets on the operation mix, the scale, and the pause. All three are domain facts: a log is appended to, a price list is read by index, a nightly job absorbs a 24 MB copy; a 5 ms request does not, and that copy is about 2.4 ms at ten gigabytes a second.

The gap question: which operation dominates, and is the resize pause acceptable at the size the domain reaches?

ImportantWhen the domain mandates it

Collect-then-process workloads: buffer a query result, iterate all of it, discard it. Appends dominate, iteration dominates, and the order kept is the order received — the order the domain produced. Positional access is a need here, not a convenience.

WarningWhen it’s a guess dressed as engineering

Edits in the middle of a long-lived list. The call reads like O(1); each call shifts half the array — 100,000 moves per edit at 100,000 elements, behind one method name. Or the count reaches millions and nothing records that anyone compared the doubling pause to a latency budget.

TipThe faithfulness test

Do appends or index reads dominate — and is the resize pause within the budget at peak size?

  • If yes → the pause fits the budget. Check the peak size the doubling reaches, then the copy cost there.
  • If no → say which half failed. Mix unmeasured: count the operations. Pause over budget: reserve capacity, or move the copy off the request path.
  • If you can’t answer → unclear. You haven’t found the array wrong — you’ve found incomplete domain knowledge. Count appends, middle inserts, and index reads for a week.

Case study: Linked list (the splice contract)

Construct: Node plus pointer, allocated one at a time. Given a reference to a node, insert and remove are O(1): rewire pointers, shift nothing. Search is O(n), positional access is O(n), and each traversal step is a dependent load from an address neither the compiler nor the prefetcher can predict. The predictions: splice at a held position dominates, random access never happens, the cost per element is acceptable.

The data-structure knowledge gap it signals

The O(1) claim is conditional. The structure is fast only when the caller already holds the position. If the caller holds an index or a key, the structure finds the node first, and the find is O(n).

The gap question: is the position already in hand when the write arrives?

ImportantWhen the domain mandates it

Cursor-and-splice workloads. An LRU (least recently used) cache keeps an eviction chain: the hash map holds the node, so moving it to the front is O(1) pointer surgery that copies nothing. An allocator free list pops a block from the head. A kernel intrusive list embeds the node in the object, so one object sits on many lists.

WarningWhen it’s a guess dressed as engineering

“Insertion is O(1), so the list beats the array.” The workload builds the list, then checks whether a key already exists — search, then insert. The search is O(n) with a cache miss per step, and a contiguous array scans the same data faster. Or the list is long and read hot: pointer chasing over 100,000 nodes turns a sub-millisecond scan into milliseconds.

TipThe faithfulness test

Do you hold a position and splice — or search, then insert?

  • If yes → the O(1) claim holds. Check what the splice touches, and that no one else holds a stale pointer.
  • If no → the O(1) claim is false for you: the search dominates. Measure the search against a contiguous scan.
  • If you can’t answer → unclear. You haven’t found the list wrong — you’ve found incomplete domain knowledge. List the insert sites, and mark which ones arrive holding a node.

Case study: Stack (the last-in rule)

Construct: One end is both readable and writable; the other is sealed. Push, pop, and peek are O(1), and nothing below the top is reachable without popping what sits above. The structure can serve only the most recent item, so it encodes the claim that of everything it received, the most recent matters now, and first.

The data-structure knowledge gap it signals

The structure does not prefer recency; it makes recency the only rule. Reversal is a real domain relation where the last edit is the first to undo, or the innermost block the first to close.

The gap question: is “most recent first” the domain’s own rule for what happens next, or a container default standing in for a rule nobody stated?

ImportantWhen the domain mandates it

Undo history reverses in exact reverse order, because the edits were causally ordered and only the newest is safe to reverse. A parser tracks open brackets: the innermost is the only legal closer, and the grammar bounds the depth. Depth-first traversal keeps its frontier here, so backtracking resumes where it stopped.

WarningWhen it’s a guess dressed as engineering

A severity queue that happens to use a stack. Arrival order becomes priority without anyone deciding it: a low-severity ticket filed a minute ago outranks a payment outage filed an hour ago. The structure authored a policy the domain never agreed to, and the policy is invisible in the push and pop calls. Or a stack holds a history the domain wants to browse, and nobody can jump to a known revision or compare two.

TipThe faithfulness test

Is “most recent first” the domain’s own rule for what happens next?

  • If yes → LIFO is the domain’s rule. Check the depth the domain permits, and what bounds it.
  • If no → the order is a container artifact. Name the rule the domain does have — priority, deadline, revision — and let it into the structure.
  • If you can’t answer → unclear. You haven’t found the stack wrong — you’ve found incomplete domain knowledge. Ask who decides which item is handled next.

Case study: Queue and deque (the arrival-order contract)

Construct: A queue adds at the tail and removes at the head, both O(1) in a ring buffer. A deque frees both ends for O(1) reads and writes. The queue encodes one rule — service order is arrival order — and the deque encodes two: both ends carry meaning, neither is a leftover. That is a fairness claim before it is a data-structure claim.

The data-structure knowledge gap it signals

The structure fixes the ordering rule and hides the backlog inside itself. An unbounded queue is also a latency store: when arrival outruns service, waiting time grows without limit and the container never objects.

The gap question: is arrival order the rule the domain chose, or the one it inherited?

ImportantWhen the domain mandates it

Fair service in arrival order, where the domain names the fairness: job queues, request lines, print spools, a connection pool’s wait queue. Each promises that no later arrival overtakes an earlier one. A deque earns its second end the same way: undo consumes one end, redo returns items to the other, and the two ends are two domain facts.

WarningWhen it’s a guess dressed as engineering

FIFO as accidental policy. One queue carries nightly batch work and customer-facing work, and the batch fills it, so urgency is irrelevant by construction and no line of code decided that. The deque has its own version: one end is used, the other is a field no code path reads — the structure claims two domain facts and the domain supplied one.

TipThe faithfulness test

Is first-come-first-served a rule the domain recognizes?

  • If yes → FIFO is the domain’s fairness rule. Check what bounds the queue when service is slower than arrival.
  • If no → the order is accidental. Name the rule the domain has — priority, deadline, tenant quota — and put it in the structure or the scheduler above it.
  • If you can’t answer → unclear. You haven’t found the queue wrong — you’ve found incomplete domain knowledge. Measure arrival rate against service rate at peak.

Case study: Hash map (the exact-key index)

Construct: A hash function maps a key to a bucket: lookup, insert, and delete are O(1) expected, O(n) worst case when every key collides. The buckets encode no order a reader may rely on; iteration follows the hash, the capacity, and the insertion history. It predicts that lookup by exact key dominates, key order carries no meaning, keys are unique, and the hash is a pure function of the key’s value.

The data-structure knowledge gap it signals

Uniqueness and orderlessness are domain claims, not storage options. A map enforces the first — a second insert on the same key overwrites — and hides the second, so a display path built on iteration order turns nondeterministic the day the capacity changes.

The gap question: does any downstream consumer read the order the entries came back in?

ImportantWhen the domain mandates it

Identity lookup where the key is the identity: a user by id, a session by token, an order by number, a cache entry by URL. Counting occurrences, deduplicating a stream by key, joining two collections on a shared identifier. The domain asks what belongs to this exact key, and nothing about sequence or proximity.

WarningWhen it’s a guess dressed as engineering

Order taken from the map. A file records it and a test asserts it, so the next capacity change turns the diff into noise and the failure into an intermittent one.

Range queries cost a full O(n) scan: a hash has no proximity to exploit, so “all users from A to M” reads every entry. Mutable keys rot in place: change a hashed field after insert, and the entry becomes unreachable and undeletable.

TipThe faithfulness test

Is lookup by exact key the only access pattern — and is “no meaningful order” a domain fact or an oversight?

  • If yes → the map is the domain’s index. Check that keys stay immutable while stored, and that the uniqueness it enforces is the domain’s rule.
  • If no → you need order or range, which a hash cannot answer. Use an ordered index, and keep the map only where exact lookup pays.
  • If you can’t answer → unclear. You haven’t found the map wrong — you’ve found incomplete domain knowledge. List the queries the domain asks, then the order it presents results in.

Case study: Hash set (the membership contract)

Construct: A hash set answers one question: is this value in the collection? Membership, insert, and delete are O(1) expected. There is no index, no position, no count per value, no second copy — inserting a value already present changes nothing and reports nothing. It predicts that membership is the only question, duplicates are not distinct facts, and order is not a fact.

The data-structure knowledge gap it signals

The set stores one fact per value — presence — and drops multiplicity and sequence. Correct where the domain asks only whether something is present, and a silent rewrite where two identical arrivals are two events.

The gap question: what does the domain do when the same thing arrives twice?

ImportantWhen the domain mandates it

Membership as the whole question. Deduplicating event ids so a retried delivery is processed once. A permission check against granted roles. Tags on an entity, where a repeated tag is the same tag. Here the domain has no multiplicity and no order, and the type states that.

WarningWhen it’s a guess dressed as engineering

Duplicates the domain keeps apart. Two identical line items are two items: quantity, a unit price, a customer decision to buy twice. The set merges them, the total is half, and the bug looks like arithmetic rather than representation.

A set standing in for a relation the domain enumerates in order. Grants are fine unordered; the audit log of when each was granted is not. Or two records share a key, the set calls them one member because equality is defined on that key, and a dedup rule nobody stated is now in force.

TipThe faithfulness test

Did the domain decide that two identical submissions are one fact?

  • If yes → they are one fact. Check that the equality the set uses is the domain’s identity rule.
  • If no → membership is the wrong question. You need multiplicity, or distinct entities with their own identity, and a set carries neither.
  • If you can’t answer → unclear. You haven’t found the set wrong — you’ve found incomplete domain knowledge. Ask what the domain does when the same thing arrives twice.

Case study: Sorted array

Construct: A sorted array keeps keys in order in one contiguous block: binary search O(log n), range scan O(log n + k), random access O(1), and insertion or deletion O(n), because every later element shifts. The prediction is that order is a property of the data, and that writes are rare enough to pay for in bulk.

The data-structure knowledge gap it signals

The choice assumes that reads dominate writes, that order is a domain fact rather than a display preference, and that the working set fits one block. The gap question is the measured write rate against the read rate, and who owns the order when a write does arrive. A sorted array with an unasked question behind it is a sort nobody consumes.

ImportantWhen the domain mandates it

Reference data rebuilt in batch: price lists, tax brackets, ranking tables, leaderboards recomputed by a job. Writes happen inside the batch that owns them, reads hit a finished artifact, and the same array serves an ordered report without a second structure. The batch interval is the staleness the domain accepted when it scheduled the rebuild.

WarningWhen it’s a guess dressed as engineering

Interleaved inserts on a live stream: at 100,000 rows and a thousand writes a second, the shifts are 10⁸ element moves a second, spent preserving an order nothing asked for. The seductive version keeps the invariant by hand — two code paths inserting “in the right place”, a background re-sort, a flag asserting the array is sorted. Sortedness then becomes a distributed invariant with no owner, holding until one writer appends and forgets.

TipThe faithfulness test

Measured, do reads dominate writes — and is one owner named for the sort?

  • If yes → the order is a domain property and one owner holds the writes. Check the rebuild interval against the staleness reads tolerate.
  • If no → say which half failed. No owner: name one. Writes outrun reads: the sort is decoration — a hash map or a tree pays less.
  • If you can’t answer → unclear. You haven’t found the array wrong — you’ve found incomplete domain knowledge. Count peak inserts per second, then count the code paths that write.

Case study: Binary search tree (unbalanced)

Construct: A binary search tree orders keys by construction, so search, insert, and delete cost O(h) in the height h, and a full traversal costs Θ(n). The O(log n) claim holds only while the height stays a small multiple of log₂ n, and the height is not a property of the algorithm. It is a property of the order the keys arrived in.

The data-structure knowledge gap it signals

The domain must say what insertion order looks like: a sequence, a migration, a sorted export, a replay of an ordered log, or users typing. Uncorrelated input keeps the height a small multiple of log₂ n, in expectation; the bound is probabilistic, so the structure is knowledge. If the domain ever emits keys in order, the bound fails, and it fails silently. The gap question is the worst realistic insertion order, not the average.

ImportantWhen the domain mandates it

Keys genuinely arrive uncorrelated with their order: random identifiers, hashes, names typed by people. Writes and reads interleave, ordered traversal is used, no single writer controls the sequence, and the tree delivers its bound with two pointers per node — cheaper to build and to restructure than a balancing variant.

WarningWhen it’s a guess dressed as engineering

Sorted or sequential input: auto-increment identifiers, timestamps, a sorted CSV import, a replay of an ordered log. Bulk-loading sorted data builds a spine instead of a tree: every operation degrades to O(n), and a recursive insert can exhaust the stack. It passes every test, because the fixtures are shuffled; production feeds it what the database returns, ordered by primary key. The complexity claim was never earned, only assumed from the name.

TipThe faithfulness test

Is the insertion order under your control — no import, no migration, no sequential id that could arrive sorted?

  • If yes → the bound is earned. Trace each input path once for correlation, then leave the tree unbalanced.
  • If no → the bound is not delivered: the order arrives. Balancing is the repair, and it costs the pointers and rotations the unbalanced case was avoiding.
  • If you can’t answer → unclear. You haven’t found the tree wrong — you’ve found incomplete domain knowledge. Instrument the depth in production, and sample the insertion sequence.

Case study: Self-balancing binary search tree (AVL, red-black)

Construct: A self-balancing tree restores its own height after every write: AVL keeps child heights within one and rotates on violation, red-black keeps a colour and rotates less often for a looser bound. Both give O(log n) worst case for search, insert, and delete under any insertion order, paid for in per-node bookkeeping and rotation work on the write path.

The data-structure knowledge gap it signals

The domain must say whether input order is outside its control — user-supplied keys, imports from unknown sources, an adversary choosing keys to degenerate the tree — or whether a latency bound is a requirement someone signed. The gap question is whether that input can occur, and whether the guarantee was ever stated rather than assumed.

ImportantWhen the domain mandates it

Ordered maps and sets whose contract requires any input to work: C++ std::map, Java TreeMap. Any input, guaranteed logarithmic bounds, ordered iteration available. Key spaces an untrusted party contributes to also qualify.

WarningWhen it’s a guess dressed as engineering

A red-black tree hand-rolled for a 5,000-key table whose insertion order the team could have declared, so the balance covers a risk nobody tested for. The policy covers a risk the domain excludes, and it is paid for in rotation logic that must be right.

TipThe faithfulness test

Can adversarial or sorted input actually occur here — or is the worst-case guarantee a requirement someone stated?

  • If yes → the balance is knowledge. Record the threat or the bound that demanded it, next to the structure.
  • If no → unrequested insurance. Compare a sorted array for read-mostly use, a hash map for unordered lookup, and a heap when only the extreme is read.
  • If you can’t answer → unclear. You haven’t found the tree wrong — you’ve found incomplete domain knowledge. Find who required the bound, then measure the input order.

Case study: B-tree

Construct: A B-tree is a balanced multi-way search tree whose nodes hold many sorted keys, sized to the storage block. Height is log base b of n, so a billion keys at b = 500 sit three or four levels deep, and linked leaves make a range scan a sibling walk rather than a re-descent.

The data-structure knowledge gap it signals

Two facts must exist for the width to be knowledge: the actual transfer unit of this medium, and a measured volume that made memory insufficient. Without them the node size is a copied constant. The gap question is what this medium transfers per read, and what measurement showed the working set no longer fits in RAM — a B-tree over data that does fit pays for an I/O it never performs.

ImportantWhen the domain mandates it

On-disk indexes and databases: SQLite, PostgreSQL, InnoDB, LMDB. Wide shallow trees matched to the block amortize one read across hundreds of keys.

WarningWhen it’s a guess dressed as engineering

B-trees over in-memory data, justified by borrowed authority: databases use B-trees, so the service uses one for a 5,000-entry lookup table that fits in 400 KB of RAM. In memory the unit is a 64-byte cache line. A 4 KiB node spans 64 of them, so each comparison jumps to an address the CPU did not fetch. A sorted array reads one contiguous pass. The second trap is sizing carried across media: disk reasoning applied to flash, or a 16 KiB node inherited from a database default on a device that reads 4 KiB, so each node read is four transfers.

TipThe faithfulness test

Is the node width matched to this medium’s measured transfer unit — and has a measurement shown the working set no longer fits in memory?

  • If yes → the width is knowledge. Size the node to the unit; the height then follows arithmetically.
  • If no → say which fact is missing. Width unmatched: size the node to the transfer unit. Working set fits: an in-memory array is cheaper than an I/O you never make.
  • If you can’t answer → unclear. You haven’t found the B-tree wrong — you’ve found incomplete domain knowledge. Measure the read transfer size, then the working set, then compare against RAM.

Case study: Heap / priority queue

Construct: A binary heap is a complete tree flattened into an array, each parent no greater than its children. Reading the extreme is O(1); inserting and extracting it are O(log n). That is the whole contract: arbitrary lookup is O(n), arbitrary removal is O(n) without a side index, and iteration has no meaningful order.

The data-structure knowledge gap it signals

The heap claims what the domain does next, and urgency is a domain decision before it is a number. Someone must state the rule that produces the priority: deadline, severity, cost, distance. The gap question is whether extracting the most urgent is the actual access pattern, and who defines urgency, with what rule. A heap over an unowned priority function is a precise machine for ordering a decision nobody made.

ImportantWhen the domain mandates it

Schedulers and timers taking the earliest deadline first. Shortest-path frontiers in Dijkstra and A*, where the next node is the closest unsettled one. A stream of unknown length with only some extractions, where the heap beats sorting it whole.

WarningWhen it’s a guess dressed as engineering

A heap where the domain also needs arbitrary lookup or removal: cancel job 4471, raise the priority of 812. The missing index costs a hash map from identifier to array position, kept in sync on every swap. The other trap is priority numbers invented without a stated rule: an integer some caller increments, faithfully ordered by a heap, producing a correct maximum of a meaningless quantity.

TipThe faithfulness test

Is “extract the most urgent” the actual access pattern — and who defines urgency, with what rule?

  • If yes → the heap is the service rule made executable. Confirm the priority function is documented and owned.
  • If no → the operations are not a priority queue. Ordered access wants a balanced tree; exact lookup wants a map.
  • If you can’t answer → unclear. You haven’t found the heap wrong — you’ve found incomplete domain knowledge. Ask for the rule that assigns the number, then measure how often a middle element is needed.

Case study: Trie / prefix tree

Construct: A trie consumes one symbol of the key per level, so the path from the root spells the key and every prefix is a node on that path. Lookup is O(m) in key length, independent of how many keys are stored, and a prefix query is a subtree walk rather than a scan.

The data-structure knowledge gap it signals

Every other structure treats a key as an atom; the trie treats it as a sequence, which is worth paying for only if something asks about the sequence. The domain must have a feature whose semantics are prefix matching, and it must own what a prefix is. The gap question is whether the domain queries prefixes or only whole keys — and which feature does it.

ImportantWhen the domain mandates it

Longest-prefix match in routing tables, where the answer is deliberately not an exact key. Search-as-you-type autocomplete, where each keystroke is a prefix query. Spell correction, where a trie prunes whole subtrees on a prefix mismatch. The caller asks for “everything starting with”, and the trie answers in O(m + k) — key length plus matches — instead of scanning.

WarningWhen it’s a guess dressed as engineering

A trie serving exact lookups only: a hash map answers in O(1) with one entry, not a node per character. The trie instead pays one node per character position: ten million forty-character keys is up to four hundred million nodes against ten million entries, each a separate allocation and a cache miss. It is seductive because it is the structure that sounds chosen deliberately.

TipThe faithfulness test

Does a named feature query by prefix rather than by whole key?

  • If yes → the trie is knowledge. Name the feature; fix the alphabet and the prefix semantics in one place.
  • If no → exact lookup wants a hash map; ordered access wants a sorted array or a balanced tree.
  • If you can’t answer → unclear. You haven’t found the trie wrong — you’ve found incomplete domain knowledge. List the operations the callers perform, and see whether any is a prefix query.

Case study: Adjacency list vs adjacency matrix

Construct: A matrix keeps one bit per ordered pair: an edge test is one array index, O(1), and enumeration is Θ(n) whatever the degree. A list keeps only the edges that exist: Θ(n + m) space, O(deg) enumeration, and O(deg) membership unless a hash set is added.

The data-structure knowledge gap it signals

The domain must have decided whether the relation is sparse, and which query dominates.

The gap question: how many edges per node, and is the hot query enumeration or membership?

ImportantWhen the domain mandates it

The relation is local and sparse, counted: a follow graph, a dependency graph, a road network. Then Θ(n + m) space and O(deg) enumeration match the traversal the code performs. The matrix earns its n² when the relation is dense and small (a 200-node role matrix is 40,000 cells) or when every query is all-pairs.

WarningWhen it’s a guess dressed as engineering

The matrix arrives because it is the textbook first representation and “O(1) edge lookup” sounds strictly better. On a sparse graph it spends n² on a density claim nobody checked, while the enumeration the application actually runs gets slower. The mirror error is a list for a dense graph whose hot query is membership, where each test scans a neighbour set a matrix answers in one index.

TipThe faithfulness test

Is the relation sparse, counted — and is the hot query enumeration rather than membership?

  • If yes → both facts are known, and the choice follows. The matrix’s n² and the list’s n + m are now arithmetic, not preference.
  • If no → the matrix’s case applies: dense or all-pairs. Count the degree distribution, then read the query log.
  • If you can’t answer → unclear. You haven’t found the representation wrong — you’ve found incomplete domain knowledge. Measure average and maximum degree, then count each query type.

Case study: Union-find (disjoint sets)

Construct: Union-find keeps one parent pointer per element and answers “same group?” by walking to a representative. Only the roots are representatives, and no roster per set is kept. Two tricks — join the shorter tree under the taller one, and point each walked path straight at the representative — make each operation effectively constant on average. It encodes three claims: connectivity is the only question, groups are compared and never listed, and merges only arrive.

The data-structure knowledge gap it signals

The domain must have decided that a group is only ever compared, never named or listed.

The gap question: is a group something the domain needs to enumerate, or to undo?

ImportantWhen the domain mandates it

Connectivity questions where the group is only compared: are these two hosts in the same network segment, are these two records the same person, would this edge close a cycle in Kruskal’s forest. The representative is all the domain asked for, and storing nothing else is what keeps the operations cheap.

WarningWhen it’s a guess dressed as engineering

The structure is chosen for “sets” and then the sets are needed. Listing a group’s members means walking every element to find those sharing a root — linear per query, because the roster the domain wanted was never maintained. Splitting is worse: union-find has the merge and not its inverse, so a domain that later both merges and separates — account un-merges, cluster re-sharding — finds half its operations unimplemented.

TipThe faithfulness test

Is connectivity the only question — nobody listing members, nobody splitting a group?

  • If yes → union-find is the knowledge. Record that merges are one-directional.
  • If no → it is the wrong contract. Use a structure that maintains membership, or one that supports splits.
  • If you can’t answer → unclear. You haven’t found union-find wrong — you’ve found incomplete domain knowledge. List every operation the domain will ask for, including the inverse ones.

Case study: Bloom filter

Construct: A Bloom filter is a bit array with k hash functions: an insert sets k bits, and a query answers “definitely absent” or “maybe present”. Space follows m = −n ln p ÷ (ln 2)², so 1% costs 9.6 bits per key. A false negative is impossible and a false positive is expected.

The data-structure knowledge gap it signals

The domain must have decided that a wrong “maybe” is caught downstream by something authoritative, and the rate it can absorb — 1% costs 9.6 bits per key, 0.1% costs 14.4, half again the memory for ten times fewer false positives.

The gap question: which error can the domain absorb, and does the correcting lookup exist?

ImportantWhen the domain mandates it

Skipping an expensive lookup for the keys that are absent: a cache consults the filter before the disk read, a blocklist before the network call. At a 10% hit rate, nine calls in ten are saved by a bit test, and the store still holds the truth for every maybe-present case.

WarningWhen it’s a guess dressed as engineering

The filter is read as truth: “it says maybe-present, so we stored it” inverts a one-sided guarantee into a claim the structure never made. A workload that deletes has no operation to use, since clearing bits creates the false negative the structure guarantees. And m and k chosen by feel leave the error rate unknown, so the rate in the design note is a number nobody can reproduce.

TipThe faithfulness test

Can the domain absorb a bounded false-positive rate — and does an authoritative lookup correct a false positive?

  • If yes → the filter is knowledge: the error is bounded and corrected. Check the measured rate against the design false-positive rate p.
  • If no → say which half failed. No correction path: every maybe is a wrong answer. No accepted rate: state p, then check the lookup.

Case study: Skip list

Construct: A skip list layers sorted linked lists, each level skipping more than the one below, so search, insert, and delete cost O(log n) expected and a node’s level is drawn at random when it is inserted. An update touches a bounded neighbourhood instead of rotating a subtree, which is what makes fine-grained and lock-free variants practical.

The data-structure knowledge gap it signals

The randomized level is the price of a localized update, and it is only worth paying where concurrent writers contend. The tail is real: expected O(log n) still permits an unlucky run of levels.

The gap question: is concurrent insertion the requirement, and does the budget accept a probabilistic worst case?

ImportantWhen the domain mandates it

Concurrent ordered maps where lock granularity dominates. An in-memory database’s sorted set, a storage engine’s in-memory write buffer absorbing writes from many threads: there the short, local update is why randomization is accepted, and lock-free implementations exist because the structure permits them.

WarningWhen it’s a guess dressed as engineering

Single-threaded ordered access, where a balanced tree or a sorted array is simpler, deterministic, and has no probability to reason about — the trade has nothing on the other side. Or a hard latency bound: the SLO (service-level objective) is written as a maximum and the structure guarantees an average, so passing that SLO rests on luck nobody budgeted for. The trap is seductive because the average is excellent and every benchmark passes.

TipThe faithfulness test

Is concurrent insertion the actual requirement — and does the latency budget accept a probabilistic worst case?

  • If yes → the skip list is knowledge. Keep the level probability and seed policy beside it.
  • If no → say which half failed. No concurrent writer: it is ornament. Hard maximum latency: keep one writer’s order and a deterministic bound.
  • If you can’t answer → unclear. You haven’t found the skip list wrong — you’ve found incomplete domain knowledge. Measure contention on the write path, then state the bound as a maximum or a percentile.

Case study: LRU cache

Construct: An LRU cache keeps a hash map beside a doubly linked list, so lookup, insert, and move-to-front cost O(1) and the least recently used entry leaves first. The eviction order is a belief about the domain made mechanical: every eviction spends the prediction “recency implies reuse”.

The data-structure knowledge gap it signals

The domain must have decided that a record touched now is likelier to be touched again than one touched an hour ago, and that the working set fits. A proxy is knowledge only when a measured trace supports it — and this one fails silently.

The gap question: is there a measured trace, or only a belief about recency?

ImportantWhen the domain mandates it

Workloads with real temporal locality: a hot configuration read on every request, recently touched records within a session, a working set that fits and stays. There recency tracks reuse and the hit rate settles where capacity predicts.

WarningWhen it’s a guess dressed as engineering

A small set of keys used constantly, evicted behind a burst of one-off reads: the case LFU — evict the least frequently used — answers and recency does not. Or a hit rate nobody measures, so capacity is set by intuition dressed as tuning.

TipThe faithfulness test

Is there a measured access pattern showing recency predicts reuse — and is the hit rate watched?

  • If yes → the policy is knowledge: the trace supports it. Watch the hit rate for drift, and check the miss cost against the fetch it avoids.
  • If no → say which half failed. No trace: recency is a belief being paid for. Trace but no metric: watch the hit rate before judging the policy.
  • If you can’t answer → unclear. You haven’t found the cache wrong — you’ve found incomplete domain knowledge. Record the hit rate, then replay a trace to compare LRU with LFU and with no cache.

Case study: Ring buffer (circular buffer)

Construct: A ring buffer allocates N slots once and advances a head and a tail, so push and overwrite cost O(1) and memory is bounded by construction. The write that arrives at a full buffer destroys the oldest slot without asking. It encodes one fact and one policy: only the last N matter, and anything older is disposable.

The data-structure knowledge gap it signals

The domain must have decided how far back retention reaches, and who is allowed to lose data as a result. N is not a tuning constant — it is the answer to “how long is the history the domain uses”, written once and enforced silently.

The gap question: what is the longest window any consumer of this buffer needs?

ImportantWhen the domain mandates it

Telemetry windows where consumers read recent values and only the aggregate survives. Bounded hand-off queues where the producer must never block and dropping the oldest is the stated policy. There N comes from the sampling rate and the interval the domain asks about, so the loss is designed behaviour.

WarningWhen it’s a guess dressed as engineering

N chosen by feel, and then the auditor arrives asking for event 4000 — retention was a domain question all along, answered by whatever constant was in the example. Or overwrite treated as a technical detail, when it is a data-destruction policy nobody stated. The queue then drops evidence exactly when the producer outruns the consumer — which is when evidence matters most.

TipThe faithfulness test

Can someone name the domain rule that set N — and does it say an event older than N loses its meaning?

  • If yes → the buffer is knowledge. Record the rule beside the size, then check N against the slowest consumer.
  • If no → it is a guess. Dropping data is a decision; name the decision or change the structure.
  • If you can’t answer → unclear. You haven’t found the buffer wrong — you’ve found incomplete domain knowledge. Measure the arrival rate, then find the longest window any consumer needs.

Case study: Persistent (immutable) structures

Construct: A persistent structure never mutates in place. An update returns a new version that shares the unchanged bulk with the old one, so the old version stays valid and every observation reads one version, from a single point in time. The contract it encodes: versions are first-class, and readers outnumber writers enough that the sharing pays.

The data-structure knowledge gap it signals

The sharing pays on the read path and costs on the write path: every update allocates, and navigation gains a level of indirection. For the choice to be knowledge, the reader/writer ratio must be measured rather than assumed.

ImportantWhen the domain mandates it

Domains where the version is a fact. A quote is a revision nobody may overprint. A payroll run must reproduce the state it paid. A document store serves many revision readers while few authors produce them. There the structure only stops the code from destroying a state the domain already keeps.

WarningWhen it’s a guess dressed as engineering

A write-heavy workload with no version requirement: counters, sessions, position updates, each update allocating and sharing state nobody will read. The sharper trap is confusing persistent with durable. Persistent means old versions stay reachable in memory; durable means bytes survive a crash. A persistent structure gives no durability, a durable store gives no version semantics — and reaching for one to get the other leaves the real promise unimplemented.

TipThe faithfulness test

Does the domain ask for old versions — and is the reader/writer ratio measured rather than assumed?

  • If yes → the version is a domain fact and the structure is the code catching up. Check the write-path allocation budget next.
  • If no → say which half failed. No version reader: a mutable structure, with durability from the store. Ratio unmeasured: measure it before dropping the sharing.
  • If you can’t answer → unclear. You haven’t found the structure wrong — you’ve found incomplete domain knowledge. Name the feature that reads an old version, then count reads per write over a day.

Case study: Append-only log (event store)

Construct: An append-only log records facts in order and derives the current state by replaying them in order. Writes are sequential appends; reads are replays or snapshots built from replays. The contract it encodes: history is a domain fact, the present is derived from it, and that derivation can be recomputed only while the replay is deterministic.

The data-structure knowledge gap it signals

Derivation is only correct if the fold is deterministic, and it is only worth its cost if someone queries the past. The gap question is whether the past is asked about in domain terms — a dispute, a traceability requirement, a temporal query — rather than in debug terms.

ImportantWhen the domain mandates it

Ledger and audit domains. A payment ledger’s history is the asset and the balance is a view; dispute resolution asks exactly what the log keeps. Event sourcing fits where the business rule is temporal: what did we believe on 3 March, and on what record.

WarningWhen it’s a guess dressed as engineering

Log-first architecture where only the current state is ever queried. Rebuild jobs, snapshot tables, replay tooling and versioned event schemas are built, and no query ever reads the history back. Two symptoms follow. Unbounded growth with no retention rule, because nobody decided what the log is for, so nothing may be deleted. And replay time never measured at real scale, so an eleven-hour rebuild at today’s volume is discovered in the first incident.

TipThe faithfulness test

Does anyone ask about the past in domain terms — and are the retention and replay costs known at this size?

  • If yes → the past is asked about and the fold is deterministic. Record the retention rule and the measured rebuild time.
  • If no → measure before you choose. Nobody asks about the past: keep the latest row. Someone does: time a full replay and state the retention rule.
  • If you can’t answer → unclear. You haven’t found the log wrong — you’ve found incomplete domain knowledge. Name one product question that needs a past state, then time a full replay on a copy of production.

Case study: Bitmap (bitset)

Construct: A bitmap stores one membership flag per key, addressed by position. The key’s value is the array offset, so the structure encodes two claims: the universe of keys is small and dense, and the universe is closed. Set algebra then runs word-parallel, and intersection costs one AND per word.

The data-structure knowledge gap it signals

For the bitmap to be knowledge, the domain must have fixed the id space as dense and bounded, and a rule someone can state must close it. Density is a measurement: distinct keys divided by universe size.

ImportantWhen the domain mandates it

Dense id spaces with a bounded universe. Feature flags per tenant on sequential ids, presence per seat, permission bits per role, compressed bitmaps over analytics filters where the container adapts to local density. The arithmetic is then real: ten million seats is 1.25 MB, and a segment intersection is a handful of instructions.

WarningWhen it’s a guess dressed as engineering

A bitmap over a sparse id space, where ids are global snowflake values and the array is sized by the largest one. The seductive version is a universe that grows without bound, fed by an auto-incrementing sequence: the structure assumes it is closed, no rule closes it, and the array doubles forever. Compressed bitmaps soften the first case but not the second — the boundary is still a prediction.

TipThe faithfulness test

Is the id space dense, counted — and is the universe closed by a rule someone can state?

  • If yes → the bitmap is the arithmetic of the domain. Check how fast the largest id grows next.
  • If no → a hash set stores the keys you have, at a few bytes each, and allocates nothing for keys you don’t.
  • If you can’t answer → unclear. You haven’t found the bitmap wrong — you’ve found incomplete domain knowledge. Count distinct ids against the maximum id over a week.

Case study: Inverted index

Construct: An inverted index maps content to the records that contain it. It reverses the direction of the question: not what is in record X, but which records mention X. The contract it encodes: the domain looks up by content, not by identity, and that direction is the common one.

The data-structure knowledge gap it signals

Every index is a bet on a query. Each indexed field pays write amplification — one insert becomes several index writes — and storage, and collects only if a query reads the posting list it wrote. So the domain must supply a list of named queries, one per indexed field.

ImportantWhen the domain mandates it

Search is a product feature: term to documents, with the ranking and matching the product promises. Tag lookups where the reverse direction is the requirement, such as every open ticket tagged billing. Faceted filtering over a catalog, where the filter set is chosen by the user at query time and cannot be known in advance.

WarningWhen it’s a guess dressed as engineering

Indexing attributes nobody searches. A search box arrives, every text column is indexed, and no query ever reads those postings. The sharper trap is a single-key exact lookup dressed as search: one field, one value, no relevance, no analysis. A B-tree answers it in one read. The search engine adds a cluster, a tokenizer and a lag before a write is visible, none of which the lookup asked for.

TipThe faithfulness test

Does every indexed field answer an exact query named from real usage?

  • If yes → the index is the query’s shadow. Check the write cost it adds per inserted record next.
  • If no → the field is stored, not indexed. An exact single-key lookup belongs in a B-tree.
  • If you can’t answer → unclear. You haven’t found the index wrong — you’ve found incomplete domain knowledge. Collect the query log for a week before adding a field.

Case study: Interval tree

Construct: An interval tree indexes spans so that an overlap query returns the intersecting set without a scan. The contract it encodes: ranges are first-class queries — which bookings overlap this slot, which tariff applies at time T, what is the sum over this window.

The data-structure knowledge gap it signals

Overlap machinery beats a scan only when the ranges genuinely overlap and the queried ranges are narrower than the collection. Both are measurable. The domain must also produce range queries from a real feature, not a boundary that a caller happens to pass.

ImportantWhen the domain mandates it

Calendars and bookings, where conflict detection is the product requirement and the answer is a set, not a flag. Layered tariff windows — a promotional rate over a base rate — where one instant matches several rates at once. Range aggregates over numeric series, such as a dashboard summing a month of readings without reading the whole series.

WarningWhen it’s a guess dressed as engineering

Two traps. The first is non-overlapping intervals: tariff windows sorted by start answer “which applies at T” with one binary search, yet the overlap structure is built, tested, and never consulted. The last is a range index queried only at startup, where the build cost is never amortized.

TipThe faithfulness test

Do queries arrive as ranges from a named feature — and do the intervals genuinely overlap, counted?

  • If yes → the index matches the shape of the question. Measure the overlap fraction next.
  • If no → a sorted array and a binary search answer point and non-overlapping lookups with less machinery.
  • If you can’t answer → unclear. You haven’t found the interval tree wrong — you’ve found incomplete domain knowledge. Sample the query arguments and count how many pass distinct bounds.

Case study: Columnar layout

Construct: A columnar layout stores the values of one column together. The contract it encodes: analytics reads a few columns over many rows, whole-row access by key is rare, and appends dominate updates. Compression follows from the layout, because a column holds one type and often similar values.

The data-structure knowledge gap it signals

The access shape decides the physical layout, and that shape is measured from the query mix. The gap question is concrete: how many columns does the average query project, and how many rows does the average write touch?

ImportantWhen the domain mandates it

OLAP (analytical) scans and aggregations over few columns — a monthly revenue rollup reading four columns of a wide fact table. Per-column compression the layout makes possible: runs of equal values, codes for repeated strings, small deltas between numbers — each valid because the column is homogeneous. Append-heavy time series, where the row is written once and read in slices.

WarningWhen it’s a guess dressed as engineering

Transactional row-at-a-time access. A point update must find the row in every column fragment, and a row read reassembles scattered pieces, so the row stops being the unit of work. The seductive version is choosing columnar because analytics is in the future: the mix is a forecast, not a measurement, and the transactional path pays today for a report that may never be written.

TipThe faithfulness test

Measured on real queries: few columns over many rows, whole-row reads rare, updates rare?

  • If yes → the layout matches the access. Record the average columns projected per query next.
  • If no → a row store serves the unit of work. Add a columnar replica for the analytical path.
  • If you can’t answer → unclear. You haven’t found the layout wrong — you’ve found incomplete domain knowledge. Log the statements for a week and count columns projected against rows touched.
