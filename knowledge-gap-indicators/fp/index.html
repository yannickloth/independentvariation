Functional Programming as Knowledge-Gap Indicators

A list of short posts that read each pattern as a completeness check on domain knowledge.

Almost every design pattern/principle can be used as a completeness-check on domain knowledge. For FP typeclasses and algebraic structures, the mathematics (laws, coherence, composability) is the instrument; domain knowledge is why we reach for it. The domain-knowledge lens asks whether the construct encodes domain structure.

Pick a post on the left. It opens on the right.

Case study: Monad Pattern

Yorgey (Typeclassopedia): A monad sequences computations in a context, binding each result into the next. [1]

The domain knowledge gap it signals

Some operations have structured non-value outcomes a domain expert would reason about: “can return nothing,” “can fail with a domain error,” “depends on flowing context,” “must run in an order the world fixes.” In FP this knowledge lives in the underlying type — Maybe, Either, Reader, IO/Task — and the Monad pattern composes these outcomes so downstream computations respect them. (The monadic interface — bind/flatMap — is the generic machinery; the domain carrier is the underlying type.) Effect sequencing is knowledge too: write-before-acknowledge is an audit obligation; acquire-then-release is a resource fact.

ImportantWhen it’s applicable (cohesion-increasing)

The domain recognizes structured non-value outcomes — Maybe for “result or nothing,” Either for “domain error,” Reader for “shared context,” IO/Task for “fixed order.” The monad closes the gap: without it, every call site writes its own if-null or if-error branches and hand-rolls the sequencing, scattering failure handling and ordering obligations across code that shouldn’t own them.

WarningWhen it’s inapplicable (cohesion-reducing)

The inapplicable case is monadic structure with no knowledge behind the outcome. Wrapping absence the domain treats as presence in Optional improves the type contract but encodes a distinction no expert makes; an unrecognized error or unfixed order does the same. There is no knowledge-free half of this split — if nobody can name the condition or obligation behind the structure, the monad hides the gap instead of closing it.

TipThe faithfulness test

Can you name the knowledge behind the structure — the condition for “no result” or “this error,” or the obligation that fixes the order?

  • If yes → applicable. The underlying type is the code catching up — the monad instance keeps those semantics composed.
  • If no → inapplicable. The type contract may still improve, but the structure encodes a distinction no condition or obligation asked for.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Functor

Yorgey (Typeclassopedia): A functor is a type constructor whose values can be mapped over. [1]

The domain knowledge gap it signals

The fact that a domain transformation must be lifted into a context — that the operation happens inside a container or effect, and the container’s structure must be preserved — is domain knowledge. If your domain model already crystallizes that “every field in this validated form must be transformed to canonical form without discarding validation failures,” then Functor is just embodying that knowledge. The map operation is the domain’s own “transform the contents, preserve the context” rule.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that transformations respect the container’s semantics: validation errors must propagate, absent values must remain absent, list structure must survive item-wise transformation. Functor closes the gap: it prevents every call site from pattern-matching on the container to extract, transform, and re-wrap — scattering “how to reach inside” knowledge across the system. The structure survives; only the values transit.

WarningWhen it’s inapplicable (cohesion-reducing)

The “context” is not a domain container — it’s a data-transfer wrapper whose transformation always produces a trivial result. Mapping over a wrapper whose sole purpose is to carry a value through middleware adds an abstraction layer for an operation that could be a direct function call. The functor interface signals “this container has transformation semantics” when the container has none beyond transport. If every map call is immediately followed by extraction, the functor was never doing work the domain needed.

TipThe faithfulness test

Does the domain recognize that the container’s structure is separate from the values it holds — and that preserving the structure through transformations matters?

  • If yes → applicable. Functor is the code catching up to the knowledge.
  • If no → inapplicable. The container is wrapping for transport — the functor interface adds an abstraction layer the domain didn’t call for; a direct extraction-then-transform achieves the same effect.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Applicative

Yorgey (Typeclassopedia): An applicative functor applies a function inside a context to values in the same context. [1]

The domain knowledge gap it signals

The fact that multiple independent computations must combine — and that the combination preserves each computation’s failure independently while gathering all results — is domain knowledge. If your domain model already crystallizes that “validating a form means checking name, email, and address independently; all failures must be collected, not just the first one; a valid form requires all three to succeed,” then Applicative is just embodying that knowledge. The apply/zip operation is the domain’s own independent-validation-then-combine rule.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that multiple computations are independent — their results have no dependency on each other, and the combination is a domain-recognized aggregation. Applicative closes the gap: it prevents each call site from manually sequencing then combining, which would couple unrelated computations together. A form validator that chains name → email → address with flatMap would short-circuit on the first failure; Applicative collects all failures, matching the domain’s own “tell me everything that’s wrong” requirement.

WarningWhen it’s inapplicable (cohesion-reducing)

The computations are not independent — they form a sequential pipeline where each step depends on the previous. Using Applicative where computations are dependent imposes a structure the domain doesn’t support: the same domain logic would be more clearly expressed with monadic sequencing (flatMap). The code signals “these operations are independent” when they form a natural pipeline.

TipThe faithfulness test

Would a domain expert describe these computations as independently checkable — and would collecting ALL failures (not just the first) match the domain’s own reporting requirement?

  • If yes → applicable. Applicative is the code catching up to the knowledge.
  • If no → inapplicable. The computations depend on each other, and the parallel structure overstates the domain’s independence.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Fold / Reduce

Yorgey (Typeclassopedia): A fold reduces a structure to a single value by combining its elements. [1]

The domain knowledge gap it signals

The fact that a collection must be reduced to a single value — and that the reduction rule is a domain operation — is domain knowledge. If your domain model crystallizes that “total invoice value is the sum of line-item totals; the consolidated risk score aggregates individual exposure assessments; the merged document incorporates all section contributions,” then Fold embodies that knowledge. The accumulator function is the domain’s own combination rule; the initial value is the domain’s own neutral element.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that a collection resolves to a single result via a well-defined reduction rule. Fold closes the gap: prevents each call site from writing a loop with mutable state, which would scatter the reduction rule across the system and risk accidental mutation. The reduction rule is isolated — change “sum” to “max” or “weighted average,” and only the accumulator function changes, not every iteration site.

WarningWhen it’s inapplicable (cohesion-reducing)

The reduction rule has no domain semantics — it serves infrastructure needs where the result of the fold is invisible to the domain model. Counting elements for a progress bar, hashing a list for cache keys, or summarizing stream length for monitoring: these model infrastructure aggregation. Fold is a dual-use construct: when the accumulator and combination rule are domain-defined (total, aggregate, consolidate), it’s domain modeling; when they serve technical concerns, it’s infrastructure. The test discriminates the instantiation, not fold itself.

TipThe faithfulness test

Does the domain define the combination rule as a business operation — would a domain expert name the reduction (total, aggregate, consolidate, merge)?

  • If yes → applicable. Fold is the code catching up.
  • If no → inapplicable. It’s infrastructure aggregation — valid FP usage, but modeling a technical concern rather than a domain rule.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Lens

The domain knowledge gap it signals

The fact that an entity’s internal structure must be navigated and updated through a defined path — not through getters and setters — is domain knowledge. If your domain model already crystallizes that “a shipment’s destination city is accessed via order → fulfillment → address → city, and updating the city means replacing the address without touching the rest of the order,” then Lens is just embodying that knowledge. The lens is the domain’s own access path; the get/set/modify operations are the domain’s own nested-update rule.

ImportantWhen it’s applicable (cohesion-increasing)

The domain has deeply nested, immutable data structures, and domain operations target specific nested fields. Lens closes the gap: it prevents every call site from manually destructuring then reconstructing the nested path — which would scatter the structural knowledge (the shape of the order → fulfillment → address chain) across the system. The lens centralizes the access path; when the data structure changes (fulfillment moves to a different nesting level), only the lens changes, not every access site.

WarningWhen it’s inapplicable (cohesion-reducing)

The “nested path” is not a domain structure — it’s a wire-format projection. The developer builds lenses for a deeply nested JSON API response whose nesting reflects transport format, not domain semantics. Lenses remain a valid FP tool for nested immutable updates — the distinction is whether the nesting reflects domain semantics or transport format. Adding a lens library for wire-format shapes that change with API versions adds abstraction overhead the domain model doesn’t benefit from.

TipThe faithfulness test

Would the domain expert describe the access path using domain vocabulary — and would changing the nesting break something they care about?

  • If yes → applicable. Lens is the code catching up to the knowledge.
  • If no → inapplicable. It’s navigating API response shape — the nesting is wire-format detail.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Currying

Hughes: Currying turns a function of several arguments into a function that takes them one at a time. [2]

The domain knowledge gap it signals

The domain-knowledge lens for currying asks: when does staged parameter supply map onto a domain concept? If your domain model crystallizes that “a tax calculation needs the tax year, the jurisdiction, and the income amount — and these arrive from different domain events,” then Currying captures that knowledge. The partially-applied function represents “everything we know so far, waiting for the last piece.” Unlike structural patterns where the code IS the domain structure, currying is an encoding choice: a Builder expresses the same behavior, though it loses the compositional benefits.

ImportantWhen it’s applicable (cohesion-increasing)

The domain dictates that parameters are gathered across distinct phases: configuration is set at setup time, context is established at session start, and the operation parameter arrives at invocation. Currying closes the gap: prevents each call site from holding all parameters and passing them together, which would couple the final caller to what should already be resolved. The partially-applied function is a domain artifact — “everything we know so far, waiting for the last piece.”

WarningWhen it’s inapplicable (cohesion-reducing)

The parameters always arrive together — there is no domain stage where partial application is meaningful. Currying a function whose arguments are all available at the same call site signals temporal separation the domain never had. When currying’s value is purely computational (composability, type-class coherence), it’s sound FP practice with no domain connection.

TipThe faithfulness test

Setting aside currying’s type-theoretic and compositional benefits, does the domain ALSO have distinct phases of parameter gathering?

  • If yes → applicable. Currying is one faithful encoding — computational utility PLUS domain fidelity.
  • If no → inapplicable. It remains valid for partial application and composability.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Immutability

Hughes: Immutable values are never changed in place; a transformation yields a new value. [2]

The domain knowledge gap it signals

Immutability is unique: it is an FP baseline, not a pattern chosen from alternatives. Its primary justifications (referential transparency, equational reasoning, thread safety) are computational guarantees, not domain-specific rules. The domain-knowledge question is supplementary: when the domain ALSO mandates immutability, the construct gains additional justification. If your domain model crystallizes that “a ledger entry, once recorded, is never modified; corrections produce a new entry referencing the original,” then Immutability encodes domain knowledge on top of its computational benefits.

ImportantWhen it’s applicable (cohesion-increasing)

Immutability eliminates shared-mutable-state coupling by construction. When the domain also mandates append-only state (audit trails, event sourcing, ledgers), immutability closes the gap twice: it provides the computational guarantee AND matches the domain’s conceptual model.

WarningWhen it’s inapplicable (cohesion-reducing)

The domain has no concept of version history, AND the context is single-threaded with no concurrency concern, AND the data volumes make persistent-structure overhead a real cost. Enforcing immutability here serves neither domain modeling nor thread safety — the persistent data structure adds allocation and indirection for a domain that operates naturally with in-place mutation. A mutable approach is simpler in this narrow case, though the thread-safety and referential-transparency guarantees are sacrificed.

TipThe faithfulness test

In addition to the universal benefits of immutability, does the domain ALSO treat state transitions as append-only — would the domain expert describe updates as “creating a new version” rather than “changing the current one”?

  • If yes → applicable. Immutability is doubly justified — computational correctness PLUS domain fidelity.
  • If no → inapplicable. It remains valid for thread safety and referential transparency — FP’s default, not a mistake.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Higher-Order Function

Hughes: A higher-order function takes another function as an argument or returns one as a result. [2]

The domain knowledge gap it signals

An operation parameterized by another operation — a rule taking a rule as input — is knowledge. If your domain model crystallizes that “the discount policy varies by customer tier, and the order total applies whichever policy is in effect,” then Higher-Order Functions embody that knowledge; the function-accepting-function is the domain’s “supply the policy at call time” rule. The lens does not stop at the business layer: retry windows, audit logging, error recovery, and resource limits are knowledge too — failure modes, obligations, the operating environment. The question is never “domain or infrastructure.” It is whether named knowledge stands behind the parameterization.

ImportantWhen it’s applicable (cohesion-increasing)

The knowledge mandates the variation and requires the variant at the call site — a business policy (discount by tier, risk assessment) or an operational fact (retry this often; log it — audit demands it). They close the gap: the variant stops being scattered as if/else or switch branches inside the caller, which would couple the caller to every variant. The caller expresses “apply whatever rule you’re given” — the knowledge’s own delegation.

WarningWhen it’s inapplicable (cohesion-reducing)

There is no knowledge-free half of this split. HOFs are FP’s mechanism for ALL parameterized behavior. The inapplicable case is parameterization with no knowledge behind it: a caller that accepts a function “just in case” — a variation point no rule, obligation, or failure mode asked for. That coupling hard-codes a decision no knowledge has made.

TipThe faithfulness test

Can you name the knowledge that mandates the variation — the rule, failure mode, or obligation behind it?

  • If yes → applicable. The HOF is the code catching up — the parameter carries named knowledge to the call site.
  • If no → inapplicable. The variation point is speculative — coupling added before any knowledge demanded it.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Semigroup

Yorgey (Typeclassopedia): A semigroup is a type with an associative binary operation that combines two values. [1]

The domain knowledge gap it signals

The fact that two values of the same type can be combined — and that the combination is associative and produces another value of that type — is domain knowledge. If your domain model crystallizes that “two risk assessments combine into a composite risk; two budgets sum into a consolidated budget; two permission sets merge into a unified set,” then Semigroup is one encoding of that knowledge. The combine operation captures the domain’s merging rule; associativity means domain order doesn’t change the result. Unlike structural patterns where the code IS the domain structure, the typeclass is an encoding choice: a plain combine function gives the same runtime behavior, but the typeclass adds compile-time guarantees.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that entities of the same type compose into larger entities of the same type, with a closed, associative operation. Semigroup closes the gap: it prevents each call site from implementing its own combination logic, scattering the meaning of “combine these” across the system. One combine captures the domain’s merging rule.

WarningWhen it’s inapplicable (cohesion-reducing)

The combination is not domain-meaningful — it’s a data-marshaling convenience. Concatenating strings for logging, merging configuration maps, or combining statistics for a dashboard are infrastructure operations. The semigroup interface signals “these values compose into a meaningful whole” when the combination serves representation or transport, not domain semantics.

TipThe faithfulness test

Would a domain expert describe the combination as a domain operation — merging, summing, consolidating — and would they agree that the order shouldn’t matter?

  • If yes → applicable. Semigroup is one faithful encoding of the knowledge.
  • If no → inapplicable. The combination is technical aggregation — a plain function has the same runtime behavior but loses the typeclass’s compile-time guarantees.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Monoid

Yorgey (Typeclassopedia): A monoid is a semigroup with an identity element. [1]

The domain knowledge gap it signals

A type with a neutral element and closed associative combination is domain knowledge. If your domain model crystallizes that “zero is the neutral element for monetary amounts; an empty permission set is the starting point before merging,” then Monoid is one encoding of that knowledge. empty captures the domain’s identity; combine captures its associative merge. Unlike structural patterns where the code IS the domain structure, the typeclass is an encoding choice: a constant ZERO and a plain combine give the same runtime behavior, but the typeclass adds law-based reasoning and generic derivation.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates a type has a well-defined neutral element — a real value that does nothing under combination — and an associative combination rule. Monoid closes the gap: empty and combine give the canonical neutral element and merge, so no call site invents its own. This is powerful with Fold — folding a collection produces a domain aggregate with defined semantics for the empty case.

WarningWhen it’s inapplicable (cohesion-reducing)

The neutral value is not domain-defined — it’s an implementation convenience. A default configuration, empty logger, or zero-initialized counter are infrastructure neutrals. The monoid interface signals “this type has a mathematically meaningful identity” when the identity exists only to let fold handle empty collections without error. If the domain expert wouldn’t recognize the neutral value as a meaningful concept, the monoid formalizes infrastructure semantics, not domain rules.

TipThe faithfulness test

Would a domain expert name the neutral element — “zero balance,” “no permissions,” “empty order” — as a concept the domain itself uses?

  • If yes → applicable. Monoid is one faithful encoding of the knowledge.
  • If no → inapplicable. The neutral value is an implementation convenience — valid for generic programming and folding, but not a domain rule a domain expert would name.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Foldable

Yorgey (Typeclassopedia): A foldable structure is one whose elements can be combined into a single result. [1]

What Foldable actually is

Foldable answers one question: can I combine the elements of this thing into one value? The primitive is foldMap :: Monoid m => (a -> m) -> t a -> m. Two facts follow.

First, the fold is a reduction; iteration is only the derived case (toList is itself a foldMap). The result is one value of the monoid you choose — and m = [a] rebuilds the list, so a fold need not lose anything.

Second, the container varies while the element type is fixed. Maybe a and Either e a (Result) are Foldable too: foldMap f Nothing = mempty, foldMap f (Just x) = f x; foldMap f (Left e) = mempty, foldMap f (Right x) = f x. Foldable thus covers 0-or-1 elements too.

The domain knowledge gap it signals

The domain knowledge is the combining rule: which monoid, and which fold. If your domain says “line items total in order of entry,” Foldable just embodies it. The class fixes no order; direction belongs to the chosen fold and monoid, not to Foldable.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates a lawful way to combine the structure’s elements into one result. Foldable closes the gap: it keeps each call site from hand-writing a loop with mutable state, coupling the caller to the collection’s shape. When the structure changes (list to tree to stream), the fold is unchanged.

WarningWhen it’s inapplicable (cohesion-reducing)

Implementing Foldable for a structure whose domain meaning resists lawful combination, or whose traversal carries meaning that one collapse destroys. A state-machine graph, a dependency DAG, or a weighted decision tree resists it; a generic fold obscures their traversal semantics.

TipThe faithfulness test

Does the domain define a lawful combination of the structure’s elements into one result, and does one collapse lose no meaning the domain needs?

  • If yes → applicable. Foldable is the code catching up to the knowledge.
  • If no → inapplicable. The structure’s semantics are richer than one collapse.
  • If you cannot answer → unclear. The pattern is not wrong — your domain knowledge is incomplete.

Case study: Traversable

Yorgey (Typeclassopedia): A traversable structure lets an effectful action be applied to each element and the shape rebuilt. [1]

What Traversable actually is

Traversable asks: can I apply an effectful step to every element and rebuild the shape? The primitive is traverse :: Applicative f => (a -> f b) -> t a -> f (t b), mirrored by sequenceA = traverse id.

The effect must be an Applicative. Identity gives back fmap; Maybe is all-or-nothing; Either stops at the first error; Validation accumulates errors. One traverse serves them all.

The shape is preserved while the element type changes: t a becomes t b at the same positions, but one function and one effect must serve every position.

The domain knowledge gap it signals

The domain knowledge is the per-element step and the shape that must survive it. If your domain says “validate every line item and rebuild the order,” Traversable embodies it. Two limits matter: the same step runs at every position, so per-position rules need another tool; and on failure with Either you get the error, not the structure.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates the same effectful step at every position, and the structure must survive it. Traversable closes the gap: call sites stop hand-writing map-collect-rebuild, which scatters the logic and hard-wires one effect. Swap the effect and the traversal is unchanged.

WarningWhen it’s inapplicable (cohesion-reducing)

When positions are not interchangeable. An AST that needs a different effect at different node types, or a sequence whose steps are genuinely different operations rather than one uniform step, is not one traverse. A recursive function fits; forcing one traversal hides the per-position rules.

TipThe faithfulness test

Does the domain apply one uniform effectful step at every position, and must the structure’s shape survive it?

  • If yes → applicable. Traversable is the code catching up.
  • If no → inapplicable. The rules vary by position; a uniform traversal misrepresents them.
  • If you cannot answer → unclear. You have not found the pattern wrong — you have found incomplete domain knowledge.

Case study: Bifunctor

Yorgey (Typeclassopedia): A bifunctor is a type with two parameters, both of which can be mapped over. [1]

The domain knowledge gap it signals

A type with two independent parameters, each varying for its own reasons, is domain knowledge. If your domain model crystallizes that “a Result type holds either a domain error or a success value, and both sides transform independently: errors map to user-facing messages, values map to domain objects,” then Bifunctor is one encoding of that knowledge. The bimap operation captures the “transform each side independently” rule. Unlike structural patterns where the code IS the domain structure, the typeclass is an encoding choice: mapError and mapValue give the same runtime behavior, but the typeclass adds law-based reasoning and a unified interface.

ImportantWhen it’s applicable (cohesion-increasing)

The domain mandates that a two-sided type has independently transformable sides. Bifunctor closes the gap: it prevents each call site from pattern-matching, extracting, transforming, and re-wrapping both sides individually, scattering “how to reach into each side” knowledge. One bimap transforms both sides; when only one changes, first or second does it.

WarningWhen it’s inapplicable (cohesion-reducing)

The two type parameters are not independent domain concerns — one is a technical annotation. A logging wrapper carrying a logger context alongside a domain value is not a two-sided domain type: the logger side is infrastructure that changes only for technical reasons. The Bifunctor interface signals “both sides are domain-relevant and independently variable” when one side is an implementation detail piggybacking on the type.

TipThe faithfulness test

Would the domain expert describe both sides as independently meaningful — and would they say “yes, transforming an error to a user message and the value to a domain object are two separate domain operations”?

  • If yes → applicable. Bifunctor is one faithful encoding of the knowledge.
  • If no → inapplicable. One side is technical annotation — separate functions lose the law-based reasoning and the unified interface.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Contravariant

Yorgey (Typeclassopedia): A contravariant functor maps its input in the opposite direction. [1]

A contravariant type is a consumer: an Ordering[A] (a comparator) compares values instead of producing them. Contravariant maps consumers in reverse: given a way to turn a B into an A, an Ordering[A] becomes an Ordering[B]. On its own that is pure plumbing — any function adapts any consumer, so it says nothing about your domain. The domain knowledge is the coupling: which mapping the consumer uses.

The knowledge gap the pattern signals

Your domain says orders are ranked by their customer. That is a fact about what an Order is: it has a customer, and the ranking uses it. Given Ordering[Customer] and the mapping Order => Customer, contramap yields Ordering[Order] — the domain rule encoded once. If you can’t say why Order => Customer is the right mapping, you have found incomplete domain knowledge, not a missing pattern. Unlike a structural pattern, where the code IS the domain structure, this is an encoding choice — it adds reusable laws and a unified interface, not new domain knowledge.

ImportantApplicable (the mapping is a rule of your domain)

The domain states the mapping as a rule, so call sites never invent it. One contramap keeps that rule in one place — “rank B’s by mapping each to an A” — instead of scattering it across call sites.

WarningInapplicable (the mapping belongs to another domain)

The consumer sits in a different domain — a logger taking strings, a database writer taking SQL, a file sink. Logging and persistence have their own rules; contramapping into them encodes those, not a rule of your domain. Same shape, opposite verdict: a rule of your domain in one case, an adjacent domain’s rule in the other.

TipThe faithfulness test

Would an expert in your domain state the mapping as a rule — “if we rank orders by customer, sorting any collection of orders should use the customer, and change when that rule changes”?

  • If yes → applicable: the rule is real, and one contramap encodes it.
  • If no → inapplicable: the mapping belongs to another domain, and the pattern buys nothing your domain did not ask for.
  • If you can’t answer → you haven’t found the pattern wrong, you’ve found incomplete domain knowledge.

Case study: Profunctor

Yorgey (Typeclassopedia): A profunctor is a functor over two arguments, contravariant in the first and covariant in the second. [1]

A profunctor is a function-shaped type with two independently transformable sides: it consumes an input (contravariant) and produces an output (covariant). dimap maps both sides at once: pre-process the input, post-process the output. On its own that is pure plumbing — any function can be adapted, so it says nothing about your domain. The domain knowledge is the coupling: which input and output mappings the pipeline uses.

The knowledge gap the pattern signals

Your domain says validation takes a RawOrderRequest and produces a ValidationResult. That is a fact about what validation is: the input it accepts and the output it returns are domain concepts. When rules change, the input narrows (lmap) and the output enriches (rmap) on the same pipeline. Given those mappings, dimap yields one validation function — the rule encoded once. If you can’t say why those mappings are right, you have found incomplete domain knowledge, not a missing pattern. Unlike a structural pattern, where the code IS the domain structure, this is an encoding choice — it adds laws and coherence, not new domain knowledge.

ImportantApplicable (the mappings are rules of your domain)

The domain treats the pipeline’s input and output as independently variable. One dimap keeps that rule in one place — “prepare what goes in, wrap what comes out” — instead of scattering it across call sites.

WarningInapplicable (the mappings belong to another domain)

The adaptations belong to an adjacent domain — a request parser, a response formatter. Those have their own rules; wrapping a core function in them encodes those, not a rule of your domain. Same shape, opposite verdict: your domain’s rule in one case, an adjacent domain’s rule in the other.

TipThe faithfulness test

Would an expert in your domain state the input mapping (narrowing) and output mapping (enriching) as distinct domain rules that vary independently?

  • If yes → applicable: the rules are real, and one dimap encodes them.
  • If no → inapplicable: the mappings belong to another domain, and the pattern buys nothing your domain did not ask for.
  • If you can’t answer → you haven’t found the pattern wrong, you’ve found incomplete domain knowledge.

Case study: Alternative

Yorgey (Typeclassopedia): Alternative is an applicative functor with an empty value and a choice operation. [1]

Alternative is the FP typeclass behind the <|> operator, read as “try this, else that.”

The gap it signals

That a computation can fail, and that there is a domain-recognized fallback (not just an error), is domain knowledge. If your model says “try the primary payment processor; if it fails, use the secondary; if a config key is missing, use the default,” then Alternative is one encoding of that rule. <|> captures the “try this, else that” part. Unlike structural patterns, where the code is the domain structure, here the operator is a choice: if/else gives the same runtime behavior, but the operator adds law-based reasoning.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates fallback: primary-then-secondary, preferred-then-default. Alternative keeps that rule in one place instead of scattering if/else or try/catch across call sites. For a left-biased instance like Maybe, <|> chains read left-to-right, matching “prefer X, but Y is acceptable.”

WarningWhen the domain doesn’t (cohesion-reducing)

A fallback that looks purely technical is still a domain decision. “On a 5xx, use a mirror” is a requirement. A parser that tries several grammars states a domain fact — the accepted input formats. The gap is not that these are technical. The gap is that Alternative does not merely record a fallback: it records an order. It fits only when the domain names the alternatives and ranks them. If the domain treats the mirrors as interchangeable, it never ranked them, and <|>’s left bias asserts a preference no one decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Name the alternatives and their order the way a domain expert would — “primary processor, secondary processor,” “preferred carrier, backup carrier.”

  • If yes → applicable. Alternative is a faithful encoding of a decided rule.
  • If the alternatives are interchangeable → the operator adds an order the domain never made. Decide the order, or use a construct that does not rank.
  • If you can’t name them → you haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Algebraic Data Types

Lipovača: An algebraic data type is built by combining other types as sums (one of) and products (all of). [3]

The domain knowledge gap it signals

An algebraic data type (ADT) builds a type from other types — a sum (one of these) or a product (all of these together). Whether a domain concept is a sum or a product is domain knowledge. If your domain model crystallizes that “a Payment is either CreditCard, BankTransfer, or Cash — and a CreditCard payment always has a card number, expiry, and CVV together,” then ADTs embody that knowledge. The sum type is the domain’s own enumeration of cases; the product type is the domain’s own bundled fields. ADTs make illegal states unrepresentable — which is precisely what domain knowledge demands.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates product types (fields always appear together) and sum types (alternatives are mutually exclusive). ADTs prevent representing states the domain says cannot exist — eliminating validation logic that would scatter across the system.

WarningWhen the domain doesn’t (cohesion-reducing)

A sum type asserts its cases are mutually exclusive and complete; a product type asserts its fields always co-occur. The domain may violate both. Categories that overlap — a party is both customer and supplier — cannot be one branch of a sum. Categories the business keeps adding make a closed sum a change magnet. Fields that arrive independently — a middle name, a sometimes-present tax ID — make a product a togetherness nobody decided. That is the finding: the exclusivity or the togetherness is unwritten.

TipThe faithfulness test

Can the domain expert enumerate the mutually exclusive cases and the co-occurring fields — and would a misplaced field be a domain error?

  • If yes → applicable. ADTs are the code catching up.
  • If no → the cases overlap or stay open, or the fields do not always co-occur; the ADT asserts a structure the domain doesn’t have.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Pattern Matching

Lipovača: Pattern matching selects a branch by the shape of a value and binds its parts. [3]

The domain knowledge gap it signals

Pattern matching selects a branch by the shape (variant) of a value, and the compiler checks that every case is handled. The fact that an operation behaves differently for each variant — and that the set is closed — is domain knowledge. If your domain model already crystallizes that “a Payment is either CreditCard, BankTransfer, or Cash, and each type has its own processing rules; every payment MUST be processed through one of these paths,” then Pattern Matching is just embodying that knowledge. Each match arm is a domain rule; exhaustiveness checking is the domain’s own “every case must be handled” constraint.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates exhaustive handling over a closed set of variants. Pattern matching closes the gap: the compiler warns about every non-exhaustive match site, matching the domain’s own “these are all the possibilities” rule. Adding a new Payment variant flags every such site until the new case is handled, making domain evolution visible.

WarningWhen the domain doesn’t (cohesion-reducing)

The set of variants is open or externally defined — the domain doesn’t know all the cases at compile time. A plugin system, a configuration schema, or a message format from an external service: these have runtime-discovered variants. The open set is knowledge, and so is the default: what happens to an unknown variant is a domain decision. Pattern matching with sealed types fits only when the domain names that default. If the domain has not named it, a catch-all or open-union encoding asserts a fallback no one decided. That is the gap: the unknown-case rule is unwritten.

TipThe faithfulness test

Does the domain define a closed, knowable set of variants — and would an unhandled variant be a domain error, not acceptable default behavior?

  • If yes → applicable. Pattern Matching is the code catching up to the knowledge.
  • If no → inapplicable. The case set is open, and exhaustive matching overstates the domain’s completeness.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Lazy Evaluation

Hughes: Lazy evaluation defers a computation until its result is needed. [2]

The domain knowledge gap it signals

The fact that a value may never be demanded — and that deferring it is a domain decision, not only a performance optimization — is domain knowledge. If your domain model already crystallizes that “most requests never open the full report detail; only a few accounts need the risk breakdown; the customer may never submit the form and so never need a premium quote,” then Lazy Evaluation embodies that knowledge. The thunk is the domain’s own “derive only if demanded” contract: the value is computed only when something asks for it.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain treats the derived value as demand-driven — computing it eagerly would do work the domain may never ask for. Lazy Evaluation closes the gap: the value is not computed unless it is demanded. The laziness is a domain rule here, not merely a caching trick.

WarningWhen the domain doesn’t (cohesion-reducing)

Even a “purely performance” deferral is a domain decision: someone chose when the value is needed. Lazy evaluation fits only when the domain names that timing — compute on first request, or compute at period close. If the timing is an arbitrary knob the domain never fixed, laziness asserts a demand schedule no one decided. If the domain always demands the value, laziness asserts a suspension no one asked for. That is the gap: the timing is unwritten.

TipThe faithfulness test

Would the domain expert describe a scenario where this computation genuinely should not happen — not “should happen later,” but “may never happen at all”?

  • If yes → applicable. Lazy Evaluation is the code catching up to the knowledge.
  • If no → inapplicable. The timing is an arbitrary knob — the domain has not named when the value is needed.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Trampoline

The domain knowledge gap it signals

A trampoline is a loop that runs recursive steps as plain returns, so deep recursion does not overflow the stack. Stack safety is one axis. The domain question is the other: when the computation has meaningful discrete phases the domain recognizes, the trampoline’s steps are those phases. If your domain model crystallizes that “processing a batch of claims requires progression through validation, assessment, approval, and payout — each step is a domain phase,” then the trampoline’s structure is the domain’s own.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates stepwise execution where each step is a meaningful domain unit — AND the computation is deeply recursive, requiring stack safety. Trampoline closes the gap: its steps are the domain’s phases, and it runs them without overflowing the stack.

WarningWhen the steps are not domain phases (cohesion-neutral)

Stack safety is not knowledge-free: the runtime’s stack bound is a fact about the environment the code runs in, and the trampoline fits it. The inapplicable case is naming each step a domain phase when no rule or state the expert recognizes stands behind it. Then the phase names are invented, not discovered — calling each step a “phase” asserts a domain granularity no one decided. That is the gap: the phase boundaries are unwritten.

TipThe faithfulness test

Beyond the need for stack safety, would the domain expert describe the computation as a sequence of distinct, named domain phases?

  • If yes → applicable. Trampoline is doubly justified — runtime safety AND domain fidelity.
  • If no → no phase knowledge. It remains correct for stack safety — a real environment fact, never a mistake.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Memoization

Michie: Memoization stores a function’s result under its arguments so a repeated call reuses it. [4]

The domain knowledge gap it signals

Memoization stores a computation’s result under its inputs, so a repeated call reuses it. That a result is determined solely by its inputs — and that caching it is a domain guarantee, not just a performance optimization — is domain knowledge. If your domain model already crystallizes that “a tax table lookup for a given bracket always returns the same rate; a risk score for a given exposure profile is immutable for the scoring period,” then Memoization is just embodying that knowledge. The cache is the domain’s own “this value, once computed, is stable” guarantee.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates determinism: for a given key, the same inputs always produce the same output. When validity is period-bounded, the period is part of the key. Memoization closes the gap: it avoids redundant recomputation and fixes one value per input set. The cached value becomes the single source of truth — matching the domain’s own “the rate doesn’t change mid-period” constraint.

WarningWhen the domain doesn’t (cohesion-reducing)

Even a caching optimization is a domain decision: someone chose to reuse the result, and how long. Memoization fits only when the domain names a stability window. When the output changes for reasons external to its inputs, the window is unfixed; memoizing a database query, a time-dependent computation, or a stateful function then adds staleness risk. The cache asserts a stability the domain never guaranteed. That is the gap: the validity window is unwritten.

TipThe faithfulness test

Does the domain guarantee that the same inputs always yield the same output — and would a differing result for the same inputs be a domain error?

  • If yes → applicable. Memoization is the code catching up to the knowledge.
  • If no → inapplicable. The function’s output is time-dependent or externally mutable, and caching risks domain-incorrect results.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Pure Function

Hughes: A pure function has no side effects: its result depends only on its arguments. [2]

The domain knowledge gap it signals

The fact that a domain demands deterministic, side-effect-free computation is domain knowledge. Purity is also the FP default, but the domain’s demand for it is still a choice. The question is whether the domain demands referential transparency. If your domain model crystallizes that “computing a tax liability from income and bracket must yield the same result every time for the same inputs — and must not depend on or modify anything outside those inputs,” then the Pure Function matches the domain’s own determinism constraint. Purity is double-counted: computational correctness AND domain fidelity. Domain-essential effects are handled with effect types, not by violating purity.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates that certain computations are deterministic and side-effect-free. Pure Functions close the gap: they prevent the system from introducing hidden dependencies (global state, clock time, random seeds) into computations the domain says should be deterministic. Testing, reasoning, and caching become trivial — consequences of that determinism, not just technical benefits.

WarningWhen the determinism constraint is unstated (cohesion-neutral)

The pattern does no harm here. It also gives no signal. In functional code, purity is the default, so the code reads the same whether or not the domain requires determinism. Two cases collapse into one: “the domain requires this result to stay stable” and “this function is pure by habit.” The code cannot tell them apart. The requirement is real, but it is unwritten. The gap is the missing statement, not a missing constraint.

TipThe faithfulness test

Does the domain impose determinism constraints on certain computations — and would a non-deterministic result (same inputs, different output) be a domain error?

  • If yes → applicable. The pure function is the code catching up to the knowledge.
  • If no → no named constraint. It remains FP’s default — never wrong, but the requirement is unstated.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Recursion Scheme

Meijer et al.: A recursion scheme is a reusable function that captures a standard traversal of a recursive data type. [5]

The domain knowledge gap it signals

A recursion scheme is a reusable function that captures a standard traversal of a recursive data type, such as a fold. When a domain operation is defined over such a type and the recursion pattern is domain-meaningful — not just algorithmic convenience — that is domain knowledge. If your domain model crystallizes that “an org chart folds to its root to compute headcount,” then a Recursion Scheme encodes that knowledge. The fold captures bottom-up reduction; the unfold captures top-down generation. Unlike structural patterns, where the code is the domain structure, the recursion scheme is an encoding choice. A recursive function or Visitor gives the same behavior, but loses the clean separation of traversal from per-node logic.

ImportantWhen the domain mandates it (cohesion-increasing)

Recursion Schemes close the gap: they separate “how to walk the structure” from “what to do at each node.” When the data type changes, only the per-node function changes; the traversal updates.

WarningWhen the domain doesn’t (cohesion-reducing)

The data structure is not domain-recursive — it is a tree-shaped intermediate representation. A JSON AST, parse tree, or object graph recurses structurally. But the shape is still a decision: the domain chose it. A recursion scheme fits only when the domain names the tree as a hierarchy it owns. If the shape is a format detail the domain never named, the scheme formalizes an artifact and couples operations to a shape that changes when the format evolves. That is the gap: the tree’s domain standing is unwritten.

TipThe faithfulness test

Is the recursive structure a domain concept — would an expert describe the tree as “an organization of sub-organizations” or “an expression of sub-expressions”?

  • If yes → applicable. Recursion Schemes are one faithful encoding of the knowledge.
  • If no → inapplicable. The tree is a format detail the domain never named — a recursive function expresses the same traversal without formalizing it.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.

Case study: Continuation

Reynolds: A continuation is a function that represents the rest of a computation. [6]

The domain knowledge gap it signals

A continuation is a function that represents “the rest of the computation,” passed in so the caller decides what happens next. That a computation’s next step is a domain decision passed at runtime — that “what happens after” is not fixed — is knowledge. If your domain model crystallizes that “after payment processing, send a confirmation email on success or queue a fraud review on failure,” then Continuations encode that knowledge. CPS captures the domain’s “here’s what to do next” parameterization. Unlike structural patterns where the code is the domain structure, CPS is an encoding choice: a Strategy, a callback, or an event emitter gives the same behavior, but loses CPS’s composable control flow.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain mandates that the “and then” is itself a domain decision, not a fixed algorithm. Continuations close the gap: they prevent the computation from hardcoding its successor, which would couple the processor to the notification and fraud systems. The continuation is supplied at the call site — the business process determines the next step.

WarningWhen the domain doesn’t (cohesion-reducing)

The “and then” is always the same — but even a fixed callback is a domain decision: someone chose that the step must happen. The construct fits only when the domain names the next step as a decision point. Passing a logger, a metrics collector, or a response writer as a continuation transforms plumbing into CPS when no rule varies the step. The interface then signals a choice no one makes. That is the gap: the fixed step is unstated, not “merely plumbing.”

TipThe faithfulness test

Does the domain have multiple, different “what happens next” paths — and would an expert describe the continuation as a business-process decision point?

  • If yes → applicable. Continuation is one faithful encoding of the knowledge.
  • If no → inapplicable. The step never varies — a direct call expresses the same fixed step without passing a continuation.
  • If you can’t answer → unclear. You haven’t found the pattern wrong — you’ve found incomplete domain knowledge.
