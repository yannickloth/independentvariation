Analysis Patterns as Knowledge-Gap Indicators

A list of short posts that read each pattern as a completeness check on domain knowledge.

Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Analysis patterns are the purest case: they ARE recurring domain structures — so the gap question is simply “is our situation genuinely one of these?”

Case study: Party

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Analysis patterns are the purest case: they ARE recurring domain structures — so the gap question is simply “is our situation genuinely one of these?”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: Model people and organizations with a common supertype, Party. [1]

Party is the analysis pattern that lets a person and an organisation stand in for each other wherever a role applies.

The domain knowledge gap it signals

The fact that a person and an organisation can play the same role — both can be a customer, a supplier, an employee — is domain knowledge. If your domain crystallises that “whoever we invoice may be a person or a company, and downstream we don’t care which,” then Party is that fact made executable: a common abstraction above Person and Organisation, where the roles live.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain assigns the same roles and rules to people and organisations: both order, both pay, both are contacted. Party closes the gap: it prevents duplicating every role (“CustomerContact” vs “CorporateContact”) and every rule for each subtype, and it lets contracts, accounts, and addresses point at one concept. The abstraction is the domain’s own “who matters, not what kind of who” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here people and organisations look like separate kinds, with different lifecycles and different rules. But it is still a domain decision whether they share a role. Party fits only when the domain names a role that is true of both. If the domain has not named one, the abstraction asserts a sameness nobody decided, and every consumer branches on type to escape it. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Can a domain expert state a rule using only “the customer” / “the contact” — a phrase that is true whether it is a person or a company?

  • If yes → applicable. Party is the code catching up to the knowledge; the shared role is the domain’s own.
  • If no → inapplicable. Model Person and Organisation separately; the abstraction fabricates a role the domain doesn’t share.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Organization Structure

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Analysis patterns are the purest case: they ARE recurring domain structures — so the gap question is simply “is our situation genuinely one of these?”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: Represent an organization structure as a hierarchy of Parties. [1]

Organization Structure is the analysis pattern that models an organisation as typed units joined by rule-carrying relationships.

The domain knowledge gap it signals

The fact that the organisation has formal relationships with rules — “regional offices report to headquarters,” “this division owns these cost centres” — is domain knowledge. Organization Structure models those relationships as typed, rule-carrying structures: a parent, a child, a type, and the constraints each type implies.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain reasons about the org chart: who may approve, who consolidates to whom, which unit is liable. Organization Structure closes the gap: it prevents the reporting rules from being hardcoded paths or ad-hoc parent pointers that change shape with every reorganisation. Each relationship type is the domain’s own “this kind of unit relates to that kind this way” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the need looks like a simple directory — an org picker, an email list. But the shape is still a domain decision: someone chose what a unit is and how units relate. Organization Structure fits only when the domain attaches rules to the shape — approvals, liability, consolidation. If it attaches none, the typed relationships assert governance nobody decided. The same gap appears when the real structure is informal: typing an expertise network dresses politics in constraints nobody wrote down. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the business attach rules to the org shape — approvals, liability, consolidation — or do people just need to find each other in a list?

  • If yes → applicable. Organization Structure is the code catching up to the knowledge; the typed relationships are the domain’s own.
  • If no → inapplicable. A simple directory expresses the need without fabricating governance.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Organization Hierarchy

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Analysis patterns are the purest case: they ARE recurring domain structures — so the gap question is simply “is our situation genuinely one of these?”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: An organization hierarchy in which each organization has at most one parent. [1]

Organization Hierarchy is the analysis pattern that treats every unit as having exactly one superior.

The domain knowledge gap it signals

The fact that the organisation is a strict tree — every unit has exactly one superior, authority flows one way — is a domain claim, and often an unexamined one. Organization Hierarchy is that claim made executable: single-parent structure with transitive rules (“the whole branch reports up through here”).

ImportantWhen the domain mandates it (cohesion-increasing)

The domain genuinely is a tree: command chains, statutory consolidation, single ownership. The hierarchy closes the gap: transitive queries (“all subunits”), single-line accountability, and roll-up rules become simple and correct because the domain guarantees one parent. The strictness is the domain’s own “no shared bosses, no dotted lines” rule.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the organisation looks like a tree, and a hierarchy looks purely structural. But it is still a domain decision: someone claimed authority is single-threaded. Organization Hierarchy fits only when the domain names exactly one superior per unit. If the real authority is many-threaded — matrix, shared services, dotted lines — the domain has not named a single parent, and the tree asserts a chain nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Can every unit in the business name exactly one superior — and would experts confirm there are no “it depends” reporting lines?

  • If yes → applicable. The hierarchy is the code catching up to the knowledge.
  • If no → inapplicable. Model a graph or multiple typed structures; the tree would encode an org that doesn’t exist.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Fowler: Record the accountability of one party to another. [1]

Accountability is the analysis pattern that records who answers to whom, for what, and for how long.

The domain knowledge gap it signals

The fact that one party is answerable to another for something — with a scope, a start, and sometimes an end — is domain knowledge. Each accountability is the domain’s own “this party answers to that party for this” rule, with a lifetime the domain recognises.

Accountability fits only when the business names an answerer for each thing — with a scope and a lifetime. If responsibility is genuinely diffuse and nobody is named, the relationship asserts an owner nobody decided. That is the finding: the domain knowledge is unwritten.

  • If no → inapplicable. Model routing or staffing instead; the pattern would invent a responsible party.

Case study: Knowledge Level

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Analysis patterns are the purest case: they ARE recurring domain structures — so the gap question is simply “is our situation genuinely one of these?”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: Separate the knowledge level (the rules) from the operational level it governs. [1]

Knowledge Level is the analysis pattern that separates the rules about kinds of things from the things themselves.

The domain knowledge gap it signals

The fact that the business distinguishes kinds of things from the things themselves — job positions vs. the people in them, account types vs. accounts, ward categories vs. wards — is domain knowledge. A Knowledge Level is that distinction made executable: one layer defines the types and their rules; the other holds the operational objects that must obey them.

ImportantWhen the domain mandates it (cohesion-increasing)

The experts maintain the rules about kinds separately from the instances: HR defines positions, finance defines account types, and changes to one never touch the other. The knowledge level closes the gap: it prevents type rules from being copy-pasted onto each instance, where a rule change means editing every record. The level is the domain’s own “the rules of the kind live with the kind” structure — a classic and legitimate use of meta-data.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the types never vary and never carry rules — it looks like one kind, with a config table only developers edit. But it is still a domain decision: someone claimed the business owns rules about kinds. Knowledge Level fits only when the experts maintain those rules and change them without touching the instances. If the table is only a developer lookup, the layer asserts business governance nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Do the experts maintain rules about kinds of things — and do they change those rules without touching the individual things?

  • If yes → applicable. The Knowledge Level is the code catching up to the knowledge; the meta-layer is the domain’s own.
  • If no → inapplicable. Keep types in the schema; the extra layer fabricates business governance.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Quantity

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Analysis patterns are the purest case: they ARE recurring domain structures — so the gap question is simply “is our situation genuinely one of these?”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: A number together with a unit of measure. [1]

Quantity is the analysis pattern for a number that carries its unit of measure.

The domain knowledge gap it signals

The fact that a number in this domain is never just a number — it is an amount of something, in a unit, comparable only to its own kind — is domain knowledge. If your domain crystallises that “5 kilograms cannot be added to 3 metres,” then Quantity is that fact made executable: a value carrying its unit, with conversion and comparison rules that respect the physics the business lives by.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain measures, doses, ships, or prices things where unit confusion is a real error — medicine, logistics, engineering, energy. Quantity closes the gap: it prevents raw floats from mixing, which would let litres meet tonnes and nobody notice. The unit is the domain’s own “of what?” rule; permitted conversions are the domain’s own “how these kinds relate” knowledge; comparison within kind is the domain’s own ordering.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the numbers look dimensionless — counts, scores, percentages. But it is still a domain decision: someone claimed these are plain counts, not measurements. Quantity fits only when the domain names a unit for the value. If no expert would say “five of what unit?”, the wrapper asserts dimensional rules nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the business state amounts with units — “42 tonnes, not 42” — and would adding unlike units be a business error, not just a bug?

  • If yes → applicable. Quantity is the code catching up to the knowledge; the unit is the domain’s own.
  • If no → inapplicable. Use plain numbers; the wrapper invents dimensional rules that don’t exist.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Money

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Analysis patterns are the purest case: they ARE recurring domain structures — so the gap question is simply “is our situation genuinely one of these?”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: A quantity whose unit is a currency. [1]

Money is the analysis pattern for an amount that carries its currency.

The domain knowledge gap it signals

The fact that an amount in this domain always belongs to a currency — and that mixing currencies is a domain error, not a rounding detail — is domain knowledge. Money is that fact made executable: amount plus currency, with addition restricted to like currency and comparison routed through explicit conversion. It is Quantity specialised to the one domain every business shares.

ImportantWhen the domain mandates it (cohesion-increasing)

The business prices, bills, budgets, or reports — and experts never say an amount without a currency, or totals that silently mix pounds and euros. Money closes the gap: it prevents double arithmetic from merging currencies, which produces numbers no accountant can sign. Rounding rules belong here too: where the penny goes is domain knowledge (who keeps the fraction), not a Math.rint call.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the amounts look like single-currency internal metrics — estimates, scores, capacity. But it is still a domain decision: someone claimed these numbers carry no currency. Money fits only when the domain names a currency for the amount. If the number is a plain metric, the wrapper asserts currency baggage nobody decided. The opposite misfit is the same gap from the other side: raw doubles for billable amounts surface later as penny-discrepancy postmortems. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Would an expert say “that’s euros” about every amount — and would adding a pounds figure to a euros figure be a business mistake even if the code allowed it?

  • If yes → applicable. Money is the code catching up to the knowledge; currency is the domain’s own constraint.
  • If no → inapplicable. Keep plain numbers for dimensionless metrics; the wrapper invents currency.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Fowler: A value observed or measured about something. [1]

Observation is the analysis pattern that treats a recorded statement as a first-class thing, separate from the truth it records.

The domain knowledge gap it signals

The fact that a statement about a subject was made by someone, at a time, against a protocol is domain knowledge. ImportantWhen the domain mandates it (cohesion-increasing)

The domain keeps observations as evidence: clinical findings, inspections, sensor readings, survey answers. Observation closes the gap: it prevents measurements from being overwritten columns, where history, provenance, and the observer vanish. Each observation carries the domain’s own “who saw what, when, how” rule — and later corrections add new observations rather than rewriting evidence.

Here the need looks like the current value of a field, and the domain seems to care about the state, not the act. If only the latest value is ever needed, the dated record asserts provenance nobody decided. That is the finding: the domain knowledge is unwritten.

Would experts ask about a past observation — “what was measured, by whom, when?” — or do they only ever need the current value?

  • If yes → applicable. Observation is the code catching up to the knowledge; the recording is the domain’s own evidence.
  • If no → inapplicable. Keep a plain current-value field; the observation log invents an archive no one reads.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Fowler: An observation of a value, together with its unit of measure. [1]

Measurement is the analysis pattern for a value that carries the procedure that produced it.

The domain knowledge gap it signals

The fact that a measured quantity comes from a procedure, against a defined scale, with a normal range — that how a value is obtained is part of its meaning — is domain knowledge. Measurement is Observation specialised for quantities: the value carries its protocol, because the domain says a number without its method is not interpretable.

ImportantWhen the domain mandates it (cohesion-increasing)

The domain’s experts judge values only relative to how they were taken: lab assays, calibrations, instrument readings. Measurement closes the gap: it prevents bare numbers from being compared across protocols, where “the same test” done differently yields different answers. The protocol reference is the domain’s own “this number means this, taken this way” rule; reference ranges are the domain’s own norms.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the quantity looks directly meaningful — a stated price, an entered weight — and no expert would ask “measured how?”. But it is still a domain decision: someone claimed the value stands without a procedure. Measurement fits only when the domain names the method as part of the value’s meaning. If the value stands on its own, the protocol reference asserts methodology nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Do experts need to know the method to interpret the number — would the same figure from different procedures be a different fact?

  • If yes → applicable. Measurement is the code catching up to the knowledge; the protocol is the domain’s own context.
  • If no → inapplicable. A Quantity suffices; the protocol reference fabricates methodology.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

Case study: Phenomenon / Category (typed observations)

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Analysis patterns are the purest case: they ARE recurring domain structures — so the gap question is simply “is our situation genuinely one of these?”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: A controlled vocabulary of phenomena and categories for typed observations. [1]

Phenomenon and Category are the analysis patterns that model a controlled vocabulary of things that can be observed or classified.

The domain knowledge gap it signals

The fact that the business has a controlled vocabulary of things that can be observed or classified — diagnosis codes, defect types, product categories — and that free text is not acceptable, is domain knowledge. Phenomenon types and categories are that fact made executable: the vocabulary itself is modelled, with each observation pointing at a term the domain owns.

🧠 Why it matters here Whether the list of valid values is closed is one of the most consequential hidden gaps in data modeling: an open set sneaks in as varchar, and surfaces years later as a migration.

ImportantWhen the domain mandates it (cohesion-increasing)

The experts maintain the term list, report against it, and change it deliberately (“add a new defect class”). Modelling categories closes the gap: it prevents free-text classification, where “scrached” and “scratch on surface” are the same defect and reporting dissolves. Each term is the domain’s own vocabulary item; adding a term is a domain decision with an owner.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the values look genuinely open — notes, descriptions, keywords the experts never control. But the list is still a domain decision: someone chose whether the vocabulary is closed. Phenomenon and Category fit only when the domain owns a fixed term list and admits new terms deliberately. If the business owns prose, the closed table asserts a vocabulary nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Would experts agree on the complete list of valid terms today — and insist new terms go through them, not around them?

  • If yes → applicable. Categories are the code catching up to the knowledge; the vocabulary is the domain’s own.
  • If no → inapplicable. Keep free text; a closed list would censor the domain.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.

🔥 Almost every design pattern/principle can be used as a completeness-check on domain knowledge. Analysis patterns are the purest case: they ARE recurring domain structures — so the gap question is simply “is our situation genuinely one of these?”

Reaching for a pattern? Ask “does the domain knowledge mandate the coupling this pattern would add or remove?” If you can’t answer, you’ve found a knowledge gap. If you can, the knowledge prescribes the structure directly — the pattern adds nothing the domain hadn’t already decided.

Fowler: Separate things tracked individually (assets) from things tracked by quantity (inventory). [1]

Inventory and Asset are the analysis patterns that separate things tracked individually from things counted in bulk.

The domain knowledge gap it signals

The fact that the business distinguishes things it owns and tracks individually from stuff it counts — this van (serial number, service history) vs. 400 litres of diesel — is domain knowledge. The Inventory/Asset distinction is that fact made executable: discrete trackable assets vs. aggregate quantities, with different identity, valuation, and lifecycle rules.

ImportantWhen the domain mandates it (cohesion-increasing)

The experts manage some things individually — “vehicle F-112 needs servicing” — and others in bulk — “we hold 400 litres.” The split closes the gap: it prevents one representation from serving both, where either the van is counted in litres or the diesel gets serial numbers. Each side carries the domain’s own rules: assets take maintenance and depreciation; inventory takes quantities, batches, and expiry.

WarningWhen the domain doesn’t (cohesion-reducing)

Inventory/Asset fits only when accounting and operations agree on the split. If the two halves disagree, the pattern encodes one side and the split is unwritten. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Does the business distinguish “track this one” from “count this stuff” — and would both accounting and operations sign the same split?

  • If yes → applicable. The distinction is the code catching up to the knowledge.
  • If no (they disagree) → unclear — resolve the split with the business first; that’s the gap.
  • If the domain is all-one-kind → inapplicable. Model only the kind that exists.
  • If you can’t answer → you’ve found incomplete domain knowledge.

A Posting Rule is the analysis pattern that maps a business event to the accounting entries it books.

The domain knowledge gap it signals

The fact that the business has named derivation rules — “when we bill, the service account is credited and the tax account is charged” — is domain knowledge. A Posting Rule is that fact made executable: the trigger-to-entries mapping as a first-class thing, owned by accounting logic rather than scattered through process code.

ImportantWhen the domain mandates it (cohesion-increasing)

The experts state the derivations and expect them to hold everywhere, all the time — invoices, fees, taxes, accruals. Posting Rules close the gap: they prevent the debit/credit logic from being hand-written inside each workflow, where three billing paths produce three slightly different ledgers. The rule is the domain’s own “this event books those entries” law, and changing it is a domain decision in one place.

WarningWhen the domain doesn’t (cohesion-reducing)

Here the postings look like developer bookkeeping — cache counters, usage stats, with no accountant. But it is still a domain decision: someone chose how these numbers are derived. A Posting Rule fits only when the domain names the derivation as fiscal and owned. If the counters are merely convenient, the rule engine asserts fiscal discipline nobody decided. That is the finding: the domain knowledge is unwritten.

TipThe faithfulness test

Can the rule be read to a finance expert and confirmed as the way the business books this event — identical across every path that triggers it?

  • If no → inapplicable. Keep simple internal updates; the rule engine fabricates governance.
  • If you can’t answer → unclear. You haven’t found the pattern wrong; you’ve found incomplete domain knowledge.
