Clean Architecture Is Conditional: A Formal Response to Rico Fritzsche

ivp
engineering
architecture
coupling
Rico Fritzsche argues we should retire Clean Architecture, Hexagonal Architecture, and the layered family in favor of Functional Core / Imperative Shell. Much of the diagnosis holds. This post adds one scope condition to it, and notes that Clean Architecture’s own criterion, dependency toward stability, is a proxy rather than a derivation.
Published

October 18, 2026

Rico Fritzsche recently published “Why Are We Still Talking About Clean Architecture?”, an argument to retire Clean Architecture, Hexagonal Architecture, Onion Architecture, and the layered family in favor of a Functional Core / Imperative Shell split.

A large part of his diagnosis is correct, and the Independent Variation Principle (IVP) says exactly why. The addition I would make is one of scope. The family’s prescription describes one case among several, and which case applies is settled by the domain rather than by the style. Clean Architecture is conditionally right — the condition is narrower than the style’s own justification admits, and that justification is worth examining. The same condition applies, with a smaller footprint, to the Functional Core / Imperative Shell split.

IVP (structural formulation). Given the element set EE and the change-driver assignment Γ(e)\Gamma(e) — the set of change drivers whose state changes create a modification requirement for element ee — the principle is the conjunction of four conditions [1]:

  1. Admissibility — every element has at least one change driver: ∀e∈E,|Γ(e)|≥1\forall e \in E,\ |\Gamma(e)| \geq 1.
  2. Element Form — every element is either pure (|Γ(e)|=1|\Gamma(e)| = 1) or irreducibly composite: no proper subset of its driver set can achieve its purpose, and no decomposition into sub-elements with strictly smaller driver sets jointly preserves that purpose.
  3. Separation — elements assigned different sets of change drivers reside in different modules: Γ(e1)≠Γ(e2)⇒M(e1)≠M(e2)\Gamma(e_1) \neq \Gamma(e_2) \Rightarrow M(e_1) \neq M(e_2).
  4. Unification — elements assigned the same set of change drivers reside in the same module: Γ(e1)=Γ(e2)⇒M(e1)=M(e2)\Gamma(e_1) = \Gamma(e_2) \Rightarrow M(e_1) = M(e_2).

Equivalently, the modules of an IVP-compliant system are the Γ\Gamma-equivalence classes of EE, so the partition is the quotient 𝒫Γ=E/∼Γ\mathcal{P}_\Gamma = E/\!\sim_\Gamma; the uniqueness theorem proves it is the unique cost-minimising modularisation [1]. Separation and Unification are the partition content: failing Separation is contamination (elements driven by different conditions co-reside), and failing Unification is scatter (elements that change together are split across modules).

A change driver is an exogenous forcing condition whose change creates a requirement for governed elements to change — a condition anchored in a regulation, a contract, an interface specification, or another domain artifact whose authority is external to the system. Drivers are discovered, not chosen.

1 What Fritzsche gets right

1.1 Dependency inversion changes placement, not drivers

Fritzsche writes: “Dependency inversion makes it possible to reverse source code dependencies… However, the functional dependencies remain.”

That is the placement result. A change driver is external and fixed by the domain. No design move adds, removes, or transmutes one. Dependency inversion changes where a dependency sits in the source. It does not change the driver that forces the dependency to exist. The BookingService in his example still needs the reservation data before it can apply its rules — whether it reaches that data through a driver, an adapter, or an interface.

1.2 An abstraction can relocate coupling, not delete it

Fritzsche: an abstraction “can hide these differences, but it cannot simply eliminate them.”

This is the essential-versus-accidental coupling distinction. Coupling is essential when a domain artifact requires two elements to share a resource. The domain artifact is the reason the shared access exists; remove the artifact and the sharing disappears. Essential coupling cannot be eliminated by any abstraction, because the obligation that creates it does not live in the code. It can only be relocated — and relocation makes the knowledge reappear somewhere else.

1.3 Boundaries by architectural role are not anchored

Fritzsche wants to stop “dividing an application based on technical concerns.” The cohesion analysis already says why that is right [2]. A layer groups elements by technical role — “what kind of code is this?” A port is defined by the application, not by an external domain artifact. These boundaries fail the conditions a partitioning rule must meet: they are not determinate (two designers can disagree on where the port goes, with no fact of the matter) and not externally anchored (no artifact outside the software says which elements belong together). The accent is on the right syllable.

So the diagnosis holds. The conclusion is where a scope condition applies.

2 A scope condition: the core is conditional

The family of styles prescribes one structural thing: a domain layer whose modules embody no knowledge of infrastructure systems. Call this the infra-ignorant core.

The question is not whether that core is desirable. The question is whether it exists for a given domain. The analysis in The Domain–Infrastructure Boundary as a Structural Property of the Driver Set answers with a biconditional. An infra-ignorant core exists if and only if no domain change-driver has correctness conditions that require knowledge of an infrastructure system. Call this condition H (Knowledge Independence).

H is a property of the domain’s governing artifacts. It is not a design choice. The architect cannot decide H; the architect can only discover it.

A stronger condition, H0 (Behavioural Self-Containment), holds when a module computes everything it needs from its own inputs, with no dependence on external state of any kind. H0 implies H. The converse fails: a module can read external domain state — a customer’s recorded credit history — while remaining entirely ignorant of infrastructure.

Two conditions that can fail independently give exactly three cases:

Case Condition The core
(a) H0 holds A pure functional core exists.
(b) H holds, H0 fails An infra-ignorant core exists, but the module needs external domain state.
(c) H fails The infra-ignorant core is impossible.

Fritzsche’s argument applies squarely in case (a). The domain decides how far that case reaches.

2.1 How H fails

H fails in two ways, and neither is a modelling mistake.

Direct. A governing artifact states a correctness condition in terms of infrastructure behaviour. “A patient record must be retrievable within 500 ms under peak load” is a change driver anchored in a medical-device regulation. Its correctness condition is a statement about storage and indexing performance. No implementation ignorant of storage semantics satisfies it.

Indirect. A domain rule’s correctness depends on the outcome of an infrastructure process. A credit rule says: “approve an order only if the customer’s outstanding balance, including committed but not yet settled orders, stays within the credit limit.” “Committed but not yet settled” refers to persistence state under concurrent write. Two storage architectures with different isolation levels produce different answer sets for the same underlying events, and therefore different approval outcomes. The domain rule’s correctness is functionally determined by the storage layer’s guarantee.

This second case is where Fritzsche’s own example points. He writes: “Query capabilities, transaction behaviour, and consistency guarantees are largely determined by the database used.” Correct — and when a domain rule’s correctness condition depends on those guarantees, the database is not a detail. It is part of the domain’s causal structure.

The result is decisive: when H fails, no reformulation of the domain removes the required knowledge while preserving correctness. The infra-ignorant core is not hard to reach. It is impossible.

3 Clean Architecture’s own criterion is dependency toward stability

Clean Architecture’s conditionality has a second source, independent of H. It lies in the style’s own criterion.

The Dependency Rule — “source-code dependencies point inward” — rests on a stability ordering: the domain rules are said to be more stable than the frameworks, databases, and delivery mechanisms that serve them, so dependencies should point toward the domain. Martin quantifies stability with two structural metrics [3]. Instability is I=Ce/(Ca+Ce)I = C_e/(C_a + C_e), the ratio of efferent to total coupling. Abstractness is AA, the fraction of abstract types. The Main Sequence A+I=1A + I = 1 is the claimed optimal locus.

Neither metric references a change driver. II counts packages in the import graph; AA counts abstract type declarations. They measure structural self-containment — an element counts as “stable” because nothing imports force it to change — not actual change frequency, and not change-driver identity. “Depend toward stability” is therefore a proxy for the change-driver structure, not a measurement of it [4].

And it is a proxy, not a derived criterion. The IVP proof does not use it: the optimum is fixed by Γ\Gamma-equality, and stability does not appear in the argument. The Main Sequence is, at best, a one-directional diagnostic — IVP-compliant designs land on it as a byproduct, but landing on it does not imply IVP compliance. So the ordering the style rests on is a heuristic that correlates with the change-driver structure in some domains and is silent in the rest. It cannot certify that a ring boundary is the correct one.

This is why Clean Architecture is not merely conditional. The band in which it is right is narrow: its rings coincide with the IVP partition only where role tracks the change driver and ring position tracks real stability — the single-capability, substitutable-provider domain the style was calibrated against. Outside that band the ordering inverts or flattens: a volatile domain core, or a concrete-but-inert framework, and the Dependency Rule points dependencies toward the most volatile elements. The Clean Architecture verdict works this out ring by ring.

The inversion is sharpest exactly where H fails. If a domain rule’s correctness condition requires storage isolation semantics, the domain rule is no longer the more stable element; the infrastructure behaviour whose outcome the rule depends on is. A faithful application of Martin’s own stability principle would then move that behaviour toward the dependency target — the opposite of what the rings do. The style’s stability ordering and its infra-ignorant core pull in opposite directions the moment H fails. That tension stays invisible to the style, because the style has no criterion but stability to see it with.

4 Where the same condition applies

Fritzsche’s answer is the Functional Core / Imperative Shell split: a business calculation with no external interactions and no side effects, surrounded by a shell that retrieves inputs and persists results. He wants “business logic that does not perform any external interactions, does not cause any side effects, and whose result depends solely on the values passed to it.”

That is a precise description of case (a) — H0 exactly. And it is the right answer there. The open question is how far it generalises; where the domain does not fall in case (a), the split needs a qualification.

Two consequences follow.

The ports set aside are the answer in case (b). Fritzsche says we need “neither to reverse the direction of dependencies nor to introduce technical interfaces whose sole purpose is to hide infrastructure implementations.” That is right for interfaces whose purpose is to hide infrastructure. In case (b), though, the module genuinely needs external state, and that state is entirely domain-governed. The port is not a hiding device. It is the faithful expression of a domain obligation, written in domain vocabulary. In case (b) the hexagonal prescription is not unnecessary indirection; it is the form the domain calls for.

Consistency is not automatically a shell detail. Fritzsche puts “responsibility for consistency” in the shell. In case (c) the classification differs. When a domain rule’s correctness condition depends on transaction isolation or retry-and-idempotency semantics, that consistency knowledge is relevant causal domain knowledge — knowledge the module must embody to respond correctly to its drivers. Moving it to the shell does not remove it from the domain. It hides it. And an obligation that is hidden cannot be verified against the governing artifact.

4.1 The proposed boundary faces the same question

Fritzsche proposes new boundaries: “the natural boundaries of these units are the domain capabilities,” and each capability “remains cohesive within its own boundaries.”

“Capability” is an organisational construct. Its boundary shifts with reorganisation. Two organisations structure the same business differently. Grouping by business capability meets the same question as grouping by architectural role: it is not externally anchored in a stable domain artifact, and it is not determinate. The boundary it draws is organisational, which the domain does not necessarily share.

Here “cohesive” is used in its ordinary sense. In the theory, cohesion has a precise meaning: correctness relative to a partitioning rule. A claim of cohesion is only as good as the rule it is measured against; for “capability”, that rule has yet to be supplied.

5 On the empirical argument

Fritzsche’s case against interchangeability is empirical: “how often have I seen someone come up with the idea of replacing the database technology in an existing application? Exactly zero times!”

Frequency is not the criterion. Whether a domain rule’s correctness conditions require infrastructure knowledge is a question about the governing artifacts, not about how often a change happens in practice. “Infrastructure changes less often than business rules” is the same stability-ordering move that Martin uses to justify the dependency rule [3]. A frequency observation, however accurate, does not by itself settle a structural claim.

There is also a symmetry worth noting. “The database is a detail” is true from the client’s perspective and false from the database’s. From the order-management domain, the relational engine is infrastructure. From the engine’s own perspective, durability, isolation, and recovery semantics are the domain, governed by the SQL standard and hardware contracts. A transaction manager ignorant of storage semantics cannot implement its own obligations. The infra-versus-domain boundary is relative to the observer’s change-driver scope. It is not a fixed property of software.

6 What to do instead

The lesson is not “Clean Architecture, forever” and not “Clean Architecture, never.” It is that the core-oriented styles are conditional guides, and the prior question is which case a domain belongs to. For each domain module, two questions, answered from the governing artifacts:

  1. Does any correctness condition require knowledge of an infrastructure system? (This decides H.)
  2. Does the module depend on any external state at all? (This decides H0.)

The three cases then prescribe different responses:

  • Case (a), H0. A pure functional core. No repository, port, or adapter. Adding one is unnecessary indirection. This is Fritzsche’s Functional Core, and it is right here.
  • Case (b), H holds. A port or repository expressed in domain vocabulary. The module needs external state, but the state is domain-governed, so the contract is expressible in domain terms. This is the case the hexagonal prescription was designed for, and it is right here.
  • Case (c), H fails. Accommodate the infrastructure knowledge. Either keep it in the domain module, or move it to an explicitly domain-scoped adapter whose change-driver assignment is stated and whose behaviour is independently testable against the domain change-driver. What is not sound is enforcing infra-ignorance and accepting an incorrect or unverifiable model as the cost of structural conformance.

The style does not choose the case. The domain does.

7 Wrapping up

Fritzsche is right that dependency inversion moves a dependency without removing the driver behind it. He is right that an abstraction cannot delete essential coupling, only relocate it. He is right that role-based layers are not domain boundaries. Where a domain’s business logic is genuinely self-contained — case (a) — his Functional Core is exactly correct.

The qualification I would add is one of scope. The infra-ignorant core exists if and only if H holds, and H is discovered from the domain’s governing artifacts, not assumed. When H fails, every style in the family — Clean, Hexagonal, Onion, and Functional Core / Imperative Shell alike — arrives at the same fork: embody the required knowledge, or ship a model that cannot satisfy its obligations.

The question is not whether we should still talk about Clean Architecture. It is which domains Clean Architecture was ever talking about. That question has an answer, and it is a property of the domain, not a matter of taste.
